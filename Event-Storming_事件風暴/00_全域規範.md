# 全域規範

> 本檔記錄跨所有流程共通的事件風暴規範，由 `/es-formulation` 依使用者裁決逐項寫入。

## Event 共通攜帶資訊

所有流程中的每一個 Event，發生時皆必須攜帶以下共通欄位：

| 欄位 | 型別 | 說明 |
|------|------|------|
| 事件ID | UUID | 事件唯一識別碼 |
| 發生時戳（UTC） | Timestamp（UTC，毫秒精度） | 事件發生的絕對時間 |
| 發生時戳（使用者當地時區） | Timestamp + 時區代碼 | 供跨時區規則判定使用 |
| 觸發 Actor | Actor 識別碼 | 執行 Command 導致此 Event 的角色 |
| 關聯 Aggregate ID | ID | 此 Event 所改變狀態的 Aggregate |

共通欄位之外，各 Event 另行定義其專屬欄位。

### 規則

- 每一個 Event 必須同時記錄 UTC 時戳與使用者當地時區時戳。
- 跨時區規則（簽到換日、每日任務重置、中斷判定）一律以使用者當地時區時戳為判定基準。
- UTC 時戳的精度為毫秒。

### 統一換日時點

全模型的換日時點為**使用者當地時區的 04:00**。

| 適用對象 | 說明 |
|----------|------|
| 簽到「當日」判定 | 04:00 前簽到計入前一日 |
| 每日任務重置 | 當地時間 04:00 重置 |

- 當地時間 00:00–03:59 的行為一律計入前一個自然日。
- 採 04:00 而非 00:00：健身族群多有深夜運動習慣，午夜換日會使凌晨訓練與簽到落到隔日，不符使用者直覺。
- 簽到與每日任務採同一換日時點，模型中不存在第二個換日時點。
- 本換日時點不適用於「連續訓練天數」的自然日計數，該處另有 36 小時寬限規則。

#### 當地時區的取得來源

- 「使用者當地時區」一律取自**使用者裝置的當前時區**，非使用者 Aggregate 儲存的時區欄位。
- 理由：儲存的時區為註冊當下填入，使用者出國、搬家或變更裝置語系後即過期。
- 跨時區移動導致同一當地日期重複觸發重置時，由冪等機制擋下
  （請求識別碼 ＝ 排程名稱 ＋ 週期起點 ＋ 使用者 ID，週期起點為使用者當地日期），不會重置兩次。
- 使用者 Aggregate 的時區欄位僅供顯示與統計，不作為換日與中斷判定的依據。

*來源：`.clarify/resolved/event/全流程Event_每個Event應攜帶哪些資訊與時間戳.md`（選項 B）*

## Event 冪等性原則

所有流程中的 Event，重複發生時一律以 **Command 請求識別碼**去重。

### 規則

- 每一個 Command 請求必須攜帶請求識別碼。
- 系統以請求識別碼判定重複：識別碼已處理過者視為重複請求。
- 重複請求回傳原次執行的結果，不重複產生 Event。
- 本原則統一適用於全模型，各 Event 不另行定義冪等規則。

### 排程觸發的請求識別碼

排程觸發的 Command 無使用者端請求，其請求識別碼由業務自然鍵推導。

**請求識別碼 ＝ 排程名稱 ＋ 週期起點 ＋ 使用者 ID**

| 排程類 Event | 週期起點 |
|--------------|----------|
| 每日任務已重置 | 使用者當地日期（以當地時間 04:00 為換日點） |
| 訓練已結算 | 該筆訓練的訓練紀錄 ID |
| 簽到連續天數已中斷 | 該次中斷判定所屬的使用者當地日期 |
| 連續訓練天數已歸零 | 該次歸零判定所屬的使用者當地日期 |
| 排行榜週期已結算 | 該排行榜週期的起始日 |
| 能力值已退步 | 該肌群維度的 120 小時計時起算點 |

#### 規則

- 排程類 Command 不產生隨機識別碼，一律由上表的自然鍵推導。
- 同一週期重跑時算出相同的請求識別碼，視為重複請求，不重複產生 Event。
- 「能力值已退步」的週期起點為肌群維度層級，六個維度各自獨立去重。
- 排程類 Event 不因本規則而免除各自的 Precondition，兩者並存。

*來源：`.clarify/resolved/event/全流程Event_各Event重複發生時的冪等處理原則.md`（選項 A）；
排程情境之補充來源：`.clarify/resolved/event/全流程Event_排程觸發的Event其冪等去重鍵如何產生.md`（選項 A）*

## Actor 清單

全模型的 Actor 共五種，所有 Command 的執行者必須指派為其中之一。

| Actor | 類型 | 說明 |
|-------|------|------|
| 使用者 | 人 | 平台的一般使用者 |
| 管理員 | 人 | 平台管理員，具備審核與處置權限 |
| 系統 | 自動 | 排程、自動判定與套用調整的觸發者 |
| AI | 自動 | 產出訓練調整建議的角色，獨立於外部系統 |
| 外部系統 | 外部 | 平台外的服務，如 Google / Apple、App Store、物流商 |

### 規則

- 發文者、互動者、學徒、教官、成員、對方皆非獨立 Actor，一律歸為「使用者」。
- 上述稱呼僅為使用者在特定情境下的角色描述，不得作為 Command 的 Actor 值。
- 教官不因具備額外權限而獨立為 Actor，其權限差異以使用者的教官身分旗標表達。
- 團隊隊長不為獨立 Actor，其權限差異以團隊內的角色欄位表達。
- AI 僅負責產出建議，不執行套用；套用調整的 Actor 為系統。
- 本清單非封閉清單，新增 Actor 需經明確裁決。

*來源：`.clarify/resolved/command/Actor_模型中各角色名稱的定義與統一.md`（選項 A′）；
AI 一項與清單封閉性之修訂來源：`.clarify/resolved/command/AI已調整訓練_AI是否視為獨立Actor.md`（選項 D″）*

## Command 清單

### 命名與盤點規範

- 每一個 Event 皆有對應的 Command，Command 與 Event 原則上一對一；多對一者於備註標明。
- Command 命名一律為祈使句「動詞＋受詞」，去除主語與「已」字。
- Command 命名反映使用者意圖，不得使用畫面元件名稱。
- 每一個 Command 必須指派 Actor，值域限於〈Actor 清單〉的五種。
- 系統排程與外部回呼觸發的 Event 同樣有 Command，其 Actor 為系統或外部系統。
- 每一個 Command 請求必須攜帶請求識別碼（承〈Event 冪等性原則〉）。
- 隊長、學徒、教官、成員、發文者、互動者皆非 Actor，於備註以括號標明其角色。
- 本清單為 Command 的唯一定義處，各流程檔的 [串聯] 註記為其摘要，不另建清單。
- Command 的輸入參數尚未逐一定義（待決策 Partial），由後續釐清項目補齊。

## Aggregate 邊界

### 使用者 Aggregate

「使用者」為核心 Aggregate，含身分與個人資料、三項成長數值、兩個旗標。

| 欄位群 | 內容 |
|--------|------|
| 身分與個人資料 | 帳密、身高、體重、性別、生日、單位偏好、健身偏好、時區 |
| 成長數值 | 經驗值、能力值、階級 |
| 旗標 | 社群互動功能解鎖旗標、教官身分旗標 |

#### 已定義欄位

| 欄位 | 型別 | 單位 | 合法範圍 | 說明 |
|------|------|------|----------|------|
| 身高 | float（一位小數） | 公分 | 50–250 | 儲存一律以公制為準 |
| 體重 | float（一位小數） | 公斤 | 20–300 | 儲存一律以公制為準 |
| 生日 | date | — | 對應年齡 13–120 歲 | 年齡為衍生欄位，不直接儲存 |
| 單位偏好 | 列舉 | — | 公制 / 英制 | 僅影響顯示，不影響儲存 |
| 能力值 | 6 維數值（每維 int） | — | 各維獨立 | 依肌群分維：胸 / 背 / 腿 / 肩 / 手 / 核心 |
| 性別 | 列舉 | — | 男 / 女 | 必填，二元列舉 |
| 每週健身天數 | int | 天 | 1–7 | 必填 |
| 每次健身時長 | 列舉 | — | 30 分鐘以下 / 30–60 / 60–90 / 90 分鐘以上 | 必填，區間列舉 |
| 處罰狀態 | 列舉 | — | 無 / 警告 / 社群功能停權 / 帳號停權 / 永久停權 | 獨立於社群互動功能解鎖旗標 |
| 處罰到期時戳 | Timestamp / 空值 | — | 限期處罰才有值 | 警告與永久停權為空值 |
| 粉絲數 | int | — | ≥ 0 | 衍生自關注關係，儲存以供成就判定 |

其餘欄位的型別、單位與合法範圍由後續釐清項目逐一定義。

#### 規則

- 身高與體重一律以公制儲存，英制僅為顯示偏好，由單位偏好欄位決定。
- 英制顯示範圍由公制範圍換算：身高 20–98 in、體重 44–661 lb，不另設獨立範圍。
- 年齡不直接儲存，一律由生日衍生計算。
- 年齡未滿 13 歲者不得完成註冊。
- 性別為必填的二元列舉，值域為男 / 女，不含其他選項，亦不可留白。
- 每週健身天數為精確整數，範圍 1–7 天。
- 每次健身時長為區間列舉，不記錄精確分鐘數，因使用者無法精確估計單次時長。
- 兩者皆為註冊 9 項必填之一，不設預設值。

- 經驗值與階級的門檻計算關係在使用者 Aggregate 內部保證一致，不跨 Aggregate。
- 能力值的提升與退步皆改動使用者 Aggregate。
- 能力值為 6 個肌群維度：胸、背、腿、肩、手、核心，各維獨立升降。
- 能力值的提升依動作所屬肌群，只提升該動作對應的維度。
- 「能力值已提升」「能力值已退步」「能力值已部分回復」三個 Event 皆須攜帶所影響的肌群維度。
- 動作 Aggregate 須具備「所屬肌群」欄位，值域為上述 6 個肌群。
- 訓練屬性（力量 / 耐力 / 爆發）本階段不進模型，列為未來擴充。
#### 能力值提升公式

**該維提升點數 ＝（本次該肌群訓練量 ÷ 該肌群基準訓練量）× 基準提升點數**

其中訓練量 ＝ 重量 × 次數 × 組數，逐組累加。

| 肌群 | 基準訓練量 |
|------|-----------|
| 腿 | 4,000 |
| 背 | 2,500 |
| 胸 | 2,000 |
| 肩 | 1,200 |
| 手 | 800 |
| 核心 | 600 |

| 參數 | 初始值 | 說明 |
|------|--------|------|
| 基準提升點數 | 10 點 | 一次達到基準訓練量的訓練所得 |
| 單次訓練單維上限 | 30 點 | 基準提升點數的 3 倍 |

- 各肌群採獨立基準訓練量而非統一換算率：腿部訓練量天生為手臂的數倍，
  統一換算率會使所有使用者的六維呈現同一形狀（腿最高、手最低），六個維度將失去表達差異的價值。
- 基準訓練量的意義為「該肌群一次認真訓練的典型總量」，可由真實訓練資料估算校準，非抽象係數。
- 設單次訓練單維上限：能力值有退步機制，提升若無上限，一次超長訓練可抵銷數個月退步，兩邊尺度將對不上。
- 上述參數皆為平台級可調，由管理員於後台維護。
- 提升不依訓練頻率加權；持續性已由連續訓練天數與獎勵加成承擔，不在能力值重複疊加。

#### 徒手動作的訓練量代入

**徒手動作代入重量 ＝ 基準體重 × 該動作的體重係數**

| 參數 | 初始值 | 說明 |
|------|--------|------|
| 基準體重 | 70 公斤 | 全體使用者共用，與實際體重無關 |

- 動作 Aggregate 新增「體重係數」欄位，僅徒手動作有值（如伏地挺身 0.6、引體向上 1.0）。
- 訓練紀錄仍照實儲存重量 0，體重係數僅於計算能力值與訓練量時代入；實績與計算輸入分開。
- 採基準體重而非使用者實際體重，理由有三：
  - 「減重」為常見目標類選項之一，用實際體重會使減重成功者的徒手動作成長變慢，形同懲罰達成目標。
  - 用實際體重時增重可刷分，計分規則不應有此性質。
  - 訓練量同時餵給個人排行榜分數，用實際體重會使跨使用者名次受體重影響。
- 另一實務理由：體重為使用者自填且多數人不定期更新，不依賴該欄位可避免資料過期導致計分錯誤。
- 代價：體重明顯高於基準者做徒手動作的額外負荷不被反映，此為刻意取捨。

#### 能力值退步參數

| 參數 | 初始值 | 說明 |
|------|--------|------|
| 退步百分比 | 2.5% | 每滿 120 小時未訓練退步一次 |
| 六維註冊初始值 | 各維皆 10 | 亦為退步下限 |

| 停練時間 | 累計衰減 |
|----------|----------|
| 10 天 | −5% |
| 1 個月 | −14% |
| 3 個月 | −37% |
| 6 個月 | −60% |
| 1 年 | −84%（趨近下限 10） |

- 六維註冊初始值一致，不依註冊問卷的健身經驗分級；新手與老手的差異已由訓練量決定成長速度自然反映。
- 初始值 10 等同一次基準訓練所得的點數，其意義為「無論荒廢多久仍保有一次認真訓練的水準」。
- 上述參數皆為平台級可調，由管理員於後台維護。
- 退步不解決能力值累積無上限的問題：退步僅於該肌群 120 小時未訓練時觸發，規律訓練者永不退步。

- 能力值退步為每滿 120 小時未訓練退步固定百分比，可持續發生。
- 能力值退步的下限為註冊初始值，不低於該值。
- 六個肌群維度各自獨立計時：自該維最後一次訓練**日的日界**起算滿 120 小時，才退該維。
- 退步僅影響逾時的維度，其餘維度不受影響。
- 社群互動功能解鎖旗標為單調遞增，一經設定不可撤銷。
- 教官身分旗標承載教官的權限差異，教官不因此成為獨立 Actor。

- 處罰狀態為獨立欄位，值域五值：無 / 警告 / 社群功能停權 / 帳號停權 / 永久停權。
- 社群功能停權以處罰狀態欄位表達，不得以撤銷社群互動功能解鎖旗標實作。
- 限期處罰（社群功能停權、帳號停權）須記錄處罰到期時戳。
- 警告與永久停權的處罰到期時戳為空值。
- 處罰狀態於「處罰已撤銷」或「處罰已到期解除」發生時回復為無。
- 受處罰者具教官身分時，教官資格一併撤銷。

- 粉絲數為儲存欄位，隨「使用者已關注帳號」與「使用者已取消關注」同步增減。
- 不變條件：粉絲數 ＝ 關注關係中被關注者為本人的筆數。
- 粉絲數不採即時彙總：粉絲成就門檻最高 10000，即時 count 於熱門帳號成本過高。
- 粉絲數不允許與關注關係不一致，避免粉絲成就的解鎖判定抖動。

### 課表內容結構（共用）

訓練計畫、自訂訓練、本次訓練課表三者的「課表內容」共用同一結構，為三層巢狀。

| 層級 | 內容 |
|------|------|
| 第一層 | 動作清單（每項為一個動作 ID） |
| 第二層 | 該動作的組數（int，≥ 1）與建議組間休息秒數 |
| 第三層 | 每一組的目標重量與目標次數 |

| 第三層欄位 | 型別 | 單位 | 合法範圍 | 必填 |
|------------|------|------|----------|------|
| 目標重量 | float（精度 0.5） | 公斤 | ≥ 0 | 必填 |
| 目標次數 | int | 次 | ≥ 1 | 必填 |

#### 規則

- 訓練計畫與自訂訓練的課表內容格式完全一致，不因來源而有結構差異。
- 每一組可各自設定不同的目標重量，不強制整個動作共用同一重量。
- 目標重量為必填，值為 0 代表徒手（自身體重）動作。
- 目標重量的 0 於 Read Model 顯示為「自重」，儲存值一律為 0，不另存字串。
- 目標重量的型別、精度與合法範圍與訓練紀錄的實績重量一致。
- 平台訓練計畫的目標重量為管理員設定的**建議起始重量**。
- 使用者自訂訓練的目標重量由使用者於「使用者已設定該組的重量&次數」時填入。

#### 組間休息秒數的取值優先序

| 順位 | 來源 |
|------|------|
| 1 | 課表內容於該動作指定的建議休息秒數 |
| 2 | 該動作 Aggregate 的預設組間休息秒數 |
| 3 | 全站預設 90 秒 |

- 休息秒數為動作層級，不逐組設定：不同動作的合理休息差異大（大重量深蹲 3 分鐘、二頭彎舉 60 秒），
  但同一動作的各組差異小。
- 使用者可隨時跳過休息，跳過即觸發「組間休息已結束」。
- 不採不可跳過的強制計時：休息計時僅為輔助，強制等待會擋住真正的業務事實
  （使用者已開始下一組卻無法記錄），且會與 40 分鐘逾時中斷判定互相干擾。

#### 快照產生時的目標重量帶入規則

- 「使用者已選擇訓練課表」產生本次訓練課表快照時，逐組決定目標重量。
- 該使用者曾記錄過該動作的成績者，目標重量帶入其最近一次該動作的實際重量。
- 未曾記錄過該動作者，目標重量沿用來源課表的值（平台計畫為建議起始重量）。
- 〔推導〕組序對應：以組序逐一對應；本次組數多於上次時，超出的組沿用上次最後一組的重量。
- 帶入只影響快照，不改動來源課表的目標重量。

*來源：`.clarify/resolved/aggregate/訓練計畫_訓練計畫與自訂訓練的動作與組數結構為何.md`（選項 A ＋ 使用者補充：逐組不同重量、徒手以 0 表示、建議起始重量、帶入上次重量）*

### 本次訓練課表 Aggregate

「本次訓練課表」為獨立 Aggregate，於開始訓練時自來源課表複製快照，承載本次訓練的計畫內容。

| 欄位 | 型別 | 說明 |
|------|------|------|
| 來源類型 | 列舉 | 訓練計畫 / 自訂訓練 / 空白課表 |
| 來源課表 ID | ID / 空值 | 來源類型為空白課表時為空值 |
| 課表內容 | — | 自來源複製的快照，結構見〈課表內容結構（共用）〉 |
| 總計畫組數 | int | ≥ 0，供訓練進度條計算分母 |

#### 規則

- 「使用者已選擇訓練課表」時自來源課表複製快照，產生一份本次訓練課表。
- 快照於選擇課表時即產生，非等到開始訓練，因 AI 訓練前調整發生於開始訓練之前。
- 快照一經產生即與來源課表脫鉤，來源課表其後的任何改動不影響已產生的快照。
- AI 訓練前調整與 AI 訓練中調整只改本次訓練課表的快照，不改來源課表。
- AI 自動優化訓練只改課表範本（訓練計畫 / 自訂訓練），不改任何既有快照。
- 「訓練課表已套用新強度」作用範圍為「本次訓練」者改本 Aggregate，為「課表範本」者改來源課表。
- 訓練進度條的總計畫組數取自本 Aggregate，不取自來源課表。
- 空白課表為合法的初始狀態，其總計畫組數為 0、來源課表 ID 為空值。
- 本 Aggregate 與訓練紀錄為一對一：前者為計畫，後者為實績，兩者不合併。

*來源：`.clarify/resolved/aggregate/訓練課表_本次訓練課表是否為獨立Aggregate與其快照機制.md`（選項 A）*

### 連續訓練 Aggregate

連續訓練天數以**自然日**計數，並提供 **36 小時寬限**；寬限自**上次訓練日的日界**起算。

| 欄位 | 型別 | 說明 |
|------|------|------|
| 上次訓練日期 | date | 使用者當地日期，作為中斷判定的計時基準 |

#### 規則

- 同一自然日內訓練一次以上，該日計為 1 天，不重複計數。
- 計時起點為上次訓練日的日界，即該日結束、次日當地時間 04:00。
- 距上次訓練日的日界未超過 36 小時再次訓練，連續天數續計，即使中間跨過一個未訓練的自然日。
- 距上次訓練日的日界超過 36 小時，連續訓練天數歸零。
- 自然日的判定以使用者當地時區時戳為基準；36 小時的判定以上次訓練日期推得的日界為基準。
- 計時基準取自「上次訓練日期」欄位（使用者當地日期），非訓練的實際時戳。
- 採日界而非時戳：使所有使用者的期限統一落在同一時點，不因當日幾點訓練而差異數小時，
  與連簽中斷判定的計時基準一致。

#### 連續訓練中斷判定的計時起點

四個門檻一律自**上次訓練日的日界**起算。

| 距日界 | 判定 |
|--------|------|
| +24 小時 | 中斷預告已發送 |
| +36 小時 | 連續訓練天數已歸零、使用者已失去獎勵加成、連練中斷通知已發送 |
| +96 小時 | 退步預告已發送 |
| +120 小時 | 能力值已退步 |

- 單次訓練已逾時中斷者，該筆訓練仍計入「上次訓練日期」，同樣重設計時
  （承既有裁決：已中斷的訓練仍進入訓練結算流程，中斷前已記錄的組數全數保留）。
- 能力值退步的六維各自獨立計時，計時起點為**該維最後一次訓練日的日界**。

- 獎勵加成為連續訓練天數的衍生值：每連續一天 +1%，上限 30%。
- 加成雖為衍生值，「使用者已失去獎勵加成」與「使用者已獲得獎勵加成」仍各為獨立 Event。
- 不建模「使用者已恢復獎勵加成」：加成的重新累積由「使用者已獲得獎勵加成」承接。

*來源：`.clarify/resolved/aggregate/連續訓練_連續訓練天數的判定基準.md`（選項 C）；
計時起點由時戳修正為日界之來源：`.clarify/resolved/rule/連續訓練中斷判定_24至120小時的計時起點為何.md`（選項 C）*

### 連續簽到 Aggregate

| 欄位 | 型別 | 初始值 | 說明 |
|------|------|--------|------|
| 連續天數 | int | 首次簽到為 1 | 簽到中斷時歸零 |
| 累計天數 | int | 首次簽到為 1 | 永不歸零，單調遞增 |
| 中斷前連續天數 | int | 0 | 中斷發生時保存歸零前的連續天數，供補簽回復使用 |
| 歷史最長連續天數 | int | 首次簽到為 1 | 永不減少，記錄歷來達到過的最大連續天數 |
| 上次簽到日期 | date | — | 使用者當地日期，作為中斷判定的計時基準 |

#### 規則

- 累計天數為單調遞增，任何情況下皆不減少。
- 歷史最長連續天數為單調遞增，任何情況下皆不減少。
- 連續天數於簽到中斷時歸零，歸零前先將原值寫入中斷前連續天數。
- 補簽成功時，連續天數回復為：中斷前連續天數 ＋ 補回的天數 ＋ 中斷後已簽到的天數。
- 補簽券使用後，中斷前連續天數清空為 0。
- 不變條件：累計天數 ≥ 歷史最長連續天數 ≥ 連續天數。
- 不變條件：中斷前連續天數 > 0 代表存在一次尚可補救的中斷。

#### 連簽中斷判定的計時起點

計時起點為**上次簽到日的日界**，即該日結束、次日當地時間 04:00。

| 距日界 | 判定 |
|--------|------|
| +24 小時 | 整整錯過 1 天 → 連簽中斷預告已發送 |
| +36 小時 | 錯過 1.5 天 → 簽到連續天數已中斷 |
| +48 小時 | 錯過 2 天 → 補簽提醒已發送 |

- 不以上次簽到的實際時戳起算：那會使警告時點取決於使用者昨天幾點開 App，
  且可能在使用者今日仍有簽到資格時就發出中斷預告。
- 計時基準取自連續簽到 Aggregate 的「上次簽到日期」欄位（使用者當地日期），非時戳。
- 三個門檻對應「錯過 1 天 / 1.5 天 / 2 天」，與既有的 24 / 36 / 48 小時設定一致，不改寫數值。

*來源：`.clarify/resolved/aggregate/連續簽到_連續天數與累計天數的定義與型別.md`（選項 D′）*

### 虛擬貨幣 Aggregate

站內虛擬貨幣只有一種，名稱為**金幣**。

| 欄位 | 型別 | 說明 |
|------|------|------|
| 金幣餘額 | int | 持有的金幣數量 |

#### 規則

- 全模型僅有金幣一種虛擬貨幣，不區分免費幣與付費幣。
- 金幣的取得來源為各類獎勵發放與儲值。
- 金幣的消耗用途為購買虛擬商品與購買補簽券。
- 金幣餘額不得為負值。

#### 金幣對法幣的比率

| 參數 | 初始值 | 說明 |
|------|--------|------|
| 金幣對法幣比率 | 1 金幣 ＝ 1 元 | 平台級可調參數，由管理員於後台設定 |

- 全站單一比率，不依商品或規格而異。
- 補差額金額 ＝（商品價格 − 可折抵金幣數）× 比率換算後的法幣金額。
- **訂單成立時鎖定當時比率**，其後比率變動不影響該筆訂單。
- 比率變動不追溯既有訂單，不需補償邏輯。
- 不採逐商品規格自訂折抵率：維護成本高且使用者難以理解折抵差異。
- 本比率同時為金幣儲值流程的定價基礎。

- 儲值的路徑為獨立的金幣儲值流程，納入軟體邊界。
- 儲值走 App Store 應用內購買，因金幣屬數位內容，為 Apple 強制要求。
- 儲值的 Actor 為外部系統（App Store 通知觸發），與虛擬商品的真實金流同屬一體系。
- 儲值成功產生「使用者已儲值金幣」，失敗產生「儲值已失敗」。
- 儲值面額與贈送規則尚未給定（待決策 Partial）。

儲值路徑之增列來源：`.clarify/resolved/event/金幣_金幣儲值的流程與Event全數缺失.md`（選項 A）；
比率之增列來源：`.clarify/resolved/aggregate/虛擬貨幣_金幣對法幣的補差額比率為何.md`（選項 A）*

### 每日任務池 Aggregate

每日任務的項目由管理員於後台設定任務池，每日隨機抽取指派。

| Aggregate | 層級 | 說明 |
|-----------|------|------|
| 每日任務池 | 平台級 | 可抽取的任務項目清單；由管理員維護，可調整 |
| 每日任務 | 每使用者 | 當日指派給該使用者的任務與進度 |

#### 規則

- 每日任務池由管理員設定，非寫死於系統。
- 每日重置時自任務池隨機抽取固定數量指派給使用者。
- 任務池調整不改動任何使用者當日已指派的任務。
- 全平台使用同一個任務池，不依使用者狀態或會員身分產生差異。

| 參數 | 初始值 | 說明 |
|------|--------|------|
| 每日抽取數量 | 3 項 | 存於每日任務池 Aggregate，由管理員調整 |

- 每日抽取 3 項，**允許與前一日重複**，不做去重。
- 採 3 項而非 5 項：每日任務的完成方式為完成每日訓練與社群互動，一日的合理行為量約為 3 項；
  5 項會使「每日任務已完成」的加碼獎勵與加碼分數變成少數人才拿得到。
- 不做跨日去重：任務池內容本為「訓練一次」「按讚 3 次」等日常行為，連續兩日重複屬正常；
  且去重規則會隱含要求任務池維持足夠數量，管理員縮減池子時系統將抽不出來。
- 任務池項目數少於抽取數量時，抽出全部項目。

*來源：`.clarify/resolved/aggregate/每日任務_任務項目與數量由誰定義.md`（選項 B）*

| 欄位 | 型別 | 說明 |

| 作者 | 使用者 ID | 發文者 |
| 文字內容 | 字串 | 貼文文字 |
| 圖片 | 圖片集合 | 不支援影片 |
| 發布時間 | Timestamp | 沿用 Event 共通時戳規範 |
| 可見範圍 | 列舉 | 公開 / 僅關注者 / 私人 |
| 關聯訓練紀錄 | 訓練紀錄 ID | 分享訓練成果時帶入，發布原生貼文時為空 |
| 按讚數 | int | 衍生自互動 |
| 留言數 | int | 衍生自互動 |
| 狀態 | 列舉 | 已發布 / 已刪除 |
| 已編輯旗標 | bool | 曾經編輯過即為真，供讀者辨識 |
| 編輯歷史 | 有序集合 | 每次編輯前的文字內容與時戳 |

#### 規則

- 貼文不支援影片，僅支援文字與圖片。
- 貼文無標籤欄位，不做分類。
- 可見範圍由發文者於發布時指定，三選一。
- 「發文者已分享訓練成果」產生的貼文，關聯訓練紀錄欄位必有值。
- 「發文者已發布貼文」產生的貼文，關聯訓練紀錄欄位為空。
- 互動者對貼文按讚或留言前，該貼文須對其可見。

#### 狀態機

| 起始狀態 | 觸發 Event | 目標狀態 |
|----------|-----------|----------|
| — | 發文者已發布貼文 / 發文者已分享訓練成果 | 已發布 |
| 已發布 | 貼文已刪除 | 已刪除（終止） |

#### 刪除與編輯規則

- 刪除為軟刪除：狀態轉為已刪除，資料保留。
- 不採硬刪除：貼文可被檢舉，硬刪除會使已成案的檢舉失去指涉對象。
- 已刪除貼文的按讚與留言一併隱藏但保留，供獎勵回收與成就計數判定使用。
- 編輯保留完整歷史版本：每次編輯前的文字內容與時戳寫入編輯歷史。
- 保留歷史的理由：避免「發爭議內容 → 被檢舉 → 審視前改為無害內容」的規避漏洞；且申訴未設時效上限，需長期可稽核。
- 編輯後已編輯旗標為真，Read Model 須對讀者顯示「已編輯」。
- 留言 Aggregate 的狀態值域與刪除編輯規則比照本節，不另定義。

*來源：`.clarify/resolved/aggregate/貼文_貼文的欄位內容型態與可見範圍.md`（選項 C）*

| 欄位 | 型別 | 說明 |

#### 規則

- 關聯的唯一鍵為 貼文 ID ＋ 互動者 ID，同一人對同一貼文只能有一筆。
- 貼文 Aggregate 的「按讚數」為衍生欄位，來源為關聯集合的筆數。

| 起始狀態 | 觸發 Event | 目標狀態 |
|----------|-----------|----------|

- 實體與虛擬訂單共用同一個 Aggregate，以類型欄位區分適用的狀態子集。

- 虛擬訂單無出貨狀態；已付款與已發放為兩個不同狀態，發放可為非同步。
- 收貨資訊僅實體訂單有值。

#### 收貨資訊欄位

| 欄位 | 型別 | 必填 | 說明 |
|------|------|------|------|
| 收件人姓名 | 字串 | 必填 | — |
| 手機號碼 | 字串 | 必填 | 須符合手機號碼格式 |
| 郵遞區號 | 字串 | 必填 | 物流商所需，獨立成欄以利格式檢核 |
| 地址 | 字串 | 必填 | 單一自由文字欄，不拆縣市 / 鄉鎮區 / 街道 |
| 備註 | 字串 | 選填 | — |

  而出貨後的物流已定案留在系統邊界之外，本系統僅將地址原封不動交付物流商，無拆解用途。
- 不收集電子郵件：出貨通知的管道尚未定案，且通知類 Event 清單中無出貨通知，
  不為不存在的功能收集個資。
- 手機號碼不寫死為特定國別格式：模型無「限特定地區」的既有裁決，寫死將成為隱形的地區假設。
- 虛擬訂單的付款可為虛擬貨幣扣除、真實金流，或兩者併用。

- 「商品發放已失敗」不改變訂單狀態，訂單於發放成功前維持已付款。
- 發放失敗時系統自動重試，重試次數上限 3 次。
- 達重試上限仍失敗者轉人工處理，不自動退款。

### 團隊分數 Aggregate

團隊有兩個獨立分數與兩個獨立排行榜，衡量不同的事。

| Aggregate | 計算方式 | 衡量對象 |
|-----------|----------|----------|
| 團隊日常分數 | 全體成員個人排行榜分數加總 | 成員的訓練努力程度 |
| 團隊限時分數 | 完成限時任務的成員數 × 固定分，全員完成時另加成 | 團隊的動員參與率 |

#### 規則

- 團隊日常分數直接沿用成員的個人排行榜分數，不另定一套計分規則。
- 團隊限時分數不依訓練量計算，每位成員完成一次限時任務即加固定分。
- 團隊全體成員皆完成限時任務時，額外給予加成。
- 限時任務為每日指派，非以排行榜週期為單位。
- 兩個分數不合併，兩個排行榜各自維護，對應兩種獨立的排行獎勵。
- 固定分的數值與全員完成的加成幅度尚未給定（待決策 Partial）。

*來源：`.clarify/resolved/aggregate/團隊日常分數_日常分數與限時分數的計算公式.md`（選項 A + 使用者補充）*

### 帶徒上限設定 Aggregate

帶徒上限的參數由管理員於後台設定，屬平台級可調參數。

| 參數 | 預設值 | 說明 |
|------|--------|------|
| 初始帶徒上限 | 1 人 | 成為教官時的起始值 |
| 每次提升幅度 | +1 人 | 每達一個聲望門檻提升的人數 |
| 帶徒上限最大值 | 5 人 | 提升的上界，達此值後不再提升 |
| 聲望門檻清單 | 30 / 75 / 150 / 300 | 觸發提升的四級聲望值 |
| 教官初始聲望 | 15 | 「使用者已成為教官」時的起始聲望 |

#### 門檻設計依據

| 升級段 | 所需點數 | 同時帶徒數 | 估算耗時 |
|--------|---------|-----------|----------|
| 1 → 2 人 | 30 | 1 人 | 約 7.5 週 |
| 2 → 3 人 | 45 | 2 人 | 約 6 週 |
| 3 → 4 人 | 75 | 3 人 | 約 6 週 |
| 4 → 5 人 | 150 | 4 人 | 約 9 週 |

估算假設：平均每次評分 +2 點（4 星）、每位學徒每週 2 次評分（問答與師徒任務各一）。達上限約需 7 個月。

- 門檻採遞增而非等差：帶徒數愈多、取得聲望愈快，等差門檻會使後段升級速度失控（最後一級僅需第一級的四分之一時間）。
- 遞增比例為 1 : 2.5 : 5 : 10，使四段耗時大致相當。
- 教官初始聲望為第一門檻的一半。聲望地板值為 0，若初始亦為 0，新教官前幾次差評扣完仍是 0，差評將失去嚇阻力。

#### 規則

- 上述參數皆由管理員調整，非寫死於系統。
- 參數調整不使任何教官的既有帶徒上限降低（承第 46 題的單調遞增裁決）。
- 帶徒上限達最大值 5 人後，聲望再提升亦不再增加上限。

#### 名額佔用規則

- **申請中的師徒申請佔用帶徒名額**：送出申請即佔用，避免超收。
- 名額佔用數 ＝ 已建立的師徒關係數 ＋ 申請中的師徒申請數。
- 「對方已拒絕申請」或「師徒申請已逾期」發生時，釋放所佔名額。
- 師徒申請的逾期時限為 168 小時（7 天），自申請時戳起算；時限不做成可調參數。
- 「師徒關係已解除」發生時，釋放所佔名額。
- 「師徒關係已恢復」發生時，重新佔用名額；名額已滿者不得恢復。

*來源：`.clarify/resolved/aggregate/教官帶徒上限_帶徒上限的初始值與提升幅度.md`（選項 C 之機制 + 使用者給定的數值 + 代號①）*

### 教官測驗設定 Aggregate

教官測驗的題庫與及格標準由管理員於後台設定，屬平台級可調參數。

| Aggregate | 層級 | 說明 |
|-----------|------|------|
| 教官測驗設定 | 平台級 | 題庫、題數、配分、及格標準；由管理員維護，可調整 |
| 教官測驗 | 每次作答 | 該次作答的題目、作答內容與判定結果 |

| 教官測驗設定參數 | 初始值 | 說明 |
|------------------|--------|------|
| 選擇題題庫 | — | 由系統即時判定 |
| 簡答題題庫 | — | 由管理員人工審核 |
| 選擇題題數 | 20 題 | 自題庫隨機抽取 |
| 簡答題題數 | 3 題 | 自題庫隨機抽取 |
| 選擇題及格標準 | 答對 ≥ 80%（20 題中 ≥ 16 題） | 系統即時判定 |
| 簡答題及格標準 | 全數通過 | 管理員人工審核 |
| 及格判定方式 | 雙門檻（兩者皆須通過） | 不採總分制 |

#### 規則

- 題庫、題數、配分與及格標準皆由管理員調整，非寫死於系統。
- 測驗保留選擇題與簡答題兩種題型，人工審核 Policy 維持有效。
- 選擇題由系統即時判定，簡答題由管理員人工審核。
- 設定調整不改動任何已完成作答的既有測驗結果。

- 及格判定採雙門檻：選擇題答對 ≥ 80% **且** 簡答題全數通過，兩者缺一不可。
- 不採總分制：總分制下選擇題滿分者可簡答全錯仍及格，將使人工審核形同虛設。
- 題目一律自題庫隨機抽取，不固定；固定題目將使題庫答案外流後測驗淪為背誦。
- 隨機抽取亦為重考機制的前提，否則重考等於重看同一份考卷。

### 對話 Aggregate

對話為聊天室本身，與其中的訊息分屬兩個 Aggregate。

| 欄位 | 型別 | 說明 |
|------|------|------|
| 參與者 | 使用者 ID ×2 | 對話的雙方 |
| 建立時間 | Timestamp | 沿用 Event 共通時戳規範 |
| 各方刪除狀態 | 每位參與者一個布林值 | 單方刪除只影響該方，對方仍可見 |

#### 規則

- 單則訊息一經發送即不可刪除，故刪除只發生於對話層級。
- 對話不儲存封鎖狀態，封鎖為獨立 Aggregate。

### 私訊 Aggregate

| 欄位 | 型別 | 說明 |
|------|------|------|
| 對話 ID | 對話 ID | 所屬對話 |
| 發送者 | 使用者 ID | 訊息發送方 |
| 內容 | 字串 | 訊息內容 |
| 發送時戳 | Timestamp | 沿用 Event 共通時戳規範 |
| 已讀時戳 | Timestamp / 空值 | 未讀時為空值 |

#### 規則

- 私訊為獨立 Aggregate，不併入對話。
- 私訊可被檢舉，檢舉對象類型「私訊」指涉本 Aggregate 的 ID。

#### 已讀判定

- 判定條件為**開啟對話**，非訊息進入畫面可視範圍。
- 「使用者已讀取私訊」的 Precondition：使用者開啟對話，且該對話中存在以其為接收方、已讀時戳為空的私訊。
- Postcondition：上述私訊的已讀時戳一律寫入當下時戳。
- 已讀狀態於發送方的對話畫面**被動呈現**，不發送推播通知。
- 不建模「已讀通知已發送」Event，亦不列入通知類 Event 清單。
- 已讀回條本階段不可關閉，使用者 Aggregate 不新增相關隱私設定欄位。
- 不採「進入可視範圍才標記已讀」：捲動位置為前端實作細節，無客觀判定標準，
  且同一則訊息在不同螢幕尺寸下的判定會不一致，Precondition 將無法驗收。
- 訊息數量無上限成長，故不作為對話的子集合，避免讀取對話狀態時載入全部歷史。
- 私訊一經發送不可刪除亦不可編輯。

### 封鎖 Aggregate

封鎖為獨立 Aggregate，不附屬於對話。

| 欄位 | 型別 | 說明 |
|------|------|------|
| 封鎖者 | 使用者 ID | 執行封鎖的一方 |
| 被封鎖者 | 使用者 ID | 被封鎖的一方 |
| 封鎖時戳 | Timestamp | 沿用 Event 共通時戳規範 |

#### 規則

- 封鎖為單向關係，唯一鍵為 封鎖者 ID ＋ 被封鎖者 ID。
- 可封鎖從未與其對話過的對象，故封鎖不得掛在對話之下。
- 封鎖的影響範圍超出私訊，其連帶效果由 `rule/使用者已封鎖對象_封鎖是否連帶解除關注與師徒與團隊關係.md` 定案。
- 「使用者已封鎖對象」新增一筆封鎖；「使用者已解除封鎖」移除該筆封鎖。

*來源：`.clarify/resolved/aggregate/使用者已建立對話_對話與私訊的Aggregate歸屬與欄位.md`（選項 B ＋ D）*

### 階級設定 Aggregate

階級總數固定為 **99 階**，門檻以公式表達，由管理員於後台調整參數。

| 參數 | 初始值 | 說明 |
|------|--------|------|
| 階級總數 | 99 | 初始階級為 1 |
| 滿等累計經驗值 | 8,340 | 一般使用者約 365 天可達 |
| 曲線指數 p | 2 | 冪次曲線，前期密集後期拉長 |

**累計經驗值門檻公式**：C(n) ＝ 滿等累計經驗值 × ((n − 1) / 98)^p，n 為階級（2–99）

| 階級 | 2 | 10 | 20 | 50 | 99 |
|------|---|----|----|----|----| 
| 累計門檻 | 1 | 70 | 313 | 2,085 | 8,340 |

#### 滿等累計經驗值的推導基準

| 來源 | 數額 | 頻率 |
|------|------|------|
| 每日簽到 | 10 點 | 每日 |
| 訓練結算 | 30 點 | 每週 3 次 |

每週 160 點 × 52 週 ≈ 8,340 點。

#### 規則

- 階級總數為 99，初始階級為 1，第 99 階為滿等。
- 門檻以公式計算，不逐階列舉數值；管理員調整的是三個參數，非 98 個數字。
- 採冪次曲線（p ＝ 2）：前期升級密集提供回饋，末段拉長維持長期目標。
- **滿等所需累計經驗值不得低於一般使用者 365 天可取得的累計經驗值。**
- 經驗值數額調整時，階級門檻須同步重新校準，以維持上述 365 天下限。
- 上表的每日簽到與訓練結算數額為推導基準，實際值以獎勵定義 Aggregate 為準。
- 並非每一階都解鎖進階訓練計畫，僅指定階級解鎖。
- 門檻調整不改動任何使用者既有的階級。

*來源：`.clarify/resolved/aggregate/階級設定_階級總數與各階門檻初始值為何.md`（選項甲：99 階、p ＝ 2、365 天下限）*

### 訓練計畫 Aggregate

全模型只有一個「訓練計畫」Aggregate，初階與進階計畫共用同一結構。

| 欄位 | 型別 | 說明 |
|------|------|------|
| 名稱 | 字串 | 計畫名稱 |
| 適用條件 | — | 健身經驗、目標、器材，供註冊推薦比對 |
| 所需階級 | 階級 / 空值 | 空值為初階計畫，有值為進階計畫 |
| 課表內容 | — | 見〈課表內容結構（共用）〉；目標重量為管理員設定的建議起始重量 |

#### 規則

- 「進階訓練計畫」非獨立 Aggregate，僅為所需階級欄位有值的訓練計畫。
- 所需階級為空的計畫，供註冊流程的推薦 Policy 使用。
- 所需階級有值的計畫，於使用者達該階級時解鎖。
- 一個階級可解鎖多個訓練計畫，非一對一關係。
- 進階計畫不另需會員訂閱即可使用。
- 並非每一階都解鎖訓練計畫，僅指定階級解鎖，與 99 階的階級總數脫鉤。
- 各階級對應解鎖哪些計畫的清單，由管理員於後台維護（待決策 Partial：初始清單未給定）。

#### 統一語言

「進階訓練計畫」為描述性用語，非獨立 Aggregate 名稱；模型中的 Aggregate 一律稱「訓練計畫」。

*來源：`.clarify/resolved/aggregate/進階訓練計畫_解鎖的計畫內容與階級對應關係.md`（選項 A）*

### 三個成長數值的區別

模型中有三個容易混淆的數值，其歸屬、用途與生命週期皆不同。

| 術語 | 所屬 Aggregate | 用途 | 生命週期 |

| 經驗值 | 使用者 | 判定階級提升 | 單調遞增，永不減少 |

## 跨流程同名 Event

以下 Event 在多條流程中出現，經確認為**同一個事實**，統一定義一次，來源為其攜帶資訊。

| Event | 出現流程 | 攜帶的來源值 |
|-------|----------|--------------|
| 經驗值已提升 | 新手任務流程、每日簽到流程、訓練結算流程 | 新手任務 / 每日簽到 / 訓練結算 |
| 能力值已提升 | 新手任務流程、訓練結算流程 | 新手任務 / 訓練結算 |
| 個人排行榜分數已增加 | 每日任務流程（2 處）、訓練結算流程 | 每日任務進度 / 每日任務全部完成 / 訓練結算 |
| 使用者已提出調整要求 | AI 訓練前調整流程、AI 訓練中調整流程 | 訓練前調整 / 訓練中調整 |
| AI 已再次確認需求 | AI 訓練前調整流程、AI 訓練中調整流程 | 訓練前調整 / 訓練中調整 |
| 使用者已確認需求 | AI 訓練前調整流程、AI 訓練中調整流程 | 訓練前調整 / 訓練中調整 |
| 使用者已確認使用新訓練強度 | AI 訓練前調整流程、AI 自動優化訓練流程 | 訓練前調整 / 自動優化 |
| 使用者已拒絕調整 | AI 訓練前調整流程、AI 訓練中調整流程、AI 自動優化訓練流程 | 訓練前調整 / 訓練中調整 / 自動優化 |
| 訓練課表已套用新強度 | AI 訓練前調整流程、AI 訓練中調整流程、AI 自動優化訓練流程 | 作用範圍＝本次訓練 / 課表範本 |
| 使用者已支付 | 實體商品購買流程、虛擬商品購買流程 | 商品類型＝實體 / 虛擬；支付管道＝第三方金流 / App Store |

### 規則

- 同名跨流程 Event 僅有一份定義，不依來源拆分為多個 Event。
- 來源以攜帶資訊區分，各來源的提升幅度由該來源流程的 Policy 決定。
- 「能力值已提升」與訓練中斷流程的「能力值已退步」為兩個獨立 Event，不合併為單一變動 Event。
- AI 調整類 Event 的來源值域為三值：訓練前調整 / 訓練中調整 / 自動優化。
- 三條 AI 流程的作用範圍差異（本次訓練 / 剩餘動作 / 課表範本）以來源值表達，不另拆 Event。
- 「使用者已確認使用新訓練強度」與 AI 訓練中調整流程的「使用者已確認調整」為兩個不同 Event，本次未歸併。
- 「訓練課表已套用新強度」為單一 Event，三條 AI 流程共用，以作用範圍區分改動標的。
- 「訓練課表已套用新強度」的作用範圍值域為二值：本次訓練 / 課表範本。
- AI 訓練前調整流程與 AI 訓練中調整流程的作用範圍皆為「本次訓練」，AI 自動優化訓練流程為「課表範本」。
- 「訓練課表已套用新強度」的 Actor 為系統；AI 僅產出建議，不執行套用。
- 不建模「訓練課表套用已失敗」：套用為本機資料寫入，失敗屬技術性交易回滾，非業務事實。

- 「使用者已支付」為單一 Event，實體與虛擬兩條購買流程共用，與訂單為單一 Aggregate 的設計對稱。
- 「使用者已支付」的商品類型值域為二值：實體 / 虛擬。
- 「使用者已支付」的支付管道值域為二值：第三方金流 / App Store。
- 實體商品的支付管道為第三方金流（信用卡 / 行動支付，回呼觸發）。
- 虛擬商品的真實金流支付管道為 App Store，與會員訂閱同屬一體系。
- 「使用者已支付」的 Actor 一律為外部系統，兩種支付管道僅為提供者差異，不改變 Actor。

### 規則

- 「中斷」一詞不得單獨使用，必須帶明確主體（單次訓練 / 連續訓練天數）。
- 「追蹤」為棄用詞，一律改用「關注」，對應 Event 為「使用者已關注帳號」。
- Policy 與 Rule 中引述行為時，一律直接使用既有 Event 全名，不得另造簡稱。

*來源：`.clarify/resolved/event/連練天數已中斷_與訓練紀錄流程的使用者訓練已中斷如何區分.md`（選項 B+C）；
AI 調整五個 Event 之增列來源：`.clarify/resolved/event/使用者已拒絕調整_三條AI流程的同名Event是否為同一事實.md`（選項 A）*
