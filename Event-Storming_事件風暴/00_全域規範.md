# 全域規範

> 本檔記錄跨所有流程共通的事件風暴規範，由 `/es-formulation` 依使用者裁決逐項寫入。

## Event 共通攜帶資訊

所有流程中的每一個 Event，發生時皆必須攜帶以下共通欄位：

| 欄位 | 型別 | 說明 |
|------|------|------|
| 事件ID | UUID | 事件唯一識別碼 |
| 發生時戳（UTC） | Timestamp（UTC，毫秒精度） | 事件發生的絕對時間 |
| 發生時戳（使用者當地時區） | Timestamp + 時區代碼 | 供跨時區規則判定使用 |
| 觸發 Actor | Actor 識別碼 | 執行 Command 導致此 Event 的角色 |
| 關聯 Aggregate ID | ID | 此 Event 所改變狀態的 Aggregate |

共通欄位之外，各 Event 另行定義其專屬欄位。

### 規則

- 每一個 Event 必須同時記錄 UTC 時戳與使用者當地時區時戳。
- 跨時區規則（簽到換日、每日任務重置、中斷判定）一律以使用者當地時區時戳為判定基準。
- UTC 時戳的精度為毫秒。

### 統一換日時點

全模型的換日時點為**使用者當地時區的 04:00**。

| 適用對象 | 說明 |
|----------|------|
| 簽到「當日」判定 | 04:00 前簽到計入前一日 |
| 每日任務重置 | 當地時間 04:00 重置 |

- 當地時間 00:00–03:59 的行為一律計入前一個自然日。
- 採 04:00 而非 00:00：健身族群多有深夜運動習慣，午夜換日會使凌晨訓練與簽到落到隔日，不符使用者直覺。
- 簽到與每日任務採同一換日時點，模型中不存在第二個換日時點。
- 本換日時點不適用於「連續訓練天數」的自然日計數，該處另有 36 小時寬限規則。

#### 當地時區的取得來源

- 「使用者當地時區」一律取自**使用者裝置的當前時區**，非使用者 Aggregate 儲存的時區欄位。
- 理由：儲存的時區為註冊當下填入，使用者出國、搬家或變更裝置語系後即過期。
- 跨時區移動導致同一當地日期重複觸發重置時，由冪等機制擋下
  （請求識別碼 ＝ 排程名稱 ＋ 週期起點 ＋ 使用者 ID，週期起點為使用者當地日期），不會重置兩次。
- 使用者 Aggregate 的時區欄位僅供顯示與統計，不作為換日與中斷判定的依據。

*來源：`.clarify/resolved/event/全流程Event_每個Event應攜帶哪些資訊與時間戳.md`（選項 B）*

## Event 冪等性原則

所有流程中的 Event，重複發生時一律以 **Command 請求識別碼**去重。

### 規則

- 每一個 Command 請求必須攜帶請求識別碼。
- 系統以請求識別碼判定重複：識別碼已處理過者視為重複請求。
- 重複請求回傳原次執行的結果，不重複產生 Event。
- 本原則統一適用於全模型，各 Event 不另行定義冪等規則。

### 排程觸發的請求識別碼

排程觸發的 Command 無使用者端請求，其請求識別碼由業務自然鍵推導。

**請求識別碼 ＝ 排程名稱 ＋ 週期起點 ＋ 使用者 ID**

| 排程類 Event | 週期起點 |
|--------------|----------|
| 每日任務已重置 | 使用者當地日期（以當地時間 04:00 為換日點） |
| 訓練已結算 | 該筆訓練的訓練紀錄 ID |
| 簽到連續天數已中斷 | 該次中斷判定所屬的使用者當地日期 |
| 連續訓練天數已歸零 | 該次歸零判定所屬的使用者當地日期 |
| 排行榜週期已結算 | 該排行榜週期的起始日 |
| 能力值已退步 | 該肌群維度的 120 小時計時起算點 |
| 使用者帳號已刪除 | 〔推導〕該次刪除申請的刪除申請時戳 |
| 能力值日快照已產生 | 該筆快照所屬的使用者當地日期（以當地時間 04:00 為換日點） |

#### 規則

- 排程類 Command 不產生隨機識別碼，一律由上表的自然鍵推導。
- 同一週期重跑時算出相同的請求識別碼，視為重複請求，不重複產生 Event。
- 「能力值已退步」的週期起點為肌群維度層級，六個維度各自獨立去重。
- 排程類 Event 不因本規則而免除各自的 Precondition，兩者並存。

*來源：`.clarify/resolved/event/全流程Event_各Event重複發生時的冪等處理原則.md`（選項 A）；
排程情境之補充來源：`.clarify/resolved/event/全流程Event_排程觸發的Event其冪等去重鍵如何產生.md`（選項 A）*

## Actor 清單

全模型的 Actor 共五種，所有 Command 的執行者必須指派為其中之一。

| Actor | 類型 | 說明 |
|-------|------|------|
| 使用者 | 人 | 平台的一般使用者 |
| 管理員 | 人 | 平台管理員，具備審核與處置權限 |
| 系統 | 自動 | 排程、自動判定與套用調整的觸發者 |
| AI | 自動 | 產出訓練調整建議的角色，獨立於外部系統 |
| 外部系統 | 外部 | 平台外的服務，如 Google / Apple、App Store、物流商 |

### 規則

- 發文者、互動者、學徒、教官、成員、對方皆非獨立 Actor，一律歸為「使用者」。
- 上述稱呼僅為使用者在特定情境下的角色描述，不得作為 Command 的 Actor 值。
- 教官不因具備額外權限而獨立為 Actor，其權限差異以使用者的教官身分旗標表達。
- 團隊隊長不為獨立 Actor，其權限差異以團隊內的角色欄位表達。
- AI 僅負責產出建議，不執行套用；套用調整的 Actor 為系統。
- 本清單非封閉清單，新增 Actor 需經明確裁決。

*來源：`.clarify/resolved/command/Actor_模型中各角色名稱的定義與統一.md`（選項 A′）；
AI 一項與清單封閉性之修訂來源：`.clarify/resolved/command/AI已調整訓練_AI是否視為獨立Actor.md`（選項 D″）*

## Command 清單

### 命名與盤點規範

- 每一個 Event 皆有對應的 Command，Command 與 Event 原則上一對一；多對一者於備註標明。
- Command 命名一律為祈使句「動詞＋受詞」，去除主語與「已」字。
- Command 命名反映使用者意圖，不得使用畫面元件名稱。
- 每一個 Command 必須指派 Actor，值域限於〈Actor 清單〉的五種。
- 系統排程與外部回呼觸發的 Event 同樣有 Command，其 Actor 為系統或外部系統。
- 每一個 Command 請求必須攜帶請求識別碼（承〈Event 冪等性原則〉）。
- 隊長、學徒、教官、成員、發文者、互動者皆非 Actor，於備註以括號標明其角色。
- 本清單為 Command 的唯一定義處，各流程檔的 [串聯] 註記為其摘要，不另建清單。

### Command 輸入參數的推導規則

Command 的輸入參數**不逐一列表**，一律由下式推導：

> **Command 的輸入參數 ＝ 其導致的 Event 之專屬攜帶欄位 ＋ 目標 Aggregate ID ＋ 請求識別碼**

#### 規則

- 採推導規則而非逐一列表：Command 的輸入與其導致的 Event 所攜帶的資訊，
  本質上是同一份資料的兩端 —— 使用者填什麼，Event 就記什麼。
  逐一列表會產生大量「請求識別碼 ＋ 對象 ID」的重複列，真正有資訊量的欄位不到三成。
- Event 的**共通 5 欄位**（事件 ID、UTC 時戳、當地時區時戳、觸發 Actor、關聯 Aggregate ID）
  為系統產生，**不是** Command 的輸入。
- 各流程檔以〔攜帶資訊：…〕標註的專屬欄位，即為該 Command 的輸入參數。
- 必填／選填沿用 Event 攜帶欄位的定義：型別標註為「⋯ / 空值」者為選填，其餘為必填。
- 型別、單位與合法範圍沿用該欄位在其 Aggregate 中的既有定義，不另立一套。
- 排程與外部系統觸發的 Command，其請求識別碼由〈排程觸發的請求識別碼〉的自然鍵推導，
  不由呼叫方提供。
- **一 Command 兩結果**者（現有 3 處：審核公開訓練、回報支付結果、回報儲值結果），
  輸入另含一個「判定結果」參數，該參數決定產生兩個互斥 Event 中的哪一個。
- 查詢類 Command（不產生 Event 者）的輸入為其 Read Model 的篩選與分頁條件，
  由該 Read Model 的定義承載，不套用本推導規則。
- 本規則不適用時，該 Command 逐一補問並於本節列為例外；本輪盤點未發現例外。

*來源：`.clarify/resolved/command/全流程Command_226個Command的輸入參數尚未定義.md`（選項 A）*

## Aggregate 邊界

### 使用者 Aggregate

「使用者」為核心 Aggregate，含身分與個人資料、三項成長數值、兩個旗標。

| 欄位群 | 內容 |
|--------|------|
| 身分與個人資料 | 帳密、身高、體重、性別、生日、單位偏好、健身偏好、時區 |
| 成長數值 | 經驗值、能力值、階級 |
| 旗標 | 社群互動功能解鎖旗標、教官身分旗標 |

#### 已定義欄位

| 欄位 | 型別 | 單位 | 合法範圍 | 說明 |
|------|------|------|----------|------|
| 身高 | float（一位小數） | 公分 | 50–250 | 儲存一律以公制為準 |
| 體重 | float（一位小數） | 公斤 | 20–300 | 儲存一律以公制為準 |
| 生日 | date | — | 對應年齡 13–120 歲 | 年齡為衍生欄位，不直接儲存 |
| 單位偏好 | 列舉 | — | 公制 / 英制 | 僅影響顯示，不影響儲存 |
| 能力值 | 6 維數值（每維 int） | — | 各維 10–999（漸近理論上限 1,000） | 依肌群分維：胸 / 背 / 腿 / 肩 / 手 / 核心 |
| 本次中斷各維累積退步量 | 6 維數值（每維 int） | 點 | 各維 ≥ 0 | 該維每次退步時累加，該維恢復訓練時歸零；供回歸任務的部分回復計算 |
| 性別 | 列舉 | — | 男 / 女 | 必填，二元列舉 |
| 每週健身天數 | int | 天 | 1–7 | 必填 |
| 每次健身時長 | 列舉 | — | 30 分鐘以下 / 30–60 / 60–90 / 90 分鐘以上 | 必填，區間列舉 |
| 健身經驗 | 列舉 | — | 新手 / 中階 / 進階 | 必填單選，值域見〈健身經驗設定 Aggregate〉 |
| 累積訓練次數 | int | 次 | ≥ 0 | 單調遞增；「訓練已結算」時 +1，三種終止狀態皆計入 |
| 累積訓練天數 | int | 天 | ≥ 0 | 單調遞增；該當地日期首次「訓練已結算」時 +1，同日後續場次不再 +1 |
| 偏好訓練時段 | 星期 → 時段區間集合 | — | 見〈偏好訓練時段〉 | 供無訓練紀錄者的訓練提醒使用 |
| 處罰狀態 | 列舉 | — | 無 / 警告 / 社群功能停權 / 帳號停權 / 永久停權 | 獨立於社群互動功能解鎖旗標 |
| 累計違規次數 | int | 次 | ≥ 0 | 「使用者已受處罰」時 +1、「處罰已撤銷」時 −1；決定處罰階梯的級距 |
| 處罰到期時戳 | Timestamp / 空值 | — | 限期處罰才有值 | 警告與永久停權為空值 |
| 粉絲數 | int | — | ≥ 0 | 衍生自關注關係，儲存以供成就判定 |
| 帳號狀態 | 列舉 | — | 正常 / 待刪除 / 已刪除 | 獨立於處罰狀態，兩者並存 |
| 刪除申請時戳 | Timestamp / 空值 | — | 帳號狀態為待刪除時才有值 | 30 天冷靜期的計時起點 |

其餘欄位的型別、單位與合法範圍由後續釐清項目逐一定義。

#### 規則

- 身高與體重一律以公制儲存，英制僅為顯示偏好，由單位偏好欄位決定。
- 英制顯示範圍由公制範圍換算：身高 20–98 in、體重 44–661 lb，不另設獨立範圍。
- 年齡不直接儲存，一律由生日衍生計算。
- 年齡未滿 13 歲者不得完成註冊。
- 性別為必填的二元列舉，值域為男 / 女，不含其他選項，亦不可留白。
- 每週健身天數為精確整數，範圍 1–7 天。
- 每次健身時長為區間列舉，不記錄精確分鐘數，因使用者無法精確估計單次時長。
- 兩者皆為註冊 9 項必填之一，不設預設值。

- 經驗值與階級的門檻計算關係在使用者 Aggregate 內部保證一致，不跨 Aggregate。
- 能力值的提升與退步皆改動使用者 Aggregate。
- 能力值為 6 個肌群維度：胸、背、腿、肩、手、核心，各維獨立升降。
- 能力值的提升依動作所屬肌群，只提升該動作對應的維度。
- 「能力值已提升」「能力值已退步」「能力值已部分回復」三個 Event 皆須攜帶所影響的肌群維度。
- 動作 Aggregate 須具備「所屬肌群」欄位，值域為上述 6 個肌群。
- 訓練屬性（力量 / 耐力 / 爆發）本階段不進模型，列為未來擴充。
#### 能力值提升公式

**該維提升點數 ＝（本次該肌群訓練量 ÷ 該肌群基準訓練量）× 基準提升點數**

其中訓練量 ＝ 重量 × 次數 × 組數，逐組累加。

| 肌群 | 基準訓練量 |
|------|-----------|
| 腿 | 4,000 |
| 背 | 2,500 |
| 胸 | 2,000 |
| 肩 | 1,200 |
| 手 | 800 |
| 核心 | 600 |

**遞減報酬係數 ＝ 1 −（該維現值 ÷ 理論上限）**

**該維實際提升點數 ＝ 基準公式結果 × 遞減報酬係數**

| 參數 | 初始值 | 說明 |
|------|--------|------|
| 基準提升點數 | 10 點 | 一次達到基準訓練量的訓練所得 |
| 單次訓練單維上限 | 30 點 | 基準提升點數的 3 倍 |
| 能力值上限 | 1,000 點 | 各維共用；為**可達成**的硬上限，非漸近線 |

- 能力值採遞減報酬而非硬上限：硬上限會使資深使用者的六維圖全部貼齊天花板、頂端失去區辨度，
  遞減報酬則使數值有界的同時仍保有頂端差異，並符合「新手進步快、老手進步慢」的訓練生理。
- 能力值上限 1,000 為**可達成**的值，能力值 ≤ 1,000。
- [統一語言] 「理論上限」已更名為「能力值上限」：原名隱含不可達成，與現行裁決不符。
- [待決策 Partial] 現行遞減報酬係數 ＝ 1 −（該維現值 ÷ 能力值上限），
  在現值趨近 1,000 時係數趨近 0，數學上**永遠到不了 1,000**。
  「可達成」與現行公式直接衝突，公式須調整 → 記於 `.clarify/aggregate/能力值_遞減報酬公式如何使上限1000可達成.md`
- 〔推導〕套用順序：先以單次訓練單維上限 30 點截斷基準公式結果，再乘遞減報酬係數。
- 各肌群採獨立基準訓練量而非統一換算率：腿部訓練量天生為手臂的數倍，
  統一換算率會使所有使用者的六維呈現同一形狀（腿最高、手最低），六個維度將失去表達差異的價值。
- 基準訓練量的意義為「該肌群一次認真訓練的典型總量」，可由真實訓練資料估算校準，非抽象係數。
- 設單次訓練單維上限：能力值有退步機制，提升若無上限，一次超長訓練可抵銷數個月退步，兩邊尺度將對不上。
- 上述參數皆為平台級可調，由管理員於後台維護。
- 提升不依訓練頻率加權；持續性已由連續訓練天數與獎勵加成承擔，不在能力值重複疊加。

#### 徒手動作的訓練量代入

**徒手動作代入重量 ＝ 基準體重 × 該動作的體重係數**

| 參數 | 初始值 | 說明 |
|------|--------|------|
| 基準體重 | 70 公斤 | 全體使用者共用，與實際體重無關 |

- 動作 Aggregate 新增「體重係數」欄位，僅徒手動作有值（如伏地挺身 0.6、引體向上 1.0）。
- 訓練紀錄仍照實儲存重量 0，體重係數僅於計算能力值與訓練量時代入；實績與計算輸入分開。
- 採基準體重而非使用者實際體重，理由有三：
  - 「減重」為常見目標類選項之一，用實際體重會使減重成功者的徒手動作成長變慢，形同懲罰達成目標。
  - 用實際體重時增重可刷分，計分規則不應有此性質。
  - 訓練量同時餵給個人排行榜分數，用實際體重會使跨使用者名次受體重影響。
- 另一實務理由：體重為使用者自填且多數人不定期更新，不依賴該欄位可避免資料過期導致計分錯誤。
- 代價：體重明顯高於基準者做徒手動作的額外負荷不被反映，此為刻意取捨。

#### 能力值退步參數

| 參數 | 初始值 | 說明 |
|------|--------|------|
| 退步百分比 | 2.5% | 每滿 120 小時未訓練退步一次 |
| 六維註冊初始值 | 各維皆 10 | 亦為退步下限 |

| 停練時間 | 累計衰減 |
|----------|----------|
| 10 天 | −5% |
| 1 個月 | −14% |
| 3 個月 | −37% |
| 6 個月 | −60% |
| 1 年 | −84%（趨近下限 10） |

- 六維註冊初始值一致，不依註冊問卷的健身經驗分級；新手與老手的差異已由訓練量決定成長速度自然反映。
- 初始值 10 等同一次基準訓練所得的點數，其意義為「無論荒廢多久仍保有一次認真訓練的水準」。
- 上述參數皆為平台級可調，由管理員於後台維護。
- 退步不負責限制能力值的累積量：退步僅於該肌群 120 小時未訓練時觸發，規律訓練者永不退步；
  累積量的收斂由提升公式的遞減報酬承擔，兩者職責分開。

#### 能力值部分回復參數

**該維回復點數 ＝ 該維本次中斷累積退步量 × 回復比例**

| 參數 | 初始值 | 說明 |
|------|--------|------|
| 回復比例 | 50% | 完成回歸任務時，各維各自回復本次中斷累積退步量的一半 |

- 回復由「使用者已完成回歸任務」觸發，對應 Event 為「能力值已部分回復」，攜帶所影響的肌群維度。
- 六維各自獨立回復，**不論該維是否於回歸任務中被訓練**：該維若有訓練，訓練本身已產生
  「能力值已提升」，再依訓練維度回復即重複計酬；真正需要補償的是未被回歸任務涵蓋、卻同樣退步的維度。
- 回復幅度採累積退步量的比例而非固定點數：停練越久退越多、補回越多，幅度與損耗掛鉤；
  固定點數對高能力值者是零頭、對低能力值者可能一次補滿，跨使用者不對稱。
- 回復後不超過本次中斷前的水準，符合「不回復至退步前水準」的既有 Postcondition（回復比例 < 100% 已自然保證）。
- 回復比例為平台級可調，由管理員於後台維護。

#### 能力值等級

能力值除以點數呈現外，另以**等級**呈現，作為點數的衍生標籤。

**等級值域（六階，由高至低）**

| 等級 | S | A | B | C | D | E |
|------|---|---|---|---|---|---|

- 六階不含 F：S 為最高、E 為最低。
- 等級為**衍生欄位**，由能力值點數推導，不獨立儲存為可直接改寫的值。

**判定基準：絕對點數門檻，六維共用同一組門檻**

- 六維共用一組門檻，不依維度分設，亦不依健身經驗分級分設。
- 不採全平台相對百分位。
- 能力值上限 1,000 為可達成之值，S 級的頂點即 1,000。
- [待決策 Partial] 六個等級的具體點數門檻尚未給定。

**為何六維共用同一組門檻**：跨肌群的正規化已由〈能力值提升公式〉的
獨立基準訓練量完成 —— 腿的 500 點與手的 500 點代表同等程度的認真訓練。
再依維度分設門檻，等於把已拉平的尺度又拉歪一次。

**為何不採相對百分位**：其一，等級會在使用者沒有訓練時變動（他人進步即自己掉級），
與「能力值代表身體能力」的定義衝突，且會產生沒有 Command、沒有使用者行為的等級下降。
其二，需全平台分佈的即時統計，而排行榜已定案採延遲更新正是為避開此成本。
其三，早期使用者少時分佈無意義。

**為何不依健身經驗分級分組**：健身經驗為註冊時自填一次、其後不更新的欄位，
作為長期分級基準會逐漸失真；且分組後「新手的 S」與「進階的 S」不是同一件事，
綜合能力等級將失去對外可比性。

**兩層等級並存**

| 層級 | 對象 | 每人持有數 |
|------|------|-----------|
| 維度能力等級 | 六個肌群維度各自一級 | 6 個 |
| 綜合能力等級 | 六維彙總後的單一等級 | 1 個 |

- 維度能力等級服務「看出自己哪裡強、哪裡弱」：六維雷達圖翻譯為一句可行動的話。
- 綜合能力等級服務對外呈現與單一比較基準。
- 兩層並存不視為與階級（1–99）功能重疊：階級由經驗值決定、衡量投入程度，
  綜合能力等級由能力值決定、衡量身體能力，兩者的來源數值與業務意義不同。

- 警告與永久停權的處罰到期時戳為空值。

- 受處罰者具教官身分時，教官資格一併撤銷。

#### 偏好訓練時段

本欄位表達的是「**使用者有空可以訓練的時段**」，而非「使用者慣常訓練的時段」。
其填寫對象為尚無任何訓練紀錄的新手，該族群尚未形成訓練習慣，答不出慣常時段，但答得出何時有空。

**結構為三層**

| 層級 | 內容 |
|------|------|
| 第一層 | 星期（固定 7 筆：週一至週日） |
| 第二層 | 該日的時段區間集合（0 到 N 個，可為空） |
| 第三層 | 每個區間的起始時間與結束時間 |

| 第三層欄位 | 型別 | 合法範圍 |
|------------|------|----------|
| 起始時間 | time | 00:00–23:30，以 30 分鐘為刻度 |
| 結束時間 | time | 00:30–24:00，以 30 分鐘為刻度 |

#### 規則

- 時間粒度為 **30 分鐘**，一日 48 格。
- 採 30 分鐘而非 15 分鐘或 1 小時：15 分鐘於手機上單格過窄、拖拉易誤觸；
  1 小時無法表達 6:30 或 18:30 這類常見時點。且與「每次健身時長」的 30 分鐘刻度一致。
- **區間不得跨日**：結束時間須大於起始時間，且與起始時間同屬一個星期日。
- 不變條件：同一日的各區間彼此不重疊。
- 〔推導〕拖拉造成重疊時自動合併為單一區間。
- 某日的區間集合為空，代表該日無空閒時段，該日不發送訓練提醒。
- **訓練提醒於區間的起始時間發送**。
- 使用者以拖拉方式調整區間起訖、以按鈕新增區間、以長按刪除區間；
  上述皆為介面操作，不各自建模為 Event，一律由「使用者已選擇偏好訓練時段」承接。
- 本欄位由新手任務流程的「使用者已選擇偏好訓練時段」寫入（Actor：使用者）。
- **[待決策 Partial]** 兩段式發送的型別銜接：既有裁決為「有訓練紀錄者由系統依訓練紀錄的
  時戳分布推算」，但推算的輸出型別須與本欄位的區間集合一致，否則兩條路徑產出不同結構
  → 記於 pending-gaps-3.md 之 I18。

*來源：`.clarify/resolved/aggregate/使用者_偏好訓練時段欄位的型別與值域.md`
（使用者自述結構 ＋ 粒度 30 分鐘、不可跨日、提醒於區間起點發送）*

#### 累積訓練次數

- 累積訓練次數為**單調遞增**，任何情況下不減少。
- 三種終止 Event（使用者已完成訓練 / 使用者已提前結束訓練 / 單次訓練已逾時中斷）
  皆於「訓練已結算」發生時 +1。
- 中斷的訓練計入：承「中斷仍計入連續訓練天數」的既有裁決，理由相同 ——
  逾時中斷最常見的原因為練畢未按結束而非未訓練，扣除等於懲罰確實有訓練者。
  且同一筆訓練若在連續天數算數、在累積次數不算，兩個計數器對同一件事將給出不同答案。
- 採**儲存欄位**而非由訓練紀錄即時 count：教官資格初審為系統即時判定，
  而訓練紀錄為一人多筆的高頻寫入資料（此為訓練紀錄不併入使用者的既有理由），
  每次判定全表 count 的成本問題與粉絲數相同，處理方式一併沿用。
- 本欄位為兩處 Precondition 的判定依據：教官資格初審門檻、自訂訓練功能解鎖。
- 「訓練成就的累積門檻」與「AI 每 3 次自動優化」是否共用本欄位，尚未定案（待決策 Partial）。

*來源：`.clarify/resolved/aggregate/使用者_累積訓練次數欄位的定義與計入條件.md`（選項 A）*

- 粉絲數為儲存欄位，隨「使用者已關注帳號」與「使用者已取消關注」同步增減。
- 不變條件：粉絲數 ＝ 關注關係中被關注者為本人的筆數。
- 粉絲數不採即時彙總查詢：粉絲成就門檻最高 10000，即時 count 於熱門帳號成本過高；
  改以計數欄位於關注 / 取消關注時 +1 / −1，該次寫入為即時。
- 粉絲數不允許與關注關係不一致，避免粉絲成就的解鎖判定抖動。
- **即時性：顯示與粉絲成就判定共用同一個粉絲數欄位，兩者皆為即時，不設延遲重算路徑。**
- 不採「顯示延遲、成就判定即時」的雙路徑：同一件事分兩條路徑會出現畫面數字與成就狀態
  對不起來的情形，且計數欄位的維護成本本就極低，延遲重算換不到對等的好處。

#### 帳號生命週期

| 狀態 | 說明 |
|------|------|
| 正常 | 帳號可正常使用 |
| 待刪除 | 已申請刪除，帳號停用，資料全數保留，冷靜期計時中 |
| 已刪除 | 冷靜期屆滿並執行軟刪除（終止狀態） |

| 起始狀態 | 觸發 Event | 目標狀態 |
|----------|-----------|----------|
| — | 使用者帳號已建立 | 正常 |
| 正常 | 使用者已申請刪除帳號 | 待刪除 |
| 待刪除 | 使用者已取消刪除帳號申請 | 正常 |
| 待刪除 | 使用者帳號已刪除 | 已刪除（終止） |

- 帳號刪除納入軟體邊界：App Store 自 2022 年起強制要求 App 內提供帳號刪除功能，
  而本模型的訂閱與儲值皆走 App Store，無法將此路徑留在系統邊界之外。
- 冷靜期為 30 天，自刪除申請時戳起算；期間帳號停用、資料全數保留、不執行任何刪除。
- 冷靜期內可取消刪除，帳號狀態回復為正常並清空刪除申請時戳。
- 冷靜期屆滿執行**軟刪除**：使用者所產生的內容全數保留，僅將個人識別資料匿名化。
- 不採硬刪除：貼文已定案軟刪除以免已成案的檢舉失去指涉對象，AI 調整對話亦定案永久保存
  供申訴使用且申訴未設時效上限；硬刪除一位使用者會同時打斷這兩條稽核鏈。
- 帳號狀態獨立於處罰狀態，兩者並存，不互相取代。
- 帳號狀態為已刪除者，不得再發生任何以其為 Actor 的 Command。
- 冷靜期長度為平台級可調參數，由管理員於後台維護。

*來源：`.clarify/resolved/event/使用者帳號已建立_帳號刪除與註銷的Event全數缺失.md`（選項 A ＋ C，冷靜期 30 天）*

### 回歸任務 Aggregate

| 欄位 | 型別 | 說明 |
|------|------|------|
| 指派時戳 | Timestamp | 「回歸任務已指派」發生的時點 |
| 時限起算時戳 | Timestamp / 空值 | 使用者首次登入查看時寫入；未查看時為空值 |
| 狀態 | 列舉 | 已指派 / 已完成 / 已逾期 |

#### 規則

- 時限長度為 **7 天**，自**使用者首次登入查看**時起算，非自指派時刻起算。
- 時限起算時戳由 Event「使用者已查看回歸任務」寫入，該 Event 的 Actor 為使用者。
- 「使用者已查看回歸任務」的 Precondition 為：回歸任務狀態為已指派，且時限起算時戳為空值；
  故該 Event 對同一筆回歸任務僅發生一次。
- 時限起算時戳不由 Read Model 的讀取寫入：Read Model 已定案不改變任何狀態。
- 「使用者已登入」與「使用者已查看回歸任務」為兩個不同 Event，登入不等於看見回歸任務。
- 時限起算時戳為空值者，逾期判定不啟動；使用者未回來查看即不會逾期。
- 採首次查看起算的理由：回歸任務的觸發條件為「能力值已退步」，即使用者已 120 小時未訓練，
  指派當下多半不在使用 App。若自指派時刻起算，使用者回來時任務已所剩無幾或早已逾期，
  等於懲罰了這個機制想挽回的對象。
- 「距前一次指派滿 7 天方可再次指派」為指派頻率規則，與本時限無關，兩者並存。

*來源：`.clarify/resolved/rule/回歸任務已指派_限時的時限長度為何.md`（選項 C）*

### 成就結構

成就拆為兩個 Aggregate，因兩者生命週期不同。

| Aggregate | 層級 | 說明 |
|-----------|------|------|
| 成就定義 | 平台級 | 成就的類型、門檻、對應獎勵；由平台維護，可調整 |
| 使用者成就解鎖紀錄 | 每使用者 | 該使用者已解鎖的成就與解鎖時點 |

全模型共 7 類成就，皆共用上述結構：

| 成就類型 | 所屬流程 |
|----------|----------|
| 連簽成就 | 每日簽到流程 |
| 累簽成就 | 每日簽到流程 |
| 連續訓練成就 | 訓練結算流程 |
| 累積訓練成就 | 訓練結算流程 |
| 新手成就 | 新手任務流程 |
| 互動成就 | 發文與互動流程（分享 / 發文 / 按讚 / 留言 4 類） |
| 粉絲成就 | 關注流程 |

#### 規則

- 成就門檻屬成就定義 Aggregate，調整門檻不改動任何既有的解鎖紀錄。
- 使用者成就解鎖紀錄一經寫入不再變動。
- 7 個「⋯成就已解鎖」Event 維持各自獨立，不合併為單一「成就已解鎖」Event。
- 每個成就門檻**終身僅解鎖一次**，重複達成不再解鎖亦不再發放獎勵。
- 使用者成就解鎖紀錄為單調遞增，一經解鎖不可撤銷（含粉絲數下降的情形）。

#### 訓練類成就的門檻計數單位

**累積訓練成就與連續訓練成就的門檻皆以「天數」計數**，一日內訓練多場僅計 1 天。

| 成就類型 | 計數單位 | 對應欄位 |
|----------|---------|---------|
| 累積訓練成就 | 累積訓練**天數** | 使用者 Aggregate「累積訓練天數」 |
| 連續訓練成就 | 連續訓練**天數** | 連續訓練 Aggregate「連續訓練天數」 |

- 使用者 Aggregate 須新增「**累積訓練天數**」欄位（int，≥ 0，單調遞增），
  於該當地日期首次「訓練已結算」時 +1，同日後續場次不再 +1。
- **本欄位與既有的「累積訓練次數」不同，兩者並存不合併**：
  累積訓練次數計場次（一日兩場計 2），供教官初審門檻使用；
  累積訓練天數計日數（一日兩場計 1），供累積訓練成就使用。
- 兩者的計入條件一致：三種訓練終止狀態皆計入。
- 採天數而非次數：一日內連開多場訓練即可快速推進成就門檻，以次數計會使成就可被短時間刷完。

*來源：`.clarify/resolved/aggregate/成就_各類成就的統一資料結構.md`（選項 B）；*
*`.clarify/resolved/rule/訓練成就門檻_累積門檻計算的是天數或次數.md`（選項 C）；*
*`.clarify/resolved/rule/連簽成就已解鎖_同一門檻重複達成時是否重複發放.md`（選項 A）*

### 獎勵信箱 Aggregate

已完成但未領取的獎勵於重置時補發至此，不作廢。

| 欄位 | 型別 | 說明 |

### 排行榜歷史紀錄 Aggregate

| 欄位 | 型別 | 說明 |

| 榜別 | 列舉 | 個人週榜 / 個人月榜 / 團隊日常 / 團隊限時 |

### 通知類 Event 的發送規則

模型的通知類 Event 皆標記為〔不需精準追蹤〕，但同日重疊時需有明確的取捨規則。

#### 不合併，但設同日總量上限

- 各則通知**各自發送**，不合併為單一摘要通知。
- 同一使用者同日推播總數設上限，超出上限者依優先序由低至高捨棄。
- 推播總數上限為平台級可調參數，由管理員於後台維護。

#### 優先序（由高至低）

| 序 | 類別 | 說明 |
|----|------|------|
| 1 | 期限即將失效類 | 連簽中斷預告、補簽提醒、中斷預告等，錯過即產生不可回復的損失 |
| 2 | 行動引導類 | 訓練提醒等，引導使用者執行當日行為 |
| 3 | 例行提醒類 | 每日登入提醒（簽到），優先度最低 |

- 同日若同時存在期限即將失效類與例行提醒類，**優先發送期限即將失效類**。
- 不合併的理由：各則通知的訴求完全不同（簽到 / 去訓練 / 回來），
  合併為「你有 3 則待辦」會使每一則都失去行動指引。
- 設總量上限的理由：同日湊齊多則通知時會構成騷擾，使用者關閉推播權限的代價是永久性的。

[待決策 Partial] 通知類 Event 的完整清單及其各自的優先序歸類尚未逐一盤點。

*來源：`.clarify/resolved/rule/通知類Event_同日多個通知重疊時的合併與優先序.md`（選項 A ＋ 優先序）*

### 動作 Aggregate

動作分兩種來源，共用同一個 Aggregate。

| 欄位 | 型別 | 說明 |
|------|------|------|
| 名稱 | 字串 | 動作名稱 |
| 動作類型 | 列舉 | 重訓 / 有氧 |
| 所屬肌群 | 列舉 / 空值 | 胸 / 背 / 腿 / 肩 / 手 / 核心；**動作類型為有氧者為空值** |
| 所需器材 | 列舉 | 健身房（全器材）/ 居家器材 / 徒手；供訓練計畫推薦比對 |
| 所需器材明細 | 列舉複選 | 具體品項（啞鈴 / 槓鈴 / 壺鈴 / 彈力繩 / 機械 / 徒手…）；僅供動作庫篩選 |
| 所需器材明細 | 列舉複選 | 具體品項（啞鈴 / 槓鈴 / 壺鈴 / 彈力繩 / 機械 / 徒手…）；僅供動作庫篩選 |
| 體重係數 | float / 空值 | 僅徒手的重訓動作有值，如伏地挺身 0.6、引體向上 1.0 |
| 預設組間休息秒數 | int | 該動作的建議休息時長；平台動作庫由管理員設定，自建動作由建立者設定 |
| 示範內容 | — | 動作示範 |
| 來源 | 列舉 | 平台動作庫 / 使用者自建 |
| 建立者 | 使用者 ID | 來源為使用者自建時才有值 |

#### 規則

- 平台動作庫由平台維護，所有使用者皆可選用。
- 使用者可自建私人動作，僅建立者本人可選用。
- 使用者自建的動作**不計入能力值計算**，訓練該動作不產生「能力值已提升」。
- 所需器材的值域與註冊流程「使用者已選擇健身器材」一致。

**器材的兩層粒度**

| 層級 | 欄位 | 值域 | 用途 |
|------|------|------|------|
| 粗 | 所需器材 | 健身房（全器材）/ 居家器材 / 徒手 | 訓練計畫推薦比對（硬約束，第一優先維度）|
| 細 | 所需器材明細 | 啞鈴 / 槓鈴 / 壺鈴 / 彈力繩 / 機械 / 徒手… | 動作庫的手動篩選 |

- 註冊流程的「使用者已選擇健身器材」**維持 3 級不變**，不改為複選具體品項。
- 兩層並存，粗層供比對、細層供瀏覽；推薦比對的既有規則完全不受影響。
- 明細值域由管理員於後台維護，比照健身目標與健身經驗的既有處理方式。
- **明細篩選只能由使用者手動選取**：系統僅知道使用者的 3 級器材，不知道他實際擁有哪些品項，
  故動作庫的預設篩選只能套用 3 級，明細層無預設值。
- 註冊不改為逐項勾選的理由：註冊已有 9 項必填且逐欄位建模（用意為分析漏斗流失），
  加入逐項器材會拉長漏斗；而動作庫是使用者已在使用 App 之後才進入的畫面，篩得細無此代價。

[待決策 Partial] 明細值域的完整清單、是否需獨立的器材設定 Aggregate、
以及粗層與細層的對應關係（如「健身房」是否自動涵蓋全部明細），皆尚未定案。

**自建動作的欄位必填規則**

| 欄位 | 平台動作庫 | 使用者自建 |
|------|-----------|-----------|
| 所屬肌群 | 必填（有氧為空值） | **必填**（有氧為空值） |
| 所需器材 | 必填 | **選填**，可為空值 |

- 自建動作的所屬肌群必填，理由**不是**能力值歸屬（自建動作已定案不計入能力值），
  而是動作庫 Read Model 的依肌群篩選、以及訓練歷史的部位統計：
  留空的自建動作會在這兩處變成無法歸類的孤兒項。
- 自建動作的所需器材選填：該欄位的用途為訓練計畫推薦時的比對維度，
  而自建動作不參與推薦比對，留空無後果。
- 所需器材為空值的自建動作，於動作庫依器材篩選時不出現於任何器材分類。

*來源：`.clarify/resolved/rule/使用者已建立自訂動作_自建動作的所屬肌群是否必填.md`（選項 C）*
- 預設組間休息秒數為動作層級的屬性；平台動作庫由管理員於後台維護，使用者自建動作由建立者設定。
- 管理員調整某動作的預設休息秒數，不改動任何已產生的本次訓練課表快照。

#### 有氧動作

有氧動作（跑步、飛輪、划船等）納入模型，與重訓動作共用同一個動作 Aggregate，以動作類型欄位區分。

| 項目 | 重訓 | 有氧 |
|------|------|------|
| 所屬肌群 | 六選一，必填 | 空值 |
| 計入能力值 | 是（依所屬肌群提升該維） | **否** |
| 計入經驗值 | 是 | 是 |
| 計入個人排行榜分數 | 是 | 是 |

- **不新增第 7 個能力值維度**：能力值維持 6 個肌群維度，為純重訓實力指標。
- 有氧動作**不觸發「能力值已提升」**，比照使用者自建動作的既有處理方式。
- 有氧的訓練量計入個人排行榜分數與經驗值：註冊必填的常見目標類四項中，
  「減重」與「提升體能」主要靠有氧達成，若完全零回饋，這兩類使用者做完一小時有氧
  六維與排行榜皆毫無變化。
- **不採折算至既有六維**（如跑步折算至腿與核心）：只跑步的人腿部能力值會持續上升，
  而他做深蹲的能力其實沒變，六維的語意會被汙染、雷達圖日後無法解讀。

  先把重訓做完整，能力值的定義維持乾淨。

  （現為目標重量與目標次數，對有氧不適用），尚未定案 → 記於 pending-gaps-3.md 之 I16。

### 課表內容結構（共用）

訓練計畫、自訂訓練、本次訓練課表三者的「課表內容」共用同一結構，為三層巢狀。

| 層級 | 內容 |
|------|------|
| 第一層 | 動作清單（每項為一個動作 ID） |
| 第二層 | 該動作的組數（int，≥ 1）與建議組間休息秒數 |
| 第三層 | 每一組的目標重量與目標次數 |

| 第三層欄位 | 型別 | 單位 | 合法範圍 | 必填 |
|------------|------|------|----------|------|
| 目標重量 | float（精度 0.5） | 公斤 | ≥ 0 | 必填 |
| 目標次數 | int | 次 | ≥ 1 | 必填 |

#### 規則

- 訓練計畫與自訂訓練的課表內容格式完全一致，不因來源而有結構差異。
- 每一組可各自設定不同的目標重量，不強制整個動作共用同一重量。
- 目標重量為必填，值為 0 代表徒手（自身體重）動作。
- 目標重量的 0 於 Read Model 顯示為「自重」，儲存值一律為 0，不另存字串。
- 目標重量的型別、精度與合法範圍與訓練紀錄的實績重量一致。
- 平台訓練計畫的目標重量為管理員設定的**建議起始重量**。
- 使用者自訂訓練的目標重量由使用者於「使用者已設定該組的重量&次數」時填入。

#### 組間休息秒數的取值優先序

| 順位 | 來源 |
|------|------|
| 1 | 課表內容於該動作指定的建議休息秒數 |
| 2 | 該動作 Aggregate 的預設組間休息秒數 |
| 3 | 全站預設 90 秒 |

- 休息秒數為動作層級，不逐組設定：不同動作的合理休息差異大（大重量深蹲 3 分鐘、二頭彎舉 60 秒），
  但同一動作的各組差異小。
- 使用者可隨時跳過休息，跳過即觸發「組間休息已結束」。
- 不採不可跳過的強制計時：休息計時僅為輔助，強制等待會擋住真正的業務事實
  （使用者已開始下一組卻無法記錄），且會與 40 分鐘逾時中斷判定互相干擾。
- **本節的「隨時可跳過」僅指組間休息計時**；勾選下一組另受〈防作弊：連續快速勾選的阻擋〉限制。

#### 防作弊：連續快速勾選的阻擋

**Precondition：若前一個組間間隔小於最小組間間隔，則本組須距前一組滿最小組間間隔，方可發生
「使用者已完成該組」。**

| 參數 | 初始值 | 說明 |
|------|--------|------|
| 最小組間間隔 | 30 秒 | 相鄰兩組完成時戳的間隔門檻 |
| 容許的連續快速勾選次數 | 1 次 | 容許幾次低於門檻的間隔後開始阻擋 |

上述參數皆為平台級可調，由管理員於後台維護。

**判定方式**

- 組間間隔 ＝ 相鄰兩組「使用者已完成該組」的完成時戳之差。
- 效果等同於：**不允許連續出現兩個低於 30 秒的間隔**。
- 一場訓練的第一組無前一個間隔，不受限制。
- 出現一次 ≥ 30 秒的正常間隔後，快速勾選的額度回復。
- 阻擋的解除時點為**自前一組的完成時戳起算滿 30 秒**，非自被阻擋當下起算。

**範例**

| 事件 | 時點 | 間隔 | 判定 |
|------|------|------|------|
| 組 1 勾選 | t=0 | — | 通過（第一組不受限） |
| 組 2 勾選 | t=10s | 10s | 通過（容許一次） |
| 組 3 勾選 | t=15s | — | **阻擋**，須等至 t=40s |
| 組 3 勾選 | t=40s | 30s | 通過，額度回復 |

**規則**

- 判定範圍為**整場訓練，不分動作**：作弊的形狀不限於同一動作，跨動作連點同樣需擋。
- 採「容忍一次再阻擋」而非一律阻擋：訓練中偶爾補登一組為正常行為，一律阻擋會誤傷。
- 阻擋**不建模為 Event**：其為 Precondition 未滿足，非業務事實。
- **已知取捨**：連續兩組皆於 30 秒內完成的情形會被阻擋（如大重量 5 下約 20 秒完成）。
  循環訓練與超級組不受影響 —— 兩次勾選的間隔包含執行該組所需的時間，
  多數情形本就超過 30 秒。
- 本機制為**事前阻擋**，與 AI 訓練品質評分「紀錄合理性」維度的**事後偵測**並存，
  兩者不互相取代：前者及於所有使用者，後者僅用於教官資格初審。

*來源：`.clarify/resolved/rule/組間休息已開始_休息時長由誰決定可否跳過.md`（原裁決）；
防作弊機制之增列來源：`.clarify/resolved/rule/使用者已完成該組_連續快速勾選的防作弊阻擋.md`
（使用者主動提出，2026-08-02）*

### 本次訓練課表 Aggregate

「本次訓練課表」為獨立 Aggregate，於開始訓練時自來源課表複製快照，承載本次訓練的計畫內容。

| 欄位 | 型別 | 說明 |
|------|------|------|
| 來源類型 | 列舉 | 訓練計畫 / 自訂訓練 / 空白課表 |
| 來源課表 ID | ID / 空值 | 來源類型為空白課表時為空值 |
| 課表內容 | — | 自來源複製的快照，結構見〈課表內容結構（共用）〉 |
| 總計畫組數 | int | ≥ 0，供訓練進度條計算分母 |

#### 規則

- 「使用者已選擇訓練課表」時自來源課表複製快照，產生一份本次訓練課表。
- 快照於選擇課表時即產生，非等到開始訓練，因 AI 訓練前調整發生於開始訓練之前。
- 快照一經產生即與來源課表脫鉤，來源課表其後的任何改動不影響已產生的快照。
- AI 訓練前調整與 AI 訓練中調整只改本次訓練課表的快照，不改來源課表。
- AI 自動優化訓練只改課表範本（訓練計畫 / 自訂訓練），不改任何既有快照。
- 「訓練課表已套用新強度」作用範圍為「本次訓練」者改本 Aggregate，為「課表範本」者改來源課表。
- 訓練進度條的總計畫組數取自本 Aggregate，不取自來源課表。
- 空白課表為合法的初始狀態，其總計畫組數為 0、來源課表 ID 為空值。
- 本 Aggregate 與訓練紀錄為一對一：前者為計畫，後者為實績，兩者不合併。

#### 訓練中加入動作

課表內容並非只能於開始訓練前決定 —— 本 Aggregate 於**訓練進行中可新增動作與組**。

| 項目 | 內容 |
|------|------|
| Command | 加入動作至本次訓練 |
| Event | 使用者已加入動作至本次訓練 |
| Actor | 使用者 |
| 輸入參數 | 動作 ID、組數、各組目標重量、各組目標次數、本次訓練課表 ID、請求識別碼 |

- Precondition：本次訓練狀態為進行中，且尚未結算。
- Postcondition：於課表內容新增該動作與其各組，總計畫組數隨新增組數增加。
- 本 Command 對總計畫組數**只增不減**；已加入的動作與組不可再移除。
- 不想練的組不勾選即可，該組不計入已完成組數，僅使進度百分比低於 100%。
- 本 Command 只改本 Aggregate，不改來源課表，亦不改任何自訂訓練 Aggregate。
- 加入的組無快照帶入值：目標重量與次數由使用者於加入時指定。
- 兩種入口共用本路徑：空白課表取得其第一個動作、一般課表於訓練中臨時加練計畫外動作。

**總計畫組數整體仍非單調遞增**：本 Command 只增，但 AI 訓練中調整可使其下降。
既有規則〈訓練進度條〉「AI 調整導致總計畫組數變動時，進度百分比允許下降」不受本次裁決影響。

| 欄位 | 型別 | 單位 | 合法範圍 | 說明 |

| 開始時戳 | Timestamp | — | — | 「使用者已開始訓練」的發生時點 |
| 結束時戳 | Timestamp / 空值 | — | — | 三種終止 Event 之一的發生時點；進行中為空值 |

#### 組紀錄欄位（子聚合）

| 欄位 | 型別 | 單位 | 合法範圍 | 說明 |
|------|------|------|----------|------|
| 動作 ID | 動作 ID | — | — | 所執行的動作 |
| 組序 | int | — | ≥ 1 | 該動作的第幾組 |
| 重量 | float（精度 0.5） | 公斤 | ≥ 0 | 0 代表自身體重（徒手）動作 |
| 次數 | int | 次 | ≥ 1 | 不記錄次數為 0 的失敗組 |
| 完成時戳 | Timestamp | — | — | 「使用者已完成該組」的發生時點；供 AI 品質評分計算每組耗時 |

#### 狀態機

| 起始狀態 | 觸發 Event | 目標狀態 |
|----------|-----------|----------|
| — | 使用者已開始訓練 | 進行中 |
| 進行中 | 使用者已完成訓練 | 已完成（終止） |
| 進行中 | 使用者已提前結束訓練 | 已提前結束（終止） |
| 進行中 | 單次訓練已逾時中斷 | 已中斷（終止） |

#### 規則

- 重量允許為 0，用於自身體重（徒手）動作。
- 重量不允許負值。
- 次數最小為 1，不記錄次數為 0 的失敗組。
- 重量一律以公制儲存，英制顯示沿用使用者 Aggregate 的單位偏好欄位，訓練紀錄不另存單位。

- 採兩層結構：一次訓練含多個動作、每個動作含多組，而「快照帶入最近一次該動作的實際重量」
  要求能**跨訓練、依動作**查詢單組資料；單層巢狀結構做不到這件事而不掃描全部歷史。
- 組紀錄**不獨立為 Aggregate**：無任何外部對象指涉它，亦不會脫離所屬訓練而單獨存在。
  （留言之所以自貼文獨立，理由為「留言可被檢舉，需有獨立身分供指涉」，組紀錄無此需求。）
- 總訓練量與已完成組數為**儲存欄位**，非即時彙總：承粉絲數的既有裁決（衍生值仍儲存），
  且訓練紀錄結算後即凍結、永不再變，其彙總值是永遠不會失效的快照。
- 不變條件：總訓練量 ＝ 各組紀錄「重量 × 次數」的累加（徒手動作代入體重係數換算後的重量）。
- 不變條件：已完成組數 ＝ 組紀錄的筆數。
- 三種終止狀態皆進入訓練結算流程；「訓練已結算」後訓練紀錄凍結，一律不可修改。
- 訓練時長為衍生值（結束時戳 − 開始時戳），不另存欄位。
- 課表名稱為衍生值（經本次訓練課表 ID 取其來源課表），不另存欄位。
- 能力值提升所需的「依肌群分別累加的訓練量」，由組紀錄的動作 ID 取其所屬肌群後分組累加，
  不另存六維訓練量欄位。

### 訓練進度條 Aggregate

進度百分比 ＝ **已完成組數 / 總計畫組數**

#### 規則

- 訓練進度條**不要求單調遞增**。
- AI 調整訓練導致總計畫組數變動時，進度百分比允許下降。
- 總計畫組數為 0（空白課表）時不顯示進度條，進度條不成立。
- 空白課表發生「使用者已加入動作至本次訓練」後總計畫組數大於 0，進度條自該時點起成立。
- 總計畫組數取自本次訓練課表 Aggregate，不取自來源課表。

#### 進度條變動的 Event

- 進度條的漲跌共用單一 Event「訓練進度條已變動」，不拆為已增加與已減少兩個 Event。
- 「訓練進度條已變動」為多對一：由「使用者已完成該組」或「使用者已取消該組」導致。
- 不拆為雙向兩個 Event：進度條已定案不要求單調遞增，漲跌本為同一個數字在動，
  且其漲跌無獨立的業務後果（與「使用者已失去獎勵加成」不同，後者有實質後果故獨立成 Event）。
- 「使用者已取消該組」為獨立 Event：取消勾選的行為軌跡是 AI 訓練品質評分「紀錄合理性」
  維度的判讀依據之一（該維度需判讀是否一路直接勾選預帶值），不建模將使該評分少一項輸入。
- 修改已記錄的重量與次數**不另建 Event**：其不改變已完成組數，僅改實績值。

### 連續訓練 Aggregate

連續訓練天數以**自然日**計數，並提供 **36 小時寬限**；寬限自**上次訓練日的日界**起算。

| 欄位 | 型別 | 說明 |
|------|------|------|
| 上次訓練日期 | date | 使用者當地日期，作為中斷判定的計時基準 |

#### 規則

- 同一自然日內訓練一次以上，該日計為 1 天，不重複計數。
- 計時起點為上次訓練日的日界，即該日結束、次日當地時間 04:00。
- 距上次訓練日的日界未超過 36 小時再次訓練，連續天數續計，即使中間跨過一個未訓練的自然日。
- 距上次訓練日的日界超過 36 小時，連續訓練天數歸零。
- 自然日的判定以使用者當地時區時戳為基準；36 小時的判定以上次訓練日期推得的日界為基準。
- 計時基準取自「上次訓練日期」欄位（使用者當地日期），非訓練的實際時戳。
- 採日界而非時戳：使所有使用者的期限統一落在同一時點，不因當日幾點訓練而差異數小時，
  與連簽中斷判定的計時基準一致。

#### 連續訓練中斷判定的計時起點

四個門檻一律自**上次訓練日的日界**起算。

| 距日界 | 判定 |
|--------|------|
| +24 小時 | 中斷預告已發送 |
| +36 小時 | 連續訓練天數已歸零、使用者已失去獎勵加成、連練中斷通知已發送 |
| +96 小時 | 退步預告已發送 |
| +120 小時 | 能力值已退步 |

- 單次訓練已逾時中斷者，該筆訓練仍計入「上次訓練日期」，同樣重設計時
  （承既有裁決：已中斷的訓練仍進入訓練結算流程，中斷前已記錄的組數全數保留）。
- 能力值退步的六維各自獨立計時，計時起點為**該維最後一次訓練日的日界**。

- 獎勵加成為連續訓練天數的衍生值：每連續一天 +1%，上限 30%。
- 加成雖為衍生值，「使用者已失去獎勵加成」與「使用者已獲得獎勵加成」仍各為獨立 Event。
- 不建模「使用者已恢復獎勵加成」：加成的重新累積由「使用者已獲得獎勵加成」承接。

*來源：`.clarify/resolved/aggregate/連續訓練_連續訓練天數的判定基準.md`（選項 C）；
計時起點由時戳修正為日界之來源：`.clarify/resolved/rule/連續訓練中斷判定_24至120小時的計時起點為何.md`（選項 C）*

### 連續簽到 Aggregate

| 欄位 | 型別 | 初始值 | 說明 |
|------|------|--------|------|
| 連續天數 | int | 首次簽到為 1 | 簽到中斷時歸零 |
| 累計天數 | int | 首次簽到為 1 | 永不歸零，單調遞增 |
| 中斷前連續天數 | int | 0 | 中斷發生時保存歸零前的連續天數，供補簽回復使用 |
| 歷史最長連續天數 | int | 首次簽到為 1 | 永不減少，記錄歷來達到過的最大連續天數 |
| 上次簽到日期 | date | — | 使用者當地日期，作為中斷判定的計時基準 |

#### 規則

- 累計天數為單調遞增，任何情況下皆不減少。
- 歷史最長連續天數為單調遞增，任何情況下皆不減少。
- 連續天數於簽到中斷時歸零，歸零前先將原值寫入中斷前連續天數。
- 補簽成功時，連續天數回復為：中斷前連續天數 ＋ 補回的天數 ＋ 中斷後已簽到的天數。
- 補簽券使用後，中斷前連續天數清空為 0。
- 不變條件：累計天數 ≥ 歷史最長連續天數 ≥ 連續天數。
- 不變條件：中斷前連續天數 > 0 代表存在一次尚可補救的中斷。

#### 連簽中斷判定的計時起點

計時起點為**上次簽到日的日界**，即該日結束、次日當地時間 04:00。

| 距日界 | 判定 |
|--------|------|
| +24 小時 | 整整錯過 1 天 → 連簽中斷預告已發送 |
| +36 小時 | 錯過 1.5 天 → 簽到連續天數已中斷 |
| +48 小時 | 錯過 2 天 → 補簽提醒已發送 |

- 不以上次簽到的實際時戳起算：那會使警告時點取決於使用者昨天幾點開 App，
  且可能在使用者今日仍有簽到資格時就發出中斷預告。
- 計時基準取自連續簽到 Aggregate 的「上次簽到日期」欄位（使用者當地日期），非時戳。
- 三個門檻對應「錯過 1 天 / 1.5 天 / 2 天」，與既有的 24 / 36 / 48 小時設定一致，不改寫數值。

*來源：`.clarify/resolved/aggregate/連續簽到_連續天數與累計天數的定義與型別.md`（選項 D′）*

### 虛擬貨幣 Aggregate

站內虛擬貨幣只有一種，名稱為**金幣**。

| 欄位 | 型別 | 說明 |
|------|------|------|
| 金幣餘額 | int | 持有的金幣數量 |

#### 規則

- 全模型僅有金幣一種虛擬貨幣，不區分免費幣與付費幣。
- 金幣的取得來源為各類獎勵發放與儲值。
- 金幣的消耗用途為購買虛擬商品與購買補簽券。
- 金幣餘額不得為負值。
- **金幣不可於使用者之間轉讓或交易**：取得後僅能由本人消耗，無使用者對使用者的移轉路徑。

#### 金幣對法幣的比率

| 參數 | 初始值 | 說明 |
|------|--------|------|
| 金幣對法幣比率 | 1 金幣 ＝ 1 元（**暫定，尚未定案**） | 平台級可調參數，由管理員於後台設定 |

- 全站單一比率，不依商品或規格而異。
- 補差額金額 ＝（商品價格 − 可折抵金幣數）× 比率換算後的法幣金額。
- **訂單成立時鎖定當時比率**，其後比率變動不影響該筆訂單。
- 比率變動不追溯既有訂單，不需補償邏輯。
- 不採逐商品規格自訂折抵率：維護成本高且使用者難以理解折抵差異。
- 本比率同時為金幣儲值流程的定價基礎。

**[待決策 Partial] 本比率尚未定案。** 使用者於第 57 題明確表示「尚未定案金幣跟真實金流的比例，暫時先不決策」。
上表之 1:1 為暫定占位值，非最終裁決。下列已定案項目的量級皆以此暫定值為基準，比率一經改動須連帶複核：
補差額計算、金幣儲值定價、補簽券售價 150 金幣、各獎勵來源的金幣數額。

- 儲值的路徑為獨立的金幣儲值流程，納入軟體邊界。
- 儲值走 App Store 應用內購買，因金幣屬數位內容，為 Apple 強制要求。
- 儲值的 Actor 為外部系統（App Store 通知觸發），與虛擬商品的真實金流同屬一體系。
- 儲值成功產生「使用者已儲值金幣」，失敗產生「儲值已失敗」。
- 儲值面額與贈送規則尚未給定（待決策 Partial）。

儲值路徑之增列來源：`.clarify/resolved/event/金幣_金幣儲值的流程與Event全數缺失.md`（選項 A）；
比率之增列來源：`.clarify/resolved/aggregate/虛擬貨幣_金幣對法幣的補差額比率為何.md`（選項 A）*

### 新手任務範本 Aggregate

新手任務的項目清單由管理員於後台設定，屬平台級可調參數。

| Aggregate | 層級 | 說明 |
|-----------|------|------|
| 新手任務範本 | 平台級 | 任務項目清單與數量；由管理員維護，可調整 |
| 新手任務 | 每使用者 | 指派給該使用者的任務與完成進度 |

#### 規則

- 新手任務範本由管理員設定，非寫死於系統。
- 「新手任務已指派」時依當時的範本內容產生該使用者的新手任務。
- 範本調整不改動任何使用者已指派的新手任務。
- 全平台使用同一份範本，不依註冊資料或會員身分產生差異。

- 新手任務的逐項完成建模為「使用者已完成單項新手任務」Event，攜帶任務項目 ID。
- 該 Event 的請求識別碼為 使用者 ID ＋ 任務項目 ID，同一項目只能完成一次。
- 「使用者已完成新手任務」的判定為該使用者的全部單項皆已完成。
- 不建模「新手任務進度已更新」：進度為衍生值，由逐項完成推導。

#### 任務項目的結構

新手任務的項目為**管理員於後台提供的動作 ＋ 目標次數**（如原地深蹲 15 下、開合跳 30 下），
共用〈課表內容結構（共用）〉的三層結構，不另定結構。

| 層級 | 內容 |
|------|------|
| 第一層 | 動作清單（每項為一個動作 ID） |
| 第二層 | 該動作的組數 |
| 第三層 | 每一組的目標重量與目標次數 |

#### 執行機制

新手任務的執行**不走訓練紀錄流程**，自成一套簡化的勾選機制。

| 項目 | 新手任務 | 一般訓練 |
|------|----------|----------|
| 產生訓練紀錄 | 否 | 是 |
| 產生訓練量 | 否 | 是 |
| 能力值來源 | 獎勵定義給定 | 訓練量公式計算 |
| 經驗值來源 | 獎勵定義給定（100） | 獎勵定義給定（30） |
| 計入個人排行榜分數 | 否 | 是 |
| 計入累積訓練次數 | 否 | 是 |
| 計入連續訓練天數 | 否 | 是 |

- 新手任務不產生訓練紀錄，故不產生訓練量；能力值與經驗值一律由獎勵定義 Aggregate
  的新手任務獎勵內容給定，非由訓練量公式計算。
- 不沿用訓練紀錄流程：新手任務採簡化的勾選機制，不引入快照、訓練進度條、組間休息計時
  與 40 分鐘逾時中斷判定。
- 「使用者已完成單項新手任務」的 Actor 為**使用者**：使用者實際做完該動作後勾選。
- **連帶後果**：因不計入累積訓練次數，「使用者已解鎖自訂訓練功能」（Precondition 為
  累積訓練次數 ≥ 1）不會因完成新手任務而觸發，須待使用者完成第一次正式訓練結算。
- **[待決策 Partial]** 簡化勾選機制的細節（是否記錄實際次數、可否取消勾選）尚未定案
  → 記於 pending-gaps-3.md 之 I17。
- **[待決策 Partial]** 新手任務含有氧動作（如開合跳）時，課表內容第三層的承載方式
  同〈有氧動作〉之待決策 → 記於 pending-gaps-3.md 之 I16。

### 每日任務池 Aggregate

每日任務的項目由管理員於後台設定任務池，每日隨機抽取指派。

| Aggregate | 層級 | 說明 |
|-----------|------|------|
| 每日任務池 | 平台級 | 可抽取的任務項目清單；由管理員維護，可調整 |
| 每日任務 | 每使用者 | 當日指派給該使用者的任務與進度 |

#### 規則

- 每日任務池由管理員設定，非寫死於系統。
- 每日重置時自任務池隨機抽取固定數量指派給使用者。
- 任務池調整不改動任何使用者當日已指派的任務。
- 全平台使用同一個任務池，不依使用者狀態或會員身分產生差異。

| 參數 | 初始值 | 說明 |
|------|--------|------|
| 每日抽取數量 | 3 項 | 存於每日任務池 Aggregate，由管理員調整 |

- 每日抽取 3 項，**允許與前一日重複**，不做去重。
- 採 3 項而非 5 項：每日任務的完成方式為完成每日訓練與社群互動，一日的合理行為量約為 3 項；
  5 項會使「每日任務已完成」的加碼獎勵與加碼分數變成少數人才拿得到。
- 不做跨日去重：任務池內容本為「訓練一次」「按讚 3 次」等日常行為，連續兩日重複屬正常；
  且去重規則會隱含要求任務池維持足夠數量，管理員縮減池子時系統將抽不出來。
- 任務池項目數少於抽取數量時，抽出全部項目。

#### 任務項目的結構

每日任務池的任務項目為**可組態的 Event 訂閱**。

| 欄位 | 型別 | 說明 |
|------|------|------|
| 任務名稱 | 字串 | 顯示給使用者的名稱 |
| 判定來源 Event | Event 名稱 | 系統訂閱此 Event 以累計進度 |
| 目標次數 | int（≥ 1） | 該 Event 發生幾次視為完成 |
| 獎勵定義 ID | 獎勵定義 ID | 完成該項時發放的獎勵 |

**範例**

| 任務名稱 | 判定來源 Event | 目標次數 |
|---------|---------------|---------|
| 完成一次訓練 | 訓練已結算 | 1 |
| 按讚 3 則貼文 | 互動者已按讚貼文 | 3 |
| 今日簽到 | 使用者已簽到 | 1 |

#### 完成判定

- 系統訂閱該項目的判定來源 Event，該 Event 每發生一次累計 1 次進度。
- 進度達目標次數時，該項任務完成。
- 每次進度變動產生「每日任務進度已更新」，Actor 為系統。
- 「每日任務已完成」的判定為當日指派的全部項目皆已完成。
- 進度的計數範圍限**當日**，隨「每日任務已重置」清空（承既有 Policy）。
- 〔推導〕同一個 Event 可同時被當日的多項任務訂閱，各自獨立累計，互不扣抵。

#### 規則

- 任務項目為可組態的 Event 訂閱：管理員新增任務時只需指定判定來源 Event 與目標次數，
  不需改動系統程式；模型現有的每一個 Event 皆可作為判定來源。
- 每日任務的完成判定 Actor 為**系統**，與新手任務由使用者勾選的機制不同，兩者不共用結構。
- 不採使用者手動回報：每日任務全部完成另有加碼獎勵與加碼排行榜分數，
  手動回報無從驗證，等於開放刷分。
- 不增設「任務類型」欄位與抽取分散規則：管理員若某類僅放一項則天天抽到同一項、
  某類未放則分散規則卡死。此與既有「不做跨日去重」的裁決理由相同 ——
  該規則會隱含要求任務池維持特定的項目結構，管理員調整池子時系統將抽不出來。

任務項目結構與完成判定之來源：`.clarify/resolved/aggregate/每日任務池_任務項目的結構與完成判定來源為何.md`
（第 15b 題，選項 A）*

### 個人排行榜分數 Aggregate

| 欄位 | 型別 | 說明 |
|------|------|------|
| 週累計分數 | int | 當前週榜週期的累計分數，週榜結算時歸零 |
| 月累計分數 | int | 當前月榜週期的累計分數，月榜結算時歸零 |
| 週榜所屬組別 | 列舉 | 本週榜週期鎖定的階級區間組別，共 10 組 |
| 月榜所屬組別 | 列舉 | 本月榜週期鎖定的階級區間組別，共 10 組 |

**排行榜週期**

| 榜別 | 週期長度 | 起訖時點 |
|------|----------|----------|
| 個人週榜 | 每週 | 週一 04:00 起算，下週一 04:00 結算並重置 |
| 個人月榜 | 每月 | 每月 1 日 04:00 起算，次月 1 日 04:00 結算並重置 |
| 團隊日常排行榜 | 每月 | 同個人月榜 |
| 團隊限時排行榜 | 每月 | 同個人月榜 |

#### 各來源的計分方式

| 來源 | 計分方式 |
|------|----------|
| 訓練結算 | 依訓練量換算分數 |
| 每日任務進度 | 固定分數 |
| 每日任務全部完成 | 固定加碼分數 |

#### 規則

- 個人排行榜分數與經驗值為兩個不同數值，不可混用。
- 經驗值單調遞增供階級判定；個人排行榜分數於週期結算時重置。
- 連續訓練獎勵加成**不**套用於個人排行榜分數：加成為複利式優勢，會使落後者永遠追不上，與階級分組排行的公平性設計方向相反。
- 三種來源的具體分數值尚未給定（待決策 Partial）。
- 個人排行榜為**週榜與月榜並存**，同一次得分**同時累加**至週累計分數與月累計分數兩個獨立計數器。
- 兩個計數器各自於各自週期歸零，互不干擾；「排行榜已重置」一次只歸零一個計數器。
- 不採「月榜依週榜名次換算積分」：週榜名次已依階級分組，跨週加總組內名次的意義難以解釋。
- 不採「單一分數即時彙總算出週 / 月區間」：排行榜為延遲更新，即時彙總正是要避開的成本。
- 04:00 起算沿用模型既有的換日基準，使所有「一天」的定義一致：半夜訓練的場次計入前一天。
- 週期長度取每週與每月：一週對齊使用者的訓練節奏（每週健身天數為註冊必填欄位），
  落後者下週即有機會；月榜提供較長的累積尺度。

#### 分組鎖定

所屬組別**於週期起點鎖定**，非依當下階級即時推導。

- 組別取該使用者於週期起算時點的階級；週期內升階不改變本週期所屬組別。
- 新組別自下一週期起生效，於該週期的重置時點一併寫入。
- 週期內升階者分數全額保留：不歸零、不轉組、不移除舊組名次。
- 兩榜各自鎖定：週榜於每週一 04:00、月榜於每月 1 日 04:00；同一使用者兩榜的所屬組別可能不同。
- 「排行榜已重置」的 Postcondition 因此有兩項：歸零該榜別的累計分數，並以當下階級重寫該榜別的所屬組別。

**為何鎖定而非即時推導**：分數與組別若可在週期內脫鉤，兩個方向皆可操縱 ——
於週期尾聲才升階，可將低組累積的分數整包帶進新組洗名次；刻意壓階不升，則可穩坐低組第一。
鎖定使「升階」與「排行」互不干擾，使用者不必為名次計算升階時機。

已知代價：於週期初升階者，該週期仍與舊組競爭，舊組其他人這一輪較吃虧。
此偏差最多持續一個週期，且方向單一（強者暫留弱組）。

*來源：`.clarify/resolved/aggregate/個人排行榜分數_分數的計算公式為何.md`（選項 A）；*
*`.clarify/resolved/rule/排行榜週期已結算_週期中升階跨組時分數與名次如何處理.md`（選項 A）*

### 團隊 Aggregate

| 欄位 | 型別 | 說明 |
|------|------|------|
| 成員清單 | 使用者 ID 集合 | 人數上限 5 人；每筆含加入時戳 |
| 隊長 | 使用者 ID | 建立者預設為隊長，可轉讓 |
| 可見性 | 列舉 | 公開 / 私密，建立時指定，預設公開，**可事後變更** |
| 團隊狀態 | 列舉 | 生效中 / 已解散（終止狀態） |

#### 角色

| 角色 | 權限 |
|------|------|
| 隊長 | 踢除成員、轉讓隊長、解散團隊 |
| 成員 | 參與團隊任務、退出團隊 |

#### 規則

- 團隊人數上限為 5 人，含隊長在內。
- 建立團隊無門檻，任何使用者皆可建立。
- 建立者預設為隊長，隊長可轉讓給其他成員。
- 加入團隊有兩條路徑並存：隊長邀請，與公開團隊的加入申請。
- 公開團隊可被搜尋並接受加入申請；私密團隊僅能經隊長邀請加入。
- 兩條路徑皆由隊長把關，不採公開直接加入。
- 「使用者已加入團隊」為多對一，由「使用者已接受邀請」或「隊長已核准加入申請」導致。
- 可見性於建立團隊時指定，其後可由隊長變更（「隊長已變更團隊可見性」）。
- 團隊僅有隊長與成員兩種角色，無副隊長。
- 隊長與成員的權限差異以團隊內的角色欄位表達，兩者的 Actor 皆為「使用者」。

#### 單一團隊歸屬與換隊冷卻

| 參數 | 值 | 說明 |
|------|-----|------|
| 換隊冷卻期 | 12 小時 | 自「使用者已退出團隊」起算 |
| 無懲罰退出窗口 | 3 小時 | 自「使用者已加入團隊」起算，窗口內退出不觸發冷卻 |

- 一位使用者同時僅能屬於一個團隊，須先退出方可加入新團隊。
- 兩參數皆為平台級可調，由管理員於後台維護。
- 冷卻期的職責僅為避免同一日內反覆進出造成的成員名單與分數抖動。
- **冷卻期不負責防止「月底跳槽蹭排行獎勵」** —— 12 小時對每月結算的排行榜量級過小；
  該防刷職責另由團隊分數的加入 / 退出計算規則承擔（尚未定案）。

#### 待回應的邀請與申請

- 邀請與加入申請皆自送出起算 **168 小時（7 天）**未回應即逾期，
  對應 Event「團隊邀請已逾期」與「加入申請已逾期」。
- **待回應狀態不佔用 5 人名額**；名額僅由已加入的成員計算。
- 超收由「使用者已加入團隊」當下的 Precondition 擋下，不重複防守。
- 與師徒申請佔用帶徒名額的既有裁決刻意不一致：教官的帶徒上限來自聲望、為稀缺的獎勵；
  團隊的 5 人上限非誰掙得，性質不同。

#### 解散

- 「團隊已解散」採**軟刪除**：團隊狀態轉為已解散，不實體刪除 Aggregate。
- 兩個團隊分數凍結於解散當下，不再累加；退出兩個排行榜，本週期不發放團隊排行獎勵。
- 成員的個人排行榜分數不受影響：團隊分數為成員個人分數的加總，加總消失不改動原始值。
- 採軟刪除的理由：排行榜歷史紀錄 Aggregate 存有團隊 ID 與最終名次，
  實體刪除會使歷史紀錄指向不存在的 ID。

*`.clarify/resolved/rule/使用者已建立團隊_一位使用者可否同時加入多個團隊.md`；*
*`.clarify/resolved/rule/隊長已邀請成員_團隊邀請與加入申請是否逾期失效.md`（選項 B）；*

### 貼文 Aggregate

| 欄位 | 型別 | 說明 |
|------|------|------|
| 作者 | 使用者 ID | 發文者 |
| 文字內容 | 字串 | 貼文文字 |
| 圖片 | 圖片集合 | 不支援影片 |
| 發布時間 | Timestamp | 沿用 Event 共通時戳規範 |
| 可見範圍 | 列舉 | 公開 / 僅關注者 / 私人 |
| 關聯訓練紀錄 | 訓練紀錄 ID | 分享訓練成果時帶入，發布原生貼文時為空 |
| 按讚數 | int | 衍生自互動 |
| 留言數 | int | 衍生自互動 |
| 狀態 | 列舉 | 已發布 / 已刪除 |
| 已編輯旗標 | bool | 曾經編輯過即為真，供讀者辨識 |
| 編輯歷史 | 有序集合 | 每次編輯前的文字內容與時戳 |

#### 規則

- 貼文不支援影片，僅支援文字與圖片。
- 貼文無標籤欄位，不做分類。
- 可見範圍由發文者於發布時指定，三選一。
- 「發文者已分享訓練成果」產生的貼文，關聯訓練紀錄欄位必有值。
- 「發文者已發布貼文」產生的貼文，關聯訓練紀錄欄位為空。
- 互動者對貼文按讚或留言前，該貼文須對其可見。

#### 狀態機

| 起始狀態 | 觸發 Event | 目標狀態 |
|----------|-----------|----------|
| — | 發文者已發布貼文 / 發文者已分享訓練成果 | 已發布 |
| 已發布 | 貼文已刪除 | 已刪除（終止） |

#### 刪除與編輯規則

- 刪除為軟刪除：狀態轉為已刪除，資料保留。
- 不採硬刪除：貼文可被檢舉，硬刪除會使已成案的檢舉失去指涉對象。
- 已刪除貼文的按讚與留言一併隱藏但保留，供獎勵回收與成就計數判定使用。
- 編輯保留完整歷史版本：每次編輯前的文字內容與時戳寫入編輯歷史。
- 保留歷史的理由：避免「發爭議內容 → 被檢舉 → 審視前改為無害內容」的規避漏洞；且申訴未設時效上限，需長期可稽核。
- 編輯後已編輯旗標為真，Read Model 須對讀者顯示「已編輯」。
- 留言 Aggregate 的狀態值域與刪除編輯規則比照本節，不另定義。

*來源：`.clarify/resolved/aggregate/貼文_貼文的欄位內容型態與可見範圍.md`（選項 C）*

### 留言 Aggregate

留言為獨立 Aggregate，因其具內容、可編輯、且可被檢舉，需有獨立身分供指涉。

| 欄位 | 型別 | 說明 |
|------|------|------|
| 作者 | 使用者 ID | 留言者 |
| 貼文 ID | 貼文 ID | 所屬貼文 |
| 文字內容 | 字串 | 留言文字 |
| 發布時間 | Timestamp | 沿用 Event 共通時戳規範 |
| 狀態 | 列舉 | 已發布 / 已刪除，與貼文一致 |
| 已編輯旗標 | bool | 曾經編輯過即為真 |
| 編輯歷史 | 有序集合 | 每次編輯前的文字內容與時戳 |

#### 規則

- 留言為獨立 Aggregate，不併入貼文。
- 留言可被檢舉，檢舉對象類型「留言」指涉本 Aggregate 的 ID。
- 留言支援編輯與刪除，各對應「留言已編輯」「留言已刪除」Event。
- 不支援巢狀回覆：模型無「回覆留言」Event，互動成就門檻亦只計留言次數。
- 貼文 Aggregate 的「留言數」為衍生欄位，來源為本 Aggregate。
- 留言的刪除為軟刪除、編輯保留歷史，規則比照貼文。

### 按讚的建模方式

按讚**不建模為獨立 Aggregate**，以貼文的關聯集合表達。

#### 規則

- 按讚無內容、不可編輯、不可被檢舉，只有存在與否兩態。
- 「互動者已按讚貼文」新增一筆關聯；「按讚已取消」移除該筆關聯。
- 關聯的唯一鍵為 貼文 ID ＋ 互動者 ID，同一人對同一貼文只能有一筆。
- 貼文 Aggregate 的「按讚數」為衍生欄位，來源為關聯集合的筆數。

### 商品 Aggregate

商品為單一 Aggregate，其下含「商品規格」子聚合。

| 商品欄位 | 型別 | 說明 |
|----------|------|------|
| 類型 | 列舉 | 實體 / 虛擬 |
| 名稱 | 字串 | 商品名稱 |
| 圖片 | 圖片集合 | 商品圖片 |
| 上架狀態 | 列舉 | 已上架 / 已下架 |
| 虛擬商品子類型 | 列舉 / 空值 | 消耗品 / 權限解鎖；類型為實體時為空值 |
| 解鎖標的 | 訓練計畫 / 空值 | 僅權限解鎖類有值，指向該商品所解鎖的訓練計畫 |

| 商品規格欄位 | 型別 | 說明 |
|--------------|------|------|
| 規格名稱 | 字串 | 實體商品為尺寸；虛擬商品為單一預設規格 |
| 價格 | int | 各規格獨立定價 |
| 庫存 | int | 各規格獨立庫存，≥ 0 |

#### 規則

- 實體商品與虛擬商品共用同一個商品 Aggregate，不拆為兩個。
- 價格與庫存皆屬商品規格層級，商品層級無單一價格與庫存。
- 虛擬商品亦以商品規格表達，僅有一個預設規格。
- 「商品已售完」為**規格（尺寸）層級**的 Event，攜帶售完的規格資訊。
- 某一規格售完不影響其他規格，其他規格仍可購買。
- 庫存不得為負值。

#### 虛擬商品的兩個子類型

| 子類型 | 例 | 庫存 | 發放的意義 |
|--------|-----|------|-----------|
| 消耗品 | 補簽券 | 適用 | 道具入庫，可持有多份 |
| 權限解鎖 | 進階訓練計畫 | **不適用** | 將解鎖標的寫入使用者的已購買計畫清單 |

- 權限解鎖類商品不適用庫存，**不產生「商品已售完」**：解鎖為冪等狀態，非可消耗的資源。
- 權限解鎖類商品的「商品已發放」＝將解鎖標的寫入使用者的已購買計畫清單，永久保存。
- Precondition：**已以階級達標或金幣購買永久取得該計畫者，不得重複購買**。
- 僅以會員身分（續約生效）解鎖者**仍可購買**：其用途正是在權益失效前轉為永久取得。
- 權限解鎖類商品須與訓練計畫兩處對應：商品後台維護價格與上架狀態，
  訓練計畫後台維護所需階級與解鎖金幣價格，以解鎖標的欄位綁定。

*來源：`.clarify/resolved/aggregate/商品_商品的欄位定義與價格庫存設定.md`（選項 D，尺寸層級）；
`.clarify/resolved/aggregate/進階訓練計畫_三種解鎖方式與管理員設定.md`（三方式 ＋ 購買路徑 A）*

#### 實體訂單狀態子集

| 起始狀態 | 觸發 Event | 目標狀態 |

| 待付款 | 使用者已支付 | 已付款 |

| 待付款 | 使用者已取消訂單 | 已取消（終止） |
| 已付款 | 商品已出貨 | 已出貨（終止） |
| 已付款 | 訂單已退款 | 已退款（終止） |

#### 虛擬訂單狀態子集

| 起始狀態 | 觸發 Event | 目標狀態 |
|----------|-----------|----------|
| — | 使用者已確認購買 | 待付款 |
| 待付款 | 虛擬貨幣已扣除 / 使用者已支付 | 已付款 |

| 已付款 | 商品已發放 | 已發放（終止） |

#### 規則

- 實體與虛擬訂單共用同一個 Aggregate，以類型欄位區分適用的狀態子集。
- 實體訂單的終止狀態為已出貨，出貨後的物流留在系統邊界之外，無「已送達」「已完成」狀態。
- 虛擬訂單無出貨狀態；已付款與已發放為兩個不同狀態，發放可為非同步。
- 收貨資訊僅實體訂單有值。

#### 收貨資訊欄位

| 欄位 | 型別 | 必填 | 說明 |
|------|------|------|------|
| 收件人姓名 | 字串 | 必填 | — |
| 手機號碼 | 字串 | 必填 | 須符合手機號碼格式 |
| 郵遞區號 | 字串 | 必填 | 物流商所需，獨立成欄以利格式檢核 |
| 地址 | 字串 | 必填 | 單一自由文字欄，不拆縣市 / 鄉鎮區 / 街道 |
| 備註 | 字串 | 選填 | — |

- 地址不做結構化拆解：拆欄位須維護行政區資料且行政區會改名合併，屬持續維護負擔；
  而出貨後的物流已定案留在系統邊界之外，本系統僅將地址原封不動交付物流商，無拆解用途。
- 不收集電子郵件：出貨通知的管道尚未定案，且通知類 Event 清單中無出貨通知，
  不為不存在的功能收集個資。
- 手機號碼不寫死為特定國別格式：模型無「限特定地區」的既有裁決，寫死將成為隱形的地區假設。
- 虛擬訂單的付款可為虛擬貨幣扣除、真實金流，或兩者併用。

- 「商品發放已失敗」不改變訂單狀態，訂單於發放成功前維持已付款。
- 發放失敗時系統自動重試，重試次數上限 3 次。
- 達重試上限仍失敗者轉人工處理，不自動退款。

### 團隊分數 Aggregate

團隊有兩個獨立分數與兩個獨立排行榜，衡量不同的事。

| Aggregate | 計算方式 | 衡量對象 |
|-----------|----------|----------|
| 團隊日常分數 | 全體成員個人排行榜分數加總 | 成員的訓練努力程度 |
| 團隊限時分數 | 完成限時任務的成員數 × 固定分，全員完成時另加成 | 團隊的動員參與率 |

#### 規則

- 團隊日常分數直接沿用成員的個人排行榜**月累計分數**，不另定一套計分規則。
- 團隊兩個排行榜的週期皆為每月，與個人月榜同起訖。
- 團隊限時分數不依訓練量計算，每位成員完成一次限時任務即加固定分。
- 團隊全體成員皆完成限時任務時，額外給予加成。
- 限時任務為每日指派，非以排行榜週期為單位。
- 兩個分數不合併，兩個排行榜各自維護，對應兩種獨立的排行獎勵。
- 固定分的數值與全員完成的加成幅度尚未給定（待決策 Partial）。

*來源：`.clarify/resolved/aggregate/團隊日常分數_日常分數與限時分數的計算公式.md`（選項 A + 使用者補充）*

### 帶徒上限設定 Aggregate

帶徒上限的參數由管理員於後台設定，屬平台級可調參數。

| 參數 | 預設值 | 說明 |
|------|--------|------|
| 初始帶徒上限 | 1 人 | 成為教官時的起始值 |
| 每次提升幅度 | +1 人 | 每達一個聲望門檻提升的人數 |
| 帶徒上限最大值 | 5 人 | 提升的上界，達此值後不再提升 |
| 聲望門檻清單 | 30 / 75 / 150 / 300 | 觸發提升的四級聲望值 |
| 教官初始聲望 | 15 | 「使用者已成為教官」時的起始聲望 |

#### 門檻設計依據

| 升級段 | 所需點數 | 同時帶徒數 | 估算耗時 |
|--------|---------|-----------|----------|
| 1 → 2 人 | 30 | 1 人 | 約 7.5 週 |
| 2 → 3 人 | 45 | 2 人 | 約 6 週 |
| 3 → 4 人 | 75 | 3 人 | 約 6 週 |
| 4 → 5 人 | 150 | 4 人 | 約 9 週 |

估算假設：平均每次評分 +2 點（4 星）、每位學徒每週 2 次評分（問答與師徒任務各一）。達上限約需 7 個月。

- 門檻採遞增而非等差：帶徒數愈多、取得聲望愈快，等差門檻會使後段升級速度失控（最後一級僅需第一級的四分之一時間）。
- 遞增比例為 1 : 2.5 : 5 : 10，使四段耗時大致相當。
- 教官初始聲望為第一門檻的一半。聲望地板值為 0，若初始亦為 0，新教官前幾次差評扣完仍是 0，差評將失去嚇阻力。

#### 規則

- 上述參數皆由管理員調整，非寫死於系統。
- 參數調整不使任何教官的既有帶徒上限降低（承第 46 題的單調遞增裁決）。
- 帶徒上限達最大值 5 人後，聲望再提升亦不再增加上限。

#### 名額佔用規則

- **申請中的師徒申請佔用帶徒名額**：送出申請即佔用，避免超收。
- 名額佔用數 ＝ 已建立的師徒關係數 ＋ 申請中的師徒申請數。
- 「對方已拒絕申請」或「師徒申請已逾期」發生時，釋放所佔名額。
- 師徒申請的逾期時限為 168 小時（7 天），自申請時戳起算；時限不做成可調參數。
- 「師徒關係已解除」發生時，釋放所佔名額。
- 「師徒關係已恢復」發生時，重新佔用名額；名額已滿者不得恢復。

*來源：`.clarify/resolved/aggregate/教官帶徒上限_帶徒上限的初始值與提升幅度.md`（選項 C 之機制 + 使用者給定的數值 + 代號①）*

| 欄位 | 型別 | 說明 |
|------|------|------|
| 申請者 | 使用者 ID | 提出申請的使用者 |
| 申請時戳 | Timestamp | 沿用 Event 共通時戳規範 |
| 訓練完成率分數 | int | 0–100，AI 評分維度一 |
| 訓練規律性分數 | int | 0–100，AI 評分維度二 |

| 加權平均分 | int | 0–100，三維加權平均 |

#### 規則

- 教官申請為獨立 Aggregate，不併入使用者：一位使用者可有多次申請紀錄，且被駁回後可重新申請。
- 「AI 已產出訓練品質評分」的請求識別碼 ＝ 使用者 ID ＋ 教官申請 ID，同一筆申請只評分一次。

  掛在尚未存在的測驗紀錄上會產生空指涉。
- 重新申請時產生新的一筆教官申請，重新評分；既有申請的評分不被覆寫。
- 本 Aggregate 的狀態機、以及申請與教官測驗的關聯基數尚未定義（待決策 Partial）。

### 教官測驗設定 Aggregate

教官測驗的題庫與及格標準由管理員於後台設定，屬平台級可調參數。

| Aggregate | 層級 | 說明 |
|-----------|------|------|
| 教官測驗設定 | 平台級 | 題庫、題數、配分、及格標準；由管理員維護，可調整 |
| 教官測驗 | 每次作答 | 該次作答的題目、作答內容與判定結果 |

| 教官測驗設定參數 | 初始值 | 說明 |
|------------------|--------|------|
| 選擇題題庫 | — | 由系統即時判定 |
| 簡答題題庫 | — | 由管理員人工審核 |
| 選擇題題數 | 20 題 | 自題庫隨機抽取 |
| 簡答題題數 | 3 題 | 自題庫隨機抽取 |
| 選擇題及格標準 | 答對 ≥ 80%（20 題中 ≥ 16 題） | 系統即時判定 |
| 簡答題及格標準 | 全數通過 | 管理員人工審核 |
| 及格判定方式 | 雙門檻（兩者皆須通過） | 不採總分制 |

#### 規則

- 題庫、題數、配分與及格標準皆由管理員調整，非寫死於系統。
- 測驗保留選擇題與簡答題兩種題型，人工審核 Policy 維持有效。
- 選擇題由系統即時判定，簡答題由管理員人工審核。
- 設定調整不改動任何已完成作答的既有測驗結果。

- 及格判定採雙門檻：選擇題答對 ≥ 80% **且** 簡答題全數通過，兩者缺一不可。
- 不採總分制：總分制下選擇題滿分者可簡答全錯仍及格，將使人工審核形同虛設。
- 題目一律自題庫隨機抽取，不固定；固定題目將使題庫答案外流後測驗淪為背誦。
- 隨機抽取亦為重考機制的前提，否則重考等於重看同一份考卷。

### 對話 Aggregate

對話為聊天室本身，與其中的訊息分屬兩個 Aggregate。

| 欄位 | 型別 | 說明 |
|------|------|------|
| 參與者 | 使用者 ID ×2 | 對話的雙方 |
| 建立時間 | Timestamp | 沿用 Event 共通時戳規範 |
| 各方刪除狀態 | 每位參與者一個布林值 | 單方刪除只影響該方，對方仍可見 |

#### 規則

- 對話可為空：「使用者已建立對話」發生時尚無任何私訊。
- 「使用者已刪除對話」為單方刪除，只改該方的刪除狀態，對方不受影響。
- 單則訊息一經發送即不可刪除，故刪除只發生於對話層級。
- 對話不儲存封鎖狀態，封鎖為獨立 Aggregate。

### 私訊 Aggregate

| 欄位 | 型別 | 說明 |
|------|------|------|
| 對話 ID | 對話 ID | 所屬對話 |
| 發送者 | 使用者 ID | 訊息發送方 |
| 內容 | 字串 | 訊息內容 |
| 發送時戳 | Timestamp | 沿用 Event 共通時戳規範 |
| 已讀時戳 | Timestamp / 空值 | 未讀時為空值 |

#### 規則

- 私訊為獨立 Aggregate，不併入對話。
- 私訊可被檢舉，檢舉對象類型「私訊」指涉本 Aggregate 的 ID。

#### 已讀判定

- 判定條件為**開啟對話**，非訊息進入畫面可視範圍。
- 「使用者已讀取私訊」的 Precondition：使用者開啟對話，且該對話中存在以其為接收方、已讀時戳為空的私訊。
- Postcondition：上述私訊的已讀時戳一律寫入當下時戳。
- 已讀狀態於發送方的對話畫面**被動呈現**，不發送推播通知。
- 不建模「已讀通知已發送」Event，亦不列入通知類 Event 清單。
- 已讀回條本階段不可關閉，使用者 Aggregate 不新增相關隱私設定欄位。
- 不採「進入可視範圍才標記已讀」：捲動位置為前端實作細節，無客觀判定標準，
  且同一則訊息在不同螢幕尺寸下的判定會不一致，Precondition 將無法驗收。
- 訊息數量無上限成長，故不作為對話的子集合，避免讀取對話狀態時載入全部歷史。
- 私訊一經發送不可刪除亦不可編輯。

### 封鎖 Aggregate

封鎖為獨立 Aggregate，不附屬於對話。

| 欄位 | 型別 | 說明 |
|------|------|------|
| 封鎖者 | 使用者 ID | 執行封鎖的一方 |
| 被封鎖者 | 使用者 ID | 被封鎖的一方 |
| 封鎖時戳 | Timestamp | 沿用 Event 共通時戳規範 |

#### 規則

- 封鎖為單向關係，唯一鍵為 封鎖者 ID ＋ 被封鎖者 ID。
- 可封鎖從未與其對話過的對象，故封鎖不得掛在對話之下。
- 封鎖的影響範圍超出私訊，其連帶效果由 `rule/使用者已封鎖對象_封鎖是否連帶解除關注與師徒與團隊關係.md` 定案。
- 「使用者已封鎖對象」新增一筆封鎖；「使用者已解除封鎖」移除該筆封鎖。

*來源：`.clarify/resolved/aggregate/使用者已建立對話_對話與私訊的Aggregate歸屬與欄位.md`（選項 B ＋ D）*

### 申訴 Aggregate

申訴為獨立 Aggregate，承接使用者對平台處置的異議。

| 欄位 | 型別 | 說明 |
|------|------|------|
| 申訴者 | 使用者 ID | 提出申訴的使用者 |
| 所申訴的處罰 | 處罰識別 | 指涉「使用者已受處罰」的該次處罰 |
| 理由 | 字串 | 申訴理由 |
| 申訴時戳 | Timestamp | 沿用 Event 共通時戳規範 |
| 狀態 | 列舉 | 待審視 / 已成立 / 已維持原處罰 |

#### 狀態機

| 起始狀態 | 觸發 Event | 目標狀態 |
|----------|-----------|----------|
| — | 使用者已申訴 | 待審視 |
| 待審視 | 處罰已撤銷 | 已成立（終止） |
| 待審視 | 管理員已審視申訴（判定不成立） | 已維持原處罰（終止） |

#### 規則

- 申訴為獨立 Aggregate，不併入檢舉：兩者方向相反 —— 檢舉是「A 檢舉 B 的內容」，
  申訴是「B 對平台的處置提異議」；且檢舉已定案「多人檢舉合併為同一案件」，申訴不可能合併。
- 申訴不併入使用者 Aggregate：申訴為有生命週期的案件，壓成扁平欄位後第二次申訴會覆寫第一次的紀錄。
- **申訴期限為 30 天**，自「使用者已受處罰」的發生時戳起算。
- **同一處罰限申訴一次**：已有申訴紀錄者不得再次申訴，不論該次申訴成立與否。
- 「使用者已申訴」的 Precondition：該使用者存在生效中的處罰、距處罰發生未滿 30 天、
  且該處罰尚無申訴紀錄。
- 「處罰已撤銷」時累計違規次數 −1，其可稽核的依據即為本 Aggregate 的申訴紀錄。
- 永久停權亦適用本機制：永久停權已定案無到期解除，僅能經申訴撤銷。
- 申訴不成立時不另立 Event（既有裁決），狀態由「管理員已審視申訴」的判定結果轉入已維持原處罰。

#### 申訴期限與證據保存期限的區別

模型有兩處以「申訴機制未設時效上限」作為永久保存的理由（AI 調整對話、貼文與留言的編輯歷史）。
該理由與本節的 30 天期限**不衝突**，兩者指涉不同的事：

| 項目 | 期限 | 說明 |
|------|------|------|
| 申訴的**提出**期限 | 30 天 | 自處罰發生起算 |
| 申訴所需**證據**的保存期限 | 無上限 | 不得定期清除 |

- 一則兩年前的貼文可能今日才被檢舉、今日才受處罰，30 天內申訴時仍需調閱兩年前的編輯歷史。
- 故 AI 調整對話與編輯歷史的永久保存規則維持不變，不因申訴期限有上限而改為定期清除。

*來源：`.clarify/resolved/aggregate/申訴_申訴是否為獨立Aggregate及其欄位與狀態機.md`（選項 A ＋ 使用者給定的 30 天期限）*

### 健身經驗設定 Aggregate

健身經驗的值域由管理員於後台維護，屬平台級可調參數。

| 初始值域 | 界定基準 | 填寫規則 |
|----------|----------|----------|
| 新手 | 訓練年資未滿 6 個月 | 必填，單選 |
| 中階 | 訓練年資 6 個月–2 年 | 必填，單選 |
| 進階 | 訓練年資 2 年以上 | 必填，單選 |

#### 規則

- 值域由管理員調整，非寫死於系統。
- 必填單選，不可複選（與健身器材的可複選不同）。
- 訓練計畫 Aggregate 的「適用條件」欄位引用同一份值域清單，比照健身目標的既有處理方式。
- 值域調整不改動任何使用者已選擇的健身經驗。
- 分級以訓練年資的月數界定，不以未量化的形容詞界定：使用者的自我判斷會失準，
  而本欄位為訓練計畫推薦的第二順位比對維度，直接決定推薦哪一份課表。
- 不增設「完全沒接觸」一級：其與「新手」在推薦邏輯上拿到同一份入門課表，分兩級卻無不同後果。
- 不改以「是否規律訓練 ＋ 訓練年資」兩欄表達：兩欄仍須折算回三級才能比對，
  且年資長不等於程度好（練 5 年但一週一次）。
- 值域不寫死於系統：健身目標已採平台級可調，兩個比對維度的處理方式應一致；
  性別寫死是因其為二元事實不會變，經驗分級則為產品判斷。

### 階級設定 Aggregate

階級總數固定為 **99 階**，門檻以公式表達，由管理員於後台調整參數。

| 參數 | 初始值 | 說明 |
|------|--------|------|
| 階級總數 | 99 | 初始階級為 1 |
| 滿等累計經驗值 | 8,340 | 一般使用者約 365 天可達 |
| 曲線指數 p | 2 | 冪次曲線，前期密集後期拉長 |

**累計經驗值門檻公式**：C(n) ＝ 滿等累計經驗值 × ((n − 1) / 98)^p，n 為階級（2–99）

| 階級 | 2 | 10 | 20 | 50 | 99 |
|------|---|----|----|----|----| 
| 累計門檻 | 1 | 70 | 313 | 2,085 | 8,340 |

#### 滿等累計經驗值的推導基準

| 來源 | 數額 | 頻率 |
|------|------|------|
| 每日簽到 | 10 點 | 每日 |
| 訓練結算 | 30 點 | 每週 3 次 |

每週 160 點 × 52 週 ≈ 8,340 點。

#### 規則

- 階級總數為 99，初始階級為 1，第 99 階為滿等。
- 門檻以公式計算，不逐階列舉數值；管理員調整的是三個參數，非 98 個數字。
- 採冪次曲線（p ＝ 2）：前期升級密集提供回饋，末段拉長維持長期目標。
- **滿等所需累計經驗值不得低於一般使用者 365 天可取得的累計經驗值。**
- 經驗值數額調整時，階級門檻須同步重新校準，以維持上述 365 天下限。
- 上表的每日簽到與訓練結算數額為推導基準，實際值以獎勵定義 Aggregate 為準。
- 並非每一階都解鎖進階訓練計畫，僅指定階級解鎖。
- 門檻調整不改動任何使用者既有的階級。

*來源：`.clarify/resolved/aggregate/階級設定_階級總數與各階門檻初始值為何.md`（選項甲：99 階、p ＝ 2、365 天下限）*

### 訓練計畫 Aggregate

全模型只有一個「訓練計畫」Aggregate，初階與進階計畫共用同一結構。

| 欄位 | 型別 | 說明 |
|------|------|------|
| 名稱 | 字串 | 計畫名稱 |
| 適用條件 | — | 健身經驗、目標、器材，供註冊推薦比對 |
| 所需階級 | 階級 / 空值 | 空值為初階計畫，有值為進階計畫 |
| 解鎖金幣價格 | int / 空值 | 提前購買的金幣價格；空值表示該計畫不可用金幣購買 |
| 課表內容 | — | 見〈課表內容結構（共用）〉；目標重量為管理員設定的建議起始重量 |

#### 進階訓練計畫的三種解鎖方式

三者為 **OR 關係**，任一成立即解鎖：

| # | 解鎖方式 | 生效期間 | 判定依據 |
|---|----------|----------|----------|
| 1 | 階級達標 | **永久** | 使用者現階級 ≥ 該計畫的所需階級 |
| 2 | 金幣提前購買 | **永久** | 該計畫在使用者的已購買清單中 |
| 3 | 會員身分 | **續約生效**，權益失效即回退 | 會員權益生效中 |

- 方式 3 一次解鎖**全部**進階訓練計畫，不逐份指定。
- 方式 1 為推導值，不另存：階級已定案單調遞增、永不下降，故達標後不會回退。
- 方式 2 須記錄使用者的**已購買計畫清單**，永久保存。
- 方式 2 不要求階級達標 —— 其用途正是**提前**解鎖尚未達階級的計畫。
- 已以方式 1 或 2 取得者不重複收費：解鎖為冪等狀態，非可累加的資源。

#### 會員權益失效時的回退

**僅以方式 3 取得的計畫鎖定；以方式 1 或 2 取得者維持解鎖。**

- 承第 66 題既有裁決「權益失效，進階計畫鎖定但資料保留」—— 該裁決的適用範圍
  於本次收斂為「僅靠會員身分解鎖者」，非全部進階計畫。
- 訂閱期間以金幣購買的計畫，於權益失效後**仍保有**，因方式 2 為永久取得。

#### 規則

- 「進階訓練計畫」非獨立 Aggregate，僅為所需階級欄位有值的訓練計畫。
- 所需階級為空的計畫，供註冊流程的推薦 Policy 使用。
- 一個階級可解鎖多個訓練計畫，非一對一關係。
- **所需階級與解鎖金幣價格皆由管理員於後台維護**，與既有的「各階級對應解鎖哪些計畫的清單」
  同屬平台級可調設定，不寫死於程式。
- 管理員調整所需階級，**不影響已解鎖者**（承快照脫鉤原則）。
- 管理員調整解鎖金幣價格，**不追溯已購買的訂單**，不補差額亦不退款。
- 解鎖金幣價格設為空值者改為不可購買，已購買者不受影響。
- 金幣購買走既有〈虛擬商品購買流程〉，見〈商品 Aggregate〉的權限解鎖類虛擬商品。
- 並非每一階都解鎖訓練計畫，僅指定階級解鎖，與 99 階的階級總數脫鉤。
- 各階級對應解鎖哪些計畫的清單，由管理員於後台維護（待決策 Partial：初始清單未給定）。

#### 統一語言

「進階訓練計畫」為描述性用語，非獨立 Aggregate 名稱；模型中的 Aggregate 一律稱「訓練計畫」。

*來源：`.clarify/resolved/aggregate/進階訓練計畫_解鎖的計畫內容與階級對應關係.md`（選項 A）*

- 上表數額皆為平台級可調參數，由管理員於後台維護。
- 經驗值數額調整時，階級門檻須同步重新校準以維持 365 天下限（承〈階級設定〉的既有規則）。
- **訓練結算的「能力值已提升」不由本表給定**，由能力值提升公式計算
  （本次該肌群訓練量 ÷ 該肌群基準訓練量 × 基準提升點數 × 遞減報酬係數）。
- **新手任務的「能力值已提升」只能由本表給定**：新手任務無訓練量可代入公式。
- 連續訓練獎勵加成（每連續一天 +1%，上限 30%）僅套用於訓練獎勵的金幣與道具；
  經驗值不受加成影響。

#### 訓練獎勵金幣的完成度差額

| 終止 Event | 條件 | 金幣係數 | 基準 30 的實得 |
|------------|------|----------|----------------|
| 使用者已完成訓練 | — | 100% | 30 |
| 使用者已提前結束訓練 | — | 70% | 21 |
| 單次訓練已逾時中斷 | 已完成組數 ＝ 總計畫組數 | 100% | 30 |
| 單次訓練已逾時中斷 | 已完成組數 < 總計畫組數 | 50% | 15 |

- 差額**僅套用於訓練獎勵的金幣**；能力值、經驗值、個人排行榜分數三者一律依實際訓練量計算，
  不受終止 Event 類型影響。
- 逾時中斷但已完成組數等於總計畫組數者給 100%：承「逾時中斷最常見的原因為
  **練畢未按結束**而非未訓練」的既有裁決 —— 該情形實質等同完成，不應罰。
- 〔推導〕空白課表（總計畫組數為 0）不適用完成度比較，逾時中斷一律套用 50%。
- 完成度係數與連續訓練獎勵加成皆為乘法，**套用順序不影響結果**
  （30 × 0.7 × 1.3 ＝ 30 × 1.3 × 0.7 ＝ 27.3），不需另訂套用順序。
- 本裁決解決訓練紀錄流程「獎勵不同」與訓練結算流程「結算待遇相同」的矛盾：
  兩者皆部分成立 —— 三個數值指標待遇相同，訓練獎勵的金幣有差額。
- 既有決策「不採由使用者自述完成或提前結束（無人會選擇較低獎勵的選項）」**維持不變**：
  本裁決下較低獎勵確實存在（提前結束 70%），該決策的理由仍然成立。
- 註冊與新手任務的金幣為新使用者的初始資金：第一張補簽券若須靠簽到累積，
  最需要補簽券的新手反而最拿不到，故兩者皆給金幣。
- 簽到獎勵**不隨連續天數遞增**：獎勵持續簽到的職責已由連簽成就承擔
  （門檻 1 / 3 / 5 / 7 / 10 / 15 / 20 / 25 / 30 天），再做遞增等於同一件事給兩次，
  會稀釋成就那條線。

第一批初始值之來源：`.clarify/resolved/aggregate/獎勵定義_第一批_訓練與簽到類的獎勵初始值為何.md`

### 收錄判準

本表收錄的是「在各流程中**真的會各自發生一次**、需以攜帶值區分是哪一次」的 Event。

某個 Event 名稱出現在兩條流程檔中，**不必然**代表它屬於本表 —— 它也可能只是後一條流程
引述其前置條件。判別方式為：一次業務歷程中，該事實是發生一次還是多次。

| 情形 | 處理方式 |
|------|----------|
| 各流程各自發生一次 | 納入本表，定義來源值域 |
| 僅為前置條件的引述 | 不納入本表；於後一條流程改寫為 Precondition，不重複列為 Event |

- 「使用者已選擇訓練課表」為後者：一次訓練中該事實只發生一次，AI 訓練前調整流程的該行
  已改寫為 Precondition，並自〈Command 清單〉的 AI 訓練前調整流程移除對應 Command。

### 規則

- 同名跨流程 Event 僅有一份定義，不依來源拆分為多個 Event。
- 來源以攜帶資訊區分，各來源的提升幅度由該來源流程的 Policy 決定。
- 「能力值已提升」與訓練中斷流程的「能力值已退步」為兩個獨立 Event，不合併為單一變動 Event。
- AI 調整類 Event 的來源值域為三值：訓練前調整 / 訓練中調整 / 自動優化。
- 三條 AI 流程的作用範圍差異（本次訓練 / 剩餘動作 / 課表範本）以來源值表達，不另拆 Event。
- 「使用者已確認使用新訓練強度」與 AI 訓練中調整流程的「使用者已確認調整」為兩個不同 Event，本次未歸併。
- 「訓練課表已套用新強度」為單一 Event，三條 AI 流程共用，以作用範圍區分改動標的。
- 「訓練課表已套用新強度」的作用範圍值域為二值：本次訓練 / 課表範本。
- AI 訓練前調整流程與 AI 訓練中調整流程的作用範圍皆為「本次訓練」，AI 自動優化訓練流程為「課表範本」。
- 「訓練課表已套用新強度」的 Actor 為系統；AI 僅產出建議，不執行套用。
- 不建模「訓練課表套用已失敗」：套用為本機資料寫入，失敗屬技術性交易回滾，非業務事實。

- 「使用者已支付」為單一 Event，實體與虛擬兩條購買流程共用，與訂單為單一 Aggregate 的設計對稱。
- 「使用者已支付」的商品類型值域為二值：實體 / 虛擬。
- 「使用者已支付」的支付管道值域為二值：第三方金流 / App Store。
- 實體商品的支付管道為第三方金流（信用卡 / 行動支付，回呼觸發）。
- 虛擬商品的真實金流支付管道為 App Store，與會員訂閱同屬一體系。
- 「使用者已支付」的 Actor 一律為外部系統，兩種支付管道僅為提供者差異，不改變 Actor。

### 規則

- 「中斷」一詞不得單獨使用，必須帶明確主體（單次訓練 / 連續訓練天數）。
- 「追蹤」為棄用詞，一律改用「關注」，對應 Event 為「使用者已關注帳號」。
- Policy 與 Rule 中引述行為時，一律直接使用既有 Event 全名，不得另造簡稱。

## Read Model 清單

### 建立原則

Read Model 的存在意義是**支撐 Actor 的決策**，而非描述畫面。

- **建立判準**：僅為「Actor 下某個 Command 之前必須看見」的資訊建立 Read Model。
- **不建立**：純展示、與任何 Command 無關的畫面，不納入模型。
- **盤點方式**：以〈Command 清單〉的 226 個 Command 為索引，逐一詢問
  「Actor 下這個 Command 前必須看到什麼」，有答案者才立 Read Model。
- 判準為「是否支撐決策」，不是「是否跨 Aggregate」：單一 Aggregate 的查詢若攸關決策
  （如簽到前需看到連續天數與補簽券餘額），同樣成立 Read Model。
- 每個 Read Model 須註明：**服務的 Actor**、**支撐的 Command**、**欄位與來源**、**即時性要求**。

*來源：`.clarify/resolved/read-model/全流程ReadModel_各流程尚未定義任何Read Model.md`（選項 A）*

### Read Model：六維能力值雷達圖

| 項目 | 內容 |

| 服務的 Actor | 使用者 |
| 支撐的 Command | 選擇訓練課表、選擇動作 |

| 項目 | 內容 |
|------|------|

| 對應 Command | 產生能力值日快照 |
| 冪等去重鍵 | 排程名稱 ＋ 該筆快照所屬的使用者當地日期 ＋ 使用者 ID |

- 快照的產生**建模為業務 Event**「能力值日快照已產生」。
- 日界時點沿用全模型統一的當地時區 04:00，不另設第二個換日基準。
- 建模為 Event 而非僅視為 Read Model 的投影：承「可推導不等於不成立為 Event」的既有裁決
  （「使用者已失去獎勵加成」「商品已售完」皆為此判例）。快照是六維成長軌跡的唯一憑據，
  某日漏產生即該日歷史永久缺失、無法回補，屬有獨立業務意義的事實。
- 另一理由為結構一致性：〈排程觸發的請求識別碼〉表的每一列皆對應一個 Event，
  若僅納入冪等表而不建 Event，該表將出現無對應 Event 的孤列。
- 不採「僅於能力值變動時寫入快照」：該方案推翻第三輪「每日快照」的裁決，
  且能力值會因退步而在無訓練的日子自行下降，查詢時向前補值會把下降過程抹平成水平線。

- 雷達圖一次只呈現一個輪廓，不疊層對比：時間維度的切換已能表達成長與退步，

- 採每日快照而非「每次訓練結算時快照」：時間維度可任意切換，固定頻率保證任一日期都查得到值；

| 名次視窗 | 清單 | 自己上下各 10 名，共至多 21 筆 |
| 每筆項目 | — | 名次、使用者顯示名稱、個人排行榜分數 |
| 資料更新時間 | 時戳 | 上次重算的時點 |

  高強度使用者，多數人一輪都領不到排行獎勵。
- 分組粒度取 10 組而非 99 組：一階一榜會使高階組人數稀少，組內可能湊不滿一個名次視窗。
- 顯示採「自己上下各 10 名」的視窗，不顯示組內前段名單：避免使用者看到與自己差距過大的對手，
  減少負面比較。
- 排行獎勵依**組內名次**發放。
- 所屬組別於週期起點鎖定，不隨週期內的階級提升改變；詳見〈個人排行榜分數 Aggregate〉之〈分組鎖定〉。

  名次跳動；畫面標明更新時間以免延遲被誤認為異常。

### Read Model：訓練歷史

| 項目 | 內容 |
|------|------|
| 服務的 Actor | 使用者 |
| 支撐的 Command | 選擇訓練課表、記錄該組成績（決定今天練什麼、加多少重量） |
| 資料來源 | 訓練紀錄 Aggregate（結算後凍結，永久保存） |
| 即時性 | 即時，訓練結算後立即可查 |

**兩種檢視並存**

| 檢視 | 呈現單位 | 回答的問題 |
|------|----------|-----------|
| 訓練清單 | 以一次訓練為單位 | 我上週練了什麼、練得夠不夠（回顧與檢討） |
| 動作趨勢 | 以一個動作為單位 | 這個動作上次推幾公斤、該不該加重（訓練當下） |

**欄位**

| 檢視 | 欄位 |
|------|------|
| 訓練清單 | 日期、課表名稱、總訓練量、訓練時長；點入可看該次各動作各組明細 |
| 動作趨勢 | 該動作歷來的重量與次數，依時序排列；**另以折線圖呈現重量對時間的走勢** |

**查詢規則**

| 項目 | 裁決 |
|------|------|
| 可回溯時間範圍 | **不設限**，全部訓練紀錄皆可回溯 |
| 動作趨勢圖表 | **含折線圖**（重量對時間），與列表並存 |
| 動作名稱搜尋 | **提供**，涵蓋平台動作庫與自建動作 |

- 動作趨勢檢視的預設排序為**累積練習次數由多到少**（最常練的在前）。
- 不採「依最近一次練到的時間排序」：健身多為分部位循環（昨天練腿、今天練胸），
  最近練到的動作恰為今天不會練的，排在最前反而擋路。
- 採累積次數排序的另一理由：主力動作長期固定，順序不隨每日訓練變動，使用者記得住位置。
- 兩種檢視共用同一份訓練紀錄資料，僅多一個查詢維度。
- 訓練紀錄於結算後凍結，訓練歷史為唯讀。
- 回溯範圍不設限：訓練紀錄本已永久保存，設限不省儲存成本，只增加規則。
- **不以會員身分限制回溯範圍**：訓練紀錄為使用者自身產生的資料，以會員身分限制其存取，
  性質為「贖回」而非「擴張」，與模型既有的付費牆（自訂訓練額度、進階訓練計畫）性質不同。
  且該限制只擋得到已累積 3 個月以上歷史者 —— 恰為留存最久的一群，對新使用者零轉換貢獻。
- 提供搜尋的理由：累積次數排序只保證主力動作在前段，而使用者最需要查的常是久未練的動作
  （正因久未練才記不得上次的重量），該類動作恰好排在最後。
- 含折線圖的理由：動作趨勢回答的是「該不該加重」，重量對時間的走勢以列表呈現須由使用者自行連線。
  與〈Read Model：六維能力值雷達圖〉職責不重疊（後者呈現六維能力值，非單一動作的重量走勢）。

| 該動作上次的實際重量與次數 | 重量 / int | 來源為訓練紀錄 Aggregate 的歷史資料，供加重決策 |
| 組間休息剩餘秒數 | int | **僅於組間休息期間有值**，見下方〈組間休息倒數的呈現時機〉 |
| 防作弊剩餘阻擋秒數 | int | 僅於 30 秒阻擋生效期間有值，見〈防作弊：連續快速勾選的阻擋〉 |

- 「該動作上次的實際重量與次數」為本 Read Model 與〈Read Model：訓練歷史〉的重疊處，
  兩者不合併：訓練歷史服務的是**訓練前**選課表的決策，本欄服務的是**訓練中**每一組的加重決策，
  取數範圍僅限當下這一個動作的最近一次。
- 進度百分比與已完成 / 總計畫組數並存，不擇一：分數提供絕對量（還剩幾組），百分比提供相對量。
- 總計畫組數為 0（空白課表）時進度條不成立，本 Read Model 的前兩欄與百分比一併不呈現。
- 進度百分比不要求單調遞增（承〈訓練進度條 Aggregate〉，AI 調整可使分母變動而下降）。

#### 組間休息倒數的呈現時機

組間休息倒數**不常駐於訓練進行中頁**，而是於「組間休息已開始」後獨立呈現、
於「組間休息已結束」後消失。使用者可於倒數期間下達 Command「結束組間休息」（跳過）。

- 承〈組間休息秒數的取值優先序〉：初始秒數依課表 → 動作預設 → 全站預設 90 秒取值。
- 承既有裁決：跳過即觸發「組間休息已結束」，該 Event 為多對一（計時結束由系統觸發、跳過由使用者觸發）。

#### 防作弊剩餘阻擋秒數納入的理由

〈防作弊：連續快速勾選的阻擋〉為 Precondition 層的阻擋，若不呈現剩餘秒數，
使用者下達 Command「完成該組」時只會得到無回應，無從得知何時可再試。

#### 不納入的兩項

| 未納入 | 理由 |
|--------|------|
| 距逾時中斷判定的剩餘時間 | 逾時中斷的判定基準為「40 分鐘內未完成任何一組」（依最後一組完成時戳），不是總時長；且該判定為後端靜默判定，維持不對使用者揭露 |
| 各動作所屬肌群、該維目前能力值 | 能力值於訓練結算才更新，訓練中讀到的是舊值，作為決策依據會誤導；且已由〈Read Model：六維能力值雷達圖〉承載 |
