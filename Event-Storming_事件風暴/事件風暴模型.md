## 「事件 Event」：軟體開發的起點

在軟體開發的協作中，尋找一個業務與技術人員都能產生共鳴的起點相當重要，事件風暴（Event Storming）的 Event（事件）是最理想的切入點 — 指在領域中已經發生、對業務具有意義的事實。

Event 透過聚焦在「發生了什麼」而非「如何實作」，讓不同背景的角色可以快速共鳴。它避開了艱澀的技術術語，轉而使用人人都能理解的業務事實。更能以此延伸出系統所需的角色（Actor）、命令（Command）與資料模型（Read Model）。

Event 能夠幫助決定「哪些地方需要軟體支援」，這也是開發初期最關鍵的策略。當一個事件被視為「大家都有興趣且對業務有實質幫助」時，這就是一個值得投入開發資源的「軟體邊界」。

透過盤點 Event，企業能更有系統地判斷開發的優先順序，並篩選掉非關鍵的流程。如果某個 Event 對業務價值影響極小，或其狀態改變不需要精準的自動化追蹤，則該 Event 可能留在系統邊界之外，維持人工作業。

## 「事件 Event & 命令 Command & 角色 Actor」：三者串聯的系統運作行為

在 ES 中，系統的運作是由事件（Event）、命令（Command）、與角色（Actor）三者組成。

- Event 是系統狀態的改變，通常用「過去式」描述（如：訂單已付款），也是軟體開發的切入點。
- Command 就是觸發 Event 的具體操作。對應 Vision 的 Feature（第四層 - 功能）。

Command（因）與 Event（果）之間存在「多對一」的顆粒度差異：多種不同的 Cammand 可能會導致同一個 Event。這種區分方式有助於幫助我們在盤點需求時，先透過較粗顆粒度的事件掌握大局，再細化具體的操作路徑。

- Actor 是執行 Command 的人或系統，識別 Actor 的意義在於釐清「誰在與系統互動」以及「互動的觸發源」。

這時候我們將三串聯起來：「Actor 執行了 Command，導致 Event 的發生。」

## 「規則 Rules」：前置條件 & 後置條件是系統的驗收標準

在 ES 中，規則（Rules）是執行 Command 所需要遵守的條件，並在 Vision 中對應第六層的「驗收標準（AC）」。

Rules 分成兩種：前置條件（Preconditions）與後置條件（Postconditions）。

- Preconditions 是執行 Command 前的檢核點（如：學生擁有課程權限、單調遞增），規範了在何種狀態下執行 Command 是合法的。
- Postconditions 是系統在執行完成後，應該達到的新狀態 / 預期結果。

這種結構化的 Rules 定義對 AI 開發至關重要。透過明確的 Preconditions 與 Postconditions 描述，可以確保產出的程式碼邏輯具備嚴謹性。

補充：「單調遞增」確保進度只能往前，不能倒退。這在規則上相當重要，但常常被 AI 與人類忽略。

## 「聚合 Aggregate & 查詢模型 Read Model」：系統的狀態

在 ES 中最後兩個元素：聚合（Aggregate）與查詢模型（Read Model），描述了系統如何管理資料庫狀態以及 Actor 如何知道當前的狀態。

- Aggregate 聚合，也可稱為實體。都代表著是「資料庫中的資料單位（狀態）」，它將一群相關聯的資料聚集在一起，且每個欄位必須遵守規格、彼此不能矛盾。執行 Command 的目的就是修改 Aggregate 的內部狀態。
- Read Model 是 Actor 知道 Aggregate 狀態的方法，它不改變任何狀態。

將這兩者的關係串聯在一起：「Actor 透過 Raad Model 知道系統當前的狀態，做出對應的決策，進而執行 Command 改變 Aggregate 的內部狀態。」

這種「命令與查詢分離」的思維，讓系統設計更為清晰。有助於我們設計出更符合用戶行為邏輯的系統介面與後端結構。
