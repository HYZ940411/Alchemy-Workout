發文與互動流程
[區別] 分享與發文為兩種不同行為，獎勵可各自取得，不互斥  
[Rule] Precondition：解鎖條件以**歷史行為**計數：五個 Event 曾各發生一次即滿足，其後刪除貼文或取消按讚不影響計數  
[Rule] 不變條件：已解鎖永久保留，不因行為被刪除而撤銷  
[決策] 門檻為各一次，用意在確認「此人使用過社群功能」，非評量活躍度；行為發生過即為事實，事後刪除不使其變為未發生  
[決策] 不採「刪除後低於門檻即撤銷解鎖」：與既有規則「社群互動功能解鎖旗標為單調遞增、一經設定不可撤銷」直接衝突  
[決策] 管理員處罰不改動本解鎖旗標：既有規則已定案社群功能停權一律以使用者 Aggregate 的處罰狀態欄位表達  
發文者已分享訓練成果 〔轉發訓練成果，主要至站外，亦可轉發至站內〕  
[Rule] Postcondition：所產生貼文的關聯訓練紀錄欄位必有值

[Rule] Postcondition：發文者於發布時指定可見範圍：公開 / 僅關注者 / 私人  
[Rule] Postcondition：所產生貼文的關聯訓練紀錄欄位為空

[發布前的內容過濾]（2026-08-18 定案，App Store 1.2 要求）
[Policy] 內容送出時先經自動過濾，依判定結果分兩條路：明顯違規者當場攔截、疑似違規者照常發布並自動送審
[Rule] 適用對象為三類使用者生成內容：貼文、留言、私訊（私訊見聊天私訊流程）
[Rule] Precondition 之判定值域：過濾判定分三值——通過 / 明顯違規 / 疑似違規
[串聯] 系統執行「攔截違規內容」導致「內容已攔截」— Actor：系統（判定由系統執行，非管理員）
內容已攔截 〔攜帶資訊：內容類型（貼文 / 留言 / 私訊）、攔截原因、命中的違規類別〕
[Rule] Precondition：該內容的過濾判定為明顯違規
[Rule] Postcondition：該內容不寫入任何 Aggregate，「發文者已發布貼文」與「互動者已留言」不發生
[Rule] Postcondition：不發放任何互動獎勵，不計入互動成就
[Rule] Postcondition：使用者可修改內容後重新送出，重送為新的一次 Command，不限次數
[Rule] Postcondition：使用者不服攔截者可申訴，申訴對象自「處罰」擴充為「處罰 / 內容攔截」，走既有申訴機制
[串聯] 系統執行「標記疑似違規內容」導致「內容已標記待審」— Actor：系統（2026-08-20 新增）
內容已標記待審 〔攜帶資訊：內容類型（貼文 / 留言 / 私訊）、命中的違規類別、判定分數〕
[Rule] Precondition：該內容的過濾判定為疑似違規
[Rule] Postcondition：該內容照常發布，「發文者已發布貼文」與「互動者已留言」照常發生
[Rule] Postcondition：照常發放互動獎勵、照常計入互動成就（承「內容已發布」即為既成事實）
[Rule] Postcondition：於檢舉 Aggregate 開立案件，案件來源為系統自動標記，案件狀態為待審視
[Rule] Postcondition：**不對使用者發送任何通知**，本 Event 不入推播類清單亦不入 App 內通知類清單
[Rule] Postcondition：系統自動標記的案件無檢舉者，其檢舉者集合為空，其餘處理比照使用者檢舉的既有規則
[Rule] 本 Event 不計入累計違規次數、不觸發處罰，比照「內容已攔截」的既有處理
[決策] 疑似違規建模為獨立 Event：與「內容已攔截」對稱 —— 兩者同為過濾器的判定結果，
承同一條既有理由「攔截率與**誤擋率**為須監控的指標」；疑似違規的**誤標率**為同型指標，
不建模則後端無從得知過濾器把多少正常內容誤開了單
[決策] 不寫為「發文者已發布貼文」等既有 Event 的 Postcondition：該寫法會使 Postcondition
變成「**若**判定為疑似違規則開案」，帶條件的 Postcondition 不再是可驗收的斷言
[決策] 不與「內容已攔截」合併為單一 Event 以「處置＝攔截 / 標記」二值區分：
「已攔截」的語意即為「已擋下」，令其同時表示「未擋下、已放行」等同命名與事實相反；
且兩者的 Postcondition 完全相反（一為不寫入任何 Aggregate、一為照常發布）
[決策] 不對使用者發通知：告知使用者「你被標記了」等同揭露過濾器的判準，
承既有裁決「揭露防作弊判準即使其失效」的同型理由；管理員端則由〈Read Model：管理員待審佇列〉承接
[Rule] 明顯違規與疑似違規的判定門檻為平台級可調參數，**存於內容過濾設定 Aggregate**（2026-08-20 定案），由管理員於後台維護
[決策] 採「擋下明顯違規 ＋ 標記疑似違規」而非單一路徑：全部擋下會誤傷（判定不可能全對，誤擋等於使用者發不出正常內容）；全部放行則違規內容仍會先曝光，而 App Store 1.2 明文要求 filtering objectionable material **from being posted**
[決策] 攔截建模為 Event 而非僅前端錯誤：承既有規則「失敗須建模為 Event，不可僅在前端顯示錯誤」——攔截率與誤擋率為須監控的指標，且被攔截者可申訴，申訴時管理員須看得到當時攔截的是什麼
[決策] 攔截不計入累計違規次數、不觸發處罰：處罰階梯由管理員審視檢舉後裁定，自動判定不得直接施加處罰
[決策] 過濾服務本身（違規字詞庫、影像辨識）留在系統邊界之外，屬實作層選型；模型只承載「判定結果」與其後果
[Rule] 本規則同樣適用於分享至站內的貼文（發文者已分享訓練成果）
[互動獎勵的共通規則]  
[Rule] Postcondition：四種互動獎勵**只發放經驗值，不發放金幣**  
[Rule] Precondition：各行為**每日各有獎勵發放次數上限**：發文 1、分享 3、按讚 10、留言 5  
[Rule] Postcondition：**超過上限仍可正常操作，僅不再發放經驗值**；不阻擋行為本身  
[Rule] Precondition：**自己的貼文不計**：對自身貼文的按讚與留言不發放任何獎勵  
[Rule] 上限以使用者當地時區的 04:00 為換日時點，沿用模型唯一的換日時點  
[Rule] 四項上限皆為平台級可調參數，**存於獎勵定義 Aggregate 的「每日發放次數上限」欄位**（2026-08-20 定案），由管理員於後台維護  
[決策] 須設每日上限：互動獎勵的經驗值推動階級，而階級解鎖**進階訓練計畫**（10/25/45/70）、**自訂訓練名額 2→5**（25/45/70）、**第 9 類階級成就**與**教官初審門檻**（階級 ≥ 20）—— 無上限則按讚數百次即可繞過上述四者  
[決策] 不採「同一貼文的同一種互動只計一次」作為唯一防線：其僅防重複按同一篇，而社群動態牆的貼文數無上限，滑一小時按數百篇仍可拿滿  
[決策] 不擋行為本身：擋住按讚與留言會使社群變冷清，而社群活躍本身即為平台所欲；只停發獎勵即足  
[決策] 不另設「新帳號須完成新手任務方可取得互動獎勵」：新手任務為三選一、做一次即完成，擋不住有心刷者，卻使正常新使用者前幾天的互動拿不到獎勵；且模型已有「社群互動功能需解鎖」的既有機制  
[Rule] Postcondition：上限不影響**累計互動成就**的計數——成就計的是行為次數，與獎勵發放與否無關  
[已知風險] 成就計數不受每日上限約束，故互動成就仍可被快速刷開（按讚數百次即可推進至高階門檻）。其總量有界（每個門檻終身僅解鎖一次），但**成就獎勵的數額須將此納入考量** → 併入 `aggregate/成就獎勵_發放路徑與數額尚未建模.md`  
[Policy] 累計互動成就門檻 （分享 / 發文 / 按讚 / 留言四種成就） 累計: 1 / 5 / 15 / 50 / 100 / 250 / 500 / 750 / 1000 次  
互動成就已解鎖

[決策] 分享無反向操作 Event  
[Rule] Postcondition：取消按讚、刪除留言、刪除貼文皆**不回收**已發放的獎勵  
[Rule] 不變條件：互動成就的計數為單調遞增，反向操作不使其遞減；已解鎖的成就不撤銷  
[Rule] Precondition：同一貼文重複按讚與取消**不重複發放獎勵**：按讚獎勵的請求識別碼為 貼文 ID ＋ 互動者 ID  
[Rule] 留言獎勵的請求識別碼為 留言 ID；刪除後重新留言為新的留言 ID，屬新的一次互動  
[決策] 防刷由「同一貼文只發一次」承擔，非由回收機制承擔：有了唯一鍵，按讚 / 取消 / 再按讚的刷取路徑即不成立，回收機制隨之不必要  
[決策] 不採獎勵回收與成就遞減：與「成就解鎖紀錄單調遞增、一經解鎖不可撤銷」的既有原則相反，該原則已於連簽成就與粉絲成就兩處適用  
[決策] 不採「行為發生 24 小時後才發放（延遲確認）」：須為每一次按讚維護一個排程，而按讚為全模型最高頻的行為，成本與價值不成比例
