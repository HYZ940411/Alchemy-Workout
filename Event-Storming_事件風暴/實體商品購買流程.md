實體商品購買流程
使用者已選擇實體商品  
使用者已選擇尺寸與數量  
[Rule] 尺寸即商品規格，價格與庫存依所選規格決定  
[Rule] Precondition：所選規格的庫存 ≥ 所選數量  
[Rule] 「使用者已確認購買」時預扣庫存，非支付成功後才扣減  
[Rule] 預扣保留 15 分鐘，逾時未付款自動釋放  
[串聯] 系統執行「釋放庫存」導致「庫存已釋放」— Actor：系統（預扣逾時觸發）  
庫存已釋放  
[Rule] Precondition：該訂單狀態為待付款，且距確認購買已滿 15 分鐘  
[Rule] Postcondition：所預扣的庫存回補至該商品規格，訂單狀態轉為已取消  
[Rule] 「使用者已取消訂單」與「支付已失敗」亦一併釋放預扣庫存  
[決策] 建模「庫存已釋放」為 Event：庫存由 0 回到可售是真實的業務狀態改變，若不建模，庫存數字將在無任何 Event 的情況下自行變動；且商品補貨可購的判定需要此時點  
[決策] 不採「支付成功後才扣減」：實體商品超賣的後果是須向真實顧客道歉退款，非可由失敗補償帶過的技術問題  
[決策] 不採「出貨時才扣減」：下單至出貨可能相隔數日，該期間庫存完全不受控  
[Rule] 預扣保留 15 分鐘為平台級可調參數，由管理員於後台維護  
使用者已填寫收貨資訊  
[Rule] 欄位為收件人姓名、手機號碼、郵遞區號、地址、備註（僅備註為選填）  
[Rule] Precondition：收件人姓名非空  
[Rule] Precondition：手機號碼非空且符合手機號碼格式  
[Rule] Precondition：郵遞區號非空  
[Rule] Precondition：地址非空  
[Rule] 地址為單一自由文字欄，不拆縣市 / 鄉鎮區 / 街道  
[決策] 不拆地址：須維護行政區資料且行政區會改名合併；物流已在系統邊界外，本系統無拆解用途  
[決策] 不收集電子郵件：出貨通知管道未定案，通知類 Event 清單中亦無出貨通知  
使用者已確認購買  
[狀態] 訂單 → 待付款  
[邊界] 實體商品的支付由第三方金流執行，不走 App Store 應用內購買  
[串聯] 外部金流系統執行「回報支付結果」導致「使用者已支付」— Actor：外部系統（金流回呼觸發）  
[Rule] 支付方式支援信用卡與行動支付  
使用者已支付 〔Actor：外部系統（第三方金流）回呼〕 〔攜帶資訊：商品類型＝實體、支付管道＝第三方金流〕  
[狀態] 待付款 → 已付款  
[統一語言] 「使用者已購買實體商品」已併入「使用者已支付」，不再作為獨立 Event  
[決策] 該 Event 不改變任何 Aggregate 欄位，與「使用者已支付」同為訂單成立的同一事實  
[決策] 實體流程不比照虛擬流程新增「已成立」狀態；已付款與已出貨的區隔已由「商品已出貨」承擔  
商品已出貨 〔攜帶資訊：物流單號〕  
[狀態] 已付款 → 已出貨（終止狀態）  
[軟體邊界] 「商品已出貨」為本流程終點；物流追蹤、送達、簽收、退換貨一律留在系統邊界之外，由外部物流商負責  
[Rule] Postcondition：出貨時記錄物流單號，系統不再追蹤後續物流狀態  
[失敗與反向路徑]  
[分支] 支付未成功 → 支付已失敗  
[狀態] 待付款 → 已失敗（終止狀態）  
支付已失敗  
使用者已取消訂單  
[狀態] 待付款 → 已取消（終止狀態）  
訂單已退款  
[狀態] 已付款 → 已退款（終止狀態）  
[Rule] 「訂單已退款」僅適用出貨前，狀態轉換限於「已付款 → 已退款」  
[Rule] 訂單狀態機不新增「已出貨 → 已退款」轉換；已出貨為終止狀態  
[軟體邊界] 出貨後的退款與退貨一律留在系統邊界之外，維持**人工作業**，不建模為 Event  
[決策] 承既有邊界裁決：「商品已出貨」為本流程終點，物流追蹤、送達、簽收、退換貨皆已判定在邊界外。出貨後的退款必然伴隨退貨（寄回、驗貨、判定可否轉售），只把退款拉進系統而把退貨留在外面，會做出一個管理員可按下退款鍵、系統卻不知道貨在哪裡的按鈕  
[決策] 不移除出貨前的退款路徑：「已付款但尚未出貨時使用者反悔」為常見情境，該路徑須保留  
[決策] 本判定為標記人工作業，非刪除該情境
