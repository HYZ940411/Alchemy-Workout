聊​天​私訊​流程
使用者​已​建立​對話  
[Rule] 對話為獨立 Aggregate，欄位含參與者、建立時間、各方刪除狀態  
[Rule] 對話可為空：本 Event 發生時尚無任何私訊  
使用者​已​發送私訊  
[Rule] 可直接發送私訊的對象：互相關注者、具師徒關係者、同團隊成員，三者滿足其一即可  
[Rule] 不符上述三種關係者仍可發送，但其訊息歸類為**陌生訊息**  
[Rule] 私訊 Aggregate 須具備「訊息分類」欄位，值域為 一般訊息 / 陌生訊息，於發送當下依雙方關係判定並寫入  
[Rule] 分類於發送當下固定，其後關係變化不回溯改寫既有訊息的分類  
[Rule] 陌生訊息於對話清單分區呈現，不與一般訊息混列  
[決策] 不採「僅互相關注才可發送」：師徒關係由單向拜師建立，雙方未必互相關注，卻正是最需要私訊的一對人  
[決策] 不採「收訊方可設定僅接收互相關注者的訊息」：陌生訊息分區呈現已解決同一個需求（騷擾不進主要收件匣），且分區為全體一致的行為，不需每位使用者各自設定，亦不會出現「設定為僅接收互關者後，隊友與教官反而發不進來」的死角  
[決策] 陌生訊息不阻擋而是分區：完全開放會使騷擾直接進入主要收件匣，完全阻擋則使陌生人無法發起任何互動（如邀請入隊）  
[待決策 Partial] 陌生訊息是否有數量上限、是否須經收訊方回覆後才轉為一般訊息，尚未定案  
[Rule] 私訊為獨立 Aggregate，以對話 ID 關聯，不作為對話的子集合  
[Rule] 私訊可被檢舉；檢舉對象類型「私訊」指涉私訊 Aggregate 的 ID  
[決策] 訊息數量無上限成長，故不併入對話，避免讀取對話狀態時載入全部歷史  
使用者​已​讀取私訊  
[Rule] Precondition：使用者開啟對話，且該對話中存在以其為接收方、已讀時戳為空的私訊  
[Rule] Postcondition：上述私訊的已讀時戳一律寫入當下時戳  
[Rule] 判定條件為開啟對話，非訊息進入畫面可視範圍  
[Rule] 已讀狀態於發送方的對話畫面被動呈現，不發送推播通知  
[決策] 不建模「已讀通知已發送」Event，亦不列入通知類 Event 清單  
[決策] 已讀回條本階段不可關閉，不新增隱私設定欄位

使用者​已​封鎖​對象  
[Rule] 封鎖為獨立 Aggregate，欄位含封鎖者、被封鎖者、封鎖時戳  
[Rule] 封鎖為單向關係，唯一鍵為 封鎖者 ID ＋ 被封鎖者 ID  
[決策] 可封鎖從未對話過的對象，故封鎖不掛在對話之下  
[Rule] Postcondition：封鎖自動解除雙方的關注關係（觸發「使用者已取消關注」）  
[Rule] Postcondition：封鎖自動解除雙方的師徒關係（觸發「師徒關係已解除」），未完成的師徒任務作廢  
[Rule] Precondition：雙方不得為同一團隊的成員，方可發生「使用者已封鎖對象」  
[Rule] 欲封鎖同隊成員者，須先退出團隊；退出後 12 小時冷卻期照常適用  
[決策] 解除師徒關係：師徒關係的內容即為提問與回答，封鎖後該關係只剩空殼，且會繼續佔用教官的帶徒名額  
[決策] 已知代價：騷擾者為同隊隊友時，受害者須先退出團隊才能封鎖，等於受害者付出代價才能自保。本代價由使用者明示接受  
[決策] 團隊關係採「禁止封鎖」而非「自動退隊」：自動退隊會使一次封鎖操作連帶改變第三方（其餘隊友）的團隊組成  
[Rule] 解除封鎖不自動恢復任何已解除的關注或師徒關係  
使用者​已​解除​封鎖  
使用者​已​刪除​對話  
[Rule] Postcondition：為單方刪除，只改該方的刪除狀態，對方仍可見  
[Rule] 刪除只發生於對話層級；單則訊息一經發送即不可刪除  
使用者​已​檢舉私訊  
[決策] ​不​建​模​「​刪​除​訊​息​」，​單​則​訊​息​一​經​發​送​即​不​可​刪​除  
[Rule] ​封​鎖​為​可​逆​操​作：​「​使用者​已​封鎖​對象​」​已​發​生，​方​可​發​生​「​使用者​已​解除​封鎖​」  
[串聯] ​「​使用者​已​檢舉私訊​」​併​入​管理員​管理​社群​流程​的​「​管理員​已​審視檢舉​」​處​理
