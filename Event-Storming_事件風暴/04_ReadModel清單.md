## Read Model 清單

### 建立原則

Read Model 的存在意義是**支撐 Actor 的決策**，而非描述畫面。

- **建立判準**：僅為「Actor 下某個 Command 之前必須看見」的資訊建立 Read Model。
- **不建立**：純展示、與任何 Command 無關的畫面，不納入模型。
- **盤點方式**：以01_Command清單.md〈Command 清單〉的全部 Command 為索引，逐一詢問
  「Actor 下這個 Command 前必須看到什麼」，有答案者才立 Read Model。
- **[訂正 2026-08-21]** 原記「以 **226 個** Command 為索引」。該次盤點的基數已過期
  （Command 現約 290 個），**且其後新增的約 64 個 Command 未被該次盤點涵蓋**
  —— 〈管理員訂單佇列〉與〈管理員商品清單〉即由此漏出（商品管理權限組 6 個 Command
  一個都沒有對應的 Read Model）。日後新增 Command 時，須同步詢問其是否需要 Read Model，
  不再仰賴事後整批盤點。本檔現有 **35 個** Read Model。
- 判準為「是否支撐決策」，不是「是否跨 Aggregate」：單一 Aggregate 的查詢若攸關決策
  （如簽到前需看到連續天數與補簽券餘額），同樣成立 Read Model。
- 每個 Read Model 須註明：**服務的 Actor**、**支撐的 Command**、**欄位與來源**、**即時性要求**。

#### 設定類 Command 的 Read Model（2026-08-21 新增通則）

- **設定類 Command 一律不另立 Read Model 條目**：其 Read Model 恆為
  「該設定 Aggregate 的現值表」，欄位即該 Aggregate 的欄位表，服務的 Actor 為管理員，
  即時性為即時。
- 適用對象為〈平台設定維護〉一節的全部設定 Command，以及分列於各流程的設定 Command。
- 理由：逐一建立會產出與 Aggregate 欄位表一字不差的副本，欄位一改須改兩處。
  本作法承模型既有的同型手法 —— Command 輸入參數改用推導式而非逐一列表、
  排程識別碼改用兩條推導式而非逐案訂定。
- **新增設定 Aggregate 時不需新增 Read Model 條目**，本通則自動適用。
- **界線**：若某管理員畫面除現值外還需要**其他 Aggregate 推導的決策依據**，
  即超出本通則，須另立條目。例：〈管理員商品清單〉需呈現「未出貨訂單筆數」
  （取自訂單 Aggregate），故獨立列出而不適用本通則。

### Read Model：六維能力值雷達圖

| 項目 | 內容 |
|------|------|
| 服務的 Actor | 使用者 |
| 支撐的 Command | 選擇訓練課表、選擇動作 |
| 資料來源 | 使用者 Aggregate 的能力值 6 維欄位；能力值日快照 |
| 即時性 | 「現在」維度為即時，隨「能力值已提升 / 已退步 / 已部分回復」立即反映；歷史維度為日粒度 |

**欄位**

| 欄位 | 型別 | 說明 |
|------|------|------|
| 六維能力值 | 6 維 int | 所選時間維度當下的值，一次僅呈現單一輪廓 |
| 維度能力等級 | 6 維列舉 | 各維由該維點數推導的等級，值域 S / A / B / C / D / E |
| 綜合能力等級 | 列舉 | 六維彙總後的單一等級，值域同上 |
| 時間維度 | 列舉 | 使用者於圖表上方切換，決定要呈現哪一天的快照 |
| **耐力值** | 6 維 float / 空值 | **獨立區塊條列，不畫入雷達圖**，見〈耐力值的呈現〉；**衍生值、不儲存**，讀取時由組紀錄與該動作的歷史最佳估算 1RM 即時計算（2026-08-19），算法見03_能力值.md〈能力值的維度結構〉 |

#### 耐力值的呈現（2026-08-11 定案）

**耐力值以獨立區塊條列六個數值，不畫入雷達圖，且不作為主要呈現項目。**

- **不採「雷達圖畫第二圈輪廓」**：耐力值雖同樣依肌群分六維、與六維能力值同構，
  但畫入同一張圖會使其取得與力量同等的視覺份量 ——
  而**耐力值為附掛值**（不掛成就、無退步機制、不進綜合能力等級），
  其在模型中的地位本即次於力量，呈現份量應與之相稱。
- 雷達圖維持**單一輪廓**（承既有欄位定義「一次僅呈現單一輪廓」），不因本項而改變。
- 空值處理：無可靠最佳 1RM 的維度其耐力值為空值（承既有規則「不推測」），
  該維於區塊中呈現為空白或「—」，不以 0 表示。
- 六維皆為空值時（新使用者尚未做過大重量訓練）**不呈現本區塊**。

*來源：`.es-clarify/resolved/aggregate/能力值_耐力值的呈現位置與雷達圖是否畫第二圈輪廓.md`（選項 B）*

**能力值日快照**

| 項目 | 內容 |
|------|------|
| 產生頻率 | 每日一筆，於日界時保存當下六維值 |
| 內容 | 使用者識別碼、快照日期、六維能力值 |
| 對應 Event | 能力值日快照已產生（Actor：系統，排程觸發） |
| 對應 Command | 產生能力值日快照 |
| 冪等去重鍵 | 排程名稱 ＋ 該筆快照所屬的使用者當地日期 ＋ 使用者 ID |

- 快照的產生**建模為業務 Event**「能力值日快照已產生」。
- 日界時點沿用全模型統一的當地時區 04:00，不另設第二個換日基準。
- 建模為 Event 而非僅視為 Read Model 的投影：承「可推導不等於不成立為 Event」的既有裁決
  （「使用者已失去獎勵加成」「商品已售完」皆為此判例）。快照是六維成長軌跡的唯一憑據，
  某日漏產生即該日歷史永久缺失、無法回補，屬有獨立業務意義的事實。
- 另一理由為結構一致性：00_全域規範.md〈排程觸發的請求識別碼〉表的每一列皆對應一個 Event，
  若僅納入冪等表而不建 Event，該表將出現無對應 Event 的孤列。
- 不採「僅於能力值變動時寫入快照」：該方案推翻第三輪「每日快照」的裁決，
  且能力值會因退步而在無訓練的日子自行下降，查詢時向前補值會把下降過程抹平成水平線。

**保存年限：不設限，永久保留**（2026-08-11 定案）。

- 承既有判準「訓練歷史為使用者自身產生的資料，不以會員身分限制回溯範圍」——
  能力值日快照現為會員權益〈六維能力值的歷史變化圖〉的資料來源，適用同一判準。
- 承既有判斷「一年 365 筆，資料量可忽略」：每筆內容為使用者 ID ＋ 日期 ＋ 六個整數，
  多年累積仍屬輕量的純數值紀錄。
- **不標記為「不需精準追蹤」**：該標記與本 Event 的立案理由直接衝突 ——
  「快照是六維成長軌跡的唯一憑據，**某日漏產生即該日歷史永久缺失、無法回補**」。
- **不採降頻保存**（近期每日、久遠降為每週或每月）：其以降低資料完整性換取成本，
  同樣與上述立案理由相衝；且等於降低會員權益的解析度。
- **儲存成本若日後成為問題，由實作層處理，不以犧牲資料完整性換取**
  （冷熱分層儲存、時序壓縮等皆為實作選型，不影響模型）。
  **本項現階段不處理，待實際遇到再議**（2026-08-11 使用者裁示）。
- 帳號刪除時該使用者的全部快照一併刪除，見02_Aggregate定義.md〈帳號生命週期〉之02_Aggregate定義.md〈刪除範圍〉。

*來源：`.es-clarify/resolved/event/能力值日快照_日快照的產生是否建模為Event與其冪等去重鍵.md`（選項 A）*

- 雷達圖一次只呈現一個輪廓，不疊層對比：時間維度的切換已能表達成長與退步，
  疊層是同一件事的重複表達。
- 採每日快照而非「每次訓練結算時快照」：時間維度可任意切換，固定頻率保證任一日期都查得到值；
  依結算時點保存則快照時點不規則，久未訓練者於該區間可能一筆資料都沒有。
- 快照內容為六維整數，一年 365 筆，資料量可忽略。
- **雷達圖不顯示各維距下次退步的剩餘時數**：退步提醒的職責已由「退步預告已發送」承擔
  （該維滿 96 小時未訓練時發送），不在雷達圖重複表達。

### Read Model：個人排行榜

| 項目 | 內容 |
|------|------|
| 服務的 Actor | 使用者 |
| 支撐的 Command | 查看排行榜 |
| 資料來源 | 個人排行榜分數 Aggregate；使用者 Aggregate 的階級 |
| 即時性 | 延遲更新，固定間隔重算，畫面須標明資料更新時間 |

**分組**

| 項目 | 內容 |
|------|------|
| 分組依據 | 使用者階級 |
| 分組粒度 | 每 10 階一組，共 10 組（1–10、11–20、…、91–99） |
| 排名範圍 | 組內排名，不跨組比較 |

**欄位**

| 欄位 | 型別 | 說明 |
|------|------|------|
| 所屬組別 | 列舉 | 取個人排行榜分數 Aggregate 於本週期鎖定的組別，共 10 組 |
| 榜別 | 列舉 | 二值：週榜 / 月榜，由使用者切換 |
| 名次視窗 | 清單 | 自己上下各 10 名，共至多 21 筆 |
| 每筆項目 | — | 名次、使用者顯示名稱、個人排行榜分數 |
| 資料更新時間 | 時戳 | 上次重算的時點 |

- 排行榜採階級區間分組：分組的價值在於獎勵的可得性 —— 不分組時全平台前段永遠是同一批
  高強度使用者，多數人一輪都領不到排行獎勵。
- 分組粒度取 10 組而非 99 組：一階一榜會使高階組人數稀少，組內可能湊不滿一個名次視窗。
- 顯示採「自己上下各 10 名」的視窗，不顯示組內前段名單：避免使用者看到與自己差距過大的對手，
  減少負面比較。
- 排行獎勵依**組內名次**發放。
- 所屬組別於週期起點鎖定，不隨週期內的階級提升改變；詳見02_Aggregate定義.md〈個人排行榜分數 Aggregate〉之02_Aggregate定義.md〈分組鎖定〉。
- 即時性採延遲更新：名次為跨使用者比較，每次分數變動即重算全組成本高，而使用者不會盯著
  名次跳動；畫面標明更新時間以免延遲被誤認為異常。

### Read Model：補簽頁

| 項目 | 內容 |
|------|------|
| 服務的 Actor | 使用者 |
| 支撐的 Command | 使用補簽券 |
| 資料來源 | 連續簽到 Aggregate、補簽券 Aggregate、每日簽到紀錄 Aggregate、補簽設定 Aggregate |
| 即時性 | 即時，補簽後立即反映 |

**欄位**

| 欄位 | 型別 | 說明 |
|------|------|------|
| 最近 N 天日曆 | 清單 | 涵蓋**距今 1 至 N 天**，每日一筆共 N 筆（N ＝ 補簽設定的回補範圍，初始 7）；不含今日；狀態值域三值，判定見下 |
| 補簽券張數 | int | 目前持有數 |
| 補簽後可恢復的連續天數 | int | 對所選日期試算：模擬將該日補入每日簽到紀錄後，以逐日推算求得的連續天數 |

- 補簽券為有限資源，故 Read Model 須同時呈現**代價**（剩餘張數）與**收益**
  （補簽後可恢復的連續天數），使用者才能判斷這張券值不值得用在這一天。
- 採日曆而非日期清單：補簽是對特定日期的操作，日曆使「斷在哪一天」一眼可見。
- **日曆範圍取「最近 N 天」而非「本月」**（2026-08-23 改）：原以本月為範圍者，
  於月初可補日期多落在上月，日曆上無從點選 —— 若今日為某月 1 日，可補的 7 天全數落在上月，
  補簽功能在月初數日實質失效。改採最近 N 天後，顯示範圍恰等於可補範圍，跨月自動涵蓋。
- **N 隨補簽設定的回補範圍連動**：管理員調整回補範圍時，日曆長度自動跟隨，不需另行改動本 Read Model。
- 不採「本月＋上月」兩個月：兩個月與回補範圍無推導關係，為憑感覺的常數；
  且於月底顯得多餘、於月初仍可能不足。
- 不採「維持本月另設可補簽日期清單入口」：等同承認日曆未做到其宣稱之事，且多一個入口須維護。
- 不採「可左右翻月」：使用者須自行知道要往前翻一個月才找得到，與「一眼可見」的設計意圖相反。
- 日曆不再對齊月份格線，呈現上為一條橫向日期帶或連續 N 格；此屬呈現方式，不改變本欄位定義。
- **日曆不含今日**：今日的簽到由〈Read Model：簽到頁〉承載（該頁已定案只收「今日是否已簽到」
  一個欄位），本頁只承載「過去哪一天要補」這一個決策。故日曆涵蓋距今 1 至 N 天，恰為可補範圍。
- 補簽日期由使用者指定，不由系統自動選定最近一次中斷：持有上限有限，
  使用者可能想保留券以補更關鍵的日期。
- **日曆狀態三值的判定**（2026-08-24 明確化）：

  | 狀態 | 判定條件 |
  |------|---------|
  | 已簽 | 該日有〈每日簽到紀錄〉 |
  | 可補簽 | 無紀錄，且在回補範圍內，**且該日 ≥ 使用者的註冊日** |
  | 未簽 | 無紀錄，且（超出回補範圍 **或** 早於使用者的註冊日） |

- **「未簽」於本日曆的唯一出現情形為註冊日之前的日期**：
  日曆範圍恰等於回補範圍（距今 1 至 N 天），故「超出回補範圍」在本日曆內不會發生；
  剩下的唯一情形即註冊未滿 N 天者，其註冊日之前的格子。
  〔2026-08-24：本節原僅寫「『可補簽』狀態依已定案的可回補時間範圍判定」，
  未含註冊日條件，致新註冊者的日曆全數顯示為可補簽。〕

#### 設計約束：重複性

**本頁每次訓練後皆呈現，一年約 150 次。** 內容若每次相同即淪為壁紙，
使用者兩週後便直接關閉。故版面分為**固定核心**與**條件式亮點**兩層：
核心維持每次都有變化，亮點僅於事件發生時出現，使每次開啟保有「這次會不會有什麼」的期待。

#### 核心區塊（每次皆呈現）

| 欄位 | 型別 | 說明 |
|------|------|------|
| 實績摘要 | 衍生 | 總訓練量（**四捨五入至整數呈現**）、訓練時長、已完成組數 |
| **消耗大卡** | 衍生（int） | 「約 N 大卡」，**必須標示為估計值**；算法見02_Aggregate定義.md〈消耗大卡的估算〉 |
| **六維能力值增量** | 六維各一 int | 本次各維增加的點數，如「胸 +12」 |
| **能力值等級與小節點進度** | 六維各一 | 格式為「主階 ＋ 本節點累積 ＋ 距下一節點」，例：`B　+12　距 30 升 B+` |
| 連續訓練天數 | int | 本次訓練後的天數 |
| 經驗值增量與階級進度 | int ＋ 百分比 | 本次獲得的經驗值、當前階級與距下一階的進度 |
| 金幣獎勵 | int | 本次發放的金幣，含連續訓練獎勵加成 |

- **六維能力值增量為本區塊的主角**：其為模型中唯一表達「我變強了」的數值，
  而訓練是它唯一的來源，應佔最大版面。
- **小節點使進度回饋高頻化**：主階需 2–6 個月才跳一次，
  單次訓練對主階進度的推進不足 1%；小節點使每次訓練都看得見推進。
- 不呈現終止方式（完成 / 提前結束 / 逾時中斷），理由見02_Aggregate定義.md〈訓練紀錄 Aggregate〉。

#### 亮點區塊（僅於發生時呈現）

| 欄位 | 型別 | 說明 |
|------|------|------|
| 本次解鎖的成就 | 清單 / 空 | 本次訓練觸發的成就解鎖，可為多枚 |

**本區塊只有成就一項。** 其餘候選皆已歸入核心區塊或成就：

| 原候選 | 歸屬 |
|--------|------|
| 階級提升 | **第 9 類「階級成就」**，由成就承載 |
| 能力值主階提升 | 第 8 類「能力值成就」（首次達 D / 綜合五階 / 均衡） |
| 能力值小節點提升 | 核心區塊的等級與小節點進度，跳節點時該行自行變化 |
| 連續訓練天數里程碑 | 第 3 類「連續訓練成就」 |
| 日常階級進度 | 核心區塊的經驗值增量與階級進度 |

- **結構因此可一句話說明：核心區塊 ＝ 連續的進度，亮點區塊 ＝ 離散的里程碑，
  而里程碑在模型中即稱為成就。**
- **不採彈窗插播**：彈窗會打斷結算頁本身的閱讀，
  且成就與階級同時觸發時將連續彈出多次。成就以區塊呈現即可。
- 未觸發任何成就時本區塊不呈現，不留空位。

#### 社群區塊（每次皆呈現，版面小）

| 欄位 | 型別 | 說明 |
|------|------|------|
| 為團隊貢獻的分數 | int / 空值 | 本次訓練為團隊日常分數帶來的增量；無團隊者為空值 |
| 分享入口 | 動作 | 觸發「分享」Command，轉發本次訓練成果 |

- **「為團隊貢獻了 X 分」不需比較對象即成立**：其語意為「我幫上忙了」而非「我排第幾」，
  把個人訓練接上團隊，構成社群回饋。
- **分享入口置於此處**：結算當下為使用者最想炫耀的時刻，是該 Command 的天然位置。
- **不呈現個人排行榜分數與名次**：排行榜分數的意義來自比較，而本頁只有使用者自己，
  單看「+35 分」無從判斷多寡；且排行榜已定案為**延遲更新**，當下呈現的名次可能是錯的。
- **不呈現團隊限時任務進度**：其為第 19、20 題「就差你了」機制的核心，
  但置於此處等同要求剛練完的使用者去催別人，將回饋時刻變成待辦事項；該資訊留在我的團隊頁。
- 無團隊者本區塊僅剩分享入口，不留空位。

#### 本頁幾乎不支撐 Command

**結算為系統自動觸發，不需使用者確認**（承既有裁決
`resolved/event/訓練已結算_結算是自動觸發或需使用者確認.md` 選項 A），
故本頁唯一支撐的 Command 為「分享」，看完即可離開。

- 這使本頁在〈Read Model 建立原則〉中屬**特例**：該原則以「支撐哪個 Command」為建立索引，
  而本頁的存在理由是**揭露已發生的事實**，非支撐下一個決策。
- 其正當性在於資訊密度：結算當下同時發生 8 類事實
  （結算、獎勵、經驗值、階級、能力值、個人排行榜分數、團隊分數、成就），
  若無本頁，該 8 類 Event 對使用者皆無揭露定義。

#### 付費界線：免費看「點」，會員看「線」

**單筆與單一動作的資料全開放；跨時間的彙總視角為會員專屬。**

| 檢視 | 免費 | 會員 |
|------|------|------|
| 訓練清單，任何時間範圍 | ✅ | ✅ |
| 單一動作的趨勢折線圖 | ✅ | ✅ |
| **六維能力值的歷史變化圖** | ❌ | ✅ |
| **期間比較**（本月 vs 上月） | ❌ | ✅ |
| **月報 / 年度回顧（含 AI 文字分析）** | ❌ | ✅ |

- **免費使用者不被拿走任何既有內容**：現行開放的訓練清單、動作趨勢折線圖、
  不限回溯範圍，全數維持。**會員買到的全部是新增的東西。**
- 承既有判準：**付費牆放在「擴張」而非「贖回」** ——
  與〈Read Model：訓練歷史〉不以會員身分限制回溯範圍的裁決同一理由。

##### 六維能力值歷史變化圖的資料早已存在

模型的〈能力值日快照〉每日產生一次（見01_Command清單.md〈系統排程〉），
**目前唯一的消費者為雷達圖的當前狀態** —— 亦即平台每日都在保存能力值的歷史，
卻從未呈現給使用者。

- 做為會員權益的成本**趨近於零**：不需新增任何資料採集。
- 其價值高於單一動作的折線圖：後者只是一個動作的重量變化，
  前者是**整個人的成長軌跡**（「胸從 3 月的 C 級長到 8 月的 B+，腿一直卡在 C」）。
- **六維能力值為本平台的核心資產，而時間維度是它唯一尚未被使用的面向。**

##### 月報的內容含 AI 訓練分析

**月報 ＝ 數值回顧 ＋ AI 產出的文字分析。**

原「AI 訓練分析報告」候選權益即為本項的內容來源，**兩者為同一件事，不分列**。

| 只有數值 | 加上 AI 分析 |
|---------|-------------|
| 本月訓練 12 次、完成率 68%、胸 +15 點 | 「你這個月訓練頻率穩定，但完成率比上月低 12% —— 多數未完成集中在腿部訓練的後段」 |

**可呈現的維度只有兩個**（與教官申請的 AI 品質評分共用維度定義，但用途不同）：

| 維度 | 可否呈現 | 理由 |
|------|---------|------|
| 訓練完成率 | ✅ | 有用的自我回顧 |
| 訓練規律性 | ✅ | 同上 |
| **紀錄合理性** | ❌ | 其為抓造假的指標；承既有裁決「揭露給申請者等同公開防作弊判準」，且對誠實使用者顯示「可疑度」有害 |

- 成本為**每月每位會員一次 LLM 呼叫**，屬可預期的固定成本（會員數 × 1），
  不同於主動調整會被重度使用者拉高。
- 本項**不扣 AI 點數**：其為系統發起的權益內容，承02_Aggregate定義.md〈AI 功能的付費邊界〉的
  「使用者主動發起者扣點、系統發起者不扣」判準。

##### 兩個不採方案

- **不採「免費只看最近 3 個月的圖表」**：其擋住的是**使用者自己的資料** ——
  半年前的訓練是他做的，看不到會產生被扣住的感覺；
  且須推翻既有規則「訓練歷史的可回溯時間範圍不設限」。
- **不採「折線圖改為會員專屬」**：折線圖與回溯範圍為同一份資料的兩種呈現，
  一個開放一個收費，判準自相矛盾。

- 動作趨勢檢視的預設排序為**累積練習次數由多到少**（最常練的在前）。
- 不採「依最近一次練到的時間排序」：健身多為分部位循環（昨天練腿、今天練胸），
  最近練到的動作恰為今天不會練的，排在最前反而擋路。
- 採累積次數排序的另一理由：主力動作長期固定，順序不隨每日訓練變動，使用者記得住位置。
- 兩種檢視共用同一份訓練紀錄資料，僅多一個查詢維度。
- 訓練紀錄於結算後凍結，訓練歷史為唯讀。
- 回溯範圍不設限：訓練紀錄本已永久保存，設限不省儲存成本，只增加規則。
- **不以會員身分限制回溯範圍**：訓練紀錄為使用者自身產生的資料，以會員身分限制其存取，
  性質為「贖回」而非「擴張」，與模型既有的付費牆（自訂訓練額度、進階訓練計畫）性質不同。
  且該限制只擋得到已累積 3 個月以上歷史者 —— 恰為留存最久的一群，對新使用者零轉換貢獻。
- 提供搜尋的理由：累積次數排序只保證主力動作在前段，而使用者最需要查的常是久未練的動作
  （正因久未練才記不得上次的重量），該類動作恰好排在最後。
- 含折線圖的理由：動作趨勢回答的是「該不該加重」，重量對時間的走勢以列表呈現須由使用者自行連線。
  與〈Read Model：六維能力值雷達圖〉職責不重疊（後者呈現六維能力值，非單一動作的重量走勢）。

「訓練歷史的**跨時間彙總**（能力值歷史變化圖、期間比較、月報）」。

| 項目 | 開放對象 |
|------|---------|

**規則**

- 提供「一鍵領取全部」：可領取者逐筆各產生一次「使用者已領取成就獎勵」，比照獎勵信箱的既有處理。
- **納入「距下一門檻所需」**：9 類中有 7 類為累積次數型門檻，
  僅顯示已解鎖／未解鎖時，使用者看到的是一排灰色圖示，不知道哪一枚將達成；
  承能力值小節點「使每次訓練都看得到還差多少」的既有設計意圖。
  該欄位為衍生值，門檻與當前計數本即存在，僅相減。
- **不併入〈使用者個人檔案頁〉**：該頁同時供他人檢視（既有兩個對外可見開關），
  而領取為本人專屬操作；併入將產生「他人看得到我有沒有領獎」的非必要問題。
- 已解鎖紀錄為單調遞增、一經解鎖不可撤銷（承既有原則），故本頁不呈現「已失效」狀態。
- 本頁為成就獎勵的唯一領取入口，承〈成就獎勵的領取與發放〉「採點擊領取但不進信箱，
  因成就頁永久保留」的既有裁決。

#### 一鍵全部領取為必要功能

**獎勵信箱已定案不設有效期限、不設容量上限、無逾期清除機制**
（見02_Aggregate定義.md〈獎勵信箱 Aggregate〉），故信箱會**無上限累積**。

- 完全不領取者一年約累積 500 筆。逐筆點擊 500 次不是設計，是懲罰。
- 每日任務未領取者**每日補一筆**：出國一週回來即有 7 筆待領。
- 信箱的立案理由本即為「未領取不作廢，不因忘記點擊而失去已掙得的獎勵」；
  逐筆點擊等同把該成本又還給使用者。

#### 不設到期倒數

**信箱獎勵沒有期限**，設倒數欄位會暗示一個不存在的規則，反而製造焦慮。
「未領取筆數」佔用該位置，回答的是「我還有多少沒領」這個真實問題。

#### 兩項不納入的資訊

- **不放已領取的歷史紀錄**：領取後即結束，回顧價值低；
  金幣進出的查詢屬虛擬貨幣的帳務範疇，非本頁職責。
- **不依來源分頁**：來源僅四類、單一使用者的待領筆數量級有限，
  分頁是為數百筆的清單而設。

##### 綜合能力等級另設獨立開關

**兩個開關各自獨立，可自由組合。**

| 六維 | 綜合 | 效果 |
|------|------|------|
| 開 | 開 | 全部可見（預設） |
| **關** | **開** | **只露出整體評價，隱藏各部位細節** ← 本次新增所支援的情境 |
| 開 | 關 | 見下方說明（實質無效） |
| 關 | 關 | 完全不對外呈現能力值 |

- **支援的核心情境**：使用者可能願意讓人知道自己「整體 B 級」，
  但不想被看出「腿特別弱」——兩者為不同的隱私顧慮，應可分別控制。
- **「六維開、綜合關」實質無效**：綜合等級為六維點數的算術平均，
  六維既已可見，任何人皆可自行算出綜合等級。
  本組合允許設定但不另設限制，亦不視為缺陷。
- 兩個開關皆**不影響任何規則判定**，僅影響他人檢視時的呈現。
- 本設定僅作用於**他人檢視**；本人檢視自己的檔案與雷達圖不受影響。
- **教官身分者的例外同時適用於兩個開關**：教官的六維能力值與綜合能力等級
  皆強制對外可見、不可隱藏。理由與既有裁決相同 ——
  申請成為教官為主動行為，附帶的義務即為讓學徒能判斷其實力；
  若可隱藏，〈Read Model：教官清單〉的核心欄位將出現空值。
  教官資格撤銷後兩個例外一併解除。

- 預設為可見：能力值對外呈現正是「關注」與「申請師徒關係」兩個 Command 的判斷依據，
  預設隱藏會使該區塊形同不存在。
- 本設定僅作用於**他人檢視**；本人檢視自己的檔案與雷達圖不受影響。
- 本設定不影響任何規則判定，僅影響呈現。

**與既有裁決的關係**：既有規則「已讀回條本階段不可關閉，使用者 Aggregate
不新增**相關**隱私設定欄位」之範圍限於已讀回條，本欄位不在其範圍內，兩者並存。

#### 不採的方案

- 不採「一律不顯示能力值」：階級來自經驗值，簽到亦可累積，
  一位鮮少訓練者的階級同樣可以很高；缺少能力值時「申請拜師」無判斷依據。
- 不採「依關注關係分級（關注後才可見）」：多數使用者正是看了能力值才決定要不要關注，
  該設計顛倒因果。

**教官身分者為例外：六維能力值強制對外可見，不可隱藏。**

- 「六維能力值對外可見」欄位對教官身分旗標為真者不生效。
- 理由：申請成為教官為主動行為，附帶的義務即為讓學徒能判斷其實力；
  若可隱藏，〈Read Model：教官清單〉的核心欄位將出現空值，學徒無從選擇。
- 教官資格撤銷後該例外解除，回歸使用者自身的可見性設定。

#### 新手期的觀感問題：不做緩解機制（2026-08-11 定案）

**新手看到他人 S 級而自身為 E 級的落差，不另設任何緩解機制。**

- **第十輪的錨點下調已實質改善此問題**：03_能力值.md〈錨點分佈〉定案後，
  E 級只涵蓋**完全未訓練者**，練 1–2 個月即進入 D 級 ——
  新手停留在 E 級的時間由原本的數個月縮短至約 1–2 個月。
- **任何緩解機制都會與既有裁決相衝**：模型已明文
  「能力值對外呈現**正是**『關注』與『申請師徒關係』兩個 Command 的判斷依據」、
  「預設隱藏會使該區塊形同不存在」、「多數使用者正是看了能力值才決定要不要關注」。
  隱藏他人等級或分級展示，等於把該區塊的存在理由拿掉。
- **承既有立場**：否決「相對百分位」時已確立「能力值代表**身體能力**，
  不因他人而變動」—— 看到強者是事實，而非需要被修飾的呈現問題。
- **回饋密度已由 18 個小節點承擔**：小節點的設計用意即為
  「提供高頻的進度回饋」，新手期平均每 2–3 週即有一次節點變化，
  該機制處理的正是「自己有沒有在進步」，而非「跟別人比如何」。
- **不採「新手期前 30 天不顯示他人等級」**：其會使新使用者在最需要判斷
  「該關注誰、該向誰拜師」的時期反而看不到判斷依據。
- **不採「只顯示等級、不顯示點數」**：等級本即為離散六階，
  隱藏點數並不降低比較的強度（E 對 S 的落差在等級上更醒目），
  卻使使用者看不到自己距下一階還差多少。

| 項目 | 內容 |

| 服務的 Actor | 使用者 |

**每筆訂單的欄位**

| 欄位 | 型別 | 說明 |
|------|------|------|
| 商品名稱與規格、數量、金額、下單日期 | — | — |
| 類型 | 列舉 | 實體 / 虛擬 |
| 狀態 | 列舉 | 實體：待付款 / 已付款 / 已出貨 / 已取消 / 已失敗 / 已退款<br>虛擬：待付款 / 已付款 / 已發放 / 已取消 / 已失敗 |
| **支付明細** | — | **金幣扣除數 ＋ 法幣支付額分列**；併用支付者兩者皆有值 |
| **失敗原因** | 列舉 / 空值 | 狀態為已失敗時有值：餘額不足 / 商品售完 / 其他 |
| **取消入口** | 動作 / 停用 | 僅狀態為待付款時可用；其餘狀態明示不可取消 |

#### 支付明細須拆分呈現

模型有**併用支付**（虛擬貨幣不足時以現金補差額），且**訂單成立時鎖定當時比率**，
其後比率變動不影響該筆訂單。

- 僅顯示總額者，使用者數月後無從對照當時扣了多少金幣、補了多少現金 ——
  而那正是爭議發生時他要查的資料。
- 金幣對法幣比率已定案為 **1 元 ＝ 5 金幣**（2026-08-08；本行原記「暫定 1:1」，2026-08-20 訂正），
  但**拆分呈現與比率數值無關**，不受其阻擋。

#### 失敗原因為必要欄位

「購買已失敗」攜帶失敗原因（餘額不足 / 商品售完 / 其他），
「商品發放已失敗」亦攜帶失敗原因與已重試次數。
不呈現則使用者只看到一筆「已失敗」，**不知道錢有沒有被扣**。

#### 取消的可用條件須明示

**僅「待付款」可取消。** 終止狀態（已出貨 / 已發放 / 已取消 / 已失敗 / 已退款）皆不可。
不明示則使用者將反覆尋找取消入口。

另有一條系統發起的取消路徑：**「訂單已因商品下架取消」**，
其為系統行為，狀態同樣轉為已取消，於本頁呈現時應可與使用者自行取消區別。

#### 兩項不納入的資訊

- **不放物流追蹤**：模型明訂「實體訂單的終止狀態為已出貨，
  出貨後的物流留在系統邊界之外，無『已送達』狀態」。
  提供追蹤等同承諾一個模型中不存在的能力。
- **不另立「退款進度」欄位**：退款為管理員發起的 Command，
  模型中**只有終止狀態「已退款」，無任何中間進度狀態**，
  該資訊已由「狀態」欄位涵蓋。
  （虛擬商品另有既有裁決「發放失敗不自動退款，改為重試 3 次」。）

| 審核時限倒數 | int（小時） | 管理員的審核時限為 72 小時 |

#### 三個欄位各自對應一個缺口

- **處罰原因與依據**：無此欄位則申訴為盲寫 ——
  使用者不知自己因哪則內容被罰，寫出的申訴管理員亦無從審理。**本頁最核心的一欄。**
- **累計違規次數與下一級後果**：處罰為**階梯制**（1–2 警告 / 3–4 停權 7 天 /
  5–6 停權 30 天 / 7 起永久停權），而使用者看不到自己在第幾階。
  「你目前 4 次，再 1 次將停權 30 天」方有嚇阻效果；
  僅顯示「你被停權 7 天」則完全看不出下一步的嚴重性。
  **這是階梯制唯一能發揮作用的地方。**
- **兩個倒數皆須呈現**：申訴期限 30 天（逾期即永遠不能申訴）與
  審核時限 72 小時（第七輪所定，逾期僅產生 Event 與提示、不改變案件狀態）。
  無倒數則兩個時限對使用者而言等同不存在。

#### 不揭露檢舉人

**任何情況下不呈現檢舉者的身分。**

- 揭露檢舉人等同把檢舉機制變成報復名單，其後無人敢檢舉。
- 承模型同類的既有處理：教官不得檢視個別學徒的評分、
  AI 訓練品質評分的「紀錄合理性」維度不揭露給申請者。

#### 不呈現完整處罰歷史

累計違規次數已涵蓋使用者需要知道的部分；
逐筆列出歷史處罰的細節對「要不要申訴當前這筆」沒有幫助。

#### 權益須對照使用者自身的數字呈現

**乾巴巴列出五項權益，說服力遠低於指著他自己的數字。**

- 「無限自訂訓練」→「你目前 2 / 2，已滿」
- 「每月 20 點 AI 點數」→「你這個月用了 5 次，花了 500 金幣」

**能力值歷史那一項尤其有效**：〈能力值日快照〉每日產生，
**資料早已存在卻從未呈現給使用者** ——
「你有 89 天的成長軌跡等著」遠強於「提供歷史圖表」。

#### 狀態與到期日為必要欄位

模型設立「**已取消待到期**」狀態的理由即為
「若無此狀態，已取消者與正常訂閱者的狀態完全相同，
使用者無從得知自己還剩幾天，客服亦查不出其是否已取消」。
**無此欄位則該狀態白設。**

#### 不呈現訂閱歷史紀錄

查閱帳單為 App Store 的職責，模型亦明訂扣款與寬限期留在系統邊界之外。
自行維護一份訂閱歷史，與 App Store 對不上時反成客服負擔。

- 我的狀態三項為必要欄位：申請加入有三個會擋住的前置條件

團隊有兩條加入路徑，**主要動線為隊長邀請**（認識的對象），公開招募申請為次要路徑。

| 路徑 | 對象 | 對應 Read Model |
|------|------|----------------|
| 隊長邀請 | 認識的人 | 我的團隊頁 |
| 公開招募申請 | 不認識的人 | 團隊搜尋 |

兩者的決策內容不同：前者是「管理自己的隊」，後者是「找一支隊加入」。
合為單一 Read Model 會使欄位表同時服務兩種互不相干的決策。

| **本週評分狀態** | bool | 本週是否已評分，取自師徒關係的「最近一次評分所屬週」 |
| **本週評分剩餘天數** | int | 距週一重置尚餘幾天 |

#### 本週互動摘要的必要性

**每週互動評分的換算為 −2／0／+4／+8／+12，幅度大且直接連動教官聲望。**
學徒若只看到一顆評分按鈕，他評的是最近一次對話的心情，而非這一週。

- 摘要使評分**從憑印象變成看著紀錄**。
- 模型已定「問答不評分」（移除「學徒已評分該次問答」，理由為逐次評分尺度過敏感、
  評分者多為兩端情緒樣本）。**每週評分是問答品質唯一的承接處**，
  無摘要即無依據，等同讓每週評分退化回同一個毛病。
- 提問次數為可數值：其數的是「學徒已提問」Event 的發生次數，**不含閒聊** ——
  承既有裁決「提問為獨立 Command，單一入口兩種動作：直接打字為閒聊、點提問才產生問答」。

#### 評分剩餘天數為必要欄位

評分窗口為每週一重置，錯過即該週無法補評。
而第八輪第 17 題已定**每週評分提示歸 App 內通知類、不推播**，
該裁決的前提正是「使用者打開本頁即看得到」。**無此欄位則該裁決落空。**

#### 兩項不納入的資訊

- **不放教官的聲望與帶徒人數**：學徒已完成拜師，聲望為**選教官時**的決策資訊，
  屬〈Read Model：教官清單〉。置於此處會使評分變成「我要不要維護他的分數」，
  而非「他這週幫了我多少」。
- **不放歷史評分紀錄**：看到自己上週給 +8，本週便傾向續給 +8 ——
  錨定效應將使評分失去鑑別力，而聲望系統正是靠鑑別力運作。

- 六維能力值為指派任務的依據：無此資訊時，教官只能依學徒口述判斷該練哪裡。
- 近期訓練摘要的必要性：能力值為長期累積的結果，反映不出「這禮拜有沒有在練」；
  教官判斷該不該催、任務給多重，需要近期出勤與完成度。

#### 評分對教官的揭露界線

**教官看不到任何個別學徒給的評分，只看得到全體的總平均，且帶徒數 ≥ 3 人時才呈現。**

- **不揭露個別評分**：教官手上有指派任務、回答與解除關係三種工具，
  知道誰給低分即可報復；學徒預期到這件事就會給高分自保，
  **聲望將退化為帶徒時長的函數而非指導品質的函數**，整套聲望設計失效。
- **總平均設 3 人門檻**：人數過少時平均值等同於個別評分，門檻無意義。
- 本規則與02_Aggregate定義.md〈初始帶徒上限為何是 2 人〉配套 ——
  該處處理的是**聲望變動量可被減法還原**的洩漏，本處處理的是**畫面直接揭露**。
  兩者缺一則匿名性皆不成立。

#### 本週已計分次數為必要欄位

模型既有規則：**每位學徒每週最多 2 次任務評分計入聲望**（防「狂指派刷聲望」的合謀漏洞）。

- 不呈現則該規則成為隱形規則：教官指派了第 3 個任務、學徒也完成並評分，
  聲望卻未變動，他不會知道是上限擋住，只會認為系統故障。
- **本規則需要被看見才有嚇阻效果**：意圖合謀刷聲望者看到「本週 2/2」即知刷不動，
  較之默默不計分更有效。

#### 不呈現「該學徒本週是否已評分我」

理由與〈Read Model：我的師徒頁〉不放歷史評分同型：
呈現此欄等同把「去催學徒評分」變成一個可執行的動作，
而每週互動評分的意義在於它是**學徒自發的評價**；教官一催，該分數即不再是指導品質的訊號。

#### 近期訓練摘要對教官揭露的界線

**僅摘要層（日期、課表名稱、完成度），不含逐組重量與次數。**

- 承既有裁決〈訓練歷史不對外可見〉：該裁決的標的為**逐組重量與次數的原始紀錄**，
  且明文「不提供開關」。摘要層不在其標的範圍內。
- 摘要層可對教官揭露的理由：師徒關係為雙方同意建立的關係，
  與陌生人瀏覽個人檔案頁的情境不同。
- **不採呈現完整訓練歷史**：該做法等同為教官開一個既有裁決明文排除的例外。

#### 兩個欄位的取捨（2026-08-11 定案）

| 欄位 | 是否納入 |
|------|---------|
| ① 本週是否已被該學徒評分（每週互動評分） | **❌ 不納入** |
| ② 該學徒本週已計分的任務評分次數（0 / 1 / 2） | **✅ 納入** |

**兩者分屬不同性質，各自的既有理由皆成立且不互相衝突，故分別處理。**

**② 納入**：承〈本週已計分次數為必要欄位〉的既有論證 ——
每位學徒每週最多 2 次任務評分計入聲望（防「狂指派刷聲望」的合謀漏洞）；
不呈現則該規則成為隱形規則，教官只會認為系統故障。
且**本規則需要被看見才有嚇阻效果**：意圖合謀者看到「本週 2/2」即知刷不動。

**① 不納入**：承〈不呈現「該學徒本週是否已評分我」〉的既有論證 ——
呈現此欄等同把「去催學徒評分」變成一個可執行的動作，
而每週互動評分的意義在於它是**學徒自發的評價**；教官一催，
該分數即不再是指導品質的訊號。

- 兩者雖同源於02_Aggregate定義.md〈教官聲望 Aggregate〉的每週計分機制，
  但 ② 的作用是**讓防刷規則可被理解**，① 的作用是**讓教官知道誰還沒評分** ——
  前者服務規則的可驗收性，後者製造出一個不該存在的催促動作。
- ② 的呈現不洩漏任何個別評分內容（只顯示次數，不顯示星等），
  與〈評分對教官的揭露界線〉「教官看不到任何個別學徒給的評分」不衝突。

*來源：`.es-clarify/resolved/read-model/師徒互動頁_教官回答與指派任務前需看到哪些資訊.md`（選項 C）*

#### 分頁結構：六個肌群 ＋ 有氧 ＋ 我的動作

**有氧與自建動作各自獨立分頁，皆不混入肌群分頁。**

**有氧獨立分頁的理由**

- 有氧動作的**所屬肌群已定案為空值**（理由為有氧不進六維能力值），
  六個肌群分頁在資料上就容納不了它。
- **不採「依主要訓練部位歸入肌群分頁」**：該做法須為有氧動作補上一個肌群值，
  使「所屬肌群」欄位同時承載兩件事 —— **能力值歸屬**與**分頁歸屬**。
  一個欄位兩種語意，日後必然衝突。

**自建動作獨立分頁的理由**

1. **自建動作不計入能力值**（既有規則）。混入肌群分頁後，
   使用者會合理預期「我練了胸的動作，胸應該會漲」，而實際不會 ——
   分頁分開即消除該預期落差，與既有的「本動作不計入能力值」標示互為表裡。
2. **自建動作僅建立者本人可見**。混排將使同一個分頁對每位使用者長得不一樣。
3. 使用者需要**管理**自己建立的動作（找出來、看有哪些），獨立分頁本即為必要入口。

- **不採「自建動作不進動作庫」**：使用者將無任何地方可回顧自己建立過什麼。
- 有氧動作的每分鐘訓練量係數仍待
  `rule/個人排行榜分數已增加_各來源的分數值與換算率為何.md` 定案，
  但**分頁歸屬與係數無關**，不受其阻擋。

**每份課表的欄位**

| 欄位 | 型別 | 說明 |
|------|------|------|
| 名稱與動作數 | 字串 ＋ int | — |
| 狀態 | 列舉 | 已儲存 / 已發布 / 已申請公開 / 已公開 |
| **我的使用次數** | int | **本人**以該課表訓練的次數，取自訓練紀錄的課表 ID |
| 對關注者可見 | bool | 僅狀態為已發布 / 已申請公開 / 已公開 時可操作 |
| 審核狀態 | 列舉 / 空值 | **僅曾送審者有值**：審核中（剩 N 天）／ 已通過 ／ 未通過 |
| 駁回理由 | 字串 / 空值 | 「公開訓練審核未通過」時呈現 |

#### 逐狀態的呈現與可用動作

| 狀態 | 可用動作 | 條件式欄位 |
|------|---------|-----------|
| 已儲存 | 發布、修改、刪除 | — |
| 已發布 | 取消發布、申請公開、修改、刪除 | 對關注者可見開關 |
| 已申請公開 | 修改、刪除 | 對關注者可見開關；**審核中，剩 N 天** |
| 已公開 | 下架、修改（觸發重新審核）、刪除 | 審核狀態；**對關注者可見開關不生效**（全平台已涵蓋關注者） |
| 審核未通過 | 退回已發布 | **駁回理由** |

- **草稿不列於本頁**：其語意為「設計中，尚未儲存」，未存檔者不應出現於管理清單。
- **已刪除為終止狀態**，不再出現於本頁。

#### 三個欄位各自對應一個 Command 的缺口

- **名額使用量**：「刪除自訂訓練」已定案為釋放名額的唯一手段（第八輪第 13 題），
  使用者須先知道自己用了幾個才決定該不該刪，否則刪除為盲操作。
  且名額已滿時 AI 調整改走快照，使用者更需知道原因。
- **審核狀態與駁回理由**：模型有「公開訓練審核未通過」Event，審核時限為 14 天。
  無此欄位則送審後進入黑洞，亦不知為何被退、該改什麼再送。
- **對關注者可見開關**：其為獨立於狀態的正交欄位，
  **本頁為模型中唯一可操作它的位置**。

#### 使用次數採「我自己用了幾次」而非「被他人採用幾次」

- 本欄回答的是「這份課表我還在用嗎」，**正是決定該不該刪除以釋放名額的依據**，
  與本頁的管理職責一致；資料取自訓練紀錄既有的課表 ID，為現成資料。
- **不採「被他人採用次數」**：其為社群虛榮指標，會使管理頁變成排行榜；
  且模型中無任何地方記錄公開課表被誰採用，須新增一整套跨使用者統計。

#### 自訂訓練的涵蓋狀態

**三個狀態皆呈現：已發布、已申請公開、已公開。** 判準為「該狀態下自己可否選用」。

- **不可只取「已發布」**：狀態機的路徑為 `已發布 → 已申請公開 → 已公開`，
  使用者將課表送審並通過後，它即**不再是已發布狀態** ——
  只取已發布會使**他自己公開出去的課表從他自己的課表選擇頁消失**。
  公開給全平台使用的東西，作者反而不能用，顯然不成立。
- **不涵蓋「已儲存」**：其語意即為**未啟用、不可選用於訓練**（第六輪第 6 題所定）。
- **不採「呈現已儲存但標示為不可選」**：等同在選課表的頁面塞進一批選不了的項目；
  啟用的入口為〈Read Model：自訂訓練管理頁〉的「發布」動作，屬該頁的職責。
- **不涵蓋「草稿」**：其尚未存檔。
- 本節處理的是**使用者自己的**自訂訓練。他人的「已公開」課表屬另一個來源，
  與本項不混用。

#### 未解鎖進階計畫的呈現

**未解鎖的進階訓練計畫一併呈現，不隱藏**，並標示其三種解鎖方式的當前狀態：

| 解鎖方式 | 呈現內容 |
|----------|----------|
| 階級達標 | 尚差幾階解鎖 |
| 金幣提前購買 | 該計畫的解鎖金幣價格；解鎖金幣價格為空值者不呈現此項 |
| 會員身分 | 標示「會員可用」 |

- 未解鎖計畫為三種解鎖方式的**唯一曝光點**：使用者若看不到有哪些計畫可解，
  金幣購買與會員解鎖兩條路徑等同不存在。
- 空白課表恆為已解鎖，且必須呈現 —— 承既有裁決「自由訓練以空白課表為入口、課表為必填」，
  本頁若無空白課表，自由訓練無入口。

#### 公開課表的來源免責標示

**已公開的自訂訓練須標示「本課表由使用者提供，平台不對其安全性負責」。**

- **理由為平台自己製造的背書問題**：`管理員已審核公開訓練` 這個 Event 的存在，
  使使用者合理認為「平台看過了、應該安全」。不標示等於在課表這條路徑上再擔保一次。
- 承既有立場「我們不能為教官擔保他有這個能力」（第六輪第 14 題排除具執照門檻的專長值域）。
- 官方訓練計畫與空白課表**不標示**：前者為平台自製內容，後者無內容。
- 未公開的自訂訓練（已發布、僅自己或關注者可用）同樣標示 ——
  對關注者可見者亦為一位使用者的內容被另一位使用者採用。

#### AI 自動優化建議的呈現

**本頁為自動優化建議的唯一呈現點。** AI 於背景產出「AI 已優化訓練強度」後，
該課表旁標示「有新的優化建議」，使用者於此接受或拒絕。

- **不另發通知、不彈出對話框**：理由見〈AI 自動優化訓練流程〉。
- **常駐標記**，未處理前一直存在，不會因未讀而消失。
- **同一課表範本同時只保留最新一份建議，後者覆蓋前者**；建議不設有效期限。
- 本頁因此支撐「確認使用新訓練強度」與「拒絕調整」兩個 Command ——
  該兩 Event 原本在模型中**無任何觸發時機**，自動優化流程實質走不完。
- 僅會員可能出現本標記（自動優化為會員專屬權益）。

- 「上次訓練日期 ＋ 上次完成度」為選課表的實際決策依據（我上次練這套是什麼時候、練得如何），
  優先於課表內容摘要。
- **不採**依註冊時推薦 Policy 標示「推薦給你」：該 Policy 依註冊當下的健身經驗、目標、器材判定，
  使用者訓練數月後該標記多半過時，反而誤導。如需推薦，應另立依現況重算者，非本 Read Model 範圍。

*來源：`.es-clarify/resolved/read-model/課表選擇頁_選擇訓練課表前需看到哪些資訊.md`（選項 B ＋ 上次訓練日期與上次完成度）*

#### 動作已被替換的標示

**標示該動作已被 AI 替換，並可展開檢視原動作。**

- **使用者需要知道眼前的課表與他所選的那份不同**：他選的是胸推日，
  第一個動作卻變成啞鈴臥推 —— 無標示則他會以為自己選錯課表或懷疑系統出錯。
- **原動作必須可見**：那是他判斷「這個替換合不合理」的唯一依據。
  僅標示「已替換」而不給原動作反而更令人困惑；且「AI 已替換動作」Event
  本即攜帶原動作 ID，為現成資料。
- **本標示處即為「還原被替換的動作」的入口**，規則見〈訓練紀錄流程〉之還原路徑。
- 本欄位同時服務**申訴舉證**與 **AI 品質分析** ——
  承 Event 攜帶兩個動作 ID 時所寫的原始理由。
| 已完成組數 / 總計畫組數 | int / int | 來自訓練進度條 |
| 進度百分比 | 百分比 | 已完成組數 ÷ 總計畫組數，與上一欄同時呈現 |
| 本次累計訓練量 | int（kg） | 本次訓練已完成各組的訓練量總和 |
| 訓練時長 | 衍生值 | 現在時戳 − 開始時戳，含組間休息 |
| 該動作上次的實際重量與次數 | 重量 / int | 來源為訓練紀錄 Aggregate 的歷史資料，供加重決策 |
| 組間休息剩餘秒數 | int | **僅於組間休息期間有值**，見下方〈組間休息倒數的呈現時機〉 |
| 防作弊剩餘阻擋秒數 | int | 僅於 30 秒阻擋生效期間有值，見02_Aggregate定義.md〈防作弊：連續快速勾選的阻擋〉 |

- 「該動作上次的實際重量與次數」為本 Read Model 與〈Read Model：訓練歷史〉的重疊處，
  兩者不合併：訓練歷史服務的是**訓練前**選課表的決策，本欄服務的是**訓練中**每一組的加重決策，
  取數範圍僅限當下這一個動作的最近一次。
- 進度百分比與已完成 / 總計畫組數並存，不擇一：分數提供絕對量（還剩幾組），百分比提供相對量。
- 總計畫組數為 0（空白課表）時進度條不成立，本 Read Model 的前兩欄與百分比一併不呈現。
- 進度百分比不要求單調遞增（承02_Aggregate定義.md〈訓練進度條 Aggregate〉，AI 調整可使分母變動而下降）。

#### 組間休息倒數的呈現時機

組間休息倒數**不常駐於訓練進行中頁**，而是於「組間休息已開始」後獨立呈現、
於「組間休息已結束」後消失。使用者可於倒數期間下達 Command「結束組間休息」（跳過）。

- 承02_Aggregate定義.md〈組間休息秒數的取值優先序〉：初始秒數依課表 → 動作預設 → 全站預設 90 秒取值。
- 承既有裁決：跳過即觸發「組間休息已結束」，該 Event 為多對一（計時結束由系統觸發、跳過由使用者觸發）。

#### 防作弊剩餘阻擋秒數納入的理由

02_Aggregate定義.md〈防作弊：連續快速勾選的阻擋〉為 Precondition 層的阻擋，若不呈現剩餘秒數，
使用者下達 Command「完成該組」時只會得到無回應，無從得知何時可再試。
