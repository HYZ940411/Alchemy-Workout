# 釐清問題

樣板要求 Given / When 的名詞後面帶「Actor 或 Aggregate 的識別碼」，這個識別碼在句子裡要寫成什麼形狀——括號、佔位符號，還是具名變數？

# 定位

翻譯單元：全部 318 個翻譯單元（每一句 Given / When 都會用到）。
Gherkin 位置：Given / When 句子中，每一個 Actor 與 Aggregate 名詞後面的識別碼寫法。
對應樣板空格：樣板中「（含 Actor 的 Key）」與「括號中的 Key 代表 Actor / Aggregate 的識別碼」這一條。
相關既有共識：`00_全域規範.md`〈Event 共通攜帶資訊〉（共通 5 欄位含「觸發 Actor」與「關聯 Aggregate ID」）、
`.es-clarify/resolved/command/Actor_模型中各角色名稱的定義與統一.md`（Actor 五種，管理員的識別碼即管理員 ID）。

# 白話說明

翻譯樣板有一句「括號中的 Key 代表 Actor / Aggregate 的識別碼」，但沒說括號裡要放什麼字。
這是全模型每一句都會遇到的寫法問題，四種寫法差很多：

選 A（中文括號 ＋ 有意義的短代號）：

```gherkin
  Given 使用者（U001）持有 1 張補簽券
  And   使用者（U001）於 2026-08-20 未簽到
  When  使用者（U001）使用補簽券回補 2026-08-20
```

選 B（`<角括號>` 佔位符，Scenario Outline 風格）：

```gherkin
  Given 使用者（<使用者ID>）持有 1 張補簽券
  When  使用者（<使用者ID>）使用補簽券回補 <補簽日期>
```

選 C（不寫識別碼，靠代名詞區分）：

```gherkin
  Given 使用者持有 1 張補簽券
  When  該使用者使用補簽券回補 2026-08-20
```

選 D（識別碼寫成具名角色）：

```gherkin
  Given 使用者「小明」持有 1 張補簽券
  When  使用者「小明」使用補簽券回補 2026-08-20
```

識別碼真正發揮作用的是**多人情境**——師徒（師父與徒弟）、團隊（隊長與成員）、
關注（關注者與被關注者）、私訊（發送者與接收者）。這些流程裡若不標識別碼，
「使用者」到底是哪一個會分不清。

# 多選題

| 選項 | 描述 | 推薦 |
|------|------|------|
| A | 中文全形括號 ＋ 短代號，代號取自角色語意（`U001`、`T001`、`M001`）；單人情境也照寫 | ★ |
| B | 一律用 `<佔位符>`，實際值一律放 Examples 表 |  |
| C | 單人情境省略識別碼，只有多人情境才寫 |  |
| D | 用具名角色（「小明」「教官阿華」）取代代號 |  |
| Short | 提供其他簡短答案（<=5 字） |  |

# 推薦選項與理由

**推薦 A（中文括號 ＋ 短代號，單人情境也照寫）。**

理由一（樣板本身就是這樣寫的）：翻譯樣板在 Query 與 Command 兩個分支的每一格都標了
「（含 Actor 的 Key）」，且決議 2 特別強調「權限驗證的 Given **沿用原始完整樣板，不簡化**」。
選 C 的「單人情境省略」正是一種簡化，與決議 2 的方向相反；
而且「哪些算單人情境」又是一個需要逐案判斷的主觀決定。

理由二（模型的 Event 共通欄位支持，已查證）：
`00_全域規範.md`〈Event 共通攜帶資訊〉規定每一個 Event 都必帶
「觸發 Actor（Actor 識別碼）」與「關聯 Aggregate ID」——
也就是說模型層面**每一個事實都已經綁定識別碼**，句子裡照寫是忠實反映，省略才是資訊遺失。

理由三（不與決議 6 打架）：選 B 把識別碼一律寫成 `<佔位符>`，
會使**每一個** Scenario 都被迫變成 `Scenario Outline` ＋ `Examples`，
即使該情境只有一組資料。決議 6 的條件是「邏輯完全相同、只有輸入資料不同」才用 Outline，
選 B 等於架空這個判準。採 A 之後，需要 Outline 的地方仍可把 `U001` 換成 `<使用者ID>`，
兩者不衝突。

不推薦 D：具名角色在多人情境確實好讀，但需要為每個 Scenario 想名字（318 檔 × 多個角色），
且名字本身沒有型別資訊——看到「阿華」不知道是使用者還是教官；
選 A 的 `U001` / `M001` 前綴自帶型別。

**尚待決定的細節（屬同一題，不另立項目）**：若採 A，
gh-formulation 階段須一併確認 (1) 前綴字母表（使用者 U、管理員 M、團隊 T、貼文 P…），
(2) 括號用全形「（）」還是半形「()」。建議前綴表隨各批次翻譯逐步補齊，不預先窮舉 65 個 Aggregate。

# 補充查證（回答使用者「這是 Gherkin 的正確寫法嗎」）

- **語法層合法**：`.feature` 檔的 step text 為自由文字，Gherkin 不解析其中的括號。
  step text 中唯一具特殊意義的符號是 `<...>`，且僅在 `Scenario Outline` 內由 `Examples` 代入。
- **陷阱在 step definition 層**：已查證 Cucumber 官方 Cucumber Expressions 文件，
  pattern 中 `(` `)` ＝ 選用文字、`{` `}` ＝ 參數型別、`/` ＝ 替代文字，字面值須以反斜線跳脫；
  文件明確指出這些符號只作用於 step definition，不作用於 feature 檔文字。
- **因此全形括號有技術理由**（非僅風格一致）：全形「（）」非 ASCII 分隔符，
  step definition 的 pattern 中不需跳脫；半形則需寫成跳脫形式。
- **未完全查證之處**：「全形括號不被視為分隔符」係由文件所列分隔符為 ASCII `(` 推得，
  非文件明文。已在規約中標記為〈待實作時驗證〉，撰寫第一支 step definition 時以測試確認。
