# 釐清問題

`Rule:` 後面那一行標題要怎麼寫——寫成固定的類別名（如「權限驗證」「業務規則驗證」），還是寫成該條規則的實際內容（如「補簽券張數不足時不得補簽」）？

# 定位

翻譯單元：全部 318 個翻譯單元。
Gherkin 位置：每一個 `Rule:` 區塊的標題行。
對應樣板空格：樣板中「Rule：前置條件（Precondition）」「Rule：後置條件（Postcondition）」那一行的實際寫法。
相關既有共識：無（屬 Gherkin 撰寫慣例，事件風暴階段未觸及）。

# 白話說明

翻譯樣板加上七項 SOP 補強決議之後，同一個 Command 底下會出現好幾個 `Rule` 區塊：
決議 1 要求失敗依原因分題（權限不足／輸入驗證錯誤／業務規則違反／併發衝突各自獨立成 Rule）、
決議 2 要求權限驗證獨立成一種 Rule、決議 3 要求 Actor 觸發與 Policy 觸發分成兩個 Rule。

於是同一個檔案裡可能有五、六個 `Rule:`，標題怎麼寫就決定了這個檔案好不好讀。

選 A（固定類別名）：

```gherkin
Feature: 使用補簽券

  Rule: 權限驗證
    Scenario: ...

  Rule: 輸入驗證
    Scenario: ...

  Rule: 業務規則驗證
    Scenario: 補簽券張數不足
    Scenario: 補簽日期超過回補範圍
    Scenario: 該日已簽到

  Rule: 後置條件
    Scenario: ...
```

選 B（寫實際規則內容）：

```gherkin
Feature: 使用補簽券

  Rule: 持有張數 ≥ 1 方可使用補簽券
    Scenario: ...

  Rule: 僅可回補最近 7 天內的未簽到日
    Scenario: ...

  Rule: 補簽當日計入累計簽到天數，比照真實簽到
    Scenario: ...
```

選 C（兩者都有：類別名 ＋ 冒號 ＋ 內容）：

```gherkin
  Rule: 業務規則驗證：持有張數 ≥ 1 方可使用補簽券
```

# 多選題

| 選項 | 描述 | 推薦 |
|------|------|------|
| A | 固定五種類別名：`權限驗證` / `輸入驗證` / `業務規則驗證` / `併發衝突` / `後置條件`，全模型一致 | ★ |
| B | 逐條寫該規則的實際內容，直接沿用模型 `[Rule]` 那一行的文字 |  |
| C | 類別名 ＋ 冒號 ＋ 實際內容，兩者並存 |  |
| Short | 提供其他簡短答案（<=5 字） |  |

# 推薦選項與理由

**推薦 A（固定類別名）。**

理由一（本專案樣板的骨架就是類別）：七項 SOP 補強決議中，決議 1 明文把失敗
「依失敗原因分題，各自獨立成 Rule（權限不足／輸入驗證錯誤／業務規則違反／併發衝突）」，
決議 2 明文要求「權限驗證獨立成一種 **Rule 類型**」。也就是說，本專案的 Rule
在設計上**本來就是類別**，不是單條規則。選 B 會使 Rule 的分組單位與決議 1、2 定義的分組單位不一致——
一個「業務規則違反」類底下若有 3 條規則，選 B 會被迫拆成 3 個 Rule，決議 1 的分類就消失了。

理由二（可機械翻譯）：選 A 的標題文字是從固定的五個字串裡挑一個，零撰寫成本；
選 B 每一個 Rule 都要人工寫一句話，318 個檔案乘上平均 4–5 個 Rule ≈ 1,400 句需要逐句撰寫，
且無法保證用語一致。

理由三（模型 `[Rule]` 那一行不適合當標題，已查證）：本模型的 `[Rule]` 行往往很長且帶引用，
例如 `補簽流程.md` 的
「Postcondition：補簽當日的簽到獎勵（經驗值 10 ＋ 金幣 10）照常發放，但**補發至獎勵信箱**，不直接入帳」，
以及 `訓練結算流程.md` 中含公式與 markdown 粗體標記的整段規則。
這些直接搬進 `Rule:` 標題會使檔案極難閱讀——而規則內容本來就會出現在
`Scenario` 標題與 `Given/Then` 句子裡，寫在 Rule 標題是重複。

不推薦 C：把類別與內容併在一行會使標題長度失控（見上述 `[Rule]` 實例），
且兩段資訊之間的分隔符又是一個要訂的慣例。

**補充**：選 A 的五個類別名中，「後置條件」與其餘四個不是同一維度
（前四個是失敗原因，第五個是成功路徑）。若採 A，建議在 gh-formulation 階段一併確認
成功路徑的 Rule 標題要寫「後置條件」還是「操作成功」——這屬同一題的後續細節，
不另立釐清項目。

# 各選項的翻譯後果

| 選項 | Feature 檔數 | Scenario 條數 | 維護成本 |
|------|-------------|--------------|----------|
| A | 318（不受本題影響） | 不受本題影響；Rule 區塊數 ≈ 每檔 2–5 個 | 最低。標題從固定清單選字 |
| B | 318（不受本題影響） | 不受本題影響；Rule 區塊數會膨脹（每條規則一個 Rule） | 最高。約 1,400 句需逐句撰寫，且與決議 1 的分類衝突 |

# 影響範圍

影響每一個 Feature File 的每一個 `Rule:` 標題行。
本題與 `.gh-clarify/organization/全域_Feature標題的寫法.md` 同屬命名慣例，宜一併定案。
本題定案後，各批次的 GH4（失敗分類）題目才能直接對應到 Rule 標題。

# 解決結果

**A** —— 固定五種類別名的封閉清單：
`權限驗證` / `輸入驗證` / `業務規則驗證` / `併發衝突` / `後置條件`。
成功路徑採 `後置條件`（與樣板字面一致），不寫 `操作成功`。
同一類別下有多條規則時併入同一 Rule 區塊、以多個 Scenario 呈現，不拆成多個 Rule。

# 連帶影響

- 各批次 GH4.1（本 Command 的失敗原因共有幾類）：答案直接對應到要建幾個 Rule 區塊，
  類別名不需再逐題確認。
- **本清單為封閉清單**：若個案掃描發現第五類失敗原因，不得自行新增類別名，
  須建立 GH4.1 釐清項目由裁決決定。
- 決議 3 的兩種觸發源分屬兩個 Rule 時，其標題寫法**未在本題定案**，
  留待 GH2 個案掃描（例如是否寫成 `Rule: 後置條件（Actor 觸發）`）。
