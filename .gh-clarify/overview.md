## 3.4 建議釐清順序

本輪 9 題全屬第一階段（全域翻譯慣例），**必須在任何 Feature File 產出之前定案**。
題與題之間有依賴，順序不可任意調換：

1. **句子語言** —— 最上游。選中文或英文會改變第 3、4、7、8 題的可行選項。
2. **關鍵字語言** —— 依賴第 1 題。
3. **檔名語言** —— 依賴第 1 題。
4. **名詞是否逐字沿用統一語言** —— 依賴第 1 題（句子改英文則本題須改為對照表模式）。
5. **資料夾切分** —— 與第 6 題成對，先答切分規則。
6. **跨 Aggregate 發起端** —— 依賴第 5 題（資料夾以 Aggregate 為單位才成立）。
7. **識別碼寫法** —— 影響每一句 Given / When，且會決定 Examples 表的欄位設計。
8. **Rule 標題** —— 依賴第 2 題。
9. **Feature 標題** —— 依賴第 3 題，最後答。

第二階段之後（GH1 Feature 切分 → GH2 When → GH4 Then → GH3 Given → GH5/GH6）
於本輪 8 題定案並確認批次範圍後展開。

### 建議的第一批個案範圍：**補簽流程**（3 Command ＋ 1 Read Model）

依 `/gh-discovery` 的預設規則（尚未翻譯、且 Command 數最少的 Aggregate，用來驗證題目格式）
應選 `師徒功能解鎖流程`（1 個）或 `金幣儲值流程`（1 個），
但**建議改選補簽流程**，理由是驗證題目格式需要一個能同時觸發七類檢查的最小範圍：

| 檢查類 | 補簽流程是否觸發 | 具體觸發點 |
|---|---|---|
| GH1 Feature 切分 | ✅ | 3 個 Command 是 3 個檔還是 1 個檔（「補簽」與「使用補簽券」由同一次操作產生） |
| GH2 When 觸發源 | ✅ | 「恢復連續簽到」的 Actor 是**系統**（Policy 觸發），另兩個是使用者 |
| GH3 Given 前提 | ✅ | 需跨 Aggregate 前提（補簽券張數 ＋ 連續簽到中斷狀態 ＋ 該日未簽到） |
| GH4 Then 失敗分類 | ✅ | 至少三類失敗：張數不足、超過回補範圍、該日已簽到 |
| GH5 Outline / Examples | ✅ | 回補範圍 7 天的邊界值（第 6/7/8 天）＋ 該參數為**平台級可調參數**（存於補簽設定 Aggregate），正好觸發 GH5.6 |
| GH6 Query 專屬 | ✅ | Read Model「補簽頁」含三值狀態日曆、且有**試算欄位**（補簽後可恢復的連續天數），觸發 GH6.1 與 GH6.6 |
| GH7 組織 | ✅ | 跨 Aggregate（補簽券 → 連續簽到 → 獎勵信箱），觸發發起端判定 |

`師徒功能解鎖流程` 與 `金幣儲值流程` 各只有 1 個 Command，無失敗分類、無 Query、無邊界值，
用來驗證題目格式會有大半檢查項掃不到。

預估題數：約 12–18 題，遠低於單輪 40 題上限。
