# Gherkin 翻譯規約

> 本檔為事件風暴模型翻譯成 Gherkin 行為規格的**唯一慣例定義處**。
> 每一條規約皆來自 `.gh-clarify/resolved/` 中的一項裁決，並註明來源檔名與所選選項。
>
> 本檔**不定義業務規則**。業務規則的唯一定義處為 `Event-Storming_事件風暴/`；
> 本檔只決定「同一件事寫成幾個 Scenario、句子長什麼樣、檔案放哪裡」。
>
> 翻譯樣板來源：WaterBall 事件風暴翻譯 Gherkin ＋ 七項 SOP 補強決議。
>
> 建立日期：2026-08-23

---

## §1 全域慣例

### 1.1 句子語言

**Gherkin 句子的敘述文字一律使用中文。**

- Given / When / Then / And 的句子本體以中文撰寫。
- 句中的名詞逐字沿用 `Event-Storming_事件風暴/00_全域規範.md`
  〈統一語言：已定案術語〉的中文原名，不自行翻譯為英文。
- **不建立中英對照表**：承
  `.es-clarify/resolved/aggregate/統一語言_尚未建立標準術語詞彙表.md` 的既有裁決
  ——「另開檔案會使術語定義散在兩處，反而更難維護」。
- 不採中英混寫（英文句型夾中文名詞）。

範例：

```gherkin
Rule: 業務規則驗證
  Scenario: 補簽券張數不足時無法補簽
    Given 使用者（U001）的補簽券持有張數為 0
    When 使用者（U001）使用補簽券回補 2026-08-20
    Then 操作失敗
    And  使用者（U001）的補簽券持有張數仍為 0
```

*來源：`.gh-clarify/resolved/organization/全域_Gherkin句子的敘述文字用中文還是英文撰寫.md`（選項 A）*

### 1.2 關鍵字語言

**Gherkin 關鍵字一律使用英文原字，句子用中文（承 §1.1）。**

- 使用的關鍵字：`Feature` / `Rule` / `Background` / `Scenario` / `Scenario Outline` /
  `Examples` / `Given` / `When` / `Then` / `And` / `But`。
- **不加 `# language:` 宣告行**：檔案採 Gherkin 預設的 English 關鍵字解析。
- 不採 `# language: zh-TW`：已查證 Cucumber 官方 Gherkin 語言表，
  zh-TW **沒有 `Rule` 的中文關鍵字**（只能寫英文 `Rule`），
  而本專案樣板以 `Rule` 區塊為骨架（七項決議中的決議 1、2、3 皆以 Rule 為分組單位），
  採 zh-TW 會使骨架上最關鍵的字停在英文、其餘全中文。
- 不採 `# language: zh-CN`：該語言雖有「规则」，但為簡體字，與本專案全篇繁體中文衝突。

範例：

```gherkin
Feature: 使用補簽券

  Rule: 業務規則驗證
    Scenario: 補簽券張數不足時無法補簽
      Given 使用者（U001）的補簽券持有張數為 0
      When 使用者（U001）使用補簽券回補 2026-08-20
      Then 操作失敗
```

*來源：`.gh-clarify/resolved/organization/全域_Gherkin關鍵字用中文還是英文.md`（選項 A）*

### 1.3 檔名語言與格式

**Feature File 的檔名一律使用中文，逐字沿用 Command / Read Model 的原始名稱。**

- 修改型：檔名 ＝ `01_Command清單.md` 中的 Command 原名，例：`使用補簽券.feature`。
- 查詢型：檔名 ＝ `04_ReadModel清單.md` 中的 Read Model 原名，例：`補簽頁.feature`。
- 決議 7 的「動詞＋名詞」格式由 Command 原名本身滿足
  （`01_Command清單.md`〈命名與盤點規範〉已規定「Command 命名一律為祈使句『動詞＋受詞』」），
  不另做轉寫。
- **不建立中英檔名對照表**：理由同 §1.1。
- 不採拼音檔名。

範例：

```
Gherkin_行為規格/features/補簽券/使用補簽券.feature
Gherkin_行為規格/features/訓練紀錄/記錄該組成績.feature
```

**採中文檔名的理由（已查證）**：`Event-Storming_事件風暴/` 的 34 個檔案與
`.es-clarify/resolved/` 的 392 個檔案**全部為中文檔名**，其中包含帶括號、`&`、`>`
的長檔名（如 `訓練紀錄流程（循環：使用者已完成該組 > 組間休息已結束）.md`），
本專案已在中文檔名上完成整個事件風暴階段而未遇編碼問題。
檔名與模型一致，方能以同一關鍵字同時搜到模型檔與規格檔。

> **備註（須留意的取捨）**：業界通例偏向英文檔名（跨平台、CI 路徑安全）。
> 本專案採中文是因既有 400 餘個中文檔名的事實已先行成立，改用英文只會製造兩套命名。
> **若日後專案開源或引入非中文協作者，本條需重新評估。**

*來源：`.gh-clarify/resolved/organization/全域_FeatureFile的檔名用中文還是英文.md`（選項 A）*

### 1.4 名詞強制逐字沿用統一語言

**Gherkin 句子中的名詞，一律逐字沿用模型原名，不得簡稱、不得為通順而改寫。**

- 適用範圍：Given / When / Then / And 句子中的每一個名詞，
  以及 `Examples` 表格的欄名。
- 名詞的唯一來源：`Event-Storming_事件風暴/00_全域規範.md`〈統一語言：已定案術語〉、
  `01_Command清單.md`〈Command 清單〉、`02_Aggregate定義.md`、`04_ReadModel清單.md`。
- 承模型既有規則：`00_全域規範.md`〈統一語言：已定案術語〉之規則段落明文規定
  「**Policy 與 Rule 中引述行為時，一律直接使用既有 Event 全名，不得另造簡稱**」。
  Gherkin 的 `Rule` 區塊即模型 `[Rule]` 的翻譯，適用同一條規則。
- **曾用名一律不得出現**：承〈詞彙表維護規則〉第二條。
  已知的 21 組曾用名（追蹤／關注、進階訓練計畫／訓練計畫、
  使用者訓練已中斷／單次訓練已逾時中斷、虛擬貨幣／金幣等）
  不得以「自然說法」的形式回流至 `.feature` 檔。
- **三個成長數值不得互相簡稱**：經驗值、能力值、個人排行榜分數為三個不同數值
  （見〈三個成長數值的區別〉），句子中一律寫全名，
  不得寫成「分數」「經驗」等會產生歧義的簡稱。
- **不另建縮寫對照表**：已查證本模型最長的 Command 名為 10 個中文字、
  最長的 Aggregate 名「團隊成員資格申請」為 8 個字，無術語過長的實例。

對照範例：

```gherkin
# 正確（逐字沿用）
  Given 使用者（U001）的單次訓練已逾時中斷
  Then  使用者（U001）的個人排行榜分數已增加 50 點

# 錯誤（改寫與簡稱）
  Given 使用者（U001）的這次訓練因逾時而中斷      ← 改寫了 Event 全名
  Then  使用者（U001）的排行榜分數增加 50 點       ← 「排行榜分數」有歧義
```

> **已知取捨**：本條會使部分句子讀起來像模型摘要而非自然中文
> （例如「Given 使用者（U001）的單次訓練已逾時中斷」）。
> 此為刻意付出的代價 —— Gherkin 在本專案的第一用途是**可驗收的規格**，不是文案。

*來源：`.gh-clarify/resolved/organization/全域_Gherkin句子的名詞是否逐字沿用模型統一語言.md`（選項 A）*

### 1.5 資料夾切分規則

**每一個 Aggregate 各建一個資料夾，不做任何合併。**

- 資料夾層級為**一層**：`Gherkin_行為規格/features/<Aggregate 名>/<Command 或 Read Model 名>.feature`。
- 資料夾名逐字沿用 Aggregate 原名（中文，承 §1.3、§1.4），不加後綴、不縮寫。
- 歸屬規則只有一句：**這個 Command 改的是哪個 Aggregate，就放哪個資料夾**
  （跨 Aggregate 者見 §1.6）。
- **只裝一個檔案的資料夾是正常的**，不因檔案少而合併。
  Cucumber 以 glob 遞迴載入 `**/*.feature`，資料夾數量與層數不影響執行；
  資料夾在此只是給人看的索引。
- **不採模型的 11 個分類作為第一層**：已查證該 11 個分類僅為
  `02_Aggregate定義.md`〈獨立 Aggregate 清單〉表格中的一個欄位，
  `.es-clarify/resolved/` 的 392 個裁決中無任何一個引用過它，
  將其升格為檔案結構等於賦予它從未被裁決過的地位。
- **不採「設定類合併為 `平台設定/`」**：該做法需額外定義「多小算小」「哪些算設定類」，
  每次新增 Aggregate 都要重新裁決，與本階段「機械式翻譯、不需主觀判斷」的目標衝突。

### 1.6 跨 Aggregate Command 的歸屬

**依 Command 的「目標 Aggregate ID」判定發起端，該 Aggregate 即其資料夾。**

- 判定依據為模型**既有欄位**，非為分資料夾而新造：
  `01_Command清單.md`〈Command 輸入參數的推導規則〉明文規定

  > **Command 的輸入參數 ＝ 其導致的 Event 之專屬攜帶欄位 ＋ 目標 Aggregate ID ＋ 請求識別碼**

  每一個 Command 皆已有一個目標 Aggregate ID，直接讀取即可，不需主觀判斷。
- 其餘 Aggregate 的變動一律視為經由 `[Policy]` 串聯而來，**不影響歸檔**。
  這與模型的既有寫法一致：訓練結算流程中「能力值已提升」「個人排行榜分數已增加」
  皆掛在各自的 Postcondition 與 `[Policy]` 之下，而非「訓練已結算」Event 本身。
- **不採「依 Actor 所屬 Aggregate」**：已查證 `00_全域規範.md`〈Actor 清單〉
  僅五種 Actor（使用者／管理員／系統／AI／外部系統），其中**系統、AI、外部系統皆非 Aggregate**；
  而模型中大量 Command 的 Actor 正是「系統」（結算訓練、發放註冊獎勵、指派新手任務、
  產生能力值日快照、恢復連續簽到⋯），該做法對這些一律無解。
- **不採「依第一個 Event 所關聯的 Aggregate」**：決議 7 說的是「發起端」而非「最先被改動」，
  兩者在有 Policy 串聯時經常不同；且模型從未定義 Postcondition 的先後順序，
  該做法在本模型中不可判定。
- **不採逐案裁決**：會使 40 餘個跨 Aggregate Command 各成一題，
  與「機械式翻譯、不需主觀判斷」的目標衝突。

範例（`結算訓練` 一次改動 7 個 Aggregate，仍只放一處）：

```
features/訓練紀錄/結算訓練.feature
```

> 其改動的連續訓練、使用者、虛擬貨幣、能力值、個人排行榜分數、使用者成就解鎖紀錄
> 皆為 Policy 串聯的結果，不各自建檔、不影響本檔路徑。
> 這些連帶變動是否需在 `Then` 中斷言，屬 GH4.5 的個案題，與歸檔無關。

*來源：`.gh-clarify/resolved/organization/全域_跨Aggregate的Command發起端如何判定.md`（選項 A）*

### 1.7 識別碼（Actor Key / Aggregate ID）寫法

**識別碼一律以「全形括號 ＋ 型別前綴 ＋ 三位流水號」緊接於名詞之後，單人情境也照寫。**

- 格式：`<名詞>（<前綴><三位數>）`，例：`使用者（U001）`、`團隊（T001）`、`管理員（M001）`。
- **括號一律用全形**「（）」，不用半形「()」——理由見下方〈為什麼用全形〉。
- **單人情境也照寫，不省略**：承決議 2「權限驗證的 Given 沿用原始完整樣板，**不簡化**」；
  且「哪些算單人情境」本身即是需逐案判斷的主觀決定，與本階段目標衝突。
- 承模型既有規範：`00_全域規範.md`〈Event 共通攜帶資訊〉規定每一個 Event 皆必帶
  「觸發 Actor（Actor 識別碼）」與「關聯 Aggregate ID」——模型層面每個事實都已綁定識別碼，
  句子照寫是忠實反映，省略才是資訊遺失。
- **不採一律 `<佔位符>`**：會使每個 Scenario 都被迫配一張 `Examples` 表，
  架空決議 6 的判準（「邏輯完全相同、只有輸入資料不同」才用 Outline）。
  真正需要 Outline 之處仍可將 `U001` 換成 `<使用者ID>`，兩者不衝突。
- **不採具名角色**（「小明」「教官阿華」）：需為每個情境命名，且名字不帶型別資訊。

#### 為什麼用全形括號

`.feature` 檔的 step text 為自由文字，Gherkin 不解析其中的括號
（唯一有特殊意義的是 `Scenario Outline` 內、由 `Examples` 代入的 `<...>`），
故半形與全形在**語法層**皆合法。差別在 **step definition 層**：

已查證 Cucumber 官方 Cucumber Expressions 文件，在 step definition 的 pattern 中
`(` `)` 表示**選用文字**（`cucumber(s)` 同時匹配單複數）、`{` `}` 表示參數型別、
`/` 表示替代文字，要匹配字面值須以 `\` 跳脫。該文件並明確指出
這些符號**只作用於 step definition，不作用於 feature 檔文字**。

因此若步驟文字採半形 `()`，日後撰寫 step definition 時 pattern 內須跳脫為 `\(` `\)`；
採全形「（）」則因其非 ASCII 分隔符而被視為普通字元，不需跳脫。

> **待實作時驗證**：「全形括號不被 Cucumber Expressions 視為分隔符」一點，
> 係由官方文件所列分隔符為 ASCII `(` 推得，非文件明文。
> 撰寫第一支 step definition 時應以一則測試確認，若不成立則改回半形並於 pattern 中跳脫。

範例：

```gherkin
  Given 使用者（U001）的補簽券持有張數為 1
  And   使用者（U001）於 2026-08-20 未簽到
  When  使用者（U001）使用補簽券回補 2026-08-20
  Then  操作成功
```

需要 `Scenario Outline` 時，識別碼可改為佔位符（兩種寫法並存不衝突）：

```gherkin
  Scenario Outline: 補簽日期超出回補範圍時失敗
    Given 使用者（U001）的補簽券持有張數為 1
    When  使用者（U001）使用補簽券回補 <補簽日期>
    Then  <預期結果>

    Examples:
      | 補簽日期   | 預期結果 |
      | 距今第 6 天 | 操作成功 |
      | 距今第 7 天 | 操作成功 |
      | 距今第 8 天 | 操作失敗 |
```

> **已知取捨**：BDD 實務中有一派主張 step text 應只寫業務語言、避開 `U001` 這類識別碼，

### 1.8 Rule 標題格式

**`Rule:` 的標題一律使用固定類別名，不寫規則內容。**

#### 五種類別名（封閉清單）

| 類別名 | 對應樣板 / 決議 | 用於 |
|--------|----------------|------|
| `權限驗證` | 決議 2（獨立成一種 Rule 類型） | Actor 無權執行本 Command |
| `輸入驗證` | 決議 1（失敗原因之一） | 輸入參數格式、型別、值域不合法 |
| `業務規則驗證` | 決議 1（失敗原因之一） | 違反模型中的 Precondition |
| `併發衝突` | 決議 1（失敗原因之一） | 同一 Aggregate 的競態失敗 |
| `後置條件` | 樣板「Rule：後置條件（Postcondition）」 | 成功路徑 |

- 前四項為**失敗路徑**（依失敗原因分組），第五項為**成功路徑**，兩者不同維度但同列一表。
- 成功路徑的標題採 `後置條件`（與樣板字面一致），不寫 `操作成功`。
- 本清單為封閉清單；若某 Command 出現第五類失敗原因，
  不得自行新增類別名，應建立釐清項目（GH4.1）由裁決決定。
- 同一類別下有多條規則時，**併入同一個 `Rule` 區塊、以多個 `Scenario` 呈現**，
  不因規則多而拆成多個 Rule —— 拆開會使決議 1 的失敗分類消失。
- 決議 3 的兩種觸發源（Actor 觸發 / Policy 觸發）分屬兩個 Rule 時，
  其標題寫法待 GH2 個案掃描時定案，不在本條範圍。

#### 不採規則內容作為標題的理由

- **與決議 1、2 的分組單位衝突**：本專案的 Rule 在設計上即為**類別**而非單條規則。
  「業務規則驗證」下若有 3 條規則，寫成 3 個 Rule 會使決議 1 的分類消失。
- **模型的 `[Rule]` 行不適合當標題**（已查證）：其往往很長且含引用與 markdown 標記，例如
  `補簽流程.md` 的
  「Postcondition：補簽當日的簽到獎勵（經驗值 10 ＋ 金幣 10）照常發放，但**補發至獎勵信箱**，不直接入帳」，
  以及 `訓練結算流程.md` 中含完整公式的整段規則。
- **重複**：規則內容本就出現在 `Scenario` 標題與 `Given` / `Then` 句子中。
- 不採「類別名 ＋ 冒號 ＋ 內容」：標題長度失控，且分隔符又是一個須另訂的慣例。

範例：

```gherkin
Feature: 使用補簽券

  Rule: 權限驗證
    Scenario: ...

  Rule: 輸入驗證
    Scenario: ...

  Rule: 業務規則驗證
    Scenario: 補簽券張數不足
    Scenario: 補簽日期超過回補範圍
    Scenario: 該日已簽到

  Rule: 後置條件
    Scenario: ...
```

*來源：`.gh-clarify/resolved/organization/全域_Rule標題要寫失敗類別還是寫規則內容.md`（選項 A）*

### 1.9 Feature 標題格式

**`Feature:` 標題逐字等於 Command / Read Model 原名（與檔名完全一致），
標題下加一行來源指標註解。**

- 修改型：標題 ＝ `01_Command清單.md` 中的 Command 原名。
- 查詢型：標題 ＝ `04_ReadModel清單.md` 中的 Read Model 原名。
- 標題與檔名（§1.3）**逐字相同**，不做任何改寫。
- 標題下方緊接**一行**註解，指向該翻譯單元在事件風暴模型中的出處：
  `# 來源：Event-Storming_事件風暴/<流程檔名>.md`
  - 出處取該 Command / Read Model 所屬的流程檔。
  - 不隸屬單一流程者（〈系統排程〉、〈平台設定維護〉兩節）指向 `01_Command清單.md`。
  - 跨流程重複出現的 15 個 Command（見 §2 備註）指向其**主要流程檔**，
    並於 §2 Feature 清單標註其餘出現處。
- **只寫來源指標，不複製規則內容**：規則內容已完整存在於 `Event-Storming_事件風暴/`，
  抄入 `.feature` 會產生第二份須同步的規則描述 —— 承
  `.es-clarify/resolved/aggregate/統一語言_尚未建立標準術語詞彙表.md`
  「散在兩處，反而更難維護」的既有裁決。
- 不採自由敘述句作標題：無法保證 311 句體例一致，且模型改名時
  無法以 grep 原名找齊（本專案已有先例：
  `.es-clarify/resolved/event/使用者已記錄該組成績_流程檔名與標題仍引用已棄用的Event名.md`）。

範例：

```gherkin
Feature: 使用補簽券
  # 來源：Event-Storming_事件風暴/補簽流程.md

  Rule: 業務規則驗證
    Scenario: 補簽券張數不足
      Given 使用者（U001）的補簽券持有張數為 0
      When 使用者（U001）使用補簽券回補 2026-08-20
      Then 操作失敗
      And  使用者（U001）的補簽券持有張數仍為 0
```

*來源：`.gh-clarify/resolved/organization/全域_Feature標題的寫法.md`（選項 A ＋ 來源行）*
