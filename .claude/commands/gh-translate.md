# 四步循環

## 1. 盤點該流程的 Command

逐列（**不用 `grep -c`**）列出該流程的 Command、Actor、導致的 Event，
並依 §2.1 判定每個 Command 的歸屬：

| 判準（以模型的**註記文字**為準，不以語意推論） | 歸屬 |
|---|---|
| Actor 為使用者／管理員 | 各自成檔 |
| 該列註記「**連鎖觸發**」 | 併入發起檔，不另立檔 |
| 該列註記「**多對一**」 | 獨立成檔 |
| Actor 為系統，由某 Event 觸發，無上述註記 | 獨立成檔（§3.1 第二列） |
| 其 Event 屬〔不需精準追蹤〕7 類 | **不產檔**（§8.1） |

盤點結果先列給使用者看，再開始寫。

## 2. 逐一翻譯

依樣板與規約產出 `Gherkin_行為規格/features/<Aggregate>/<Command 原名>.feature`。

常用章節速查：

| 要決定的事 | 看哪一節 |
|---|---|
| 檔案怎麼切、放哪個資料夾 | §2.1、§1.5、§1.6 |
| `When` 怎麼寫（Actor／Policy／排程／外部回呼） | §3.1 |
| 失敗分幾個 Rule、Rule 標題怎麼寫 | §1.8、§4.4 |
| 失敗原因怎麼命名 | §4.2 |
| 失敗時要斷言哪些欄位 | §4.3 |
| 成功路徑分幾條 Scenario | §4.6 |
| 連續操作要不要另寫 | §4.7 |
| Event 要不要斷言、寫幾次 | §4.8 |
| `Given` 要寫什麼 | §5.1–§5.4 |
| 什麼時候用 `Scenario Outline` | §6.1–§6.3 |

## 4. 卡住時才提問

**只有兩種情況該停下來問：**

| 情況 | 處理 |
|---|---|
| 規約沒涵蓋的**新型態** | 問使用者，答案寫進 §8，之後同型態不再問 |
| 模型缺**業務決策** | 問使用者，並確認要不要當場改模型（改模型須明示同意） |

**其餘一律自行決定，不要問。** 判準見下節。

沒卡就直接翻下一條，不需逐條回報。

# 自決的界線（**不得放寬**）

| 級別 | 判準 | 處理 |
|------|------|------|
| **可自決** | 只改「句子怎麼寫」，選錯了改一行 | 直接決定，於規約註明「助理逕行決定」 |
| **須問使用者** | 改變 **Feature File 的數量**，或**改動既有規約條文**，或**改動事件風暴模型** | 一律提問 |

即使使用者要求加快，「改變架構」仍須提問——
使用者要的是少問無謂的題，不是放棄對架構的決定權。

# 提問格式（使用者多次反應題目太複雜）

- **一句情境 ＋ 最多一段 Gherkin ＋ 三行選項表 ＋ 最多 2 條推薦理由**
- 每題必須標推薦選項（★）
- 不附「各選項的翻譯後果」表，除非使用者追問
- **一次一題**

# 硬性規則

- **計數先列舉**：宣稱任何數量前先逐項列出再數。
  `grep -c` 是字串出現次數，不是實體數量。
  （已犯過：把 21 個字串出現次數當成 7 個 Event 的實體數）
- **引用先查證**：引用模型或規約的行號、原文前，實際讀該檔案確認。
- **判準以註記文字為準**：不得以「這個看起來像連鎖／像多對一」為由改判。
- **不改模型**：翻譯階段不新增或修改 Event、Command、規則與欄位；
  發現模型缺口時停下來問，經同意才改。
- **每產出一個檔就跑 check.py**，不靠肉眼複查。
