目標：偵測作用中事件風暴模型的歧義或遺漏決策點，將釐清問題以檔案形式記錄到 `.es-clarify/` 資料夾，產生 `overview.md` 說明釐清優先順序策略。

# 前置：確認掃描標的

先讀取事件風暴的模型檔案（流程與 Event 清單），並列出將要掃描的檔案清單。

- 方法論參考：`Alchemy-Workout-Handover/Event-Storming_事件風暴/事件風暴模型.md`
- 若找不到任何「流程 / Event 清單」檔案，**停止並回報**，不得自行臆造 Event。

事件風暴的六大元素與其串聯關係（掃描時的判準基礎）：

1. **Event（事件）**：領域中「已經發生」、對業務有意義的事實，以過去式描述。
2. **Command（命令）**：觸發 Event 的具體操作。Command 與 Event 為「多對一」。
3. **Actor（角色）**：執行 Command 的人或系統。
4. **Rules（規則）**：Preconditions（執行前的檢核點）與 Postconditions（執行後應達到的新狀態）。
5. **Aggregate（聚合）**：資料庫中的資料單位，欄位間彼此不得矛盾；Command 的目的即修改其內部狀態。
6. **Read Model（查詢模型）**：Actor 得知 Aggregate 狀態的方法，不改變任何狀態。

串聯句：「Actor 透過 Read Model 知道系統當前的狀態，做出對應的決策，進而執行 Command 改變 Aggregate 的內部狀態，並產生 Event。」

# 執行步驟

## 1. 歧義與覆蓋度掃描

針對事件風暴模型檔，使用以下檢查清單進行結構化掃描。對每一檢查項標記狀態：Clear（清楚）/ Partial（部分）/ Missing（缺失）。產生內部覆蓋度地圖以供優先級排序。

### A. 流程與事件層檢查（Event）

#### A1. 事件識別完整性
- [ ] 流程中每一個「業務狀態改變」是否都已標記為 Event？
- [ ] 是否存在隱含發生、但未被寫出來的 Event（例如逾時、自動失效、外部系統回呼）？
- [ ] 流程的起點 Event 與終點 Event 是否明確？
- [ ] 是否存在被誤列為 Event 的「畫面操作」或「技術動作」（如「按下按鈕」「寫入資料庫」）？

#### A2. 事件命名與語意
- [ ] 每個 Event 是否以**過去式**描述（如：訓練課表已建立）？
- [ ] Event 名稱是否描述「業務事實」而非「實作方式」？
- [ ] Event 名稱是否讓業務與技術人員都能無歧義理解？
- [ ] 是否存在兩個名稱不同、實則指涉同一事實的 Event？

#### A3. 事件時序與因果
- [ ] 流程中 Event 的先後順序是否明確？
- [ ] 分支路徑（成功 / 失敗 / 取消 / 逾時）是否都有對應 Event？
- [ ] 是否存在可並行發生的 Event？其交錯順序是否已釐清？
- [ ] 是否存在「單調遞增」性質的 Event 序列（進度只能往前、不能倒退）？該限制是否已寫明？
- [ ] 同一個 Event 是否可能重複發生？重複時的處理方式是否明確（冪等性）？

#### A4. 軟體邊界判斷
- [ ] 每個 Event 是否已評估「是否值得投入開發資源」？
- [ ] 對業務價值影響極小、或不需精準自動化追蹤的 Event，是否已明確標記為「留在系統邊界之外、維持人工作業」？
- [ ] 跨系統邊界的 Event（由外部系統產生）是否已標示來源？

#### A5. 事件攜帶的資訊
- [ ] 每個 Event 是否已定義「發生時必須記錄哪些資訊」？
- [ ] Event 的發生時間點是否需要記錄？時區與精度是否明確？

### B. 命令與角色層檢查（Command & Actor）

#### B1. Command 識別完整性
- [ ] 每個 Event 是否至少對應一個 Command？
- [ ] 「多對一」是否已盤點完整（是否還有其他 Command 也會導致同一 Event）？
- [ ] 是否存在由系統自動觸發（排程、逾時、事件連鎖）而非人為操作的 Command？
- [ ] Command 的顆粒度是否一致（不會有些極粗、有些極細）？

#### B2. Command 命名與意圖
- [ ] Command 是否以**祈使句 / 動詞開頭**描述（如：建立訓練課表）？
- [ ] Command 名稱是否反映使用者意圖，而非畫面元件名稱？
- [ ] Command 間的界線是否清楚（無重疊或遺漏）？

#### B3. Command 的輸入
- [ ] 每個 Command 是否已定義需要哪些輸入參數？
- [ ] 每個輸入參數是否有明確的資料型別與定義說明？
- [ ] 哪些參數為必填、哪些為選填，是否明確？

#### B4. Actor 識別
- [ ] 每個 Command 是否都已指明執行的 Actor？
- [ ] Actor 是人、系統、排程、還是外部系統，是否已區分？
- [ ] 同一個 Command 是否可能由多種 Actor 執行？若是，行為是否有差異？

#### B5. Actor 權限與觸發源
- [ ] 不同 Actor 對同一 Command 的權限差異是否已定義？
- [ ] 「誰不能執行這個 Command」是否已明確（而非只寫誰可以）？
- [ ] 觸發源是否明確（使用者主動 / 系統自動 / 外部通知）？

### C. 規則層檢查（Rules：Preconditions & Postconditions）

#### C1. 前置條件（Preconditions）完整性
- [ ] 每個 Command 是否至少有一條 Precondition？
- [ ] Precondition 是否已**原子化**（分割到不可分割為止，每一條只驗證一件事）？
- [ ] 所有必要驗證是否都已列出（權限、狀態、資料有效性、數量限制、時間窗）？
- [ ] Precondition 描述是否可驗證（非模糊形容詞）？

#### C2. 後置條件（Postconditions）完整性
- [ ] 每個 Command 是否至少有一條 Postcondition？
- [ ] Postcondition 是否已原子化（每一條只描述一項狀態變更）？
- [ ] 所有被改變的 Aggregate 欄位是否都已列出？
- [ ] 是否列出了「會連帶產生哪些其他 Event」？

#### C3. 邊界條件覆蓋
- [ ] **數值邊界**：臨界值案例是否涵蓋（剛好達標、差一點、超過）？最小值 / 最大值是否定義？
- [ ] **時間邊界**：時序相關操作是否考慮不同時間點（截止當下、逾期一秒、跨日、跨時區）？
- [ ] **狀態邊界**：狀態切換的邊界情況是否涵蓋（重複執行、在終止狀態下再次執行）？
- [ ] **組合邊界**：多條規則並存時的交集與衝突是否已處理？套用順序是否明確？
- [ ] **類別邊界**：不同值域的資料分類是否都有對應規則？
- [ ] **特殊值**：空值、零、負值的處理是否已定義？

#### C4. 單調遞增與不可逆性
- [ ] 具方向性的流程是否已寫明「不可倒退」？
- [ ] 可逆的操作（取消、退回、修改）是否已明確列為合法路徑並定義其 Event？
- [ ] 已完成 / 已結案的狀態是否還允許被修改？

#### C5. 失敗與例外路徑
- [ ] Precondition 不成立時，系統的行為是否明確（拒絕？產生失敗 Event？）？
- [ ] 錯誤訊息或使用者回饋是否已定義？
- [ ] 執行到一半失敗時，狀態是否需要回復？回復到哪個狀態？

### D. 狀態層檢查（Aggregate & Read Model）

#### D1. Aggregate 識別與邊界
- [ ] 所有核心業務概念是否都已建模為 Aggregate？
- [ ] Aggregate 命名是否清晰且無歧義？
- [ ] 是否存在隱含但未明確定義的 Aggregate？
- [ ] 每個 Aggregate 的邊界是否清楚（哪些資料屬於它、哪些不屬於）？

#### D2. Aggregate 欄位定義
- [ ] 每個欄位是否都有明確的資料型別（int, long, float, bool, string, datetime）？
- [ ] 每個欄位是否都有充足的定義說明？
- [ ] 欄位命名是否清晰且無歧義？
- [ ] 數值欄位的範圍限制是否明確（>=、<=、=、≠）？單位是否標明？

#### D3. Aggregate 內部不變條件
- [ ] 欄位間的計算關係是否明確（例如：總訓練量 = 重量 × 次數 × 組數）？
- [ ] 衍生欄位的定義公式是否清楚？
- [ ] 是否存在必須同時滿足的多欄位約束（欄位彼此不得矛盾）？
- [ ] 主鍵與唯一性規則是否明確？

#### D4. Aggregate 間的關係
- [ ] Aggregate 間的關聯關係是否完整（一對一、一對多、多對多）？
- [ ] 關聯的生命週期是否明確（父被刪除時，子如何處理）？
- [ ] 是否存在跨 Aggregate 的一致性要求？如何達成？

#### D5. 生命週期與狀態機
- [ ] 具有狀態的 Aggregate 是否定義了所有可能狀態？
- [ ] 狀態轉換規則是否完整（哪些轉換合法、哪些不合法）？
- [ ] 初始狀態與終止狀態是否明確？
- [ ] 每次狀態轉換是否都對應到一個 Event？

#### D6. Read Model 識別
- [ ] Actor 在執行每個 Command 前，需要看到什麼資訊才能做決策？是否已定義為 Read Model？
- [ ] 每個 Read Model 是否已指明「給哪個 Actor 看」？
- [ ] Read Model 是否確實**不改變任何狀態**（無副作用）？
- [ ] Read Model 的每個欄位是否可從 Aggregate 推導？來源是否明確？
- [ ] 資料的即時性要求是否明確（即時 / 可延遲）？
- [ ] 篩選、排序、分頁規則是否已定義？

### E. 串聯一致性檢查（跨元素）

#### E1. Actor → Command → Event 串聯
- [ ] 每一條「Actor 執行了 Command，導致 Event 的發生」是否都能完整寫出？
- [ ] 是否存在有 Event 但找不到 Command 的孤兒事件？
- [ ] 是否存在有 Command 但不產生任何 Event 的無效命令？

#### E2. Command → Aggregate 對應
- [ ] 每個 Command 是否明確指出它修改哪一個 Aggregate？
- [ ] 是否存在同時修改多個 Aggregate 的 Command？其一致性如何保證？

#### E3. Event → Aggregate 一致性
- [ ] Event 描述的狀態改變，是否確實反映在某個 Aggregate 欄位上？
- [ ] Postcondition 中提到的欄位，是否都存在於 Aggregate 定義中？

#### E4. Read Model → Command 支撐
- [ ] 每個需要決策的 Command，是否都有對應的 Read Model 提供判斷依據？
- [ ] 是否存在沒有任何 Actor 使用的 Read Model（過度設計）？

### F. 術語與品質檢查

#### F1. 統一語言（Ubiquitous Language）
- [ ] 是否建立了標準術語詞彙表？
- [ ] 核心概念是否都有一致的命名？
- [ ] Event / Command / Aggregate 名稱是否使用同一套業務詞彙？

#### F2. 術語衝突
- [ ] 是否存在同義詞混用（同一概念多種稱呼）？
- [ ] 是否存在同名異義（不同概念使用相同名稱）？
- [ ] 已棄用術語是否已標記並統一替換？

#### F3. 待決事項
- [ ] 是否存在 TODO 標記或未決議事項？
- [ ] 未決事項的影響範圍是否已評估？

#### F4. 模糊描述
- [ ] 是否存在未量化的形容詞（如「健全」「直覺」「適當」「快速」）？
- [ ] 模糊的「應該」「可能」是否已轉換為明確規則？


### G. Gherkin 可轉譯性檢查（BDD 前置）

事件風暴的三個元素與 Gherkin 一一對應：
**Precondition → Given ／ Command（Actor 執行）→ When ／ Postcondition ＋ Event → Then**。
本分類檢查模型是否已具備足以機械式轉譯的結構。

#### G1. Given／Then 的覆蓋率
- [ ] 每一個 Event 底下是否**至少有一條 `Precondition`**？（無則寫不出 Given）
- [ ] 每一個 Event 底下是否**至少有一條 `Postcondition`**？（無則寫不出 Then，該情境無任何斷言）
- [ ] 標為〔不需精準追蹤〕的 Event 是否**確實未建立** Precondition／Postcondition？
      （該類依全域規範不做嚴格規則驗收，有標反而是錯的）
- [ ] 連續出現的 Event 中，規則掛在後一個 Event 之下者，前一個是否確實不需自己的斷言？

#### G2. `[Rule]` 的角色標記
- [ ] 未標 `Precondition` / `Postcondition` / `不變條件` 的 `[Rule]`，是否確實屬於下列四類？
      **參數數值**（10 分／人）、**值域清單**（狀態四值）、**適用範圍**（及於全部 9 類成就）、
      **結構說明**（課表為三層結構）
- [ ] 是否有 `[Rule]` 實為設計理由（「不採⋯因為⋯」），應改標為 `[決策]`？
- [ ] 以否定句書寫的規則（「不設多層級方案」）是否已標為 `不變條件`，而非誤判為理由？

#### G3. 參數的可代入性
- [ ] Postcondition 中出現的計算式，其**參數是否都有具體數值**可代入 Examples 表格？
- [ ] 仍為 `尚未給定` 的參數有哪些？其影響哪幾條情境無法完成 Examples？

#### G4. 值域的完整性
- [ ] 狀態機與列舉欄位的值域是否完整？（值域決定 Scenario Outline 要寫幾條）
- [ ] 分支（`[分支]`）是否每一條路徑都有對應的 Event 與斷言？

#### G5. 標記作業的正確性（**若上一輪曾批次補標，本項必查**）
- [ ] 補標時是否**只加標籤前綴、未改寫原句**？
      以 `git diff` 逐條比對「去除標籤後的句子」是否與原句一致。
- [ ] 特別檢查**否定句翻為肯定句**者（「< 40 一票否決」→「≥ 40」）：
      邊界符號是否翻對（`<` vs `≤`）、方向是否正確。此類錯誤極難以肉眼發現。
- [ ] 是否有句子後半的理由在補標時被刪去？

**本分類的釐清項目歸檔原則**：
G1 的缺口歸入該 Event 所屬的 `.es-clarify/event/` 或 `.es-clarify/rule/`；
G2、G5 屬文件訂正，於 `overview.md` 列為訂正清單，不建為釐清項目；
G3 的缺口若為「參數未定案」，歸入 `.es-clarify/aggregate/`。
---

**釐清項目篩選原則**：
對於狀態為 Partial 或 Missing 的檢查項，建立釐清項目，除非：
- 釐清不會實質改變模型或驗收標準，或
- 該資訊更適合延後到實作規劃階段（內部備註）

僅納入其答案會實質影響**軟體邊界判斷、事件時序、Aggregate 建模、規則驗收、Actor 權限或 Read Model 設計**的問題。

**避免重複提問原則**：
在建立新的釐清項目前，必須先檢查 `.es-clarify/resolved/` 目錄：
- 掃描 `.es-clarify/resolved/` 下所有已解決的釐清項目
- 檢查問題主題是否已被回答（即使問法略有不同）
- 若該問題已在 resolved 中有解決記錄，則不重複建立新的釐清項目
- 若問題角度不同但相關，應在新釐清項目的「定位」或「影響範圍」中註記相關的已解決項目

## 2. 產生釐清項目檔案

**前置步驟：檢查已解決項目**

在建立任何釐清項目檔案前：
1. 讀取 `.es-clarify/resolved/` 目錄結構
2. 列出所有已解決的釐清項目檔案名稱
3. 對於每個待建立的釐清項目，比對其問題主題是否已存在於 resolved 中
4. 若已存在，跳過該釐清項目的建立

針對每個識別出的 Partial 或 Missing 檢查項，建立對應的釐清項目檔案。

### 檔案路徑規則

依「該問題的答案會改動哪一個元素」歸檔，一個問題只放一個資料夾：

| 資料夾 | 收納對象 | 範例 |
|--------|----------|------|
| `.es-clarify/event/` | Event 的識別、命名、時序、軟體邊界（檢查項 A） | `.es-clarify/event/訓練課表已完成_逾期未完成是否算完成.md` |
| `.es-clarify/command/` | Command 的識別、輸入、以及執行它的 Actor 與權限（檢查項 B） | `.es-clarify/command/記錄訓練組數_誰可以代替學員記錄.md` |
| `.es-clarify/rule/` | 前置條件、後置條件、邊界條件、例外路徑（檢查項 C） | `.es-clarify/rule/記錄訓練組數_重量為零時是否合法.md` |
| `.es-clarify/aggregate/` | Aggregate 的欄位、不變條件、關係、狀態機（檢查項 D1–D5） | `.es-clarify/aggregate/訓練紀錄_總訓練量如何計算.md` |
| `.es-clarify/read-model/` | Read Model 的欄位、來源、即時性（檢查項 D6） | `.es-clarify/read-model/本週訓練總覽_週的起算日為何.md` |

命名格式：`<元素名>_<問題全句，以底線代替分隔符號>.md`

- 元素名使用模型檔中的原始名稱，不得自行改寫。
- 跨元素的串聯問題（檢查項 E）與術語品質問題（檢查項 F），歸入「答案會實際改動」的那個元素資料夾。

### 釐清項目檔案格式

每個釐清項目檔案使用以下統一格式：

```markdown
# 釐清問題

<釐清問題之完整句子>

# 定位
```

## 3. 產生 Overview 文件

在 `.es-clarify/overview.md` 中產生釐清策略總覽，內容包含：

### 3.1 釐清項目統計

- Event 相關：X 項
- Command / Actor 相關：X 項
- Rules 相關：X 項
- Aggregate 相關：X 項
- Read Model 相關：X 項
- 總計：Z 項

### 3.2 優先級分佈

- High：X 項
- Medium：Y 項
- Low：Z 項

### 3.3 建議釐清順序

**核心原則**：順著事件風暴的推導方向 —「先確定發生了什麼，再問誰做了什麼、要遵守什麼、狀態長什麼樣」。不可跳過前一層直接問後一層。

1. **第一階段：Event 與軟體邊界**
   - 列出 `.es-clarify/event/` 中的 High 優先級項目
   - 原因：Event 是切入點，也決定了哪些流程要進系統。若 Event 本身不成立，後續 Command 與 Aggregate 全部白做。

2. **第二階段：Command 與 Actor**
   - 列出 `.es-clarify/command/` 中的 High 優先級項目
   - 原因：確認「誰在與系統互動」以及互動的觸發源，才能定義規則的檢核對象。

3. **第三階段：核心 Aggregate 與狀態機**
   - 列出 `.es-clarify/aggregate/` 中的 High 優先級項目
   - 原因：Command 的目的是修改 Aggregate 狀態，欄位與狀態機不清則規則無從寫起。

4. **第四階段：Rules 的前置 / 後置條件**
   - 列出 `.es-clarify/rule/` 中的 High 與 Medium 優先級項目
   - 原因：規則即驗收標準，需建立在已確定的 Command 與 Aggregate 之上。

5. **第五階段：邊界條件與 Read Model**
   - 交錯列出 `.es-clarify/rule/`（邊界、例外）與 `.es-clarify/read-model/` 的 Medium 項目
   - 原因：補足臨界案例，並確認 Actor 決策所需的資訊來源。

6. **第六階段：命名、術語與細節**
   - 列出所有 Low 優先級項目
   - 原因：完善統一語言與模型細節。

### 3.4 釐清策略說明

- **推導順序原則**：嚴格由 Event → Command/Actor → Aggregate → Rules → Read Model，避免在上游未定案時空轉。
- **平衡原則**：同一階段內避免連續追問同一個 Event 的細節，優先橫向覆蓋所有主要流程，再縱向深入。
- **依賴關係**：標記具有前置依賴的釐清項目（需先釐清 A 才能處理 B），例如「Aggregate 狀態機未定 → 該狀態相關的 Precondition 無法釐清」。
- **組合釐清**：標記可一併處理的相關釐清項目（例如同一 Command 的多條邊界條件）。

### 3.5 覆蓋度摘要

列出每個檢查分類（A1–A5, B1–B5, C1–C5, D1–D6, E1–E4, F1–F4）的狀態：
- **Clear**：已充分定義
- **Partial**：部分定義，已建立 X 個釐清項目
- **Missing**：尚未定義，已建立 Y 個釐清項目

## 4. 驗證產出

確保產生的釐清項目符合以下標準：

- [ ] 每個釐清項目檔案都遵循統一格式
- [ ] 檔案路徑符合命名規則（元素名清晰、問題描述精確）
- [ ] 每個問題都有明確的定位（指向具體的流程 / 元素 / 規則 / 欄位）
- [ ] 每個 Event 相關問題都能對應回「Actor 執行 Command 導致 Event」的串聯句
- [ ] 多選題選項互斥且涵蓋主要可能性
- [ ] 影響範圍清楚標記
- [ ] 優先級合理評估（符合影響 × 不確定性原則）
- [ ] `overview.md` 的釐清順序符合「Event → Command/Actor → Aggregate → Rules → Read Model」推導方向

- 提示使用者執行 `/es-formulation` 進行下一階段釐清互動

# 行為規則

- **純偵測角色**：此階段不進行任何互動式釐清，僅產出釐清項目檔案
- **不臆造模型**：若模型檔中沒有寫出的 Event、Command 或 Aggregate，一律不得自行補上；只能就「缺少它」這件事建立釐清項目
- **完整掃描**：不受 5 題限制，所有 Partial 或 Missing 檢查項都應建立釐清項目
- **結構化輸出**：嚴格遵循檔案路徑與格式規範，確保 formulation 階段能順利讀取
- **優先級評估**：根據「影響 × 不確定性」評估每個釐清項目的優先級
- **策略規劃**：在 `overview.md` 中提供清晰的釐清順序建議
- **保持精煉**：每個釐清問題應聚焦單一決策點，避免複合問題
- **可驗收性**：確保每個問題的答案可直接轉換為模型更新（Event 清單、Command 定義、Preconditions / Postconditions、Aggregate 欄位、Read Model 欄位）

# 輸出格式要求

1. **釐清項目檔案** → `.es-clarify/event/*.md`、`.es-clarify/command/*.md`、`.es-clarify/rule/*.md`、`.es-clarify/aggregate/*.md`、`.es-clarify/read-model/*.md`
2. **總覽文件** → `.es-clarify/overview.md`
3. **完成報告** → 終端輸出或回覆訊息

# 與 Formulation 階段的銜接

- Discovery 產出的釐清項目檔案將被 Formulation 階段讀取
- `overview.md` 的釐清順序將指導 Formulation 階段的提問順序
- 檔案格式設計確保 Formulation 可直接解析並呈現給使用者
- 優先級與影響範圍資訊幫助 Formulation 決定是否需提前終止釐清流程
