目標：把 `/es-discovery` 偵測出來的釐清項目，透過**一次一題**的互動問答收斂成明確答案，並立即回寫到事件風暴模型檔中，使模型逐步達到可驗收的完整度。

# 前置檢查

1. 讀取 `.es-clarify/overview.md`。若不存在，回報「請先執行 `/es-discovery`」並停止。
2. 讀取 `.es-clarify/` 下所有釐清項目檔案（`event/`、`command/`、`rule/`、`aggregate/`、`read-model/`）。
3. 讀取 `.es-clarify/resolved/` 下所有已解決項目，作為回答時的既有共識，避免推翻或重複。
4. 讀取事件風暴模型檔（流程與 Event 清單）作為回寫標的。

# 執行步驟

## 1. 決定提問順序

依 `overview.md`「3.3 建議釐清順序」排定佇列，並套用以下調整：

- **依賴優先**：若 A 的答案是 B 的前提（例如 Aggregate 狀態機未定，就無法釐清該狀態的 Precondition），則 A 必須排在 B 之前。
- **推導方向**：任何情況下不得在上游元素未定案時，先問下游元素。順序為 Event → Command / Actor → Aggregate → Rules → Read Model。
- **同一階段內**：先橫向覆蓋所有主要流程的問題，再縱向深入單一流程的細節。
- **組合提問**：若多個釐清項目屬於同一個 Command 的同一組邊界條件，可合併為一題呈現，但答案仍需分別回寫至各自檔案。

輸出佇列摘要給使用者（顯示總題數與本次預計涵蓋範圍），然後開始提問。

## 2. 逐題互動

**每次只問一題**，並嚴格遵守以下呈現格式：

1. 顯示題號與總數（例如：`第 3 題 / 共 12 題`）。
2. 顯示 **# 釐清問題** 的完整句子。
3. 顯示 **# 定位**，讓使用者知道這題在改哪一個流程的哪一個元素。
4. 以表格顯示 **# 多選題** 的所有選項。
5. 顯示 **# 優先級**。
6. 等待使用者回答，**不得自行代答或猜測**。

接受的回答形式：
- 選項代號（`A`、`B`、`C`…）
- `Short` 加上 5 字以內的簡答
- 自由文字（若使用者的答案不在選項內，直接採用其文字）
- `skip` / `跳過`：保留該項目不動，繼續下一題
- `stop` / `結束`：結束本次互動，進入步驟 5 回報

**回答驗證**：
- 若答案模糊、含未量化形容詞、或仍存在兩種解讀，**追問一次**以收斂，追問後仍模糊則記錄為 `Partial` 並繼續。
- 若答案與 `.es-clarify/resolved/` 中的既有共識矛盾，**明確指出矛盾點**並請使用者裁決要保留哪一個；使用者裁決後，一併更新被推翻的那個 resolved 檔案。
- 若答案會連帶影響其他尚未提問的釐清項目，即時告知使用者，並在該項目檔案中註記。

## 3. 回寫模型

每收到一個有效答案，**立即**回寫（不要累積到最後才一起改）：

| 答案類型 | 回寫位置 |
|----------|----------|
| Event 是否成立、命名、時序、軟體邊界 | 流程中的 Event 清單，含過去式命名與順序 |
| Command 識別、輸入參數、Actor 與權限 | 該 Event 下的 Command 定義與「Actor 執行 Command 導致 Event」串聯句 |
| Precondition / Postcondition | 該 Command 的規則區塊，一條規則一行，維持原子化 |
| Aggregate 欄位、型別、不變條件、狀態機 | Aggregate 定義區塊，欄位需標明型別與說明 |
| Read Model 欄位、來源、即時性 | Read Model 定義區塊，並註明服務哪一個 Actor |

回寫原則：
- 使用使用者的原話詞彙，維持統一語言（Ubiquitous Language）一致。
- 新增規則時保持原子化：一條規則只驗證 / 只描述一件事。
- 若答案讓某個 Event 被判定為「留在系統邊界之外」，在模型中明確標記為人工作業，不得直接刪除。
- 回寫後向使用者顯示這一題實際改動了哪些行，讓對方可即時糾正。

## 4. 歸檔已解決項目

答案回寫成功後，將該釐清項目檔案移至 `.es-clarify/resolved/<原資料夾名>/`，並在檔案末端追加：

```markdown
# 解決結果

<使用者選擇的選項代號與完整答案>

# 回寫位置

<實際更新的檔案與區塊>

# 解決日期

<YYYY-MM-DD>
```

保留原有的「釐清問題 / 定位 / 多選題 / 影響範圍 / 優先級」內容不刪除，供後續 discovery 比對「避免重複提問」。

## 5. 提前終止判斷

在下列情況下，主動建議使用者結束本輪，不必問完所有題目：

- 剩餘項目皆為 Low 優先級，且不影響任何 High 項目的答案。
- 使用者連續多題回覆 `skip`，顯示目前不是釐清的好時機。
- 某個答案推翻了上游前提，導致大量下游項目需要 `/es-discovery` 重新掃描 —— 此時應**立即停止**並建議重跑 discovery。

## 6. 回報完成

產出簡潔報告，包含：

- 本輪已解決題數 / 跳過題數 / 剩餘題數
- 剩餘項目的優先級分佈（High / Medium / Low）
- 事件風暴模型檔實際更新的區塊清單
- 若有矛盾裁決，列出被推翻的既有共識
- 下一步建議：繼續 `/es-formulation`，或先重跑 `/es-discovery` 重新掃描覆蓋度

# 行為規則

- **一次一題**：不得一次拋出多題，也不得批次要求使用者填答。
- **不代答**：使用者未回覆前，絕不自行推定答案或先行回寫。
- **即時回寫**：每題答完立刻更新模型與歸檔，避免中途中斷造成答案遺失。
- **維持原子化**：規則、欄位、Event 一律保持「一條只講一件事」。
- **不擴張範圍**：僅回答被問到的決策點，不順手新增使用者沒說過的 Event、Command 或欄位。
- **可追溯**：每個模型改動都能對應回一個 resolved 釐清項目。
