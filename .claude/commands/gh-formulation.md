目標：把 `/gh-discovery` 偵測出來的翻譯決策點，透過**一次一題**的互動問答收斂成明確答案，立即回寫成翻譯規約，並在條件成熟時直接產出可執行的 Feature File。

# 前置檢查

1. 讀取 `.gh-clarify/overview.md`。若不存在，回報「請先執行 `/gh-discovery`」並停止。
2. 讀取 `.gh-clarify/` 下所有釐清項目檔案（`feature/`、`when/`、`given/`、`then/`、`outline/`、`query/`、`organization/`）。
3. 讀取 `.gh-clarify/resolved/` 下所有已解決項目，作為本階段的既有翻譯慣例。
4. **比對業務面既有共識**：`.es-clarify/resolved/` 有 392 檔、約 27,600 行，**不得整批讀取**。
   改為先讀 `.es-clarify/overview.md`，再於**每一題出題前**，以該題的 Command / Event / Aggregate 名稱
   對 resolved 檔名做關鍵字比對，命中者才開檔細讀。回答任何一題時都不得與其矛盾。
   （這一步也是〈推薦選項〉的依據來源——推薦理由若聲稱「模型已有某慣例」，必須來自實際開過的那個檔案。）
5. 讀取事件風暴模型檔（`Event-Storming_事件風暴/` 全部檔案）作為翻譯素材來源。
6. 讀取 `Gherkin_行為規格/00_翻譯規約.md`（若不存在，於第一次回寫時建立）。
7. 讀取已產出的 `Gherkin_行為規格/features/**/*.feature`（若有）。

# 執行步驟

## 1. 決定提問順序

依 `overview.md`「3.4 建議釐清順序」排定佇列，並套用以下調整：

- **全域先於個別**：`organization/`（GH7）與影響全部檔案的慣例題，必須排在所有單一 Feature 的題目之前。已翻好的檔案若因慣例晚定而需重改，成本最高。
- **切分先於內容**：`feature/`（GH1）排在 `when/`、`then/`、`given/` 之前——不知道有幾個檔案，就不知道句子該寫進哪裡。
- **Rule 分組先於句子**：`then/` 的失敗分類（決定 Rule 數）排在 `given/` 的句子素材之前。
- **依賴優先**：若 A 的答案是 B 的前提，A 必須排在 B 之前，並在提問時告知使用者「這題會連帶決定第 X 題」。
- **組合提問**：同一個 Command 的多個 Examples 表格細節可合併為一題呈現，但答案仍需分別回寫至各自檔案。

輸出佇列摘要（總題數、本次預計涵蓋範圍、預估影響幾個 Feature File），然後開始提問。

## 2. 逐題互動

**每次只問一題**，**直接以對話文字出題，不使用選項框元件**，並嚴格遵守以下呈現格式：

1. 顯示題號與總數（例如：`第 3 題 / 共 12 題`）。
2. 顯示 **釐清問題** 的完整句子。
3. 顯示 **定位**：這題在改哪一個 Command / Query 的哪一段 Gherkin。
4. 顯示 **白話說明**：用不含模型術語的語言解釋這題在問什麼。
5. 顯示 **具體對照**：把主要選項各自翻成一小段實際的 Gherkin 片段並列出來，讓使用者用眼睛比較，而不是靠想像。
6. 以表格顯示 **多選題** 的所有選項，**推薦選項標 `★`**。
7. 顯示 **推薦理由**：為什麼推薦這個選項（引用本專案既有裁決或業界通例）。
8. 顯示 **各選項的翻譯後果**（檔案數 / Scenario 條數 / 維護成本）。
9. 顯示 **優先級**。
10. 等待使用者回答，**不得自行代答或猜測**。

### 出題的硬性規則

- **每一題都必須有推薦選項與理由。** 沒有推薦就不算出完題。理由要說明「多數團隊為什麼這樣做」，而不只是「這樣比較好」。
- **推薦前先查證。** 引用「模型裡已經有某條規則」之前，必須實際 grep / 讀取該檔案確認該規則存在且文字如你所述。憑記憶宣稱既有規則是本流程最常見的錯誤來源。
- **涉及平台規範者必須查官方文件。** App Store 審核指南、支付規則、法規相關的選項，不得憑記憶推薦；查不到就標「未查證」，且該選項不給推薦。
- **一律白話出題。** 不得直接丟「這個 Postcondition 的 Aggregate 斷言要不要展開」這種句子；改成「操作成功以後，要不要逐欄檢查資料庫裡的數字對不對？還是只看有沒有成功就好？」並附 Gherkin 片段。
- **能力值相關的題目一律拆細。** 能力值是本系統的核心，不得把多個決策點合併成一題帶過。

接受的回答形式：

- 選項代號（`A`、`B`、`C`…）
- `Short` 加上 5 字以內的簡答
- 自由文字（若使用者的答案不在選項內，直接採用其文字）
- `skip` / `跳過`：保留該項目不動，繼續下一題
- `stop` / `結束`：結束本次互動，進入步驟 6 回報

### 回答驗證

- 若答案模糊、或仍存在兩種寫法，**追問一次**以收斂；追問後仍模糊則記錄為 `Partial` 並繼續。
- 若答案與 `.es-clarify/resolved/` 的**業務共識**矛盾（例如選了一種寫法，但該寫法預設的業務行為與模型裁決不同），**立即指出矛盾點**並請使用者裁決。這種情況通常代表模型有缺口，應建議跑 `/es-discovery` 而非在此改業務。
- 若答案與 `.gh-clarify/resolved/` 的**翻譯慣例**矛盾，指出被推翻的慣例，並列出**已依舊慣例產出的 Feature File 清單**（這些檔案需要一併重改），由使用者決定是否採用。
- 若答案會連帶影響其他尚未提問的釐清項目，即時告知，並在該項目檔案中註記。

## 3. 回寫翻譯規約

每收到一個有效答案，**立即**回寫（不累積到最後）：

| 答案類型 | 回寫位置 |
|----------|----------|
| 全域慣例（語言、關鍵字、檔名、資料夾規則、Rule 標題格式） | `Gherkin_行為規格/00_翻譯規約.md` §1 全域慣例 |
| Feature 切分（哪些 Command 各自成檔、循環怎麼切） | `Gherkin_行為規格/00_翻譯規約.md` §2 Feature 清單（一列一個檔案，含路徑） |
| When 觸發源（Actor 觸發 / Policy 觸發 / 排程 / 外部回呼） | `Gherkin_行為規格/00_翻譯規約.md` §3 觸發源對照表 |
| 失敗原因分類（每個 Command 有幾類失敗 → 幾個 Rule） | `Gherkin_行為規格/00_翻譯規約.md` §4 失敗分類表 |
| Given 素材、初始值、Actor Key 寫法、Event 順序 | `Gherkin_行為規格/00_翻譯規約.md` §5 Given 素材規則 |
| Scenario Outline 判定與 Examples 欄列設計 | `Gherkin_行為規格/00_翻譯規約.md` §6 Outline 清單 |
| 關鍵 Query 判定、Read Model 斷言範圍、分頁排序 | `Gherkin_行為規格/00_翻譯規約.md` §7 Query 規則 |

**回寫原則**

- 使用使用者的原話詞彙，維持與事件風暴模型一致的統一語言。
- 每一條規約標註來源：`*來源：.gh-clarify/resolved/<資料夾>/<檔名>（選項 X）*`，比照事件風暴模型既有的註記慣例。
- **不回寫事件風暴模型本體。** 本階段只決定「怎麼翻」，不改「是什麼」。若答案實際上改動了業務規則，停下來告知使用者，並建議改由 `/es-discovery` → `/es-formulation` 處理。
- 回寫後向使用者顯示這一題實際改動了哪些行。

## 4. 產出 Feature File（條件達成時）

當某一個 Command / Query 的**全部**相關釐清項目都已解決（`feature`、`when`、`given`、`then`、`outline` 或 `query` 皆無待解項），立即依樣板產出 `Gherkin_行為規格/features/<aggregate>/<動詞+名詞>.feature`，並向使用者展示全文供確認。

產出時嚴格遵守樣板與七項決議：

- 修改型：`Rule: 前置條件` 依失敗原因**分成多個 Rule**（權限驗證／輸入驗證／業務規則驗證／併發衝突），每個失敗 Scenario 都保留 `And 驗證 <Aggregate> 狀態保持不變`；`Rule: 後置條件` 的 `Then` 依序寫「操作成功」→「改變後的狀態」→「產生的事件」。
- 查詢型：失敗 Rule 同樣依原因分開，但**不加 `And` 子句**；後置條件的 `Then` 斷言 Read Model 內容。
- 權限驗證獨立成一種 Rule，其 `Given` **沿用完整樣板，不簡化**。
- Policy 觸發的 Command，`When` 寫「當 <Event> 發生時」，且與 Actor 觸發版本**分屬不同 Rule**。
- Given 中多個 Event 的順序，只在順序影響最終狀態時才列出並標註。
- 邏輯相同、僅資料不同者，**一律**寫成 `Scenario Outline` + `Examples`，不得複製貼上。
- 檔案放在該 Aggregate 的資料夾；跨 Aggregate 者放發起端。

若該 Command 仍有待解項，不得先產出半成品檔案，改在規約的 §2 Feature 清單標記「待補：<剩餘題目>」。

## 5. 歸檔已解決項目

答案回寫成功後，將該釐清項目檔案移至 `.gh-clarify/resolved/<原資料夾名>/`，並在檔案末端追加：

```markdown
# 解決結果

<使用者選擇的選項代號與完整答案>

# 回寫位置

<實際更新的規約章節；若已產出 Feature File，列出檔案路徑>

# 產出的 Gherkin 片段

<實際寫進 .feature 的那段內容；尚未產檔者填「待該 Command 其餘題目解決後產出」>

# 解決日期

<YYYY-MM-DD>
```

保留原有的「釐清問題 / 定位 / 白話說明 / 多選題 / 推薦選項與理由 / 影響範圍 / 優先級」內容不刪除，供後續 discovery 比對「避免重複提問」。

## 6. 提前終止判斷

在下列情況主動建議結束本輪：

- 剩餘項目皆為 Low 優先級（措辭、標題格式），且不影響任何檔案的結構。
- 使用者連續多題回覆 `skip`。
- 某個答案推翻了全域慣例，導致已產出的多個 Feature File 需要重改 —— 此時**立即停止**，先完成重改再繼續。
- 某個答案顯示模型本身缺了業務決策 —— **立即停止**並建議跑 `/es-discovery`。

## 7. 回報完成

- 本輪已解決題數 / 跳過題數 / 剩餘題數
- 剩餘項目的優先級分佈與分類分佈
- `Gherkin_行為規格/00_翻譯規約.md` 實際更新的章節清單
- 本輪新產出或修改的 `.feature` 檔案清單（含 Scenario 條數）
- 若有矛盾裁決，列出被推翻的既有慣例與需連帶重改的檔案
- 下一步建議：繼續 `/gh-formulation`、重跑 `/gh-discovery`、或回頭跑 `/es-discovery`

# 行為規則

- **一次一題**：不得一次拋出多題，也不得批次要求填答。
- **不用選項框**：直接以對話文字出題，使用者會在對話中回覆。
- **必附推薦**：每題都要標出推薦選項並說明理由，理由須引用可查證的依據。
- **先查證後宣稱**：引用模型既有規則前先讀該檔案；引用平台規範前先查官方文件。
- **白話與例子**：每題都要有白話說明與具體 Gherkin 片段對照。
- **不代答**：使用者未回覆前，絕不自行推定答案或先行回寫。
- **即時回寫**：每題答完立刻更新規約與歸檔。
- **不改業務**：本階段只決定翻譯寫法，不新增或修改 Event、Command、規則與欄位。
- **能力值拆細**：能力值相關決策一律逐點提問，不合併帶過。
- **可追溯**：每一段 Gherkin 都能對應回一個 resolved 釐清項目。
