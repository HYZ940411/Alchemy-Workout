# 釐清問題

「不採逾時自動退回、亦不採管理員可強制接手」的既有理由為「模型目前無管理員 Aggregate」，而管理員 Aggregate 已於 2026-08-11 建立——該裁決是否因前提消失而重新檢視？

# 定位

流程：管理員管理社群流程
元素：Command — 審視檢舉 / 審視申訴；Aggregate — 檢舉、申訴（審視中狀態）
細節：`管理員管理社群流程.md`「[決策] 不採逾時自動退回或任何管理員可強制接手：兩者皆須在案件上記錄處理者，而模型目前無管理員 Aggregate」。現況：案件停在審視中無人可接手，僅由待審佇列的「最久等待時間」呈現

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 檢舉與申訴 Aggregate 新增「處理中的管理員 ID」欄位，並允許他人於逾時後強制接手（新增 Command「接手審核案件」與對應 Event） |
| B | 僅新增「處理中的管理員 ID」欄位（可稽核誰在審），不新增強制接手路徑；卡住的案件仍靠逾期升級提示處理 |
| C | 維持現狀不改：理由由「無管理員 Aggregate」改為「審核積壓為營運指標而非業務規則」（承〈四類審核〉的既有立場） |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

- 檢舉與申訴 Aggregate 的欄位；可能新增 Command 與 Event
- 〈Read Model：管理員待審佇列〉是否顯示處理者
- 管理員 Aggregate 的權限組與 Command 對應表（現為 30 個）
- 相關已解決項目：`resolved/aggregate/管理員_管理員的帳號與權限尚未建模.md`、`resolved/rule/四類審核_審核時限與逾期處理規則全數缺失.md`

# 解決結果

**A**：記錄處理者 ＋ 逾期後可接手。

- 檢舉與申訴 Aggregate 新增「處理中的管理員 ID」欄位（審視中時有值，終止狀態清空）。
- 新增 Command「接手審核案件」（Actor：管理員）與 Event「審核案件已接手」，
  攜帶：審核類型（檢舉 / 申訴）、案件識別碼、原處理者的管理員 ID。
- Precondition 兩條：該案件狀態為審視中且已發生「審核已逾期」；執行者不為目前的處理中管理員。
- Postcondition：處理中的管理員 ID 改寫為接手者，狀態維持審視中，不重設審核時限起算點。
- **接手條件掛在既有的「審核已逾期」之上，不另訂時間參數**（避免兩套時鐘）。
- 維持「審視中不自動退回待審視」：接手為指名的轉移，退回會使案件回到無人負責。
- 所需權限組為內容審核；管理員 Command 30 → 31，內容審核組 11 → 12。

**被推翻的既有共識**：原「不採逾時自動退回或任何管理員可強制接手」——
其唯一理由「模型目前無管理員 Aggregate」已於第六輪第 16 題失效。
