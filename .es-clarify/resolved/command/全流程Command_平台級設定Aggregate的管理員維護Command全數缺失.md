# 釐清問題

模型有多個「平台級可調」Aggregate（訓練計畫、動作之平台動作庫、成就定義、獎勵定義、健身目標設定、健身經驗設定、檢舉理由設定、帶徒上限設定、器材明細值域），其內容一律註明「由管理員於後台維護」，但〈Command 清單〉中並無任何對應的管理員維護 Command 與 Event。這些維護行為是否納入軟體邊界？

# 定位

流程：跨流程（管理員後台，不隸屬既有任一條流程）
元素：Command 與 Event（皆缺失）；Aggregate：上列 9 個平台級設定 Aggregate
細節：B1 Command 識別完整性、E1 串聯一致性、A4 軟體邊界判斷。〈Command 清單〉現有的管理員設定 Command 僅 7 個（設定新手任務範本、設定每日任務池、設定階級門檻、設定限時任務、設定教官測驗、設定會員權益、新增商品 / 設定商品資訊），上列 9 者一個都沒有。
註：`pending-gaps-3.md` 之 I11 已記錄「訓練計畫 Aggregate 無任何維護類 Command」，本項為其擴大盤點。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 全數納入：為 9 個 Aggregate 各補一個管理員 Command 與一個「管理員已設定⋯」Event，比照既有 7 個設定 Command 的處理方式 |
| B | 僅為「會改變使用者可見行為」者建模（訓練計畫、平台動作庫、成就定義、獎勵定義），其餘 5 個純值域清單留在系統邊界之外，視為後台組態 |
| C | 全數留在系統邊界之外：後台維護不產生業務事實，只需保證資料可調，不需 Event |
| D | 新增單一泛用 Event「平台設定已變更」（攜帶設定類型與變更前後值）取代 9 個各自的 Event，供稽核 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響〈Command 清單〉（可能增列至多 9 條 Command 與 9 個 Event）、Event 總數、以及各設定 Aggregate 的稽核能力（獎勵定義與成就定義的調整目前無任何紀錄可查）。若採 A 或 D，須一併定義該些 Command 的 Precondition（調整不追溯既有發放紀錄，此原則模型已多處定案）。
相關已解決項目：`resolved/command/全流程Command_各Event對應的Command清單與命名尚未建立.md`（建立本清單）、`resolved/aggregate/獎勵_獎勵的種類與統一資料結構.md`、`resolved/aggregate/成就_各類成就的統一資料結構.md`。

# 解決結果

**選項 B** —— 僅為「會改變使用者已取得或將取得之實質內容」者建模，其餘 5 個留在系統邊界之外。

| 納入軟體邊界（新增 4 Command ＋ 4 Event） | 留在系統邊界之外 |
|----------------------------------------|----------------|
| 訓練計畫、動作（平台動作庫）、成就定義、獎勵定義 | 健身目標設定、健身經驗設定、檢舉理由設定、器材明細值域、帶徒上限設定 |

判準與理由：左欄四者改動後直接改變使用者拿到什麼（獎勵數額、成就門檻、課表內容、可選動作），
且三者皆已明文承諾「調整不追溯既有紀錄」，而申訴機制未設時效上限 ——
既已承諾不追溯，就須有可稽核的依據記錄何時改的、改成什麼。
右欄五者為值域清單，改動只影響下拉選單，不改動任何已發生的事實。

不採 A（全數納入）：Event 為對稱性膨脹 5 個且無讀者。
不採 C（全數排除）：三處「不追溯」的承諾將沒有對應證據。
不採 D（單一泛用 Event）：攜帶值域為任意設定的任意變更，Precondition 與 Postcondition 皆寫不出來。
帶徒上限設定歸右欄：其調整不使既有教官的帶徒上限降低（承單調遞增裁決），不改動已取得的內容。
