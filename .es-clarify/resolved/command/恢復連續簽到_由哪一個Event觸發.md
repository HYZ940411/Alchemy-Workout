# 釐清問題

Command「恢復連續簽到」（Actor：系統）由哪一個 Event 觸發？

# 定位

流程：補簽流程
元素：Command：恢復連續簽到（`01_Command清單.md` L125，Actor：系統）
細節：`補簽流程.md` 中無任何 [Policy] 或 [串聯] 指明其觸發來源。

# 白話說明

`01_Command清單.md` L125 把這個 Command 的 Actor 標成**系統**：

```
| 恢復連續簽到 | 系統 | 連續簽到已恢復 |
```

「系統」的意思是它不是使用者按出來的，是系統自己跑的。
既然是自己跑的，就一定有個觸發它的訊號——**但模型沒說那是什麼**。

`補簽流程.md` 這三行是連著寫的，中間沒有任何箭頭、[Policy] 或 [串聯]：

```
L21  使用者已使用補簽券
⋯
L25  使用者已補簽
L26  連續簽到已恢復
```

排在一起不等於因果關係。對照同一份檔案 L20 就有明確的串聯句
（`[串聯] 使用者執行「使用補簽券」導致「使用者已使用補簽券」— Actor：使用者`），
可見這裡是漏寫而非刻意省略。

**這個問題在多張券的情境下會變得很具體**：使用者連補三天，
「恢復連續簽到」是每補一天就跑一次（跑三次），還是三天全部補完才跑一次（跑一次）？

# 多選題

| 選項 | 描述 | 推薦 |
|------|------|------|
| A | **由「使用者已補簽」觸發**：補上 [Policy]，該日被補記為已簽到後，系統重算連續天數。連補三天則觸發三次 | ★ |
| B | **由「使用者已使用補簽券」觸發**：扣券成功即重算連續天數 | |
| C | **改為使用者觸發**：Actor 由系統改為使用者，補簽後由使用者自行確認恢復 | |
| D | **整批完成後觸發一次**：使用者一次選定多天送出，全部補完才觸發一次重算 | |
| Short | 提供其他簡短答案（<=5 字） | |

# 推薦選項與理由

**推薦 A（由「使用者已補簽」觸發）。**

- **連續天數的計算依據是「那一天算不算有簽到」，不是「券有沒有被扣掉」**。
  扣券是付出代價，補簽才是產生事實。用 B 的話，萬一扣了券但補簽因故未成立
  （例如那天其實已經簽過），連續天數會被錯誤地重算。
- **與每日簽到流程的既有形狀完全一致**。`每日簽到流程.md` L40–L41 是
  「使用者已簽到 → 連續簽到已紀錄」——簽到的事實發生後，系統才去記連續天數。
  補簽這邊對應成「使用者已補簽 → 連續簽到已恢復」，是同一個句型，
  不需要為補簽另立一套時序。
- **不推薦 C**：`01_Command清單.md` L125 已明定 Actor 為系統，改成使用者是推翻既有裁決；
  而且要使用者補完之後再按一次「恢復」，多一步且沒有任何決策價值——
  沒有人會補了簽卻不想恢復連續天數。
- **不推薦 D**：D 隱含了「補簽是批次操作」這個尚未成立的前提。
  模型目前寫的是「一張補一天」（`補簽流程.md` L10、L23），一次一張、逐張處理，
  沒有任何地方定義過批次送出的界線。若要採 D，得先定義一批的範圍與失敗處理，
  改動範圍遠大於本題。
- **A 觸發三次會不會有問題？** 不會，只要連續天數的計算式是可重入的
  （每次都從當前狀態重算出正確值）。這正好與
  〈連續簽到已恢復_連續使用多張補簽券時連續天數應如何計算〉一題的推薦選項（逐日推算）相符：
  逐日推算天生可重入，跑三次和跑一次結果相同。

# 解決結果

**選項 A** —— 由「使用者已補簽」觸發。

補簽流程的完整連鎖至此定案，一個 Command 對一個 Event，Event 之間以 [Policy] 串接：

```
使用者執行「使用補簽券」   → 使用者已使用補簽券   （Actor：使用者）
        ↓ [Policy]
系統執行「補簽」           → 使用者已補簽         （Actor：系統）
        ↓ [Policy]  ← 本題定案
系統執行「恢復連續簽到」   → 連續簽到已恢復       （Actor：系統）
```

**連帶約束**：連補多天時每補一天觸發一次，故「恢復連續簽到」**須為可重入** ——
每次皆由當前狀態重算出正確值，重複執行不改變結果。
此約束為選項 A 的直接後果，已一併寫入模型。

**與第 4 題的牽動**：可重入性要求連續天數的計算式必須是「由當前狀態重算」而非「在舊值上累加」。
第 4 題若選逐日推算（推薦選項），天生滿足；若選整批延後清空，則本題須改選 D。
第 4 題定案時須回頭複核本條。
