# 釐清問題

「使用者已加入團隊」由誰觸發？加入方式為隊長邀請、使用者申請待核准，或公開直接加入？

# 定位

流程：團隊組隊流程
元素：Command「加入團隊」；Actor；Event「使用者已加入團隊」
細節：Command 識別與輸入（B1 / B3）；Actor 識別與觸發源（B4 / B5）；缺失的申請 / 邀請分支 Event（A1）。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 隊長邀請制：須補「隊長已邀請成員」與「使用者已接受邀請 / 已拒絕邀請」三個 Event |
| B | 使用者申請制：須補「使用者已申請加入團隊」與「隊長已核准 / 已拒絕加入申請」三個 Event |
| C | 公開加入：任何使用者可直接加入未滿員的團隊，不需核准，維持現有單一 Event |
| D | 以邀請碼加入：隊長產生邀請碼，持碼者直接加入，須補「隊長已產生邀請碼」Event |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響團隊組隊流程的 Event 清單、「使用者已加入團隊」的 Precondition（是否需核准）、團隊 Aggregate 是否需承載邀請 / 申請狀態，以及隊長權限清單。
本項為新掃描發現，非承接 `pending-gaps.md`。
相關已解決項目：`resolved/aggregate/團隊_團隊人數上限與角色設定.md`（已定人數上限與角色，未定加入方式）。

# 優先級

High

# 解決結果

**選項 A-2**：隊長邀請制 ＋ 公開招募申請併用（即選項 A 與 B 兩套 Event 同時採用）。

**追問與修正**：使用者指出純邀請制（原選項 A）會讓「沒有對象可邀請」的使用者無路可走——雖然建立團隊無門檻，
但 1 人團隊在日常排行榜（＝全體成員個人分數加總）等於必輸，等同有團隊而無團隊價值。故補上公開招募路徑。

**團隊可見性**：新增欄位，值域為公開 / 私密，建立時指定，預設公開。

- 公開團隊可被搜尋並接受加入申請；私密團隊僅能經隊長邀請加入。

**新增 6 個 Event**：

| 路徑 | Event |
|------|-------|
| 隊長邀請 | 隊長已邀請成員、使用者已接受邀請、使用者已拒絕邀請 |
| 公開招募申請 | 使用者已申請加入團隊、隊長已核准加入申請、隊長已拒絕加入申請 |

- 兩條路徑皆由隊長把關，不採公開直接加入（陌生人不得硬塞進 5 人小隊）。
- 「使用者已加入團隊」成為多對一 Event，由「使用者已接受邀請」或「隊長已核准加入申請」導致。
- 拒絕後該筆邀請 / 申請失效，可再次邀請 / 申請。
- 不採 A-3（系統媒合）：需要媒合規則參數，且媒合品質差時使用者會反覆退出重配。
