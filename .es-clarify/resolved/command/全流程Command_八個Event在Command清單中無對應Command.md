# 解決結果

**選項 A** —— 逐一補上 7 個獨立 Command（原題 8 個，「AI 調整已失敗」已於本輪第 1 題解決）：

| Command | Actor | 導致的 Event |
|---------|-------|--------------|
| 發送訓練提醒 | 系統 | 訓練提醒已發送 |
| 變更團隊可見性 | 使用者（隊長） | 隊長已變更團隊可見性 |
| 判定團隊邀請逾期 | 系統 | 團隊邀請已逾期 |
| 判定加入申請逾期 | 系統 | 加入申請已逾期 |
| 釋放庫存 | 系統 | 庫存已釋放 |
| 因商品下架取消訂單 | 系統 | 訂單已因商品下架取消 |
| 駁回申訴 | 管理員 | 申訴已駁回 |

**「駁回申訴」採獨立 Command（A）而非併入審視申訴（C）的理由**：
申訴與檢舉是同形的兩段動作（先審視、再處置），檢舉路徑已用 3 個 Command 完成
（審視檢舉 / 下架違規內容 / 駁回檢舉），申訴照做即對稱；
而「一 Command 兩結果」在模型中的三個既有用法（審核公開訓練、回報支付結果、回報儲值結果）
皆為單步判定，無「審視」這一段。採 C 另須移除既有 Command「撤銷處罰」，屬推翻既有裁決。

**不採 B（兩個逾期判定合併）的理由**：團隊邀請與加入申請為兩個不同 Aggregate、
兩個相反方向（隊長邀人 vs 他人申請），只是同為 7 天逾期；
「一 Command 兩結果」指的是同一對象的兩種判定結果，非同一動作作用於兩種對象。

**不採 D（訂單取消併入下架 Postcondition）的理由**：第五輪已明文裁決其為獨立 Event，
併入 Postcondition 會使它成為沒有 Actor 的 Event。

## 過程中辨識出的連帶缺口（已轉記，非本題裁決）

「管理員已審視檢舉」與「管理員已審視申訴」皆不改變任何 Aggregate 欄位，
審視後狀態仍為「待審視」，模型無狀態可表達「已看過未決定」。
此缺口**檢舉與申訴共有**，經使用者同意延至
`aggregate/申訴_申訴不成立時的終止狀態與Event兩處定義互相矛盾.md` 一併裁決（該檔已加註）。
