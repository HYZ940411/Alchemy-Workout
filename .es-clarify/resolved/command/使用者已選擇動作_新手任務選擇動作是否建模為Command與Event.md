# 釐清問題

新手任務範本提供三個候選動作供使用者三選一，但使用者「選擇」某個候選動作這個動作本身，是否應建模為獨立的 Command 與 Event，尚未裁決。既有的逐項完成建模理由為「供新手引導漏斗流失率分析」，而「開始了新手任務但沒選定動作」正是一個真實的流失點；但也可比照「偏好訓練時段的拖拉操作」視為純介面操作，不需建模。

# 定位

流程：新手任務流程
元素：Read Model「新手任務清單」的「已選定的動作」欄位（空值表示尚未選擇，此時不進入執行畫面）
細節：新手任務的其餘步驟（開始、完成單項、完成、領取獎勵）皆已逐一建模為 Command，唯獨「選擇動作」這一步是否建模尚未定案，造成該流程的顆粒度不一致。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 建模為 Command「選擇候選動作」與 Event「使用者已選擇候選動作」：新手任務的其餘步驟皆逐一建模，此步驟若不建模會使漏斗分析出現一個無法追蹤的斷點（開始了任務、卻不知道卡在「選動作」還是「選了動作卻沒做」）（**推薦**：與模型既有的「逐項完成建模」設計意圖一致——註冊流程正是為了漏斗分析而將 9 個必填欄位逐一建為 Event，新手任務三選一的選擇環節性質相同，且成本極低（僅一個 Command）） |
| B | 不建模，比照偏好訓練時段的拖拉操作視為純介面操作，由「已選定的動作」欄位的狀態變化直接反映在 Read Model 上，不產生業務 Event |
| C | 不建模為獨立 Event，但併入「使用者已開始新手任務」的 Postcondition 一併記錄所選動作（選擇與開始視為同一次操作） |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響新手任務流程 Command 清單的完整性、新手任務漏斗分析的顆粒度。

# 優先級

Low

# 解決結果

**選項 A**：建模為 Command「選擇候選動作」＋ Event「使用者已選擇候選動作」（Actor：使用者）。

- Precondition：「使用者已開始新手任務」已發生，且尚未選定動作。
- Postcondition：寫入新手任務 Aggregate 的「已選定的動作」欄位。
- **可改選**：選定後未勾選完成前可改選其他候選動作，本 Event 重複發生並覆蓋原值。
- 攜帶資訊：所選的任務項目 ID。

## 理由

- 新手任務的其餘步驟皆已逐一建模，此步驟不建模會使**漏斗分析出現斷點**——
  知道有人開始了任務卻沒完成，但分不出他卡在「沒選動作」還是「選了卻沒做」。
- 承註冊流程的既有設計意圖：該流程正是為了漏斗流失率分析而將 9 個必填欄位逐一建為 Event。
- **不採 B（比照偏好訓練時段的拖拉操作視為純介面操作）**：拖拉為同一欄位的反覆微調，
  中間狀態無業務意義；而「選了哪一個候選動作」是有明確業務意義的決定，且為漏斗的一個關卡。
- **不採 C（併入「使用者已開始新手任務」的 Postcondition）**：兩者為不同時點的兩個決定
  （點開始 vs 選動作），合併即無法區分卡在哪一關，等同放棄本建模的唯一理由。
