# 釐清問題

每日任務池與新手任務範本皆已定案「由管理員維護的平台級 Aggregate」，但「任務項目」本身的結構未定義：一個任務項目包含哪些欄位？系統如何判定該項目已完成？

# 定位

流程：每日任務流程、新手任務流程
元素：Aggregate「每日任務池」「新手任務範本」的任務項目結構
細節：D2 欄位定義、E3 Event → Aggregate 一致性。
現況：每日任務流程檔僅有 Policy「完成每日訓練 / 互動 累計每日任務進度」，未定義任務項目如何描述「訓練一次」「按讚 3 次」；「每日任務進度已更新」的觸發來源 Event 亦未列舉。新手任務同理，「使用者已完成單項新手任務」的 Actor 為使用者，但若任務項目為「完成一次訓練」則實際判定者為系統。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 任務項目欄位＝任務名稱、判定來源 Event、目標次數、獎勵定義 ID；系統訂閱該來源 Event 累計進度，達目標次數即完成，Actor 一律為系統 |
| B | 同 A，但另增「任務類型」欄位（訓練類 / 社群類 / 簽到類），供每日抽取時保證類型分散 |
| C | 任務項目僅有名稱與獎勵，完成判定由使用者手動回報（Actor：使用者），系統不自動判定 |
| D | 兩種任務分開建模：每日任務採 A 的自動判定，新手任務採 C 的手動回報（新手任務含「填寫個人資料」等系統難以判定的引導項） |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響每日任務池與新手任務範本 Aggregate 的欄位、「每日任務進度已更新」與「使用者已完成單項新手任務」的觸發來源與 Actor、〈Command 清單〉中兩者的 Actor 指派（現分別為系統與使用者，可能不一致）、每日抽取 3 項的抽取邏輯，以及任務清單 Read Model 的欄位來源。
相關已解決項目：`resolved/aggregate/每日任務_任務項目與數量由誰定義.md`、`resolved/aggregate/新手任務_任務項目內容與數量由誰定義.md`（兩者皆只定案「由管理員定義」，未定義項目結構）。

# 解決結果（第 15a 題）

**選項 B**

新手任務範本的任務項目**共用〈課表內容結構（共用）〉**（動作清單 → 組數 → 每組目標重量與次數），
但執行**不走訓練紀錄流程**，自成一套簡化的勾選機制。

| 項目 | 新手任務 | 一般訓練 |
|------|----------|----------|
| 產生訓練紀錄 | 否 | 是 |
| 產生訓練量 | 否 | 是 |
| 能力值來源 | 獎勵定義給定 | 訓練量公式計算 |
| 經驗值來源 | 獎勵定義給定（100） | 獎勵定義給定（30） |
| 計入個人排行榜分數 | 否 | 是 |
| 計入累積訓練次數 | 否 | 是 |
| 計入連續訓練天數 | 否 | 是 |

- 不引入快照、訓練進度條、組間休息計時與 40 分鐘逾時中斷判定
- 「使用者已完成單項新手任務」的 Actor 維持**使用者**（實際做完動作後勾選），
  此與〈Command 清單〉的既有指派一致，原先疑似的 Actor 矛盾不存在
- **連帶後果**：因不計入累積訓練次數，「使用者已解鎖自訂訓練功能」（Precondition 為
  累積訓練次數 ≥ 1）不會因完成新手任務而觸發，須待第一次正式訓練結算
