# 釐清問題

「哪一天有簽到、哪一天沒簽到」的逐日明細，應由哪一個 Aggregate（或哪一個欄位）承載？

# 定位

流程：補簽流程（亦及於每日簽到流程）
元素：Aggregate：連續簽到 Aggregate（`02_Aggregate定義.md` L2148–L2156）
細節：目前五個欄位皆為彙總值，沒有任何欄位能回答「2026-08-18 那天簽了沒」。

**本題不是重問連續簽到的欄位定義**。
`.es-clarify/resolved/aggregate/連續簽到_連續天數與累計天數的定義與型別.md`（選項 D′）
已裁決五欄位與三條不變條件，該裁決成立不變；
本題補的是**該裁決未涵蓋的逐日明細**。

# 白話說明

連續簽到 Aggregate 現在只有這五個欄位（`02_Aggregate定義.md` L2152–L2156）：

| 欄位 | 型別 | 說明 |
|------|------|------|
| 連續天數 | int | 簽到中斷時歸零 |
| 累計天數 | int | 永不歸零，單調遞增 |
| 中斷前連續天數 | int | 中斷發生時保存歸零前的連續天數 |
| 歷史最長連續天數 | int | 永不減少 |
| 上次簽到日期 | date | 使用者當地日期 |

**五個都是總數，沒有一個記得住「哪一天」。**

但模型有兩個地方非知道「哪一天」不可：

1. `補簽流程.md` L6 的 Precondition 寫著「**該日確實未簽到**」——
   要驗證這件事，就得能查出 08-18 當天的狀態。用「上次簽到日期＝08-22」是查不出來的，
   因為它只記得最後一次，中間簽過沒簽過完全不知道。
2. `04_ReadModel清單.md` L208 的補簽頁日曆是「**每日一筆，狀態值域三值：已簽／未簽／可補簽**」——
   要畫出一個月的日曆，就要有一個月的逐日資料。這份資料現在沒有來源。

# 多選題

| 選項 | 描述 | 推薦 |
|------|------|------|
| A | **新增「每日簽到紀錄」Aggregate**：每位使用者每個已簽到日一筆，欄位為使用者 ID、簽到日期、簽到方式（真實簽到／補簽）。未簽到的日子即「查無此筆」 | ★ |
| B | **於連續簽到 Aggregate 新增一個明細欄位**：如「最近 N 日簽到狀態」清單或位圖，隨簽到／補簽滾動更新 | |
| C | **不新增資料，改由 Event 流推導**：需要時重播「使用者已簽到」「使用者已補簽」兩個 Event 即時算出 | |
| D | **不建模為 Aggregate，只在 Read Model 層保存**：視為補簽頁的展示資料，不屬領域狀態 | |
| Short | 提供其他簡短答案（<=5 字） | |

# 推薦選項與理由

**推薦 A（新增「每日簽到紀錄」Aggregate）。**

- **它是被 Precondition 驗證的東西，就必須是領域狀態，不能只活在 Read Model**。
  `補簽流程.md` L6 拿「該日確實未簽到」當作補簽的前置檢核，這是一條會擋下操作的規則；
  規則所檢核的資料放在 Read Model（選項 D）等於把驗收依據放在不保證一致的地方。
- **「簽到方式」欄位一次解決兩件事**：補簽頁日曆的三值狀態（已簽／未簽／可補簽）需要區分
  真實簽到與補簽日；而〈連續簽到已恢復_連續使用多張補簽券時連續天數應如何計算〉一題若採逐日推算，
  也正需要這份明細。一個 Aggregate 同時餵兩處。
- **本模型已有同型的先例**：`02_Aggregate定義.md` 中「能力值日快照」即為「每人每日一筆」的明細型
  Aggregate（見 `.es-clarify/resolved/aggregate/能力值日快照_保存年限與是否標記為不需精準追蹤.md`），
  本題採同一形狀，不引入新的建模手法。
- **不推薦 B**：把一份會成長的清單塞進彙總型 Aggregate，會讓該 Aggregate 同時承擔兩種職責，
  且 N 要設多大立刻變成另一個爭議點（日曆想顯示多久就得設多大）。
- **不推薦 C**：模型全篇未採事件溯源，其他 Aggregate 一律直接保存狀態；
  單為簽到一處引入重播機制，與全模型不一致，且補簽頁標明「即時」（`04_ReadModel清單.md` L202），
  每次開頁都重播整段歷史不合理。

# 對 Gherkin 翻譯的影響

直接阻擋 `.gh-clarify/given/使用補簽券_某日未簽到這個前提要怎麼寫成Given.md`。

該項要決定「使用者於 2026-08-18 未簽到」這句 Given 怎麼寫。**目前寫不出來**，
因為模型裡沒有任何欄位承載這個事實，Given 無從對應到一個可設定的狀態：

- 選 A：`Given 使用者（U001）沒有 2026-08-18 的每日簽到紀錄`，直接對應一筆資料的有無，
  Then 也能斷言 `Then 使用者（U001）有一筆 2026-08-18 的每日簽到紀錄，簽到方式為補簽`。
- 選 B：Given 要寫成設定一整個清單／位圖，句子冗長且難讀。
- 選 C：Given 只能寫成一串前置 Event，每條 Scenario 都要鋪好幾行背景。

同時也影響 `.gh-clarify/outline/補簽頁_日曆狀態三值是否每值各寫一列.md`
與 `.gh-clarify/query/補簽頁_本月日曆的筆數與順序要不要斷言.md`——
日曆那幾筆資料從哪裡來，決定了 Then 要斷言什麼。

# 解決結果

**選項 A** —— 新增「每日簽到紀錄 Aggregate」。

| 欄位 | 型別 | 說明 |
|------|------|------|
| 使用者 ID | 使用者 ID | 紀錄所屬者 |
| 簽到日期 | date | 使用者當地日期 |
| 簽到方式 | 列舉 | 真實簽到 / 補簽 |

- 每位使用者每個**已簽到日**一筆；未簽到之日不存在對應紀錄，「查無此筆」即代表該日未簽到。
- 主鍵為（使用者 ID，簽到日期）。
- 兩個 Event 各寫入一筆：「使用者已簽到」＝真實簽到、「使用者已補簽」＝補簽。
- 連續簽到 Aggregate 的五欄位與三條不變條件**不因本題變動**。

**保留期限留待第 7 題**，故 Aggregate 規則中該條標為待定。
