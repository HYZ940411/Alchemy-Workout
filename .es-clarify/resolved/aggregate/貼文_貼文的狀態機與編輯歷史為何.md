# 釐清問題

貼文 Aggregate 的狀態機為何（刪除為軟刪除或硬刪除）？編輯後是否保留歷史版本並對讀者標記「已編輯」？

# 定位

流程：發文與互動流程
元素：Aggregate「貼文」；Event「貼文已刪除」「貼文已編輯」
細節：生命週期與狀態機（D5）；欄位定義（D2）。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 軟刪除（狀態：已發布 / 已刪除），已刪除貼文的按讚與留言一併隱藏但保留；編輯僅保留最新版本，並標記「已編輯」 |
| B | 軟刪除同 A，但編輯保留完整歷史版本供稽核 |
| C | 硬刪除（實體移除），連帶刪除其按讚與留言；編輯不保留歷史、不標記 |
| D | 軟刪除同 A，但不標記「已編輯」，讀者無從辨識 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響貼文 Aggregate 的狀態欄位、按讚與留言的生命週期（D4）、互動成就與獎勵的回收判定
（`rule/按讚獎勵已發放_取消按讚或刪除留言時獎勵與成就是否回收.md`）、以及師徒功能解鎖條件的計數基準
（`rule/師徒功能解鎖條件_被刪除的社群行為是否計入解鎖條件.md`）—— 該兩項皆需先知道刪除的語意。

# 解決結果

**選項 B**：軟刪除 ＋ 編輯保留完整歷史版本 ＋ 標記「已編輯」。

**狀態機**：

| 起始狀態 | 觸發 Event | 目標狀態 |
|----------|-----------|----------|
| — | 發文者已發布貼文 / 發文者已分享訓練成果 | 已發布 |
| 已發布 | 貼文已刪除 | 已刪除（終止） |

**新增欄位**：狀態、已編輯旗標、編輯歷史。

- 軟刪除為必須（排除硬刪除）：貼文可被檢舉，硬刪除會使已成案的檢舉失去指涉對象；
  且「取消按讚 / 刪除留言時獎勵是否回收」與「被刪除的社群行為是否計入師徒解鎖條件」兩題需資料仍在才能計算。
- 已刪除貼文的按讚與留言一併隱藏但保留。
- 保留編輯歷史的理由：避免「發爭議內容 → 被檢舉 → 審視前改為無害內容」的規避漏洞；
  且第 11 題定案的申訴未設時效上限，需長期可稽核（同第 20 題 AI 對話永久保存的邏輯）。
- 標記「已編輯」以防「先發文取得按讚、再改為完全不同內容」。

**連帶解除的 Partial**：第 21 題留言 Aggregate 的「狀態」欄位原標記為待決策，本題定案後一併填入
——留言的狀態值域、軟刪除與編輯歷史規則全部比照貼文。
