# 釐清問題

「管理員」為五種 Actor 之一，執行 27 個 Command，但模型中**無管理員 Aggregate** —— 管理員的帳號、身分識別、權限範圍與狀態皆未定義。管理員應如何建模？

# 定位

流程：管理員管理社群流程、管理員商品上架流程、教官申請流程、自訂訓練流程、
以及各平台級設定的維護（訓練計畫 / 平台動作 / 成就定義 / 獎勵定義）
元素：Aggregate（缺失）「管理員」
細節：D1 Aggregate 識別與邊界、B5 Actor 權限。
由使用者於第六輪第 15 題提出：「目前管理員沒有識別 ID 嗎？我覺得管理員也要有識別 ID」。

# 現況

| 已有 | 缺少 |
|------|------|
| Actor 清單含「管理員」一種 | 管理員 Aggregate（帳號、權限、狀態） |
| Event 共通欄位含「觸發 Actor（Actor 識別碼）」，故**個別管理員在 Event 層可辨識** | Aggregate 層無可指涉的管理員實體 |
| 27 個管理員 Command 已各自指派 Actor | 管理員之間**無權限差異**，任何管理員可執行全部 27 個 Command |
| 使用者 Aggregate 有「教官身分旗標」 | **無「管理員身分旗標」**，管理員與使用者的關係未定義 |

## 已被本缺口擋住的既有決策

第 15 題增設檢舉與申訴的「審視中」狀態時，「逾時自動退回」與「任何管理員可強制接手」
兩個方案**皆因無處記錄「處理者」而未採**，暫定為「審視中不自動退回」。
本項定案後可回頭改採。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 管理員為**使用者 Aggregate 的一個旗標**（比照教官身分旗標）：新增「管理員身分旗標」，無獨立 Aggregate，無權限分級 |
| B | 管理員為**獨立 Aggregate**：欄位含管理員 ID、顯示名稱、狀態（生效中 / 已停用）、建立時戳；與使用者帳號分離（管理員不必是平台使用者），無權限分級 |
| C | 同 B，另加**權限分級**（如內容審核 / 商品管理 / 平台設定三組），各管理員 Command 標註所需權限 |
| D | 同 C，另加**操作稽核紀錄** Aggregate：記錄每位管理員的每一次處置，供內部稽核 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

以及〈Read Model：管理員待審佇列〉是否呈現處理者與可否強制接手。

**連帶可解除的暫定裁決**：`00_全域規範.md`〈「審視中」狀態的共通規則〉
現行的「不自動退回、不可強制接手」為受本缺口所限的暫定做法。

# 解決結果

**選項 C** —— 管理員為獨立 Aggregate（與使用者帳號分離），**含權限分級**，不另立稽核紀錄。

## 欄位

| 欄位 | 型別 | 合法範圍 |
|------|------|----------|
| 管理員 ID | ID | — |
| 顯示名稱 | 字串 | — |
| 權限組 | 列舉複選 | 內容審核 / 商品管理 / 平台設定，至少 1 項 |
| 狀態 | 列舉 | 生效中 / 已停用 |
| 建立時戳 | Timestamp | — |

## 權限組與 27 個管理員 Command 的對應

| 權限組 | 數量 | Command |
|--------|------|---------|
| 內容審核 | 11 | 審視檢舉、下架違規內容、駁回檢舉、處罰使用者、審視申訴、撤銷處罰、駁回申訴、審核公開訓練、審核教官測驗、撤銷教官資格、駁回教官資格 |
| 商品管理 | 6 | 新增商品、設定商品資訊、上架商品、下架商品、出貨、退款 |
| 平台設定 | 10 | 設定訓練計畫、設定平台動作、設定成就定義、設定獎勵定義、設定階級門檻、設定每日任務池、設定新手任務範本、設定限時任務、設定會員權益、設定教官測驗 |

註：出題時誤述為「17 個 Command」，實際盤點為 **27 個**，已於回寫時更正。

## 理由

**設權限分級**：27 個 Command 的影響半徑差距極大，而模型已於〈平台級設定的軟體邊界〉
承認此差異（依「改動後是否會改變使用者已取得或將取得的實質內容」分為兩堆）。
改「獎勵定義」動到全平台經濟，改「審視檢舉」只影響一個案件；既已認定兩類不同，
將執行權綁在一起即前後不一致。日後補上須回頭改 27 個 Command 的 Precondition。

**不採 D（另立操作稽核紀錄 Aggregate）**：管理員的每個動作皆有對應 Event，
而 Event 共通欄位含「觸發 Actor（Actor 識別碼）」—— **Event 流本身即為稽核軌跡**，
另立 Aggregate 記同一件事為重複。

**不採 A（使用者旗標）**：會使一個純後台角色帶著能力值、階級、連續訓練天數等
與其無關的整套欄位，且「管理員必須先是平台使用者」此一約束無存在理由。

## 連帶

1. 每個管理員 Command 的 Precondition 一律增列「執行者狀態為生效中，
   且權限組涵蓋該 Command 所屬組別」。
2. **第 15 題的前置已解除**：管理員 ID 已存在，「處理者」欄位技術上可成立。
   惟「審視中不自動退回」為使用者的明確裁決，**不因前置解除而自動改變**；
   模型已加註，若要改採強制接手須新增「處理者」欄位並重新裁決。
3. [待決策 Partial] **管理員本身的維護**（新增 / 停用管理員、調整權限組）
   是否建模為 Command 與 Event，尚未定案，須套用〈平台級設定的軟體邊界〉的判準。
