# 釐清問題

逐日簽到明細應保留多久？只留最近 N 天，還是永久保留？

# 定位

流程：補簽流程
元素：Aggregate：逐日簽到明細的承載體（承〈連續簽到_逐日簽到明細應由哪一個 Aggregate 承載〉一題的結果）
細節：保留期限欄位／規則。

**前置依賴**：須先決定明細由誰承載，本題才有對象可設期限。
兩題建議連續處理。

# 白話說明

假設決定要保存「哪天簽了、哪天沒簽」的逐日紀錄，接著要決定**留多久**。
這個決定會直接決定使用者在補簽頁上往回翻，能看到多久以前的資料。

| 保留期限 | 使用者體驗 | 每人資料量 |
|----------|-----------|-----------|
| 只留 14 天 | 日曆只畫得出最近兩週，往前翻是空白 | 14 筆 |
| 只留 90 天 | 可回顧一季 | 約 90 筆 |
| 永久保留 | 可回顧全部歷史，第一年 365 筆 | 每年約 365 筆 |

注意：補簽本身只需要最近 7 天（回補範圍，`02_Aggregate定義.md` L4191），
**留得久是為了給使用者看，不是為了讓他補更久以前的日子。**

另外有一個對帳上的考量：模型有「累簽成就」，最高門檻是 **365 天**
（`每日簽到流程.md` L48：累計 3 / 7 / 15 / 30 / 60 / 100 / 180 / 280 / **365** 天）。
若逐日明細只留短期，累計天數這個數字就無法回頭核對，出錯時查不出是哪天算錯的。

# 多選題

| 選項 | 描述 | 推薦 |
|------|------|------|
| A | **永久保留**，不設清除機制。帳號刪除時依既有的匿名化規則處理 | ★ |
| B | **只留最近 N 天**，N 綁定回補範圍的倍數（如 2 倍＝14 天），隨補簽設定連動 | |
| C | **只留最近 90 天**，固定值 | |
| D | **只留最近 2 個月**，恰好對應補簽頁日曆能顯示的範圍 | |
| Short | 提供其他簡短答案（<=5 字） | |

# 推薦選項與理由

**推薦 A（永久保留）。**

- **資料量小到不構成理由砍它**。每人每年最多 365 筆、每筆三個欄位（使用者 ID、日期、簽到方式），
  這是本模型中最輕的一種紀錄。相較之下模型已接受「能力值日快照」這種每人每日一筆、
  欄位多得多的資料（見 `.es-clarify/resolved/aggregate/能力值日快照_保存年限與是否標記為不需精準追蹤.md`）。
- **累計天數與累簽成就需要可對帳的底稿**。`02_Aggregate定義.md` L2160 訂了
  「累計天數為單調遞增，任何情況下皆不減少」——這種永不歸零的數字一旦算錯，
  沒有明細就永遠查不出錯在哪。既有的最高成就門檻是 365 天，等於要求這個數字至少一年內都可信。
- **設期限反而多出一組要驗收的規則**：清除是哪個時點跑、清除當下正在補簽會怎樣、
  清除後日曆顯示什麼。這些全部都要寫進 Gherkin。選 A 則一條都不用寫。
- **本模型既有慣例**：`02_Aggregate定義.md` L918 對獎勵信箱寫過「未領取不作廢：
  完成任務是使用者已付出的行為」，L926 對成就寫過「一經寫入不再變動，成就頁永久保留」——
  對使用者已經做過的行為，本模型傾向不主動抹除。
- 若之後真的需要控制資料量，適當的做法是把久遠資料歸檔而非刪除，那屬實作規劃階段的議題，
  不影響本階段的驗收標準。

與 `.gh-clarify/query/補簽頁_查無資料屬失敗還是回傳空集合的成功.md`。

# 解決結果

**選項 A** —— 永久保留，不設清除機制。

理由三項：
1. 每人每年至多 365 筆、每筆三欄位，為模型中最輕的紀錄；
2. 累計天數為永不減少的單調遞增值，無明細即無法對帳，而累簽成就最高門檻達 365 天；
3. 清除機制本身會帶進「何時清除」「清除當下正在補簽如何處理」「清除後日曆顯示什麼」
   三組須驗收的規則，換不到對等的好處。

帳號刪除時依既有的個人識別資料匿名化規則處理，不另訂本 Aggregate 的刪除規則。
