# 釐清問題

訂單 Aggregate 的欄位定義與狀態機為何？實體商品訂單與虛擬商品訂單是否為同一個 Aggregate？

# 定位

流程：實體商品購買流程、虛擬商品購買流程
元素：Aggregate：訂單（模型中尚未定義）
細節：隱含但未明確定義的 Aggregate（D1）；生命週期與狀態機（D5）。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 單一訂單 Aggregate，狀態機：待付款 → 已付款 → 已出貨 → 已完成（含已取消 / 已退款分支），虛擬商品略過出貨 |
| B | 實體與虛擬拆為兩個獨立 Aggregate，狀態機不同 |
| C | 單一 Aggregate 但依商品類型有不同狀態子集，需要類型欄位 |
| D | 不建立訂單 Aggregate，直接以購買紀錄與出貨紀錄兩個 Aggregate 表達 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響訂單 Aggregate 的欄位、狀態機與每次狀態轉換對應的 Event（D5）、兩條購買流程的結構一致性、以及庫存與付款的跨 Aggregate 一致性（E2）。

# 優先級

High

# 解決結果

C — 單一訂單 Aggregate，依商品類型套用不同的狀態子集。

欄位：類型（實體 / 虛擬）、商品規格、數量、金額、狀態、收貨資訊（僅實體有值）。

**實體訂單**：待付款 → 已付款 → 已出貨（終止）；
分支終止狀態：已失敗（支付已失敗）、已取消（使用者已取消訂單）、已退款（訂單已退款）。

**虛擬訂單**：待付款 → 已付款 → 已發放（終止）；
分支終止狀態：已失敗（購買已失敗）。

未採 A（統一狀態機會使虛擬訂單存在永不進入的出貨狀態）、
B（拆兩個 Aggregate 與第 47 題「商品不拆」不對稱）、
D（會推翻第 26 題「訂單為獨立 Aggregate」）。

# 承接的既有裁決

- 第 15 題：出貨後的物流留在系統邊界之外 → 實體訂單終止於「已出貨」，無「已送達 / 已完成」。
- 第 14 題：虛擬商品發放可為非同步 → 「已付款」與「已發放」為兩個不同狀態。
- 第 47 題：商品規格為價格與庫存的持有層級 → 訂單以商品規格 ID 指涉所購項目。
- 第 19 題：實體支付走第三方金流回呼；虛擬支付可為金幣、真實金流或併用。

# 連帶影響

- `.es-clarify/pending-gaps.md` G12（出貨後的退貨退款無路徑）：本題確認「訂單已退款」的
  合法來源狀態為「已付款」，即出貨前；出貨後為終止狀態，無退款轉換。該缺口的範圍更明確。
- `.es-clarify/pending-gaps.md` G11（虛擬商品已扣款但發放失敗）：虛擬訂單停留在「已付款」
  而無法進入「已發放」的情境即為該缺口，狀態機使此空洞更為明顯。
