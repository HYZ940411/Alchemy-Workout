# 釐清問題

虛擬訂單自「待付款」轉入「已付款」的觸發 Event，00_全域規範的狀態子集列為「虛擬貨幣已扣除 / 使用者已支付」，而 `虛擬商品購買流程.md` 列為「使用者已購買虛擬商品〔交易成立〕」。三個 Event 中，何者為狀態轉換的觸發事實？

# 定位

流程：虛擬商品購買流程
元素：Aggregate「訂單」之虛擬訂單狀態子集
細節：D5 狀態機、E3 Event→Aggregate 一致性。〈Command 清單〉有「成立虛擬商品交易（系統）→ 使用者已購買虛擬商品」，但 00_全域規範的狀態機未列入該 Event；而併用支付時「虛擬貨幣已扣除」與「使用者已支付」兩者皆須成功，單獨任一者不足以轉入已付款。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 以「使用者已購買虛擬商品」為唯一觸發：前二者為其 Precondition（併用時兩者皆須成功），00_全域規範狀態機改寫為單一觸發 Event |
| B | 維持二者觸發，移除「使用者已購買虛擬商品」：交易成立即為付款完成，兩個名字指同一事實（比照「使用者已購買實體商品」已併入「使用者已支付」的既有裁決） |
| C | 拆為兩段狀態：待付款 →（虛擬貨幣已扣除 / 使用者已支付）→ 已收款 →（使用者已購買虛擬商品）→ 已付款，使併用支付的中間態可表達 |
| D | 維持現況兩處並存，於 00_全域規範註明「使用者已購買虛擬商品」為狀態轉換的正式觸發、前二者為支付動作，不改結構 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響訂單 Aggregate 的虛擬訂單狀態子集、「商品已發放」的 Precondition、併用支付（虛擬貨幣 ＋ 補差額）的原子性保證，以及〈統一語言〉表中「使用者已支付」條目的定義範圍。

# 解決結果

**選項 A** —— 以「**使用者已購買虛擬商品**」為虛擬訂單轉入已付款的**唯一觸發 Event**；
「虛擬貨幣已扣除」與「使用者已支付」為其 Precondition，本身不改變訂單狀態。

**理由為併用支付的原子性**：模型已定案虛擬商品可「虛擬貨幣 ＋ 現金補差額」併用，
且明訂「併用時，虛擬貨幣扣除與真實金流支付須**同時成功**，方可完成購買」——
故「虛擬貨幣已扣除」單獨發生不代表訂單已付款（錢已扣但補差額失敗時，訂單不得為已付款）。
那兩個 Event 天生是**條件**而非**結果**；而「使用者已購買虛擬商品」正是那個結果，
其 Command「成立虛擬商品交易」（Actor：系統）本即為「兩邊都成功了」的系統判定。

**不採 B（移除「使用者已購買虛擬商品」）**：移除後併用支付的原子性即無 Event 可承載；
且與既有裁決「『使用者已購買虛擬商品』與『商品已發放』為兩個不同事實，不合併」方向相反。

**不採 C（新增「已收款」中間狀態）**：該狀態僅在併用支付且兩邊分別完成的瞬間存在，
屬技術性中間態而非業務事實；承既有立場「不建模訓練課表套用已失敗 ——
失敗屬技術性交易回滾，非業務事實」。

**不採 D（兩處並存僅加註）**：兩處並存正是本題要解的問題。

**一併釐清**：實體訂單無此結構 —— 其僅有單一支付管道（第三方金流），
「使用者已支付」即直接轉入已付款。
