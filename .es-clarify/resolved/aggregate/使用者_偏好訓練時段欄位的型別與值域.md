# 釐清問題

使用者 Aggregate 新增的「偏好訓練時段」欄位，其型別、值域與粒度為何？是否允許多個時段、是否可依星期不同？

# 定位

流程：訓練紀錄流程（事前提醒路徑）、新手任務流程
元素：Aggregate「使用者」的「偏好訓練時段」欄位
細節：D2 欄位定義。訓練紀錄流程檔第 65 行「使用者 Aggregate 須具備『偏好訓練時段』欄位，供無訓練紀錄者使用」，第 70 行明載型別與值域未定案。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 列舉單選：早（06–10）/ 午（11–14）/ 傍晚（17–20）/ 夜（20–23），全週共用一個時段 |
| B | time 型別單選（使用者當地時區的時分），全週共用；提醒於該時點前 N 分鐘發送 |
| C | 每週 7 天各自一個時段（依註冊填入的每週健身天數決定要填幾天），型別為 星期 → 時段 的映射 |
| D | 列舉可複選（最多 2 個時段），全週共用；提醒取當日最早尚未訓練的時段 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響使用者 Aggregate 的欄位定義、「訓練提醒已發送」的發送時點判定、有訓練紀錄者「慣常時段推算」的輸出粒度須與本欄位一致（否則兩段式發送的兩條路徑產出不同型別）、以及新手選擇時段的互動設計。

# 解決結果

**使用者自述結構（不在 A–D 選項中），並補齊三個參數**

使用者描述的介面為「一週七天的七個長條圖，可拖拉空閒可運動時段，有按鈕新增、長按刪除」。
翻為資料結構為**每日多區間的連續時間**：

| 層級 | 內容 |
|------|------|
| 第一層 | 星期（固定 7 筆：週一至週日） |
| 第二層 | 該日的時段區間集合（0 到 N 個，可為空） |
| 第三層 | 每個區間的起始時間與結束時間 |

| 第三層欄位 | 型別 | 合法範圍 |
|------------|------|----------|
| 起始時間 | time | 00:00–23:30，以 30 分鐘為刻度 |
| 結束時間 | time | 00:30–24:00，以 30 分鐘為刻度 |

**三個補齊的參數**
- 時間粒度：**30 分鐘**（一日 48 格）
- 區間**不得跨日**：結束時間須大於起始時間，且與起始時間同屬一個星期日
- 訓練提醒於**區間的起始時間**發送

**語意的轉向**：本欄位表達「使用者有空可以訓練的時段」，而非原選項 A–D 預設的
「使用者通常幾點練」。填寫對象為尚無訓練紀錄的新手，該族群尚未形成訓練習慣，
答不出慣常時段但答得出何時有空。此轉向使欄位語意與其服務對象一致。

**不變條件**：同一日的各區間彼此不重疊；〔推導〕拖拉造成重疊時自動合併為單一區間。

**介面操作不建模**：拖拉調整起訖、按鈕新增區間、長按刪除區間皆為介面操作，
不各自建模為 Event，一律由「使用者已選擇偏好訓練時段」承接。

30 分鐘粒度的理由：15 分鐘於手機上單格過窄、拖拉易誤觸；1 小時無法表達 6:30 或 18:30；
且與「每次健身時長」的 30 分鐘刻度一致。
