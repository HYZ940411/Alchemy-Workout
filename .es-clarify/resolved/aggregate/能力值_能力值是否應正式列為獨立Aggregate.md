# 釐清問題

「能力值」目前不在〈獨立 Aggregate 清單〉之列、被視為使用者 Aggregate 的一組欄位，但其具備獨立的算法、六階門檻、六個退步計時器、日快照與 12 枚成就——是否應正式列為獨立 Aggregate？

# 定位

流程：訓練結算流程、訓練中斷流程、回歸任務流程（跨流程）
元素：Aggregate — 能力值（現為使用者 Aggregate 的欄位群）
細節：`03_能力值.md` 第 16 行的 `[待 discovery 判定]` 標記；檢查項 D1「是否存在隱含但未明確定義的 Aggregate」。相關欄位：六維點數、本次中斷各維累積退步量、各維最後訓練日（退步計時基準）、能力值日快照

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 維持現狀：能力值仍為使用者 Aggregate 的欄位群，僅將 `03_能力值.md` 的待判定標記移除並註明「刻意不獨立」的理由（六維點數與使用者為一對一、無獨立生命週期） |
| B | 正式列為獨立 Aggregate（清單 51 → 52），欄位含六維點數、六維累積退步量、六維退步計時基準；日快照另為其子聚合或關聯 Aggregate |
| C | 折衷：點數留在使用者 Aggregate，但將「能力值日快照」單獨列為獨立 Aggregate（其為一人多筆、有自己的生命週期與保存年限） |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

- 〈獨立 Aggregate 清單〉的數量與分類
- 「能力值已提升 / 已退步 / 已部分回復」三個 Event 的「關聯 Aggregate ID」該指向誰
- 帳號刪除的〈刪除範圍〉逐列處理對象
- 相關已解決項目：`resolved/aggregate/使用者_使用者Aggregate的欄位與邊界尚未定義.md`、`resolved/aggregate/能力值日快照_保存年限與是否標記為不需精準追蹤.md`

# 優先級

High

# 解決結果

**B**：正式列為獨立 Aggregate（〈獨立 Aggregate 清單〉51 → 52）。

- **判準確立為「是否有一套自成體系的規則」，而非一人幾筆** —— 承連續訓練與連續簽到的既有先例
  （該二者同為一人一筆卻皆獨立）。
- 欄位：使用者 ID、六維點數、六維初始值（同為退步下限）、本次中斷各維累積退步量、各維最後訓練日。
- 不變條件 5 條（點數 ＝ 歷史最高標準化分數與初始值取大者、≥ 初始值、≤ 999、
  綜合點數為算術平均且不儲存、兩層等級皆為衍生值）。
- **三個 Event（能力值已提升 / 已退步 / 已部分回復）的「關聯 Aggregate ID」改為能力值 ID**，
  不再指向使用者 ID。
- 能力值日快照為其關聯 Aggregate（一對多），非欄位；耐力值不屬本 Aggregate（為附掛值）。
- 使用者 Aggregate 移出「能力值」與「本次中斷各維累積退步量」兩列。

**使用者於本題追問「B 會比較好維護嗎」**，已說明：改善的是模型與文件層
（歸屬明確、Event 關聯正確、不變條件有處可列），實作層無差異（一對一仍可同表儲存），
代價為一次性的改寫成本。
