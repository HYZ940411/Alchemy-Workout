# 釐清問題

「關注關係」與「粉絲數」分別屬於哪一個 Aggregate？粉絲數為儲存欄位或由關注關係即時彙總的衍生值？

# 定位

流程：關注流程、師徒功能解鎖流程
元素：Aggregate（尚未定義）；Event「使用者已關注帳號」「對方帳號粉絲數已增加」「對方帳號粉絲數已減少」
細節：Aggregate 識別與邊界（D1）；內部不變條件（D3）；Event → Aggregate 一致性（E3）。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 新增獨立「關注關係」Aggregate（關注者、被關注者、時間）；粉絲數為使用者 Aggregate 的儲存欄位，隨關注 / 取消關注同步增減 |
| B | 同 A 但粉絲數不儲存，一律由關注關係即時彙總，無粉絲數欄位 |
| C | 關注關係併入使用者 Aggregate 的關注清單欄位，粉絲數為衍生值 |
| D | 粉絲數為儲存欄位且允許與關注關係短暫不一致（非同步彙總） |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響「對方帳號粉絲數已增加 / 已減少」是否為獨立 Event 或衍生狀態、粉絲成就的判定資料來源
（`rule/粉絲成就已解鎖_粉絲數下降後成就是否撤銷.md`）、粉絲數 Read Model 的即時性
（`read-model/對方帳號粉絲數已增加_粉絲數的即時性要求為何.md`）、以及貼文「僅關注者可見」的判定依據。
本項為新掃描發現，非承接 `pending-gaps.md`。

# 優先級

High

# 解決結果

**選項 A**：新增獨立「關注關係」Aggregate；粉絲數為使用者 Aggregate 的儲存欄位，同步增減。

**關注關係 Aggregate**：關注者、被關注者、關注時戳；單向關係，唯一鍵為兩者 ID。

- 與第 22 題的封鎖同屬「使用者對使用者的單向關係、雙方皆非擁有者」，故採同一處理方式。
  對照組為按讚：按讚有明確擁有者（貼文），故做成關聯集合而非獨立 Aggregate。
- 不併入使用者 Aggregate：清單無上限成長，且雙向皆需查詢。
- 貼文可見範圍「僅關注者」的判定依據為本 Aggregate。

**粉絲數為儲存欄位**（使用者 Aggregate，int ≥ 0）：

- 若不儲存（選項 B），「對方帳號粉絲數已增加」將不改變任何 Aggregate 欄位，不符 Event 定義
  —— 與第 4 題刪除「使用者已購買實體商品」為同一論證。
- 粉絲成就門檻最高 10000，即時彙總於熱門帳號成本過高（不採 B / C）。
- 不允許與關注關係不一致（不採 D），避免粉絲成就的解鎖判定抖動。
- 不變條件：粉絲數 ＝ 關注關係中被關注者為本人的筆數。

- 獨立 Aggregate 清單 39 → 40 項。
