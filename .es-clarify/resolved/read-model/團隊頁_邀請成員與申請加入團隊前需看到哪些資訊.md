# 釐清問題

使用者執行 Command「申請加入團隊」前必須看到什麼（如何搜尋公開團隊）？隊長執行「邀請成員」「核准加入申請」「踢除成員」「轉讓隊長」前必須看到什麼？

# 定位

流程：團隊組隊流程、團隊任務流程
元素：Read Model（尚未定義）；支撐 Command「申請加入團隊」「邀請成員」「核准加入申請」「踢除成員」「轉讓隊長」「解散團隊」「完成一次限時任務」
細節：D6 Read Model 識別（篩選、排序）、E4 Read Model → Command 支撐。
既有規則「公開團隊可被搜尋並接受加入申請」—— 搜尋所依據的 Read Model 未定義。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 兩個 Read Model：公開團隊搜尋（團隊名稱、目前人數 / 5、團隊日常分數、月榜名次）＋ 我的團隊頁（成員清單與各成員本月分數貢獻、待處理邀請與申請、今日限時任務完成狀況） |
| B | 同 A，公開團隊搜尋另加篩選條件（依名次區間、依人數是否已滿） |
| C | 僅建「我的團隊頁」；公開團隊的探索改為系統隨機推薦，不提供搜尋 Read Model |
| D | 同 A，我的團隊頁另加各成員的連續訓練天數與最後訓練日期，供隊長判斷是否踢除長期不活躍成員 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響 Read Model 清單、團隊 / 團隊日常分數 / 團隊限時分數 / 個人排行榜分數四者的查詢組合、「團隊人數未達上限 5 人」Precondition 的事前可見性、成員個人分數貢獻的揭露是否造成團隊內壓力，以及限時任務的完成狀況呈現。
相依：`rule/隊長已邀請成員_團隊邀請與加入申請是否逾期失效.md`（待回應項目是否呈現於團隊頁）、`rule/團隊已指派限時任務_限時任務的內容結構與完成判定條件.md`、`rule/團隊日常分數已增加_成員中途加入或退出時分數如何計算.md`。

# 解決結果

**選項 B ＋ 拆為兩個 Read Model ＋ 關注對象優先**

## 觸發重構的前提

使用者於本題進行中指出：**「團隊的主要目的是讓親朋好友可以一起運動」**。

此前提使原題方向失準 —— 原選項將「管理自己的隊」與「找一支隊加入」塞進同一個
Read Model，並花費篇幅比較各隊強弱，而後者屬次要路徑的需求。

| 路徑 | 對象 | 對應 Read Model |
|------|------|----------------|
| 隊長邀請（**主要動線**） | 認識的人 | 我的團隊頁 |
| 公開招募申請（次要） | 不認識的人 | 團隊搜尋 |

## 一、Read Model：我的團隊頁

支撐 Command：邀請成員、退出團隊、轉讓隊長、踢除成員、變更團隊可見性。

欄位：團隊名稱、團隊可見性、成員清單（顯示名稱 / 階級 / 角色）、目前人數 / 上限、
待回應的邀請、待回應的加入申請、團隊日常分數、團隊限時分數、兩個排行榜名次、
本週限時任務與各成員完成狀態。即時。

**分數與名次於此呈現**：那是全隊的共同目標，成員看自己隊的成績為正當需求。

## 二、Read Model：團隊搜尋

支撐 Command：申請加入團隊。

欄位：**關注對象所屬的公開團隊（優先呈現於前段）**、團隊名稱搜尋、目前人數 / 上限、
我是否已屬團隊、換隊冷卻剩餘時間、是否在重新分隊期。即時。

- 〔推導〕僅列可見性為公開且狀態非已解散的團隊。
- **關注對象優先為使用者指定**：關注關係即使用者的社交圈，較團隊排名更接近
  「我想加入誰的隊」。
- **不呈現團隊分數與排行榜名次**（使用者主動提出）：挑隊非主要動線，
  呈現排名只會鼓勵「找強隊蹭排行獎勵」，與團隊定位相反。
- 我的狀態三項為必要：申請加入有三個會擋住的前置條件，不呈現則使用者反覆申請被拒且不知原因。

## 不採的方案

- **不採 C**（團隊近期活躍度）：限時任務為每日指派，「最近一次」的全員完成率為單日樣本，
  噪音過大；要有意義須算移動平均，屬新的衍生欄位。
- **不採 D**（各成員六維能力值）：團隊的價值為集體分數而非個人實力展示；
  且成員能力值可見性已有使用者自身的開關，團隊頁繞過它會與
  〈六維能力值的對外可見性〉衝突。
