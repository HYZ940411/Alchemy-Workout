# 釐清問題

排行榜 Read Model 應顯示哪些欄位、顯示前幾名、是否顯示使用者自身名次？資料即時性要求為何？

# 定位

流程：排行榜週期結算流程、每日任務流程、訓練結算流程
元素：Read Model：排行榜（個人 / 團隊日常 / 團隊限時，尚未定義）；服務對象 Actor：使用者
細節：Read Model 識別、欄位來源、即時性、篩選排序分頁（D6）。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 顯示前 100 名（名次 / 帳號 / 分數）加上自身名次，即時更新 |
| B | 顯示前 100 名加自身名次，每 5 分鐘更新一次（可延遲） |
| C | 顯示前 50 名加自身名次與前後各 5 名，每小時更新 |
| D | 僅於週期結束後公布完整排名，週期中僅顯示自身分數 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響排行榜 Read Model 的欄位定義、資料來源（三個分數 Aggregate）、即時性與快取策略、以及是否需要分頁規則。

# 優先級

Medium

# 解決結果

**選項 A ＋ 使用者追加的階級分組**

- **分組**：依使用者階級，每 10 階一組，共 10 組（1–10、11–20、…、91–99）；排名僅於組內比較。
- **顯示**：組內「自己上下各 10 名」的名次視窗（至多 21 筆），不顯示組內前段名單。
- **排序**：依個人排行榜分數由高至低。
- **即時性**：延遲更新，固定間隔重算，畫面須標明資料更新時間。
- **獎勵**：個人排行獎勵依組內名次發放。

使用者裁決理由：不希望使用者看到離自己太遠的對手，以免激發負面情緒。
補充分析（使用者採納）：分組的另一價值在於獎勵的可得性 ——
不分組時全平台前段永遠是同一批高強度使用者，多數人一輪都領不到排行獎勵。

不採一階一榜（99 組）：高階組人數稀少，組內可能湊不滿一個名次視窗。
不採全平台單一榜：只解決「看不到」而未解決「拿不到」。
