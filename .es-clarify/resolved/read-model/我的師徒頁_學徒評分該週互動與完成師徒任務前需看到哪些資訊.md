# 釐清問題

第五輪新增的 Command「評分該週互動」（Actor：學徒）及既有的「完成師徒任務」「提問」「解除師徒關係」皆由**學徒方**下達，但模型只有服務教官方的〈Read Model：師徒互動頁〉，學徒方無任何 Read Model。學徒在下達這些 Command 前需看到哪些資訊？

# 定位

流程：師徒互動流程
元素：Read Model（缺失）「我的師徒頁」；服務的 Actor：使用者（學徒方）
細節：D6 Read Model 識別、E4 Read Model → Command 支撐。〈Read Model 清單〉建立原則明訂「以 Command 為索引，逐一詢問 Actor 下這個 Command 前必須看到什麼」；每週互動評分的兩條 Precondition（該週內雙方有互動、每週最多一次）學徒目前完全看不到。

# 解決結果（2026-08-08，第八輪第 25 題）

**B** —— 教官基本資料 ＋ 待完成的師徒任務清單 ＋ **本週互動摘要** ＋ **本週評分狀態與剩餘天數**。

## 補的缺口

模型原有〈Read Model：師徒互動頁〉但**服務的是教官方**（回答提問、指派任務）。
**學徒側完全沒有 Read Model**，其兩個 Command（評分該週互動、完成師徒任務）無畫面支撐。

## 本週互動摘要的內容（使用者追問後具體化）

模型中師徒之間僅三種互動，摘要即為此三項的計數：

| 來源 Event | 摘要呈現 |
|-----------|---------|
| 學徒已提問 → 教官已回答 | 本週提問 N 次、教官回覆 N 次 |
| 教官已指派師徒任務 | 本週指派 N 項 |
| 學徒已完成師徒任務 | 已完成 N 項 |

**必要性**：每週互動評分的換算為 −2／0／+4／+8／+12，幅度大且直接連動教官聲望。
學徒若只看到一顆評分按鈕，評的是最近一次對話的心情而非這一週。
且模型已定「問答不評分」，**每週評分是問答品質唯一的承接處** ——
無摘要即等同讓每週評分退化回「逐次評分尺度過敏感、評分者多為兩端情緒樣本」的原毛病。

## 使用者提出的兩個查證點（皆已釐清，模型無誤）

1. **「我們不是沒有師徒提問環節了嗎？」**
   —— 第五輪移除的是 Event「**學徒已評分該次問答**」與問答的學徒評分欄位，
   **不是問答本身**。`學徒已提問` 與 `教官已回答` 兩個 Event 皆仍存在
   （`師徒互動流程.md:40、45`）。

2. **「上次問題不是卡在學徒已提問該怎麼判斷嗎？」**
   —— 已於第五輪第 16.1 題以選項 A 解決：**提問為獨立 Command**，
   呈現上內嵌於師徒對話串，**單一入口、兩種動作**（直接打字為閒聊、點「提問」產生問答）。
   判斷方式為學徒自己按哪個鈕，非系統推測。
   故摘要的「提問 N 次」為可數值，不含閒聊。

## 評分剩餘天數為必要欄位

評分窗口每週一重置，錯過即無法補評。
第八輪第 17 題已定**每週評分提示歸 App 內通知類、不推播**，
該裁決的前提正是「使用者打開本頁即看得到」。**無此欄位則該裁決落空。**

## 兩項不納入的資訊

- **不放教官聲望與帶徒人數**：學徒已完成拜師，聲望為選教官時的決策資訊，屬〈教官清單〉。
  置於此處會使評分變成「我要不要維護他的分數」而非「他這週幫了我多少」。
- **不放歷史評分紀錄**：錨定效應會使學徒續給與上週相同的分數，
  評分失去鑑別力，而聲望系統正是靠鑑別力運作。
