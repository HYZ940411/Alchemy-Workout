# 釐清問題

商品管理權限組共有 6 個管理員 Command（新增商品、設定商品資訊、上架商品、下架商品、出貨、退款），其中「出貨」與「退款」是針對個別訂單下的判斷——管理員必須先看到「哪些訂單已付款待出貨」才出得了貨。但 Read Model 清單共 34 個，服務管理員的只有〈管理員待審佇列〉與〈管理員評分彙總〉兩個，皆不含訂單；訂單相關的只有服務使用者的〈我的訂單頁〉。管理員在出貨與退款之前需要看到哪些資訊，是否成立一個 Read Model？

# 定位

流程：實體商品購買流程、管理員商品上架流程
元素：Read Model（缺失）；支撐的 Command：出貨、退款、上架商品、下架商品
細節：D6 Read Model 識別、E4 Read Model → Command 支撐。〈建立原則〉明訂「以 Command 清單為索引，逐一詢問 Actor 下這個 Command 前必須看到什麼」，但該次盤點的基數為 226 個 Command，現已增至約 290 個。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A（**推薦**） | **新增〈Read Model：管理員訂單佇列〉**，服務 Actor 為管理員，支撐 Command 為出貨與退款；分頁為待出貨 / 待退款 / 已出貨；每筆呈現訂單 ID、下單日期、商品名稱與規格、數量、收貨資訊、支付明細、訂單狀態；即時性為即時。理由：完全比照既有的〈管理員待審佇列〉——那一個也是為了讓管理員知道「有哪些事等我處理」而立的，出貨是同一種形狀的工作佇列 |
| B | 新增一個涵蓋全部 6 個商品管理 Command 的〈管理員商品後台〉Read Model，訂單佇列與商品清單合為一頁 |
| C | 擴充既有的〈管理員待審佇列〉，加一個「待出貨」分頁，不另立 Read Model |
| D | 不建立：出貨與退款的實際作業在外部物流／金流後台進行，模型只承載「商品已出貨」這個事實，管理員看什麼留在系統邊界之外 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響 `04_ReadModel清單.md` 的 Read Model 總數與〈建立原則〉的盤點基數（現寫「226 個 Command」，實際約 290 個，該盤點未涵蓋其後新增的 Command）、Command「出貨」與「退款」的決策依據、以及訂單 Aggregate 的查詢欄位。
若採 D，須說明「管理員下架商品時既有未出貨訂單如何處理」（已定案規則）要靠什麼看得到那些訂單。
相關已解決項目：`resolved/read-model/管理員待審佇列_審視檢舉與各類審核前需看到哪些資訊.md`（建立管理員工作佇列的先例）、`resolved/read-model/我的訂單頁_取消訂單前需看到哪些資訊.md`、`resolved/rule/管理員已下架商品_下架時既有未出貨訂單如何處理.md`。

# 解決結果

**選項 E（提問中新增，非原四選項）** —— **新增兩個 Read Model**：

| Read Model | 支撐的 Command | 性質 |
|-----------|---------------|------|
| 管理員訂單佇列 | 出貨、退款 | 工作佇列（處理完即離開） |
| 管理員商品清單 | 新增商品、設定商品資訊、上架商品、下架商品 | 目錄管理（常駐、不清空） |

新增選項 E 的理由：原推薦選項 A 只補訂單佇列，
**商品管理權限組 6 個 Command 中的另外 4 個（新增／設定／上架／下架）仍無任何 Read Model**
——〈商品頁〉服務的是使用者，管理員沒有任何畫面可挑商品。
A 屬只補一半，剩下一半必於下一輪 discovery 再度掃出。

不採 B（一頁涵蓋 6 個 Command）：工作佇列與目錄管理的呈現與排序邏輯不同，
且既有〈管理員待審佇列〉已為工作佇列立下先例。
不採 C（擴充待審佇列）：出貨非審核，混入會使該佇列的四類審核定位失效。
不採 D（不建立）：已定案規則「下架商品時既有未出貨訂單如何處理」將無畫面可據以判斷。

**附帶清掉一處過期敘述**（`overview.md` §5 訂正 1）：
〈建立原則〉之盤點方式原記「以 **226 個** Command 為索引」，已訂正並補記
「其後新增的約 64 個 Command 未被該次盤點涵蓋，本兩項即由此漏出」，
並改為「日後新增 Command 時同步詢問是否需要 Read Model，不再仰賴事後整批盤點」。
