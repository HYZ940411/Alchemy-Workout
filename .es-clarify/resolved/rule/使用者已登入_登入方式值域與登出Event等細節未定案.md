# 釐清問題

「使用者已登入」Event 已存在於註冊流程的 Command 清單中，但其細節仍未定案：登入方式的值域（手機驗證碼 / 第三方帳號，兩者皆可，或需列舉）、是否需要建模「使用者已登出」Event、本 Event 是否應標記為「不需精準追蹤」（比照通知類 Event 的低驗收強度處理）、以及帳號狀態為「待刪除」的使用者是否仍可登入。

# 定位

流程：註冊流程
元素：Command「登入」、Event「使用者已登入」
細節：回歸任務流程的「使用者已查看回歸任務」明確依賴「使用者已登入」作為前置行為，但登入本身的規則細節尚未完整定義。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 登入方式值域比照註冊的驗證方式（手機驗證碼 / 第三方帳號授權）；不建模「使用者已登出」（其為前端本機狀態清除，不改變任何 Aggregate，無業務意義）；「使用者已登入」標記為不需精準追蹤（比照通知類 Event，僅用於觸發回歸任務查看等下游 Policy，不做嚴格 Precondition/Postcondition 驗收）；待刪除帳號仍可登入（否則使用者無法取消刪除申請）（**推薦**：登出無狀態改變、與模型「不建模純技術動作」的既有原則一致；待刪除帳號若不可登入，「使用者已取消刪除帳號申請」這個既有 Command 將無法被觸發，兩者會互相矛盾） |
| B | 登入與登出皆建模為業務 Event，用於精確計算使用者的活躍時段與線上狀態 |
| C | 待刪除帳號不可登入，僅能透過刪除確認信中的專屬連結取消刪除申請，不需一般登入路徑 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響 Event「使用者已登入」的完整定義、回歸任務流程「使用者已查看回歸任務」的前置依賴、帳號生命週期中「待刪除」狀態下使用者的可用功能範圍。為 `pending-gaps-3.md` I7 之延續。

# 解決結果

四個子題依使用者要求**逐一分開提問**，裁決如下：

| 子題 | 裁決 |
|------|------|
| ① 登入方式值域 | **A：手機號碼 / Google / Apple 三值**，與註冊入口完全對應 |
| ② 是否建模「使用者已登出」 | **A：不建模** |
| ③ 是否標記「不需精準追蹤」 | **A：不標記** |
| ④ 待刪除帳號的登入權限 | **B：可登入但功能受限**，僅能使用「取消刪除帳號申請」 |

## ① 不另加「自動登入」第四值

自動登入不是一種登入方式，而是「是否需要重新驗證」，混入同一欄位會使該欄位同時表達兩件事；
若日後需分析主動登入與自動登入的比例，較乾淨的做法為另加一個布林欄位。

## ② 不建模登出

登出不改變任何 Aggregate 狀態、不作為任何 Precondition、無任何下游讀者；
而依賴「使用者已登入」的規則有三處（回歸任務首次查看的起算、每日登入提醒的發送對象、
逾時中斷的結算畫面於下次開啟 App 時呈現），依賴登出者為**零處**。
承模型否決「平台設定已變更」單一泛用 Event 的同一理由：沒有讀者的 Event 是純粹的成本。

## ③ 不標記為不需精準追蹤（助理於出題時反轉原推薦）

本項目建檔時的推薦為「高頻 → 標記」，但**查證依賴關係後推薦反轉**：
「不需精準追蹤」的既有用法是給 6 個通知類 Event，其性質為「發出去即結束」、
失敗不阻斷任何流程，故可免除驗收；而「使用者已登入」是**三處規則的判定依據**，
標記為不需精準追蹤等同宣告這三處規則不需驗收。兩者不是同一種東西。

## ④ 可登入但功能受限，並一併明確化「帳號停用」的語意

比照模型已為永久停權者定義的同型處理（其功能對照表中「申訴為唯一可用的功能」），
待刪除帳號套用同一模式，不需為登入畫面另外設計一套特殊的取消入口。

**連帶解決一處不一致**：「使用者已登入」原有的 Precondition 只有「帳號狀態不為已刪除」
（故待刪除者本可登入），而〈帳號生命週期〉卻寫待刪除為「帳號停用」，兩處說法不一致。
本裁決明確化：**停用 ＝ 可登入但僅能取消刪除申請**，非「登不進去」。

另補上一條原本遺漏的 Precondition：處罰狀態不為永久停權
（承既有的處罰級距功能對照表，該表已載明永久停權者「登入 ❌」，但登入 Event 未寫此條件）。
