# 釐清問題

三條 AI 流程共用的失敗處理已定案「產生 Event『AI 調整已失敗』，維持原訓練內容並提示使用者稍後再試」，但**是否自動重試、重試次數上限為何**尚未裁決。

# 定位

流程：AI 訓練前調整流程、AI 訓練中調整流程、AI 自動優化訓練流程
元素：Rule：Event「AI 調整已失敗」的 Postcondition
細節：C5 失敗與例外路徑。00_全域規範〈AI 調整的失敗處理〉之 `[待決策 Partial]`：「『商品發放已失敗』的既有先例為重試 3 次、達上限轉人工，可供參考但未套用於本節」。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 不自動重試：AI 調整為使用者主動發起的互動，使用者就在畫面前，由其自行決定要不要再試一次；靜默重試會使使用者盯著轉圈更久 |
| B | 自動重試 1 次後才產生失敗 Event：多數 AI 逾時為暫時性，一次重試可救回大部分情形，且不顯著拉長等待 |
| C | 依流程分別處理：訓練前 / 訓練中調整（使用者在場）不重試；**自動優化**（系統排程觸發、使用者不在場）自動重試 3 次，達上限產生失敗 Event，比照「商品發放已失敗」的既有先例 |
| D | 三條流程一律重試 3 次，比照既有先例，不因觸發源而異 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響「AI 調整已失敗」的攜帶資訊（是否需新增「已重試次數」欄位，比照「商品發放已失敗」）、Postcondition、以及該 Event 的冪等去重鍵（重試是否算同一次請求）。
相關已解決項目：`resolved/rule/AI已微調訓練強度_AI回應逾時或失敗時的處理.md`（選項 A）、`resolved/event/商品已發放_已扣款但發放失敗時的Event為何.md`（重試 3 次之先例）。
相依：`event/AI調整已失敗_三條AI流程的同名Event是否納入跨流程同名Event表.md`。

# 解決結果

**B** —— 依「使用者是否在場等待」分流，且題目已由「重試幾次」重新框架為「使用者最長等多久」。

| 路徑 | 使用者在場 | 等待上限 | 重試 |
|------|-----------|---------|------|
| AI 訓練前調整 | 是 | 30 秒 | 上限內自動重試 1 次 |
| AI 訓練中調整 | 是 | 30 秒 | 上限內自動重試 1 次 |
| 訓練前課表調整 | 是 | 30 秒 | 上限內自動重試 1 次 |
| AI 自動優化 | 否 | 不設上限 | 重試 3 次 |

附帶裁決：
- 逾時計時自 Command 被接受起算，重試不重置計時（30 秒為總等待時間）。
- 「AI 調整已失敗」新增欄位「已重試次數」。
- 重試與原請求共用同一冪等去重鍵，不算新請求。

**原題的四個選項全數作廢** —— 第七輪使用者質疑「這四個看起來都沒有很好啊」，
查證後確認模型從未定義「等多久算逾時」，重試次數只是等待預算的分配方式。
