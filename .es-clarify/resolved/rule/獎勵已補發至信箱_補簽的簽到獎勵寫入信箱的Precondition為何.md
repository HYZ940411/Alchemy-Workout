# 釐清問題

補簽當日的簽到獎勵寫入獎勵信箱，其 Precondition 為何？屬於哪一條寫入路徑？

# 定位

流程：補簽流程
元素：Rule：Event「獎勵已補發至信箱」的 Precondition
細節：`02_Aggregate定義.md` L900–L906〈寫入信箱的兩條路徑〉表格中，缺少補簽這一列。

# 白話說明

獎勵信箱 Aggregate 的「來源」欄位（`02_Aggregate定義.md` L894）列了六種來源，
其中**包含補簽**：

```
| 來源 | 列舉 | 每日任務 / 個人排行 / 團隊日常排行 / 團隊限時排行 / 補簽的簽到獎勵 / 限時任務 |
```

但下面那張「什麼情況下會寫進信箱」的表（L900–L906）只有三列，**沒有補簽**：

| 路徑 | 適用來源 | Precondition |
|------|----------|--------------|
| 重置補發 | 每日任務 | 該筆獎勵所屬任務已完成，且於重置時點仍未領取 |
| 直接寫入 | 三個排行獎勵 | 「排行榜週期已結算」已發生，且該使用者或團隊達獎勵名次 |
| 當日結束補發 | 限時任務 | 「成員已完成一次限時任務」已發生，且於當日結束（當地 04:00）仍未領取 |

也就是說：模型承認補簽獎勵會進信箱（L912 甚至特別寫了一句
「補簽當日的簽到獎勵亦寫入信箱，承既有裁決」），**卻沒說是在什麼條件下寫進去的**。

還有一個連帶的漏洞：L914–L915 說「來源」是機器判讀欄位，
系統要依它決定領取時產生哪一個「⋯獎勵已發放」Event，並列舉了
「每日任務 / 個人排行 / 團隊日常排行 / 團隊限時排行 / 限時任務各有其 Event」——
**補簽也不在這個列舉裡**，所以使用者領取補簽獎勵時該產生哪個 Event，同樣沒有答案。

另外 `補簽流程.md` 全檔（30 行）**完全沒有出現「獎勵已補發至信箱」這個 Event**，
也沒有任何 [串聯] 指向 Command「補發獎勵至信箱」。對照 `排行榜週期結算流程.md` L11–L12
與 `每日任務流程.md` L40–L41，兩者都明寫了串聯句與 Event 行。

# 多選題

| 選項 | 描述 | 推薦 |
|------|------|------|
| A | **新增第四條路徑「補簽直接寫入」**：Precondition ＝「使用者已補簽」已發生，且該補簽日的簽到獎勵尚未發放過。補簽當下即寫入信箱，無中間狀態 | ★ |
| B | **比照重置補發**：補簽當下先掛在某處，於次日重置時點仍未領取才寫入信箱 | |
| C | **比照當日結束補發**：補簽當下先掛在補簽頁，於當日結束（當地 04:00）仍未領取才寫入信箱 | |
| D | **改為直接入帳，不進信箱**：推翻既有裁決，補簽獎勵比照真實簽到直接入帳 | |
| Short | 提供其他簡短答案（<=5 字） | |

# 推薦選項與理由

**推薦 A（新增第四條路徑，直接寫入）。**

- **模型已寫下「直接寫入」的判準，補簽正好符合**。`02_Aggregate定義.md` L909–L911
  解釋排行獎勵為何採直接寫入而非兩段式：

  > 其產生於週期結算⋯當下使用者不在 App，**模型中亦無其他頁面可承載該筆待領獎勵** ——
  > 信箱本身就是那份待領清單，不需要再造一個中間站。

  補簽獎勵的處境相同：它屬於「08-18 那一天」的獎勵，而 08-18 的簽到畫面早就過去了，
  沒有任何頁面可以掛這筆待領獎勵。選 B 或 C 都需要先造一個中間站，
  而這正是模型明文說過不要做的事。
- **B 與 C 的 Precondition 都寫不出來**：兩者的條件都是「於某時點**仍未領取**」，
  但補簽獎勵在寫入信箱之前根本沒有可領取的地方，「仍未領取」這句話沒有對象。
- **A 與既有裁決相容且不新增狀態**。
  `.es-clarify/resolved/rule/連續簽到已恢復_補簽是否計入累計簽到天數與當日獎勵.md`
  已裁決「補發至獎勵信箱、不直接入帳」，A 是唯一不引入新狀態就能滿足該裁決的路徑。
- **不推薦 D**：直接推翻既有裁決。且 `補簽流程.md` L15 的「補發至獎勵信箱，不直接入帳」
  是刻意設計——它讓補簽獎勵與真實簽到獎勵在領取方式上有所區別，
  同時又維持 L16「補簽視同該日有簽到」的數額一致。

**選 A 之後須補上的三件事**：
1. `02_Aggregate定義.md` L906 後增列一列：`| 補簽直接寫入 | 補簽的簽到獎勵 | 「使用者已補簽」已發生，且該補簽日的簽到獎勵尚未發放過 |`；
2. L900 的標題「寫入信箱的**兩**條路徑」須改為「四條路徑」（現況已有三列，標題本身即已過期）；
3. `補簽流程.md` 增列 [串聯]「系統執行『補發獎勵至信箱』導致『獎勵已補發至信箱』」與 Event 行，
   比照 `排行榜週期結算流程.md` L11–L12 的寫法；並於 L914–L915 的 Event 列舉中補上補簽對應的
   「簽到獎勵已發放」。

# 對 Gherkin 翻譯的影響

影響 `.gh-clarify/then/使用補簽券_連帶產生的Event要斷言到哪一層.md`。

補簽成功的 Scenario，其 Then 除了斷言連續天數，還要不要斷言「獎勵進了信箱」？
**目前斷言不了**，因為：

- 沒有 Precondition，就無從判斷「這一步在補簽的當下發生，還是等到明天才發生」。
  選 A → Then 可直接寫 `And 使用者（U001）的獎勵信箱新增一筆來源為「補簽的簽到獎勵」的未領取獎勵`；
  選 B/C → 這條 Then 不能放在補簽的 Scenario 裡，必須另開一條有時間推進的 Scenario。
- `補簽流程.md` 裡沒有「獎勵已補發至信箱」這個 Event，
  依全域規範「Then ＝ Postcondition ＋ Event」，翻譯時根本不會產生這條斷言，
  等於補簽獎勵這條路徑在 Gherkin 中完全沒有驗收。

# 解決結果

**選項 A** —— 新增第四條路徑「補簽直接寫入」。

| 路徑 | 適用來源 | Precondition |
|------|----------|--------------|
| **補簽直接寫入** | **補簽的簽到獎勵** | 「使用者已補簽」已發生，且該補簽日的簽到獎勵尚未發放過 |

補簽當下即寫入信箱，無中間狀態。理由同排行獎勵的直接寫入：
補簽獎勵屬於已經過去的那一天，該日的簽到畫面早已不存在，模型中無任何頁面可承載該筆待領獎勵。
而「重置補發」與「當日結束補發」兩式的 Precondition 皆為「於某時點**仍未領取**」，
補簽獎勵在進信箱前無可領取之處，該條件無對象可指，兩式皆不適用。
