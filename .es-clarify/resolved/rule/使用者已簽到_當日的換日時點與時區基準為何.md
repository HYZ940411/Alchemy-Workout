# 釐清問題

「使用者已簽到」判定為「當日」的換日時點與時區基準為何？是否與每日任務流程的 04:00 重置一致？

# 定位

流程：每日簽到流程
元素：Rule：使用者已簽到的 Precondition（當日尚未簽到）
細節：時間邊界：跨日、跨時區（C3）；與每日任務流程「每日當地時間 04:00 重置」的一致性。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 與每日任務一致，當地時間 04:00 換日 |
| B | 當地時間 00:00 換日，與每日任務的 04:00 刻意不同 |
| C | 統一使用 UTC+8 換日，不隨使用者所在地變動 |
| D | 以帳號註冊時設定的時區為準，00:00 換日 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響「使用者已簽到」的 Precondition、連續簽到 Aggregate 的天數計算、連簽中斷判定的計時基準、以及與每日任務流程重置時點的一致性。跨時區旅行時的行為由此決定。

# 優先級

High

# 解決結果

**選項 B**：以使用者當地時區的 **04:00** 換日。

- 時區基準為使用者當地時區（承 `00_全域規範.md` 既有規則，選項 C / D 的平台統一時區與 UTC 已被該規則排除）。
- 當地時間 00:00–03:59 的簽到計入前一個自然日。
- 採 04:00 而非 00:00：健身族群多有深夜運動習慣，午夜換日會使凌晨訓練與簽到落到隔日，不符直覺。
- 簽到與每日任務重置採同一換日時點，模型中不存在第二個換日時點
  ——原本選 A 會產生「簽到 00:00、任務 04:00」兩個換日時點，選 B 消除了此不一致。
- 本換日時點不適用於「連續訓練天數」的自然日計數，該處另有 36 小時寬限規則。
