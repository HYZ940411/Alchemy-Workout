# 釐清問題

「連簽中斷判定」中 24 / 36 / 48 小時的計時起點是「上次簽到的實際時間」還是「上次簽到日的日界」？

# 定位

流程：每日簽到流程
元素：Rule / Policy：連簽中斷判定（24 小時未簽到發送連簽中斷預告、36 小時未簽到天數中斷、48 小時未簽到發送補簽提醒）
細節：時間邊界與計時起點（C3）。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 以上次簽到的實際時戳起算，時戳 +24 / +36 / +48 小時 |
| B | 以上次簽到日的日界（換日時點）起算 |
| C | 以上次簽到日的隔日日界起算，即容許整個隔日都可簽到不中斷 |
| D | 不以小時計，改以「連續錯過 N 個簽到日」判定 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響連簽中斷預告已發送、簽到連續天數已中斷、補簽提醒已發送三個 Event 的觸發時點、連續簽到 Aggregate 的欄位（需記錄上次簽到時戳或日期）、以及補簽流程可回補範圍的計算基準。

# 優先級

High

# 解決結果

**選項 B**：以上次簽到日的**日界**（該日結束、次日當地 04:00）起算。

| 距日界 | 判定 |
|--------|------|
| +24 小時 | 整整錯過 1 天 → 連簽中斷預告已發送 |
| +36 小時 | 錯過 1.5 天 → 簽到連續天數已中斷 |
| +48 小時 | 錯過 2 天 → 補簽提醒已發送 |

**不採選項 A（實際時戳）的理由**：以換日時點 04:00 為例，週一 05:00 簽到者與週一 23:00 簽到者，
收到中斷預告的時間會差 18 小時，純粹取決於昨天幾點開 App；且 A 會在使用者**今日仍有簽到資格**時
就發出中斷預告。

- 不採 C：等於整體延後一天，錯過兩天才中斷，過於寬鬆。
- 不採 D：雖最直覺，但須改寫既有的 24 / 36 / 48 三個數字，無必要。
- 三個門檻對應「錯過 1 天 / 1.5 天 / 2 天」，與使用者心智模型一致。

**連帶新增欄位**：連續簽到 Aggregate 新增「上次簽到日期」（date，使用者當地日期），作為計時基準。
