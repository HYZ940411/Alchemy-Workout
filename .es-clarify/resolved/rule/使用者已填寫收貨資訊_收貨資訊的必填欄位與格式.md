# 釐清問題

「使用者已填寫收貨資訊」的必填欄位有哪些？是否支援儲存常用地址？是否支援海外配送？

# 定位

流程：實體商品購買流程
元素：Rule：使用者已填寫收貨資訊的 Precondition；Aggregate：收貨資訊
細節：Command 的輸入參數與必填 / 選填（B3）；Precondition 可驗證性（C1）。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 收件人姓名 / 手機 / 郵遞區號 / 地址皆必填，僅支援台灣本島配送，不儲存常用地址 |
| B | 上述皆必填，支援儲存多筆常用地址，僅台灣配送 |
| C | 上述皆必填加國家欄位，支援海外配送，儲存常用地址 |
| D | 僅姓名與地址必填，其餘選填 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響收貨資訊 Aggregate 的欄位定義與驗證規則、填寫收貨資訊 Command 的輸入參數、是否需要「常用地址」Aggregate、以及配送範圍的 Precondition。

# 優先級

Medium

# 解決結果

**選項 A**：收件人姓名、手機號碼、郵遞區號、地址（單一自由文字欄）、備註（選填）。

| 欄位 | 必填 | 說明 |
|------|------|------|
| 收件人姓名 | 必填 | — |
| 手機號碼 | 必填 | 須符合手機號碼格式 |
| 郵遞區號 | 必填 | 物流商所需，獨立成欄以利格式檢核 |
| 地址 | 必填 | 單一自由文字欄 |
| 備註 | 選填 | — |

**Postcondition 原子化為 4 條 Precondition**（一條驗一件事）：姓名非空、手機非空且符合格式、郵遞區號非空、地址非空。

**不拆結構化地址（不採選項 B）**：拆縣市 / 鄉鎮區 / 街道須維護行政區資料，而行政區會改名、合併，
屬持續維護負擔；且模型已定案「出貨後的物流留在系統邊界之外，由外部物流商負責」，
本系統僅將地址原封不動交付物流商，無任何拆解用途。

**保留郵遞區號（不採選項 D）**：物流商幾乎皆需要，且它是唯一「填錯會直接導致寄送失敗、
使用者又常填錯」的欄位，值得獨立成欄做格式檢核。

**不收集電子郵件（不採選項 C）**：出貨通知的管道尚未定案，且「商品已出貨」無對應的通知 Event
——通知類 Event 為一份明確清單，其中沒有出貨通知。不為不存在的功能收集個資。

**手機格式不寫死國別**：模型中無「限特定地區」的既有裁決，寫死特定國別格式會成為隱形的地區假設；
規則僅寫「符合手機號碼格式」，實際規則留給實作階段。
