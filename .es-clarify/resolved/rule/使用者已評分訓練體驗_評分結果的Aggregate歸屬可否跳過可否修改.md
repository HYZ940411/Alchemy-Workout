# 釐清問題

「使用者已評分訓練體驗」為多對一 Event（由新手任務與訓練結算兩處觸發），評分內容供〈Read Model：管理員評分彙總〉使用。但評分結果應歸屬於哪個 Aggregate（獨立的評分紀錄，或掛在訓練計畫/新手任務範本之下）、使用者可否跳過評分、評分後可否修改，三者皆未定案。

# 定位

流程：新手任務流程、訓練結算流程
元素：Event「使用者已評分訓練體驗」；Read Model「管理員評分彙總」
細節：〈管理員評分彙總〉已定案「彙總欄位（每個評分對象一列，含平均評分、評分則數、星等分布）」與「下鑽欄位（逐筆評分＋文字回饋）」，暗示評分紀錄需獨立可查詢的儲存單位，但該單位的 Aggregate 歸屬未正式定案。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 獨立為「訓練體驗評分」Aggregate，欄位含評分對象類型（新手任務/訓練計畫）、評分對象 ID、評分者 ID、星等、文字回饋、評分時戳；可跳過（不評分不阻擋任何後續 Command）；評分後不可修改（比照多數評分類機制一次性寫入）（**推薦**：模型既有慣例對「有內容、需被彙總查詢」的資料一律獨立成 Aggregate（如師徒任務評分、每週互動評分皆各自可辨識來源），且〈管理員評分彙總〉的下鑽欄位需要逐筆可查，掛在別的 Aggregate 下會使查詢須跨表拼湊；可跳過符合「評分為使用者主動回饋，非義務」的一般直覺；不可修改符合模型對已發生 Event 的一貫處理） |
| B | 掛在訓練結算/新手任務完成的 Event 攜帶欄位中，不獨立成 Aggregate，管理員評分彙總改為對 Event 記錄做延遲彙總查詢 |
| C | 獨立成 Aggregate，但強制必填不可跳過（每次訓練結算/新手任務完成皆須評分才能領取獎勵） |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響 Read Model「管理員評分彙總」的資料來源定義、Event「使用者已評分訓練體驗」的完整 Postcondition。為 `pending-gaps-3.md` I12 之延續（於新手任務流程與訓練結算流程兩處重複標記）。

# 優先級

Medium

# 解決結果

**選項 D**（於問答中新增的選項）：獨立 Aggregate ＋ **每人每份訓練計畫僅評分一次** ＋ 可跳過 ＋ 可修改。

## 三個子問題的裁決

| 子問題 | 裁決 |
|--------|------|
| Aggregate 歸屬 | **獨立為「訓練體驗評分」Aggregate**（評分對象類型、對象 ID、評分者 ID、星等、文字回饋、評分時戳；唯一鍵為 評分者 ID ＋ 對象類型 ＋ 對象 ID） |
| 可否跳過 | **可跳過**，不阻擋領取獎勵或任何後續 Command；跳過不產生 Event、不記錄狀態 |
| 可否修改 | **可修改**（覆蓋原值），修改不另立 Event |

## 本題新增的第四項裁決：評分次數上限

**使用者反問「不是會有評分次數上限了嗎」，查證後確認：訓練體驗評分原本沒有任何上限**
（模型中有上限的是師徒線的兩條——師徒任務評分每週 2 次、每週互動評分每週 1 次，
兩者為防教官刷聲望而設，與本評分無關）。

原規則為每次訓練結算皆觸發，故同一人對同一份計畫可評無限多次且全數進入彙總平均，
**等同一個人灌多票**；而〈管理員評分彙總〉的「評分則數」欄位本是給管理員判斷
平均值可信度用的，重複計入會使該欄位給出錯誤的信心。

**本題補上該缺口：每人每份訓練計畫終身僅評分一次。**
附帶使受詢問次數由「每次訓練」降為「每換一份新計畫一次」，約為原本的 1/12。

## 為何不採 C（強制必填）

使用者原傾向 C（「我是想說不要跳過」），助理不推薦，三個理由：

1. **強制會讓資料失去用途**：評分卡在獎勵發放之前，被擋住者會隨手點一個把它關掉，
   取得的是筆數而非課表品質的訊號——而本評分的唯一讀者要回答的正是「哪一份計畫該改」。
2. **擋在核心迴圈上**：原觸發條件為每次結算，用官方計畫者一個月約 12 次強制攔截。
3. **模型已有方向相反的同型判例**：〈體重的時效性〉明文「可跳過，且不得阻擋簽到」，
   理由為「跳過即無法簽到會使連續簽到天數中斷，該代價遠大於一筆體重資料」。

**真正的槓桿是「問的頻率」而非「能不能跳過」**——需要的不是每次訓練都有評分，
而是每份計畫累積到足夠的評分則數。

## 使用者確認的範圍

使用者追問「這個訓練是指官方提供的訓練嗎」——是。承既有的〈評分的涵蓋範圍〉：
官方訓練計畫 ✅、新手任務 ✅、自訂訓練 ❌、空白課表 ❌，理由為「評分對象為平台提供的內容」。
