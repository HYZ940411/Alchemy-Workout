# 釐清問題

「每日登入提醒已發送」已定案發送對象（當日尚未簽到者）、發送渠道（推播）、不取偏好訓練時段起點，但發送的「使用者當地時區固定時點」具體是幾點，尚未給定數值。

# 定位

流程：每日簽到流程
元素：Event「每日登入提醒已發送」
細節：模型已排除採用偏好訓練時段起點（避免與訓練提醒擠在同一時段），但沒有給出替代的具體時刻。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 晚間 20:00（使用者當地時區），為多數人結束一天主要活動、仍有意願完成簽到的常見時段，且與清晨的換日時點（04:00）及多數人的訓練時段錯開（**推薦**：晚間是行動應用推播的公認高互動時段之一，且與模型換日基準 04:00 拉開足夠距離，不會被誤認為與換日或訓練提醒同一批次） |
| B | 使用者當地時間中午 12:00，作為一天中段的提醒，不偏向早或晚 |
| C | 平台級可調參數，不寫死具體時刻，由管理員於後台設定初始值 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響 Event「每日登入提醒已發送」的排程觸發時刻。純數值參數，不影響任何結構性設計。

# 優先級

Low

# 解決結果

**選項 A：使用者當地時間 20:00**，平台級可調參數。

## 理由

一天將盡但仍來得及簽到，多數人已下班在家、開 App 的阻力最低；
距換日（當地 04:00）尚有 8 小時，即使未立即看到亦有充裕時間補上。

## 不採方案

- **12:00**：距換日尚有 16 小時，提醒過早，看到的人未必當下即簽。
- **22:00**：雖更接近截止而急迫感強，但已接近就寢時間，錯過即真的錯過。
- **依使用者歷史簽到時間各自推算**（比照訓練提醒的兩段式）：
  訓練提醒之所以做推算，是因訓練時間因人差異極大（早上派 vs 晚上派）；
  而簽到只要開 App 即完成、不受作息限制，為其另建一套推算機制換不到對等的好處。

## 與既有規則的相容

- 承既有裁決「發送時間不取偏好訓練時段起點」——20:00 為固定時點，與該欄位無關。
- 本 Event 屬例行提醒類（優先序 3，最低）：同日若有期限即將失效類通知，優先發送後者。
