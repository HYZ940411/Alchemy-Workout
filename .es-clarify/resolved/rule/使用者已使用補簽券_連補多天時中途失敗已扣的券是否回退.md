# 釐清問題

連續使用多張補簽券補回多天時，若中途某一張失敗，先前已成功扣除的補簽券是否回退？

# 定位

流程：補簽流程
元素：Rule：Command「使用補簽券」的例外路徑（檢查項 C5：執行到一半失敗時的狀態回復）
細節：`補簽流程.md` 全檔未定義任何失敗路徑。

# 白話說明

模型已裁決「一張補一天，可連續使用多張補回多天」
（`補簽流程.md` L10、L23）。那就一定會出現「補到一半出事」的情況。

**具體情境**：使用者手上 3 張券，想補回 08-18、08-19、08-20。

| 步驟 | 發生什麼 | 券剩幾張 |
|------|---------|---------|
| 補 08-18 | 成功 | 2 |
| 補 08-19 | 成功 | 1 |
| 補 08-20 | **失敗**（例如同一時間在另一台裝置上已經補過，或當天已超出回補範圍） | 1？還是 3？ |

第三張失敗之後：

- 前兩張已經成功的補簽算不算數？
- 已經扣掉的 2 張券要不要退回來？

模型現在完全沒寫。`補簽流程.md` 30 行裡，只有 L4、L6 兩條 Precondition
說明什麼情況下**可以**補，沒有任何一句說明**不可以**的時候會怎樣。

# 多選題

| 選項 | 描述 | 推薦 |
|------|------|------|
| A | **逐張獨立結算**：每一張券自成一個完整操作，各自成功或失敗，已成功者不回退。上例結果為：18、19 補回成功，20 未補回，剩 1 張券 | ★ |
| B | **整批原子性**：一次送出的多天視為一批，任一天失敗則全批回退，券全數退回。上例結果為：三天都沒補回，剩 3 張券 | |
| C | **整批但盡力而為**：全批送出、逐天嘗試，失敗者略過不回退，最後回報哪幾天成功 | |
| D | 不定義失敗路徑，由 UI 保證不會送出不合法的日期 | |
| Short | 提供其他簡短答案（<=5 字） | |

# 推薦選項與理由

**推薦 A（逐張獨立結算）。**

- **模型既有的措辭本來就是逐張的**。`補簽流程.md` L10 與 L23 都寫「一張補簽券補回一天，
  **可連續使用多張**」——「連續使用」描述的是重複做同一件事，不是一次做一批。
  L22 的 Postcondition 也是「補簽券持有張數 **−1**」，一次減一張，沒有批次語意。
- **B 需要引入模型目前不存在的東西**：一個「批次」的界線、一個代表批次的 Event，
  以及跨 Aggregate 的補償交易（券要退、已寫入的簽到紀錄要刪、連續天數要回算）。
  `02_Aggregate定義.md` 通篇沒有任何補償交易的先例。
- **A 對使用者也比較合理**：補回 08-18 這件事本身已經成立了，
  沒有理由因為 08-20 補不成而把它撤銷。B 的行為（三天都白補）反而更難解釋。
- **不推薦 D**：Precondition 存在的意義就是後端要擋。且 L4「持有張數 ≥ 1」這種條件
  在併發情境下（兩台裝置同時操作）UI 本來就擋不住。模型對其他流程都有明確的
  Precondition 檢核，補簽不該例外。
- **選 A 之後須補上的**：`補簽流程.md` 應明確寫出「每一次『使用補簽券』為獨立的操作單位，
  Precondition 於每一次各自檢核，先前已完成的補簽不因後續失敗而撤銷」。
  另需與〈恢復連續簽到_由哪一個 Event 觸發〉一題的推薦選項（逐次觸發、可重入）呼應。

# 對 Gherkin 翻譯的影響

影響 `.gh-clarify/feature/使用補簽券_連續使用多張補簽券補回多天要寫成一條還是多條Scenario.md`
與 `.gh-clarify/then/使用補簽券_失敗原因共有幾類.md`。

- **Scenario 的結構取決於本題**：選 A → 每張券一條 Scenario，
  「補到一半失敗」寫成一條 `When` 三次、`Then` 各自斷言的情境；
  選 B → 必須寫成單一 `When 使用者（U001）一次補回 2026-08-18、08-19、08-20`，
  Then 斷言全批回退後的狀態。
- **`.gh-clarify/then/使用補簽券_失敗原因共有幾類.md` 現在數不出類別**：
  模型沒有任何失敗路徑的描述，該項要列舉的「失敗原因」在模型中一條都找不到。
  本題至少確立「中途失敗」這一類的處理方式。

# 解決結果

**選項 A** —— 逐張獨立結算，已成功者不回退。

**每一次「使用補簽券」為獨立的操作單位**：Precondition 於每一次各自檢核，成功或失敗各自結算。
失敗時不扣券、不寫入每日簽到紀錄、不重算連續天數、不寫入獎勵信箱；
先前已完成的補簽不因後續失敗而撤銷。

範例（3 張券補 08-18/19/20，第三張失敗）：18、19 補回成功，20 未補回，剩 1 張券。

**與前面幾題的一致性**：第 2 題已定「連補多天時每補一天觸發一次」、
第 4 題的逐日推算為可重入 —— 整條連鎖本即逐張形狀，選 A 不需改動任何已定案內容。
選 B 則須將第 2、4 題一併改為批次語意。

**不採 B（整批原子性）的理由**：須先定義「一批」的界線與代表批次的 Event，
並引入跨 Aggregate 的補償交易（退券、刪除簽到紀錄、回算連續天數、撤回信箱獎勵），
模型通篇無補償交易之先例。

**不採 D（由 UI 保證）的理由**：Precondition 的意義即在於後端須擋；
且「持有張數 ≥ 1」在兩台裝置同時操作時 UI 本即擋不住。
