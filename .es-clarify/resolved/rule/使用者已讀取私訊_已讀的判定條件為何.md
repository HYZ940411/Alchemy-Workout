# 釐清問題

「使用者已讀取私訊」的已讀判定條件為何？是否通知發送方？可否關閉已讀回條？

# 定位

流程：聊天私訊流程
元素：Rule：使用者已讀取私訊的 Precondition 與 Postcondition
細節：Precondition 可驗證性（C1）；Postcondition 涵蓋的欄位（C2）。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 開啟對話即標記全部訊息為已讀，發送方可見已讀狀態，不可關閉 |
| B | 訊息進入畫面可視範圍才標記已讀，發送方可見，不可關閉 |
| C | 開啟對話即已讀，但使用者可關閉已讀回條（關閉後雙方皆看不到） |
| D | 不做已讀標記，僅記錄未讀數，此 Event 應移除 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響使用者已讀取私訊的判定條件與 Postcondition、私訊 Aggregate 的已讀欄位、是否需要未讀數 Read Model、以及使用者隱私設定欄位。

# 優先級

Medium

# 解決結果

**選項 A**：開啟對話即標記全部訊息為已讀，發送方可見已讀狀態，不可關閉。

**使用者追問「包含通知發送方嗎」→ 明確區分兩件事**：

| | 做法 | 是否採用 |
|---|------|---------|
| 已讀狀態被動可見 | 發送方打開對話時，訊息旁顯示「已讀」 | ✅ 採用（選項 A 的原意） |
| 已讀推播通知 | 主動推播「對方已讀了你的訊息」 | ❌ 不採用 |

- 不做已讀推播：會使每則訊息產生兩次推播，且「對方讀了」對發送方不構成需立即處理的事。
- 模型層面的佐證：通知類 Event 為一份明確清單（6 個，皆標記不需精準追蹤），
  要做推播須新增 Event 並列入該清單，本題不擴張。

**規則**：

- Precondition：使用者開啟對話，且該對話中存在以其為接收方、已讀時戳為空的私訊。
- Postcondition：上述私訊的已讀時戳一律寫入當下時戳。
- 不採選項 B（進入可視範圍才已讀）：捲動位置為前端實作細節，無客觀判定標準，
  同一則訊息在不同螢幕尺寸下判定不一致，Precondition 將無法驗收。
- 不採選項 C（可關閉回條）：需新增隱私設定欄位並處理對等性規則，複雜度與本 App 定位不成比例；
  且 C 隨時可在 A 之上疊加，先做 A 不擋住未來。
- 不採選項 D：私訊 Aggregate 已有「已讀時戳」欄位（第 22 題定案），選 D 須移除該欄位與一個既有 Event。
