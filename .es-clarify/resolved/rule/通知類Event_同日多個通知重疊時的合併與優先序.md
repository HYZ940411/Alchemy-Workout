# 釐清問題

模型現有 6 個通知 / 提醒類 Event，同一天可能同時滿足多個發送條件。是否全部發送、是否合併為一則、是否有優先序或每日則數上限？

# 定位

流程：訓練紀錄流程、訓練中斷流程、每日簽到流程
元素：Rule：6 個通知類 Event 的發送策略
細節：A4 軟體邊界、C5 例外路徑、C3 組合邊界。
6 個通知類 Event：訓練提醒已發送（事前）、中斷預告已發送（+24h）、連練中斷通知已發送（+36h）、退步預告已發送（+96h）、每日登入提醒已發送、連簽中斷預告已發送（+24h）、補簽提醒已發送（+48h）。
典型重疊：距上次訓練滿 24 小時當日，同時滿足「慣常時段將至」與「中斷預告」；連簽與連練的 +24 小時門檻亦常同日觸發。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 全部發送，不合併不設上限：各 Event 職責不同，合併會使任一條的發送事實不可稽核 |
| B | 設優先序，同日僅發最高優先的一則（事後補救 > 事前提醒），其餘 Event 仍產生但不實際推播 |
| C | 合併為單一推播（多則內容併陳），但各 Event 仍各自產生，維持可稽核性 |
| D | 設每日推播則數上限（如 2 則），依優先序取前 N 則；Event 全數產生，推播與否為發送層的決策 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響 6 個通知類 Event 的 Postcondition、〈通知 / 提醒類 Event 的軟體邊界〉章節（現規定「維持各自獨立，不合併為單一通知已發送 Event」—— 本題問的是**推播層**的合併，與該裁決不衝突但須寫明區別）、以及使用者的推播疲乏風險。
相依：`rule/訓練提醒已發送_慣常訓練時段的推算基準與提醒頻率.md`、`rule/每日登入提醒已發送_發送時間對象與渠道為何.md`（宜三題併處理）。

# 優先級

Medium

# 解決結果

**選項 A ＋ 優先序** —— 不合併，各自發送；同日推播總數設上限，超出者依優先序由低至高捨棄。

使用者補充：「簽到優先度較低，如果當天有中斷預告等通知，應該優先」。
優先序（高→低）：1 期限即將失效類（連簽中斷預告 / 補簽提醒 / 中斷預告）→ 2 行動引導類（訓練提醒）→ 3 例行提醒類（每日登入提醒）。
