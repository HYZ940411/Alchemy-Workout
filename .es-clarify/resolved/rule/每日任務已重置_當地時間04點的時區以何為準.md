# 釐清問題

「每日當地時間 04:00 重置清空當日每日任務進度」中的「當地時間」以何為準？裝置時區、帳號設定時區、還是註冊地？跨時區移動時如何處理？

# 定位

流程：每日任務流程
元素：Rule / Policy：每日當地時間 04:00 重置清空當日每日任務進度
細節：時間邊界：跨日、跨時區（C3）；與每日簽到流程換日時點的一致性。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 以裝置當前時區為準，跨時區移動即時生效 |
| B | 以帳號設定的時區為準，使用者可自行變更，變更後次日生效 |
| C | 全平台統一使用 UTC+8，與使用者所在地無關 |
| D | 以裝置時區為準，但同一自然日內時區變更不重複重置（防刷） |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響每日任務已重置的觸發時點、使用者 Aggregate 是否需要時區欄位、與每日簽到流程換日時點的一致性、以及跨時區使用者的公平性。與簽到換日問題有強依賴關係。

# 優先級

High

# 解決結果

**選項 A**：使用者**裝置的當前時區**。

- 不採使用者 Aggregate 儲存的時區欄位（選項 B）：該欄位為註冊當下填入，
  使用者出國、搬家或變更裝置語系後即過期，會出現「人在東京、任務按台北時間重置」。
- 平台統一時區（選項 C）已被 `00_全域規範.md` 既有規則排除（跨時區規則一律以使用者當地時區時戳為基準）。
- 使用者 Aggregate 的時區欄位僅供顯示與統計，不作為換日與中斷判定的依據。

**跨時區移動的風險已由既有機制涵蓋**：第 6 題定案的排程冪等（請求識別碼 ＝ 排程名稱 ＋ 週期起點 ＋ 使用者 ID，
週期起點為使用者當地日期）會擋下同一當地日期的重複觸發，選 A 不需額外機制。

**換日時點與簽到一致**（當地時區 04:00，承第 35 題）。
