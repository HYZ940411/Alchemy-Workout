# 釐清問題

虛擬商品交易已成立、扣款已完成，但道具入庫失敗時，應發生什麼 Event？後續為退款或重試？

# 定位

流程：虛擬商品購買流程
元素：Event「商品已發放」與「購買已失敗」之間的缺口
細節：失敗與例外路徑（C5）；訂單狀態機（D5）。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 維持不建模，於流程檔標記「發放失敗留在系統邊界之外，由客服人工處理」 |
| B | 補「商品發放已失敗」Event，系統自動重試至上限（如 3 次），仍失敗則轉人工 |
| C | 補「商品發放已失敗」Event，直接觸發退款（虛擬貨幣返還 ＋ 金流退款），訂單轉「已退款」 |
| D | 取消非同步設計，改為發放與交易成立同一交易內完成，失敗則整筆回滾至「購買已失敗」 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響虛擬訂單狀態機是否新增狀態、「購買已失敗」的失敗原因值域、金幣餘額的一致性保證。
承接 G11。**注意**：`resolved/event/商品已發放_與使用者已購買虛擬商品的差異為何.md`（選項 A）已裁決發放為非同步且未補失敗 Event；本項記錄的是該裁決留下的空洞，非推翻裁決。

# 優先級

Medium

# 解決結果

**選項 B**：補「商品發放已失敗」Event，系統自動重試至上限，仍失敗則轉人工。

- 重試次數上限為 **3 次**（採選項 B 所列數值）。
- 「商品發放已失敗」不改變訂單狀態，訂單於發放成功前維持已付款。
- 不自動退款：虛擬貨幣與真實金流併用時的雙向退款複雜度高於重試。
- 保留「發放為非同步」的既有裁決，本路徑僅補失敗處理，不改為同步。
- 與第 7 題（訂閱扣款失敗選 A 不建模）的差異：本情境失敗發生在平台內部且已收款，平台負交付責任。
