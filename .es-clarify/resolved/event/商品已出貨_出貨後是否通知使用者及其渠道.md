# 釐清問題

實體商品出貨後，模型沒有任何通知使用者的路徑（通知類 Event 清單中無出貨通知，且刻意不收集電子郵件）——使用者如何得知已出貨與物流單號？

# 定位

流程：實體商品購買流程
元素：Event — 商品已出貨；Rule — 通知類 Event 的發送規則
細節：`02_Aggregate定義.md`〈收貨資訊欄位〉「不收集電子郵件：出貨通知的管道尚未定案，且通知類 Event 清單中無出貨通知」。現況使用者僅能自行到〈Read Model：我的訂單頁〉查看

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 加入 App 內通知類（不推播、不受同日總量上限）：於我的訂單頁以紅點呈現，不新增 Event，寫為「商品已出貨」的 Postcondition |
| B | 加入推播類（行動引導類第 2 級）：出貨後推播一次，含物流單號 |
| C | 不通知，維持現狀：使用者自行至我的訂單頁查看；於規範明文記載此為刻意取捨 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

- 〈通知類 Event 的發送規則〉之推播類清單或 App 內通知類清單
- 收貨資訊欄位是否需增列電子郵件（現為刻意不收集）
- 〈Read Model：我的訂單頁〉的呈現與紅點規則

# 優先級

Medium

# 解決結果

**A**：App 內通知類（不推播、不受同日總量上限），於〈Read Model：我的訂單頁〉呈現紅點。

- **不新增 Event**：紅點為既有 Event「商品已出貨」的 Postcondition，
  比照「獎勵已補發至信箱 → 獎勵信箱紅點」的既有處理。
- **歸 App 內通知類而非推播**：承既有判準「推播類 ＝ 不看就失去東西；
  App 內通知類 ＝ 東西不會跑掉」——貨照樣會寄到，晚幾天知道不損失任何權益；
  且推播額度僅 3 則／日，已由簽到提醒、訓練提醒與期限預告佔滿。
- **不採推播夾帶物流單號**：使用者不會自推播複製單號查詢，點進訂單頁本即看得到。
- 〈收貨資訊欄位〉的「不收集電子郵件」原因已更新：出貨通知的管道已定案，不需電子郵件。

**連帶提出**：使用者同時詢問「比較重要的通知可否加上 Email 通知」，
已另建釐清項目 `event/通知類Event_是否新增電子郵件為通知渠道.md`。
