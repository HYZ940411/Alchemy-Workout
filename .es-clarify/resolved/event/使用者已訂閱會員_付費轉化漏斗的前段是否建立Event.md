# 釐清問題

付費轉化漏斗的前段（使用者抵達購買頁 / 訂閱頁但未完成購買）是否應建立 Event？

# 定位

流程：會員訂閱流程、虛擬商品購買流程、AI 功能的付費邊界（跨流程）。
元素：Event（缺失）。
細節 —— 漏斗各段目前的可量測狀態：

| 漏斗段 | 現有 Event | 可量測 |
|--------|-----------|--------|
| 遇到付費牆（AI 點數不足） | **AI 調整已拒絕** | ✅ |
| 被導向 AI 點數購買頁 | 無 | ❌ |
| 選擇商品 | 使用者已選擇虛擬商品 | ✅ |
| 確認購買 | 使用者已確認購買 | ✅ |
| 支付結果 | 使用者已支付 / 支付已失敗 | ✅ |
| 抵達會員訂閱頁 | 無 | ❌ |
| 完成訂閱 | 使用者已訂閱會員（Actor：外部系統） | ✅ |

- `02_Aggregate定義.md:1505` 已明文認定「AI 調整已拒絕」為
  「**付費轉化漏斗中最直接的訊號**，不建模則後端無從得知」——
  該處已接受「為漏斗量測而建模」是本模型的正當理由。
- 但**訂閱路徑的第一個 Event 即為 App Store 的回呼**（`使用者已訂閱會員`），
  其前完全無 Event；「看過訂閱頁卻沒訂」在模型中不存在。
- `AI 調整已拒絕` 的 Postcondition 為「導向 AI 點數購買頁」，
  但其後是否成交無任何 Event 可串接，該 Postcondition 的效果不可驗收。

**模型既有的兩則同型判例（皆採「為漏斗而建模」）**：
- `註冊流程`：9 項必填欄位逐一建為 Event，`02_Aggregate定義.md:1231` 註明「用意為分析漏斗流失」。
- `新手任務流程.md:13`：「選擇候選動作」建模的理由即為「不建模會使**漏斗分析出現斷點**」。

**反面依據**：`04_ReadModel清單.md`〈建立原則〉與回歸任務的既有裁決
「不由 Read Model 的讀取寫入時戳：Read Model 已定案不改變任何狀態，破例將使該原則失去約束力」
（`回歸任務流程.md:19`）—— 惟該處同時示範了合法解法：另立 Event「使用者已查看回歸任務」。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 新增 Event「使用者已抵達付費頁」（Actor：使用者），以「頁面類型＝AI 點數 / 會員訂閱 / 進階訓練計畫」與「來源＝AI 調整已拒絕 / 主動進入 / 權益提示」兩個攜帶欄位涵蓋三個入口 |
| B | 僅為 AI 點數購買頁建 Event（該段已有明確的上游 Event「AI 調整已拒絕」可串接），訂閱頁維持不建模 |
| C | 兩處皆不建為業務 Event，改明文裁定漏斗前段屬**產品分析埋點**、留在系統邊界之外，並於〈通知類 Event 的軟體邊界〉比照增列一節說明判準 |
| D | 兩處皆不建模，但將「已導向購買頁」寫為「AI 調整已拒絕」的 Postcondition 欄位（記錄導向與否，不記錄是否抵達） |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

- **Event 清單與 Command 清單**：選 A 新增 1 個 Event ＋ 1 個 Command；選 B 新增各 1 個但值域較窄。
- **軟體邊界的判準本身**：本題實為「純瀏覽行為是否為業務事實」的一般性裁決，其答案會回頭約束日後所有同型提案（如「看過商品頁未購買」「看過教官清單未申請」），故選 C 須連帶寫出判準，而非僅回答本題。
- **AI 調整已拒絕**：其 Postcondition「導向 AI 點數購買頁」目前無下游可驗收，選 A / B / D 皆會改變該條 Postcondition 的寫法。
- **Read Model**：`04_ReadModel清單.md`〈AI 點數頁〉（2026-08-20 新增）與〈會員訂閱頁〉為兩處承載頁；若建 Event，須指明由哪一個 Read Model 的開啟觸發，並確保不牴觸「Read Model 不改變任何狀態」。
- 相關已解決項目：`.es-clarify/resolved/read-model/AI點數餘額頁_AI點數餘額與購買頁尚無ReadModel定義.md`（第十一輪，建立了本題所指的承載頁）。

# 解決結果

**選項 A ＋ 使用者追加的限定：標記為〔不需精準追蹤〕。**

使用者裁決原話：「我想選 A，但是瀏覽看起來不太適合經營世界風暴（事件風暴），
但是他是一個值得作為業務參考的一個事件。」

該顧慮對應至模型既有的〔不需精準追蹤〕機制，故裁決為：

- 新增 Event「**使用者已抵達付費頁**」〔不需精準追蹤〕與 Command「抵達付費頁」（Actor：使用者）。
- 攜帶：頁面類型（AI 點數 / 會員訂閱 / 進階訓練計畫）、來源（AI 調整已拒絕 / 主動進入 / 權益提示）。
- **不建立 Precondition 與 Postcondition**，不改變任何 Aggregate 狀態，不觸發任何下游 Event。
- 三個付費入口共用同一 Event，以頁面類型欄位區分。

**連帶的規範層變動**：`00_全域規範.md` 原〈通知 / 提醒類 Event 的軟體邊界〉一節
**擴寫為〈〔不需精準追蹤〕Event 的軟體邊界〉**，分為兩類：
第一類通知 / 提醒（既有 6 個）、**第二類業務量測（本 Event，新增）**，
並明文化其共同判準：「有記錄價值，但不改變任何 Aggregate 狀態，因而無驗收標的」。
新增第二類成員須同時滿足「有明確業務量測用途」與「不改變任何 Aggregate 狀態」。
