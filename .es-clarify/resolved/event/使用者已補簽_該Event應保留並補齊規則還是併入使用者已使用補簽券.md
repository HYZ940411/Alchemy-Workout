# 釐清問題

「使用者已補簽」這個 Event 應保留並補齊其 [串聯] 與 Postcondition，
還是應併入「使用者已使用補簽券」而刪除？

# 定位

流程：補簽流程
元素：Event：使用者已補簽（`補簽流程.md` L25）
細節：該 Event 以單獨一行出現，前後皆無 [串聯]、無 Precondition、無 Postcondition。

# 白話說明

`補簽流程.md` 裡三個 Event 的待遇差很多：

```
L20  [串聯] 使用者執行「使用補簽券」導致「使用者已使用補簽券」— Actor：使用者
L21  使用者已使用補簽券
L22  [Rule] Postcondition：補簽券持有張數 −1
L23  [Rule] 一張補一天；可連續使用多張補回多天⋯
L24
L25  使用者已補簽                    ← 光禿禿一行，什麼都沒有
L26  連續簽到已恢復
L27  [Rule] Postcondition：連續天數回復為⋯
L28  [Rule] Postcondition：補簽券使用後，中斷前連續天數清空為 0
```

L21 有人觸發（L20 的串聯）、有後果（L22）；
L26 有後果（L27、L28）。
**只有 L25 兩樣都沒有**——不知道誰讓它發生，也不知道它發生之後改變了什麼。

`01_Command清單.md` L121–L125 又列了三個 Command：

```
| 使用補簽券 | 使用者 | 使用者已使用補簽券 |
| 補簽      | 使用者 | 使用者已補簽       |
| 恢復連續簽到 | 系統  | 連續簽到已恢復     |
```

三個 Command 對三個 Event，但流程檔只寫了一條 [串聯]（L20）。
使用者到底是按了一次還是按了三次？「補簽」和「使用補簽券」是不是同一個動作的兩種說法？
模型現在答不出來。

# 多選題

| 選項 | 描述 | 推薦 |
|------|------|------|
| A | **保留兩個 Event，補齊規則**：「使用者已使用補簽券」改動補簽券 Aggregate（張數 −1），「使用者已補簽」改動逐日簽到明細（寫入該日紀錄）。兩者為同一次操作的連鎖，補上 [串聯]／[Policy] 與各自的 Postcondition | ★ |
| B | **刪除「使用者已補簽」**，連同 `01_Command清單.md` 的「補簽」Command 一併移除；補簽即「使用者已使用補簽券」，該 Event 攜帶補簽日期 | |
| C | **反向合併**：保留「使用者已補簽」為主 Event，把「使用者已使用補簽券」降為它的 Postcondition（張數 −1） | |
| D | 保留兩者但改名以區分職責（如「補簽券已扣除」／「該日已補記為簽到」） | |
| Short | 提供其他簡短答案（<=5 字） | |

# 推薦選項與理由

**推薦 A（保留兩個 Event，補齊規則）。**

- **兩個 Event 改的是兩個不同的 Aggregate**。「使用者已使用補簽券」改補簽券 Aggregate
  的持有張數（`02_Aggregate定義.md` L2471）；「使用者已補簽」改的是那一天的簽到紀錄。
  一個 Event 對應一個 Aggregate 的狀態改變，是本模型通篇遵循的形狀
  。
  選 B 會產生一個同時改兩個 Aggregate 的 Event，且該 Event 的名字只講了扣券、沒講補簽，
  名實不符。
- **每日簽到流程有現成的同型對照**。`每日簽到流程.md` L40–L41：

  ```
  使用者已簽到
  連續簽到已紀錄
  ```

  一個動作拆成「事情發生了」與「連續天數被記下來了」兩個 Event，本來就是這個模型的寫法。
  補簽流程的「使用者已補簽 → 連續簽到已恢復」正是它的鏡像，不該只有補簽這邊被合併掉。
- **B 會讓「補簽了但沒扣到券」與「扣了券但沒補到」這兩種失敗無法分開驗收**。
  拆成兩個 Event，Gherkin 才寫得出各自的失敗情境。
- **不推薦 C**：`補簽流程.md` L4 的 Precondition 寫的是「持有張數 ≥ 1，方可發生
  **『使用者已使用補簽券』**」，明確以扣券為起點；反向合併與這條既有 Precondition 衝突。
- **不推薦 D**：改名要動 `01_Command清單.md`、`02_Aggregate定義.md`、`.gh-clarify/` 已建的
  多個項目，而問題本身是缺規則不是名字不好。

**選 A 之後須補上的三件事**：
1. `補簽流程.md` L25 前補 [串聯] 或 [Policy]，指明它由「使用者已使用補簽券」連鎖觸發；
2. L25 後補 Postcondition：該日寫入逐日簽到明細，簽到方式＝補簽；累計天數 +1（承 L14）；
3. 補上 Precondition 的歸屬——L6「所補之日期距今未滿 7 天，且該日確實未簽到」
   目前掛在檔案開頭，未指明它屬於哪一個 Event。

# 對 Gherkin 翻譯的影響

直接阻擋 `.gh-clarify/feature/使用補簽券_補簽流程的三個Command要翻成幾個FeatureFile.md`
與 `.gh-clarify/then/使用補簽券_連帶產生的Event要斷言到哪一層.md`。

- **Feature 切分算不出來**：三個 Command 是一個 Feature 還是三個，取決於它們是不是同一次操作。
  選 A → 一個 Feature、三個 Event 依序斷言；選 B → 剩兩個 Command，Feature 結構整個不同。
- **Then 沒有東西可斷言**：依全域規範，每個 Event 底下至少要有一條 Postcondition 才寫得出 Then。
  「使用者已補簽」現在一條都沒有，翻成 Gherkin 就是一個**沒有任何斷言的空 Scenario**。
- 也影響 `.gh-clarify/given/使用補簽券_Given中的Event順序要不要標示.md`——
  Event 之間的先後與因果沒寫明，Given 的鋪陳順序無從決定。

# 解決結果

**選項 A** —— 保留兩個 Event，補齊規則。

使用者按一次，系統連鎖跑三個 Command，一個 Command 對一個 Event：

```
使用者執行「使用補簽券」   → 使用者已使用補簽券   （Actor：使用者）
        ↓ [Policy] 連鎖
系統執行「補簽」           → 使用者已補簽         （Actor：系統）
        ↓ 第 2 題待定
系統執行「恢復連續簽到」   → 連續簽到已恢復       （Actor：系統）
```

**使用者於本題追問「使用者做一次 Command 觸發兩個 Event 嗎」，經查證後確認：不是。**
`01_Command清單.md` 全檔無任何一列將兩個 Event 掛在同一個 Command 之下；
L143、L409、L434 三處看似如此者，皆為「多對一」的反向情形（多個 Actor 或多個 Command 導致同一 Event）。
故本模型維持「一個 Command 對一個 Event」，多個 Event 之間以 [Policy] 連鎖。

**連帶裁決**：`01_Command清單.md` L124「補簽」Command 的 Actor 由**使用者改為系統**。
原標記會使流程變成「使用者須再按第二次」，與連鎖觸發的形狀不符。
查證確認此改動不造成命名不一致：模型中 Actor 為系統、Event 卻以「使用者已⋯」起頭者
共 **12 處**先例（L77 使用者已完成註冊、L269 使用者已提升階級、L146 使用者已完成訓練等），
Event 名稱描述的是對使用者發生的業務事實，與執行 Command 的 Actor 無關。

**同型對照**：`每日簽到流程.md` L40–L41「使用者已簽到 → 連續簽到已紀錄」，
使用者亦只按一次，「記錄連續簽到」由系統接手（`01_Command清單.md` L110，Actor：系統）。
