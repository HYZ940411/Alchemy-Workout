# 釐清問題

〈排程觸發的請求識別碼〉表目前僅列出 8 個排程類 Event，模型另有多個由排程判定觸發的 Event（單次訓練已逾時中斷、師徒申請已逾期、回歸任務已逾期、團隊邀請已逾期、加入申請已逾期、處罰已到期解除、庫存已釋放、團隊已指派限時任務）未列入，其週期起點（自然鍵）應如何推導？

# 定位

流程：跨流程（訓練紀錄、師徒互動、回歸任務、團隊組隊、團隊任務、管理員管理社群、實體商品購買）
元素：Event 冪等性原則之〈排程觸發的請求識別碼〉
細節：A3 冪等性、E1 串聯一致性。既有規則明訂「排程類 Command 不產生隨機識別碼，一律由上表的自然鍵推導」，但上表未涵蓋上列 8 個 Event，該些 Event 目前無可推導的識別碼。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 逐一補入上表，週期起點一律取「該筆對象的 Aggregate ID」（如師徒申請 ID、訂單 ID、回歸任務 ID），因逾期 / 到期對同一筆對象只發生一次 |
| B | 改為通用規則：凡「對單一 Aggregate 實例做一次性狀態判定」的排程 Event，其請求識別碼＝排程名稱 ＋ 目標 Aggregate ID，不逐一列表 |
| C | 採 B 的通用規則，但可重複發生者（團隊已指派限時任務為每日指派）仍逐一列表，週期起點取指派日 |
| D | 上列 Event 皆改為由狀態轉換的唯一性保證（Precondition 檢查現狀），不納入冪等表 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響〈排程觸發的請求識別碼〉表的完整性、上列 8 個 Event 的重複發生防護、以及〈Command 清單〉中排程類 Command 的輸入參數推導規則。
相關已解決項目：`resolved/event/全流程Event_排程觸發的Event其冪等去重鍵如何產生.md`（選項 A，建立本表）。

# 解決結果

**選項 B** —— 改為通用規則：凡「對單一 Aggregate 實例做一次性狀態判定」的排程 Event，
其請求識別碼 ＝ **排程名稱 ＋ 目標 Aggregate ID**，不逐一列表。

排程類 Event 自此分為兩類：週期性重複判定（沿用原式：排程名稱 ＋ 週期起點 ＋ 使用者 ID）
與一次性狀態判定（新式）。不併入同一張表的理由：原表的「週期起點」欄之所以存在，
是因為第一類同一使用者會反覆發生、須以週期值區分是哪一次；一次性判定的目標 Aggregate ID
本身即為天然唯一鍵，逐列填入會使該欄失去它要表達的資訊。

「團隊已指派限時任務」歸入第二類，其目標為該指派日的限時任務 —— 承既有裁決
「限時任務為全平台統一，一個指派日只有一組」，非逐團隊指派。
