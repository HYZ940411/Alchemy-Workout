# 釐清問題

「能力值日快照」為每日於日界保存一筆的系統排程行為，是否建模為業務 Event（如「能力值日快照已產生」）？若建模，其冪等去重鍵與日界時點為何？

# 定位

流程：訓練結算流程之外的系統排程
元素：Event（尚未存在）；Read Model「六維能力值雷達圖」的資料來源
細節：A3 事件時序與冪等、D6 Read Model 來源。`00_全域規範.md`〈排程觸發的請求識別碼〉表已為 6 個排程行為定義去重鍵，本項未納入。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 建模為 Event「能力值日快照已產生」，去重鍵＝使用者 ID ＋ 快照日期，日界沿用當地時區 04:00 |
| B | 不建模為 Event：快照為 Read Model 的投影，非業務事實，不進 Event 層，但仍納入排程冪等表 |
| C | 不建模為 Event，且改為「僅於能力值變動時寫入快照」，無變動之日不產生資料，由查詢時向前補值 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響〈Event 共通攜帶資訊〉與〈排程觸發的請求識別碼〉兩張表、〈Command 清單〉是否新增「產生能力值日快照」、Read Model「六維能力值雷達圖」的時間維度可查範圍，以及快照資料的保存年限。

# 解決結果

**選項 A**

建模為業務 Event「能力值日快照已產生」（Actor：系統，排程觸發），
對應 Command「產生能力值日快照」；日界時點沿用全模型統一的當地時區 04:00。

**冪等去重鍵 ＝ 排程名稱 ＋ 該筆快照所屬的使用者當地日期 ＋ 使用者 ID**
（承〈排程觸發的請求識別碼〉的既有推導公式）

理由：
1. 承「可推導不等於不成立為 Event」的既有判例（使用者已失去獎勵加成、商品已售完）；
   快照為六維成長軌跡的唯一憑據，某日漏產生即該日歷史永久缺失、無法回補。
2. 結構一致性：〈排程觸發的請求識別碼〉表的每一列皆對應一個 Event，
   若僅納入冪等表而不建 Event，將出現無對應 Event 的孤列。
3. 排除選項 C：其推翻第三輪「每日快照」的裁決；且能力值因退步而在無訓練的日子自行下降，
   查詢時向前補值會把下降過程抹平成水平線。
