# 釐清問題

〈排程觸發的請求識別碼〉把排程類 Event 分成兩類，第一類（週期性重複判定，識別碼＝排程名稱＋週期起點＋使用者 ID）是**逐一列表的封閉清單**，現列 8 個；第二類（一次性狀態判定）則明寫「不逐一列表，凡符合者一律適用」。但七個排程觸發的通知類 Event —— 每日登入提醒已發送、連簽中斷預告已發送、補簽提醒已發送、中斷預告已發送、連練中斷通知已發送、退步預告已發送、訓練提醒已發送 —— 兩張表都沒有它們。而〈〔不需精準追蹤〕Event〉一節又明寫這些 Event「仍適用冪等性原則」。這七個的去重鍵屬哪一類、週期起點取什麼？

# 定位

流程：每日簽到流程、訓練中斷流程、訓練紀錄流程
元素：Event（七個通知類）；Rule：`00_全域規範.md`〈排程觸發的請求識別碼〉
細節：A3 事件重複發生（冪等性）、C3 時間邊界。第一類表現列 8 項、第二類表現列 8 項，皆不含此七者。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A（**推薦**） | **七個全歸第一類，週期起點一律取「該次判定所屬的使用者當地日期」**，逐一補入第一類表。理由：這七個都是「同一位使用者會反覆收到」的通知，正是第一類的形狀；而取當地日期為週期起點，與同表的「簽到連續天數已中斷」「連續訓練天數已歸零」兩列完全一致——那兩列與其中四則預告根本是同一套 24／36／96 小時判定推出來的 |
| B | 分兩類：每日發送者（每日登入提醒、訓練提醒、補簽提醒）歸第一類、週期起點為當地日期；一次性預告（連簽中斷預告、中斷預告、連練中斷通知、退步預告）歸第二類，識別碼＝排程名稱＋連續簽到／連續訓練 Aggregate ID |
| C | 七個全歸第二類，識別碼＝排程名稱＋目標 Aggregate ID，不需列表 |
| D | 通知類 Event 不套用兩條推導式，另立第三條：識別碼＝通知名稱＋使用者 ID＋預定發送時點；理由是通知的自然鍵是「哪一則、發給誰、什麼時候發」 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響 `00_全域規範.md`〈排程觸發的請求識別碼〉第一類表的列數（現 8 列）、七個通知類 Event 的重複發送防護（未定義即可能在排程重跑或使用者跨時區移動時同一天推播兩次，而推播同日總量上限僅 3 則／日）、以及〈〔不需精準追蹤〕Event〉一節「仍適用冪等性原則」這句的可執行性。
相關已解決項目：`resolved/event/全流程Event_排程觸發的Event其冪等去重鍵如何產生.md`（選項 A，建立兩條推導式）、`resolved/event/全流程Event_通知與提醒類Event是否應納入軟體邊界.md`（選項 C）、`resolved/rule/每日登入提醒已發送_固定發送時點的具體時刻尚未定案.md`。

# 解決結果

**選項 A** —— 七個通知類 Event 全歸第一類（週期性重複判定），
週期起點一律取「該次發送／判定所屬的使用者當地日期」，並逐一補入第一類表（8 列 → 15 列）。

排除 B 與 C 的具體理由（作答前已查證 `00_全域規範.md:150-200` 兩張表）：

- 兩者皆將四則預告歸第二類、以「連續簽到／連續訓練 Aggregate ID」為鍵。
- 但該二 Aggregate 與使用者**一對一且終身只有一筆**，
  同一位使用者第二次中斷所推出的識別碼與第一次**完全相同**，
  將被冪等機制判為重複而不發送 —— 中斷預告只會在人生第一次中斷時發出一次。
- 第二類的前提「對單一 Aggregate 實例判定一次即結束」在此不成立。

不採 D（另立第三條推導式）：第一類的推導式已能表達「哪一則、發給誰、哪一天」，
新增第三式會使〈排程觸發的請求識別碼〉由兩式增為三式而無新增表達力。
