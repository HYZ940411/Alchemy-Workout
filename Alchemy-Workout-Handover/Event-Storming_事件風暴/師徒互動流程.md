師徒互動流程
[串聯] 使用者執行「申請師徒關係」導致「使用者已申請 師徒關係」— Actor：使用者  
[決策] 申請雙向皆可（學徒向教官拜師、教官向學徒邀請收徒），維持單一 Event  
[Rule] Precondition：教官已建立的師徒關係數未達帶徒上限；**申請中的申請不佔名額**  
[Rule] Precondition：一位學徒同時僅能有一位教官；一位教官可帶多位學徒（一對多）  
[Rule] Precondition：申請方為學徒時，該學徒須不存在生效中的師徒關係  
[決策] 不採多對多：師徒的價值在於一對一的針對性指導，多位教官會給出互相衝突的訓練建議，學徒無從取捨  
[決策] 學徒端不另設冷卻期：既有的「解除後 3 天內雙方皆不得與其他對象建立師徒關係」已涵蓋  
使用者已申請 師徒關係 〔攜帶資訊：申請方角色（學徒 / 教官）〕  
[Rule] 師徒申請為獨立 Aggregate，欄位含申請者、對象、申請方角色、申請時戳、狀態（申請中 / 已接受 / 已拒絕 / 已逾期）
[Rule] 師徒申請與「教官申請」為兩個不同 Aggregate：前者為使用者之間的拜師申請，後者為申請取得教官資格
[Rule] Precondition 之名額計算：名額佔用數 ＝ 該教官**已建立的師徒關係數**；申請中的申請不計入
[決策] 2026-09-29 改：申請中的申請**不再佔用帶徒名額**。原規則（佔用數含申請中）讓一位申請人被**別人尚未被回應的申請**擋在門外，而那些申請可能全部會被拒絕 —— 把「排隊」做成「佔位」，代價落在最無辜的人身上。另一個具體後果是畫面上的數字：送出申請的當下「帶徒 N / M」就 +1，而對方還沒答應，那行字在說一件不是事實的事
[決策] 超收改由「對方已接受申請」當下的 Precondition 擋下，不重複防守 —— 與〈團隊成員資格申請〉同一套；原本刻意與團隊不一致的理由（帶徒上限來自聲望、為稀缺獎勵）不足以支撐讓申請人互相排擠
[已知取捨] 一位教官可能同時收到遠多於上限的申請，須逐一拒絕。若成為實際負擔，應以「暫停招收」開關處理，不以佔名額的方式間接限流
[Rule] Precondition：一位學徒可同時向多位教官送出申請；名額限制在教官那一側，模型僅禁止已有生效中師徒關係者再申請
[分支] 接受 → 對方已接受申請；拒絕 → 對方已拒絕申請；逾期未回應 → 師徒申請已逾期  
[Rule] Postcondition：釋放所佔用的帶徒名額  
對方已接受申請  
師徒關係已建立  
[串聯] 學徒執行「確認師徒免責聲明」導致「學徒已確認師徒免責聲明」— Actor：學徒  
學徒已確認師徒免責聲明 〔攜帶資訊：聲明版本、確認時戳〕  
[Rule] Precondition：該學徒已有生效中的師徒關係  
[Rule] Precondition：**僅首次建立師徒關係時呈現一次**；已確認過者其後更換教官不再重複呈現  
[Rule] Precondition：本 Event 已發生，學徒方可發生「學徒已提問」與「學徒已完成師徒任務」  
[Rule] Postcondition：寫入使用者 Aggregate 的「已確認師徒免責聲明版本」欄位  
[決策] 師徒關係另設一層確認，不與註冊時的服務條款合併：其他功能出事為使用者自己的選擇，**師徒是平台把兩個人配對起來**，並提供聲望等級、專長標籤與六維能力值展示 —— 這些皆在向學徒表示「此人可信」，註冊時滑過的總則擋不住這一層  
[決策] 承既有立場「我們不能為教官擔保他有這個能力」（第六輪第 14 題排除具執照門檻的專長值域），本條處理的是該風險的剩餘部分  
[決策] 不阻擋師徒關係的建立本身，改為阻擋學徒端的互動 Command：關係建立由教官接受申請觸發，該時點學徒未必在場，設為建立的 Precondition 會使關係卡在無人可推進的狀態  
[Rule] 師徒關係為獨立 Aggregate，欄位含教官 ID、學徒 ID、建立時戳、狀態、解除時戳、解除原因、最近一次評分所屬週
[狀態] 師徒關係狀態值域二值：生效中 / 已解除；已解除非終止狀態，3 天內可恢復
[Rule] 不變條件：同一位學徒同時至多有一筆狀態為生效中的師徒關係
[Rule] 「解除原因」值域：教官方 / 學徒方 / 封鎖 / 教官資格撤銷；為冷卻期是否適用的判定依據
對方已拒絕申請  
[Rule] Postcondition：釋放所佔用的帶徒名額  
師徒申請已逾期  
[Rule] Precondition：自「使用者已申請師徒關係」起算滿 168 小時（7 天）未回應  
[Rule] Precondition 之計時基準：計時起點為申請時戳，計時基準為使用者當地時區時戳  
[決策] 採 7 天而非 3 天：涵蓋「平日忙碌、週末才開 App」的常態；3 天會使週五申請、週一才看到即逾期  
[決策] 時限不做成可調參數：不影響營收與平衡性，僅為等待窗口，做成參數只是增加無人調整的後台欄位  
[Rule] Postcondition：「師徒申請已逾期」發生後該筆申請自動失效  
[決策] 拒絕或逾期後可再次向同一對象申請，無冷卻期  
學徒已提問  
[Rule] 師徒問答為獨立 Aggregate，欄位含師徒關係 ID、提問者、提問內容、回答內容
[Rule] 提問為獨立 Command，與私訊分立：問答與閒聊為兩種不同互動，教官需區分何者需要回答
[Rule] 問答不評分：無學徒評分欄位，亦無「學徒已評分該次問答」Event
[Rule] 問答不設狀態機：一問一答，無作廢概念  
[Rule] Precondition：該教官的「已確認指導責任聲明版本」為現行版本，方可發生「教官已回答」（2026-08-20 新增）  
教官已回答  
[決策] 移除「學徒已評分該次問答」：逐次問答評分的尺度過於敏感，且評分者多為兩端情緒樣本；改由師徒任務評分承擔
[Rule] Precondition：該教官的「已確認指導責任聲明版本」為現行版本，方可發生「教官已指派師徒任務」（2026-08-20 新增）  
教官已指派師徒任務  
[Rule] 師徒任務為獨立 Aggregate，欄位含師徒關係 ID、指派者、任務內容、狀態、學徒評分  
[狀態] 師徒任務狀態值域：已指派 / 已完成 / 已作廢  
[Rule] Postcondition：「師徒關係已解除」使未完成的師徒任務轉為已作廢（終止狀態）  
[決策] 師徒任務與師徒問答分立為兩個 Aggregate；兩者生命週期不同  
學徒已完成師徒任務  
[串聯] 使用者（學徒）執行「領取師徒任務獎勵」導致「使用者已領取師徒任務獎勵」— Actor：使用者（學徒）
使用者已領取師徒任務獎勵
[Rule] Precondition：「學徒已完成師徒任務」已發生，且該筆獎勵尚未領取
[Rule] 領取位置為我的師徒頁；未領取者一直掛著，不進獎勵信箱（師徒任務的已完成為終止狀態，紀錄不消失）
師徒任務獎勵已發放  
[Rule] Postcondition：獎勵內容：經驗值 20 ＋ 金幣 15，每週最多發放 3 次；超過上限任務仍可正常完成，僅不再發放經驗值／金幣（2026-08-10，第九輪第 10f 題）  
學徒已評分該次師徒任務  
教官聲望已變動  
[Rule] Postcondition：師徒任務評分 1~5 星，聲望變動依序為 −1 / 0 / +1 / +2 / +3
[Rule] Precondition：每位學徒每週最多 2 次任務評分計入聲望；超出者仍可完成並發放學徒獎勵，僅不計入聲望
[決策] 不限制指派次數本身：教官為教學需要多指派屬正當行為，該擋的是計分而非行為
[串聯] 學徒執行「評分該週互動」導致「學徒已評分該週互動」— Actor：使用者（學徒）
學徒已評分該週互動
[Rule] Precondition：每位學徒每週最多評分一次，週期基準為統一每週一 04:00
[Rule] Precondition：該週內雙方有互動（問答、師徒任務進度、或私訊往來）方可評分
[Rule] Postcondition：每週互動評分 1~5 星，聲望變動依序為 −2 / 0 / +4 / +8 / +12
[Rule] Postcondition：未評分時聲望無變動，不視為差評
[Rule] 不變條件：聲望點數地板值為 0，扣分不使其低於 0  
[Policy]  聲望達門檻 → 提升帶徒上限  
教官帶徒上限已提升  
[Rule] **初始帶徒上限 2 人**（2026-08-08 由 1 人改為 2 人，流程檔於 2026-08-20 同步），每達一個聲望門檻 +1 人，最大值 5 人  
[Rule] 初始值、提升幅度、最大值與聲望門檻皆由管理員於帶徒上限設定 Aggregate 調整  
[Rule] Precondition：達最大值 5 人後，聲望再提升亦不增加上限  
[Rule] **聲望門檻為三級：75 / 150 / 300**（2026-08-20 定案，原四級 30/75/150/300 之最低一級因初始上限改為 2 人而刪去），各達一門檻帶徒上限 +1 人  
[Rule] Postcondition：教官初始聲望為 15，於「使用者已成為教官」時給予  
[Rule] 門檻採遞增（現為 1 : 2 : 4），因帶徒數愈多取得聲望愈快，等差會使後段升級失控  
[Rule] 初始聲望 15 維持不變：原理由為「第一門檻的一半」，第一門檻改為 75 後 15 不再是一半，但其職責（使新教官前幾次差評不致觸及地板 0）在緩衝更厚的情況下仍成立  
[Rule] 不變條件：帶徒上限為單調遞增，聲望下降時不隨之降低  
[決策] 無「帶徒上限已降低」 Event  
[終止路徑]  
[Rule] Precondition：解除需經多次確認，避免誤觸  
師徒關係已解除  
[Rule] Postcondition：教官與學徒任一方皆可單方面解除，不需對方同意  
[Rule] Postcondition：未完成的師徒任務作廢  
[Rule] Postcondition：釋放教官所佔用的帶徒名額  
[Rule] Postcondition：解除後 3 天內，雙方皆不得與其他對象建立師徒關係  
[Rule] Postcondition：解除後 3 天內可挽回，恢復原師徒關係  
[串聯] 使用者執行「提出恢復師徒關係」導致「使用者已提出恢復師徒關係」— Actor：使用者（教官與學徒任一方皆可提出）  
[Rule] Precondition：距「師徒關係已解除」未滿 3 天，方可發生「使用者已提出恢復師徒關係」  
使用者已提出恢復師徒關係  
[分支] 同意 → 對方已同意恢復；拒絕 → 對方已拒絕恢復  
對方已同意恢復  
對方已拒絕恢復  
[Rule] Postcondition：拒絕後該筆恢復提議失效，3 天內可再次提出  
[Rule] Precondition：「對方已同意恢復」已發生，方可發生「師徒關係已恢復」  
[決策] 恢復需雙方同意，不採單方面恢復；建立關係一律需雙方同意（比照「對方已接受申請」）  
[決策] 解除為單方面、恢復需雙方同意，兩者刻意不對稱，避免一方反覆解除又拉回  
師徒關係已恢復  
[Rule] Postcondition：3 天冷卻期解除，雙方恢復為師徒關係  
[Rule] Postcondition：同一筆師徒關係的狀態轉回生效中，不新建一筆
[Rule] Postcondition：清空解除時戳與解除原因；解除的歷史由 Event 序列承載
[決策] 不採新建一筆：既有師徒任務與師徒問答的「師徒關係 ID」外鍵仍指向原筆，而那些紀錄屬同一段關係
[Rule] Postcondition：重新佔用教官的帶徒名額  
[Rule] Precondition：教官的名額佔用數未達帶徒上限，方可發生「師徒關係已恢復」
