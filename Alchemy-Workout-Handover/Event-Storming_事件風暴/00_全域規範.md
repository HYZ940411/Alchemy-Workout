## Event 共通攜帶資訊

所有流程中的每一個 Event，發生時皆必須攜帶以下共通欄位：

| 欄位 | 型別 | 說明 |
|------|------|------|
| 事件ID | UUID | 事件唯一識別碼 |
| 發生時戳（UTC） | Timestamp（UTC，毫秒精度） | 事件發生的絕對時間 |
| 發生時戳（使用者當地時區） | Timestamp + 時區代碼 | 供跨時區規則判定使用 |
| 觸發 Actor | Actor 識別碼 | 執行 Command 導致此 Event 的角色 |
| 關聯 Aggregate ID | ID | 此 Event 所改變狀態的 Aggregate |

共通欄位之外，各 Event 另行定義其專屬欄位。

### 規則

- 每一個 Event 必須同時記錄 UTC 時戳與使用者當地時區時戳。
- 跨時區規則（簽到換日、每日任務重置、中斷判定）一律以使用者當地時區時戳為判定基準。
- UTC 時戳的精度為毫秒。

### 統一換日時點

全模型的換日時點為**使用者當地時區的 04:00**。

| 適用對象 | 說明 |
|----------|------|
| 簽到「當日」判定 | 04:00 前簽到計入前一日 |
| 每日任務重置 | 當地時間 04:00 重置 |

- 當地時間 00:00–03:59 的行為一律計入前一個自然日。
- 採 04:00 而非 00:00：健身族群多有深夜運動習慣，午夜換日會使凌晨訓練與簽到落到隔日，不符使用者直覺。
- 簽到與每日任務採同一換日時點，模型中不存在第二個換日時點。
- 本換日時點不適用於「連續訓練天數」的自然日計數，該處另有 36 小時寬限規則。

#### 當地時區的取得來源

- 「使用者當地時區」一律取自**使用者裝置的當前時區**，非使用者 Aggregate 儲存的時區欄位。
- 理由：儲存的時區為註冊當下填入，使用者出國、搬家或變更裝置語系後即過期。
- 跨時區移動導致同一當地日期重複觸發重置時，由冪等機制擋下
  （請求識別碼 ＝ 排程名稱 ＋ 週期起點 ＋ 使用者 ID，週期起點為使用者當地日期），不會重置兩次。
- 使用者 Aggregate 的時區欄位僅供顯示與統計，不作為換日與中斷判定的依據。

*來源：`.es-clarify/resolved/event/全流程Event_每個Event應攜帶哪些資訊與時間戳.md`（選項 B）*

## 〔不需精準追蹤〕Event 的軟體邊界

〔2026-08-20：本節原名〈通知 / 提醒類 Event 的軟體邊界〉，因新增第二類成員而擴寫。〕

以下 Event 保留為業務 Event，但標記為**不需精準追蹤**：僅記錄發生事實，不做嚴格規則驗收。

**判準：該 Event 有記錄價值，但不改變任何 Aggregate 狀態，因而無驗收標的。**

### 第一類：通知 / 提醒類（6 個）

| Event | 所屬流程 |
|-------|----------|
| 每日登入提醒已發送 | 每日簽到流程 |
| 連簽中斷預告已發送 | 每日簽到流程 |
| 補簽提醒已發送 | 每日簽到流程 |
| 中斷預告已發送 | 訓練中斷流程 |
| 連練中斷通知已發送 | 訓練中斷流程 |
| 退步預告已發送 | 訓練中斷流程 |

### 第二類：業務量測類（1 個，2026-08-20 新增）

| Event | 所屬流程 |
|-------|----------|
| **使用者已抵達付費頁** | 會員訂閱流程 |

- **本類的存在理由為業務量測**：付費轉化漏斗的前段原本完全不可量測 ——
  「AI 調整已拒絕」（已明文認定為漏斗中最直接的訊號）之後、到「使用者已選擇虛擬商品」之前無任何 Event；
  訂閱路徑的第一個 Event 更是 App Store 的回呼，其前為空白。
  故分不出訂閱率低的原因是「沒人看到訂閱頁」還是「看到了但嫌貴」——兩者的解法相反。
- 本類承模型既有的同型理由：註冊流程的 9 項必填欄位逐一建為 Event，
  用意即為漏斗流失分析；新手任務的「選擇候選動作」亦以「不建模會使漏斗分析出現斷點」為由建模。
- **本類不改變任何 Aggregate 狀態**，故無 Postcondition 可寫，亦無 Precondition 可驗
  —— 此即歸入〔不需精準追蹤〕而非一般 Event 的理由。
- 新增本類成員時須同時滿足兩條件：有明確的業務量測用途、且不改變任何 Aggregate 狀態。

### 規則

- 上述 Event 維持各自獨立，不合併為單一 Event。
- 上述 Event **不建立 Precondition / Postcondition 驗收條件**。
- 推播發送失敗不阻斷其所屬流程的後續 Event（僅適用於第一類）。
- 〔不需精準追蹤〕不等於不建模：其仍為業務 Event，仍攜帶 Event 共通 5 欄位與各自專屬欄位，
  仍適用冪等性原則。

*來源：`.es-clarify/resolved/event/全流程Event_通知與提醒類Event是否應納入軟體邊界.md`（選項 C）*

## 選擇類 Event 的軟體邊界（2026-08-20 新增）

**判準：該 Event 發生的當下，是否已有任何 Aggregate 狀態被改變。**

使用者於畫面上「選了什麼」但尚未確認送出者，**不建立 Postcondition**，
其效果由後續的確認類 Event 承接。

| Event | 效果由誰承接 |
|-------|-------------|
| 使用者已選擇實體商品 | 使用者已確認購買（訂單 → 待付款） |
| 使用者已選擇尺寸與數量 | 同上 |
| 使用者已選擇虛擬商品 | 同上 |
| 使用者已選擇數量 | 同上 |
| 使用者已選擇動作 | 使用者已儲存自訂訓練 |
| 使用者已設定該動作的組數 | 同上 |
| 使用者已設定該組的重量&次數 | 同上 |
| 使用者已選擇候選動作 | 使用者已完成單項新手任務 |

### 規則

- 上述 Event **不建立 Postcondition**：其發生時尚無任何 Aggregate 狀態改變
  （訂單未成立、課表未儲存），使用者可隨時離開而不留下任何狀態。
- 上述 Event **仍為業務 Event，不得移除**：承〈新手任務流程〉的既有裁決 ——
  「不建模會使**漏斗分析出現斷點**，知道有人開始了任務卻沒完成，
  但分不出他卡在『沒選動作』還是『選了卻沒做』」。
- 上述 Event 仍可有 Precondition（如「所選規格的庫存 ≥ 所選數量」），
  Precondition 與 Postcondition 兩者互相獨立。
- **不採「為每個選擇建立暫存 Aggregate」**：該資料於使用者離開頁面後即無用途，
  為其建模等於把畫面暫存當成業務狀態。
- 本節與〈〔不需精準追蹤〕Event 的軟體邊界〉為兩件事：
  後者「不做嚴格規則驗收」，本節的 Event **仍受 Precondition 驗收**，只是沒有後置狀態。

*來源：`.es-clarify/resolved/event/選擇類Event_純選擇操作是否應建立Postcondition.md`*

## Event 冪等性原則

所有流程中的 Event，重複發生時一律以 **Command 請求識別碼**去重。

### 規則

- 每一個 Command 請求必須攜帶請求識別碼。
- 系統以請求識別碼判定重複：識別碼已處理過者視為重複請求。
- 重複請求回傳原次執行的結果，不重複產生 Event。
- 本原則統一適用於全模型，各 Event 不另行定義冪等規則。

### 排程觸發的請求識別碼

排程觸發的 Command 無使用者端請求，其請求識別碼由業務自然鍵推導。
排程類 Event 依其發生形狀分為兩類，各適用一條推導式。

| 類別 | 形狀 | 推導式 |
|------|------|--------|
| 週期性重複判定 | 同一對象會反覆發生，須以週期值區分是哪一次 | 排程名稱 ＋ 週期起點 ＋ 使用者 ID |
| 一次性狀態判定 | 對單一 Aggregate 實例判定一次即結束 | 排程名稱 ＋ 目標 Aggregate ID |

#### 第一類：週期性重複判定

**請求識別碼 ＝ 排程名稱 ＋ 週期起點 ＋ 使用者 ID**

| 排程類 Event | 週期起點 |
|--------------|----------|
| 每日任務已重置 | 使用者當地日期（以當地時間 04:00 為換日點） |
| 訓練已結算 | 該筆訓練的訓練紀錄 ID |
| 簽到連續天數已中斷 | 該次中斷判定所屬的使用者當地日期 |
| 連續訓練天數已歸零 | 該次歸零判定所屬的使用者當地日期 |
| 排行榜週期已結算 | 該排行榜週期的起始日 |
| 能力值已退步 | 該肌群維度的 240 小時計時起算點 |
| 使用者帳號已刪除 | 〔推導〕該次刪除申請的刪除申請時戳 |
| 能力值日快照已產生 | 該筆快照所屬的使用者當地日期（以當地時間 04:00 為換日點） |
| 每日登入提醒已發送 | 該次發送所屬的使用者當地日期 |
| 訓練提醒已發送 | 該次發送所屬的使用者當地日期 |
| 補簽提醒已發送 | 該次發送所屬的使用者當地日期 |
| 連簽中斷預告已發送 | 該次判定所屬的使用者當地日期 |
| 中斷預告已發送 | 該次判定所屬的使用者當地日期 |
| 連練中斷通知已發送 | 該次判定所屬的使用者當地日期 |
| 退步預告已發送 | 該次判定所屬的使用者當地日期 |

**七個通知類 Event 於 2026-08-21 補入本表**（原兩張表皆未收錄）：

- 七者皆為「同一位使用者會反覆收到」的形狀，正是第一類。
- **四則預告（連簽中斷預告、中斷預告、連練中斷通知、退步預告）不可歸第二類**：
  其目標 Aggregate（連續簽到、連續訓練）與使用者為一對一且終身只有一筆，
  以該 Aggregate ID 為鍵時，同一位使用者**第二次中斷所推出的識別碼與第一次完全相同**，
  將被冪等機制判為重複而不發送。第二類的前提「判定一次即結束」在此不成立。
- 週期起點取當地日期，與同表既有的「簽到連續天數已中斷」「連續訓練天數已歸零」一致
  —— 那兩列與其中四則預告本就出自同一套 24／36／96 小時判定。
- 本裁決使〈〔不需精準追蹤〕Event〉一節「仍適用冪等性原則」一句成為可執行的規則。

*來源：`.es-clarify/resolved/event/通知類Event_七個排程通知Event的冪等去重鍵屬哪一類.md`（選項 A）*

#### 第二類：一次性狀態判定

**請求識別碼 ＝ 排程名稱 ＋ 目標 Aggregate ID**

本類**不逐一列表**，凡符合「對單一 Aggregate 實例做一次性狀態判定」者一律適用本式。
現有屬本類者：

| 排程類 Event | 目標 Aggregate |
|--------------|---------------|
| 單次訓練已逾時中斷 | 訓練紀錄 |
| 師徒申請已逾期 | 師徒申請 |
| 回歸任務已逾期 | 回歸任務 |
| 團隊邀請已逾期 | 團隊成員資格申請（方向＝隊長邀請） |
| 加入申請已逾期 | 團隊成員資格申請（方向＝使用者申請） |
| 處罰已到期解除 | 該次處罰（使用者 Aggregate 的處罰狀態） |
| 庫存已釋放 | 訂單 |
| 團隊已指派限時任務 | 限時任務（該指派日） |

- 本類的目標 Aggregate ID 本身即為天然唯一鍵，不需另湊週期起點。
- 不併入第一類的表：第一類須填「週期起點」正是因為同一使用者會發生很多次，
  必須靠週期值區分是哪一次；本類判定一次即結束，逐列填入會使該欄失去它要表達的資訊。
- 「團隊已指派限時任務」屬本類：承既有裁決「限時任務為全平台統一，一個指派日只有一組」，
  其目標為該指派日的限時任務，非逐團隊指派。
- 新增排程類 Event 時，先判別其屬哪一類，再套用對應推導式；兩類皆不逐案另訂識別碼。

#### 規則

- 排程類 Command 不產生隨機識別碼，一律由上述兩條推導式之一推導。
- 同一週期重跑時算出相同的請求識別碼，視為重複請求，不重複產生 Event。
- 「能力值已退步」的週期起點為肌群維度層級，六個維度各自獨立去重。
- 排程類 Event 不因本規則而免除各自的 Precondition，兩者並存。

*來源：`.es-clarify/resolved/event/全流程Event_各Event重複發生時的冪等處理原則.md`（選項 A）；
排程情境之補充來源：`.es-clarify/resolved/event/全流程Event_排程觸發的Event其冪等去重鍵如何產生.md`（選項 A）*

## Actor 清單

全模型的 Actor 共五種，所有 Command 的執行者必須指派為其中之一。

| Actor | 類型 | 說明 |
|-------|------|------|
| 使用者 | 人 | 平台的一般使用者 |
| 管理員 | 人 | 平台管理員，具備審核與處置權限；為獨立 Aggregate，見02_Aggregate定義.md〈管理員 Aggregate〉 |
| 系統 | 自動 | 排程、自動判定與套用調整的觸發者 |
| AI | 自動 | 產出訓練調整建議的角色，獨立於外部系統 |
| 外部系統 | 外部 | 平台外的服務，如 Google / Apple、App Store、物流商 |

### 規則

- 發文者、互動者、學徒、教官、成員、對方皆非獨立 Actor，一律歸為「使用者」。
- 上述稱呼僅為使用者在特定情境下的角色描述，不得作為 Command 的 Actor 值。
- 教官不因具備額外權限而獨立為 Actor，其權限差異以使用者的教官身分旗標表達。
- 團隊隊長不為獨立 Actor，其權限差異以團隊內的角色欄位表達。
- **管理員之間的權限差異以管理員 Aggregate 的「權限組」欄位表達**，
  不因權限組不同而拆為多種 Actor；比照教官與隊長的既有處理方式。
- Actor「管理員」的識別碼即管理員 Aggregate 的管理員 ID。
- AI 僅負責產出建議，不執行套用；套用調整的 Actor 為系統。
- 本清單非封閉清單，新增 Actor 需經明確裁決。

*來源：`.es-clarify/resolved/command/Actor_模型中各角色名稱的定義與統一.md`（選項 A′）；
AI 一項與清單封閉性之修訂來源：`.es-clarify/resolved/command/AI已調整訓練_AI是否視為獨立Actor.md`（選項 D″）*

## 統一語言：已定案術語

本章節為本模型的標準術語詞彙表。全模型的 Event、Command、Aggregate 命名一律以本表為準，
不另建獨立詞彙表檔案。

### 三個成長數值的區別

模型中有三個容易混淆的數值，其歸屬、用途與生命週期皆不同。

| 術語 | 所屬 Aggregate | 用途 | 生命週期 |
|------|----------------|------|----------|
| 經驗值 | 使用者 | 判定階級提升 | 單調遞增，永不減少 |
| 能力值 | 使用者 | 表達 6 個肌群的訓練成果 | 可升可降，退步下限見下方註，遞減報酬漸近理論上限 |
| 個人排行榜分數 | 個人排行榜分數（獨立） | 排行榜排名與排行獎勵 | 每個排行榜週期結算時歸零 |

> **〔2026-09-05 訂正〕** 本表原記能力值的下限為「註冊初始值」，該敘述已於
> **2026-08-22 被推翻**，流程檔已同步、本表漏未更新。
> 現行規則為：退步下限 ＝ **本次中斷前點數所處節點的主階降 2 階、小節點保留之下緣，
> 且不低於該維初始值**。完整定義與對照表見 `03_能力值.md`
> 〈退步下限：相對歷史最高的兩個主階〉，另見〈訓練中斷流程〉的同一條不變條件。
> 註冊初始值自此僅為下限的**地板**，不再等同下限本身。

- 三者為**三個不同的數值**，不可互相取代或混用。
- 「經驗值已提升」「能力值已提升」「個人排行榜分數已增加」為三個不同的 Event。
- 同一次訓練結算可同時觸發三者，但各自的計算方式不同。

### 收錄判準

本表收錄的是「在各流程中**真的會各自發生一次**、需以攜帶值區分是哪一次」的 Event。

某個 Event 名稱出現在兩條流程檔中，**不必然**代表它屬於本表 —— 它也可能只是後一條流程
引述其前置條件。判別方式為：一次業務歷程中，該事實是發生一次還是多次。

| 情形 | 處理方式 |
|------|----------|
| 各流程各自發生一次 | 納入本表，定義來源值域 |
| 僅為前置條件的引述 | 不納入本表；於後一條流程改寫為 Precondition，不重複列為 Event |

- 「使用者已選擇訓練課表」為後者：一次訓練中該事實只發生一次，AI 訓練前調整流程的該行
  已改寫為 Precondition，並自01_Command清單.md〈Command 清單〉的 AI 訓練前調整流程移除對應 Command。

### 規則

- 同名跨流程 Event 僅有一份定義，不依來源拆分為多個 Event。
- 來源以攜帶資訊區分，各來源的提升幅度由該來源流程的 Policy 決定。
- 「能力值已提升」與訓練中斷流程的「能力值已退步」為兩個獨立 Event，不合併為單一變動 Event。
- AI 調整類 Event 的來源值域為三值：訓練前調整 / 訓練中調整 / 自動優化。
- 三條 AI 流程的作用範圍差異（本次訓練 / 剩餘動作 / 課表範本）以來源值表達，不另拆 Event。
- 「使用者已確認使用新訓練強度」與 AI 訓練中調整流程的「使用者已確認調整」為兩個不同 Event，本次未歸併。
- 「訓練課表已套用新強度」為單一 Event，三條 AI 流程共用，以作用範圍區分改動標的。
- 「訓練課表已套用新強度」的作用範圍值域為二值：本次訓練 / 課表範本。
- AI 訓練前調整流程與 AI 訓練中調整流程的作用範圍皆為「本次訓練」，AI 自動優化訓練流程為「課表範本」。
- 「訓練課表已套用新強度」的 Actor 為系統；AI 僅產出建議，不執行套用。
- 不建模「訓練課表套用已失敗」：套用為本機資料寫入，失敗屬技術性交易回滾，非業務事實。

- 「AI 調整已失敗」為單一 Event，三條 AI 流程共用，以來源值區分是哪一條流程失敗。
- 不拆為三個獨立 Event：其結構與三條流程的另外 5 個同名 Event 完全相同，另拆將與該既有裁決不一致。
- 「AI 調整已失敗」的 Command 為「判定 AI 調整失敗」，**Actor 為系統**，非 AI。
- Actor 取系統而非 AI 的理由：逾時的定義為 AI **沒有回應**，AI 無法回報自己沒有回應，
  只能由等待方（系統）判定。此與「AI 僅負責產出建議，不執行套用」的既有裁決方向一致。
- 「AI 調整已失敗」的失敗原因值域為二值：逾時 / 服務錯誤。

- 「使用者已支付」為單一 Event，實體與虛擬兩條購買流程共用，與訂單為單一 Aggregate 的設計對稱。
- 「使用者已支付」的商品類型值域為二值：實體 / 虛擬。
- 「使用者已支付」的支付管道值域為二值：第三方金流 / App Store。
- 實體商品的支付管道為第三方金流（信用卡 / 行動支付，回呼觸發）。
- 虛擬商品的真實金流支付管道為 App Store，與會員訂閱同屬一體系。
- 「使用者已支付」的 Actor 一律為外部系統，兩種支付管道僅為提供者差異，不改變 Actor。

### 規則

- 「中斷」一詞不得單獨使用，必須帶明確主體（單次訓練 / 連續訓練天數）。
- 「追蹤」為棄用詞，一律改用「關注」，對應 Event 為「使用者已關注帳號」。
- Policy 與 Rule 中引述行為時，一律直接使用既有 Event 全名，不得另造簡稱。
