# 釐清問題

使用者執行 Command「發送私訊」「讀取私訊」「封鎖對象」「刪除對話」前必須看到什麼？對話清單與對話內容的欄位、排序與即時性要求為何？

# 定位

流程：聊天私訊流程
元素：Read Model（尚未定義）；支撐 Command「建立對話」「發送私訊」「讀取私訊」「封鎖對象」「刪除對話」「檢舉私訊」
細節：D6 Read Model 識別、E4 Read Model → Command 支撐。
既有 Precondition「使用者開啟對話，且該對話中存在以其為接收方、已讀時戳為空的私訊」—— 「開啟對話」即為本 Read Model 的讀取行為，其定義直接決定已讀判定的可驗收性。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 兩層：對話清單（對方名稱、最後一則訊息摘要、最後訊息時戳、未讀則數）＋ 對話內容（訊息內容、發送者、發送時戳、已讀時戳）；皆為即時 |
| B | 同 A，對話清單另加「對方是否已被我封鎖」旗標，供判斷是否解除封鎖 |
| C | 同 B，對話內容另加分頁 / 分批載入規則（訊息數量無上限成長，已定案不作為對話的子集合） |
| D | 同 C，並定義「未讀則數」的計算方式與是否需儲存為欄位（比照粉絲數的計數欄位裁決） |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響 Read Model 清單、對話 / 私訊 / 封鎖三個 Aggregate 的查詢組合、「使用者已讀取私訊」Precondition 中「開啟對話」的可驗收定義、單方刪除狀態對清單的過濾、以及未讀計數是否需新增儲存欄位。
相關待釐清項目：`rule/使用者已發送私訊_可發送私訊的對象限制為何.md`、`rule/使用者已封鎖對象_封鎖是否連帶解除關注與師徒與團隊關係.md`。
相關已解決項目：`resolved/aggregate/使用者已建立對話_對話與私訊的Aggregate歸屬與欄位.md`、`resolved/rule/使用者已讀取私訊_已讀的判定條件為何.md`。

# 解決結果

**選項 C** —— 建立兩個 Read Model：

| Read Model | 支撐的 Command | 欄位 |
|------------|---------------|------|
| 對話清單 | 開啟對話 | 訊息分類分頁、對方顯示名稱、最後一則訊息摘要與時戳、未讀數 |
| 對話內容 | 發送私訊、讀取私訊、檢舉私訊 | 對方顯示名稱、對方階級、對方教官身分標示、訊息清單（發送者 / 內容 / 時戳 / 已讀狀態） |

- 對話清單依最後一則訊息時戳新到舊排序；本人刪除狀態為真者不呈現。
- 身分資訊到階級與教官標示為止，**不呈現六維能力值**，與社群動態牆同一原則。
- 皆為即時。

**不採 D（呈現封鎖狀態）**：

- 「對方是否已封鎖我」不可見為刻意設計 —— 封鎖狀態對外可見等同把封鎖變成訊號，
  會誘發追問與騷擾，而封鎖的目的正是切斷接觸。
- 「我是否已封鎖對方」屬封鎖管理的職責，非對話頁的決策依據。
- 承〈對話 Aggregate〉既有規則「對話不儲存封鎖狀態」。
