# 釐清問題

「取消訂單」為使用者 Command，且實體訂單有 15 分鐘預扣庫存的倒數，但模型無任何服務訂單狀態的 Read Model。使用者在取消訂單（或等待出貨、查詢發放結果）前需看到哪些資訊？

# 定位

流程：實體商品購買流程、虛擬商品購買流程
元素：Read Model（缺失）「我的訂單頁」；服務的 Actor：使用者
細節：D6 Read Model 識別、E4 Read Model → Command 支撐。〈Read Model：商品頁〉僅服務購買前的決策，訂單成立後的狀態無任何 Read Model 承載；「商品發放已失敗」轉人工處理後使用者亦無處查詢。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 最小集：訂單清單（商品名稱與規格、數量、金額、訂單狀態、成立時戳），待付款者顯示**預扣剩餘時間**（15 分鐘倒數） |

| Short | 提供其他簡短答案（<=5 字） |

# 解決結果（2026-08-08，第八輪第 33 題）

**B** —— 訂單清單 ＋ **取消入口與其可用條件** ＋ **失敗原因** ＋ **支付明細拆分**。

## 三個新增欄位各自的理由

- **支付明細拆分（金幣 / 法幣分列）**：模型有**併用支付**（虛擬貨幣不足時以現金補差額），
  且**訂單成立時鎖定當時比率**。僅顯示總額者，使用者數月後無從對照當時扣了多少金幣、
  補了多少現金 —— 而那正是爭議發生時要查的資料。
  金幣對法幣比率本身仍為 `[待決策 Partial]`，但**拆分呈現與比率數值無關**，不受阻擋。
- **失敗原因**：「購買已失敗」攜帶失敗原因（餘額不足 / 商品售完 / 其他），
  「商品發放已失敗」亦攜帶。不呈現則使用者只看到「已失敗」，**不知道錢有沒有被扣**。
- **取消的可用條件明示**：僅「待付款」可取消，終止狀態皆不可；
  不明示則使用者將反覆尋找取消入口。

## 一併納入：系統發起的取消路徑

「**訂單已因商品下架取消**」（第五輪新增）為系統行為，狀態同樣轉為已取消，
呈現時應可與使用者自行取消區別。

## 助理出題時的一處不準確（已更正）

助理原稱「模型定了**不自動退款**，故退款進度沒有資料來源」。
**該規則的範圍是虛擬商品的發放失敗**（「不自動退款；虛擬貨幣與真實金流併用時的
雙向退款複雜度高於重試」），**不及於實體訂單** ——
實體訂單有 `已退款` 狀態與管理員的「退款」Command。

**結論不變但理由更正為**：退款**只有終止狀態、無任何中間進度狀態**，
該資訊已由「狀態」欄位涵蓋，不需另立「退款進度」欄位。

## 不納入物流追蹤

模型明訂「實體訂單的終止狀態為已出貨，出貨後的物流留在系統邊界之外，
無『已送達』狀態」。提供追蹤等同承諾一個模型中不存在的能力。
