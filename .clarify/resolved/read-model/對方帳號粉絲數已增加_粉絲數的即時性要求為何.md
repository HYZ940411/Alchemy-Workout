# 釐清問題

粉絲數的顯示是否需要即時更新？大量粉絲的帳號是否可接受延遲彙總？

# 定位

流程：關注流程
元素：Read Model：個人檔案頁的粉絲數（尚未定義）；服務對象 Actor：使用者
細節：Read Model 的即時性要求（D6）。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 即時更新，粉絲數為帳號 Aggregate 的計數欄位，關注時同步遞增 |
| B | 可延遲，每 5 分鐘批次彙總，成就判定亦依批次結果 |
| C | 顯示可延遲，但成就門檻判定必須即時 |
| D | 即時更新，但超過一定數量後改以概數顯示（如 1.2 萬） |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響帳號 Aggregate 是否需要粉絲數計數欄位、對方帳號粉絲數已增加的 Postcondition 一致性、粉絲成就已解鎖的判定時機、以及個人檔案 Read Model 的即時性。

# 優先級

Low

# 解決結果

**選項 B｜全部即時**

- 顯示與粉絲成就判定**共用同一個粉絲數欄位**，兩者皆為即時，不設延遲重算路徑。
- 實作方式：關注關係 Aggregate 的計數欄位於「使用者已關注帳號」+1、「使用者已取消關注」−1。
- 與既有裁決一致：既有的「不採即時彙總」指的是不做即時 count 查詢，
  而非計數欄位不即時更新；本題不推翻該裁決，僅補上即時性的明確表述。

不採 A（顯示延遲、成就判定即時）：同一件事分兩條路徑，會出現畫面數字與成就狀態對不起來的情形；
計數欄位的維護成本本就極低，延遲重算換不到對等的好處。
延遲重算的優勢僅在粉絲數計算變複雜時（如需排除已封鎖 / 已停權帳號）才成立，目前無此需求。

**提問過程備註**：本題原推薦 A，理由為「避免即時重算成本」。
使用者追問後確認該顧慮不成立（計數欄位為單次寫入，非全表彙總），推薦更正為 B。

# 回寫位置

- `00_全域規範.md`〈使用者 Aggregate 規則〉粉絲數區塊：
  修訂「不採即時彙總」為「不採即時彙總查詢」並補上計數欄位的即時寫入說明；
  新增 2 條規則（即時性共用同一欄位、不採雙路徑的理由）
