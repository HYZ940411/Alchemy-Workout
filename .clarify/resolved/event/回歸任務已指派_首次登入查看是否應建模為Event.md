# 釐清問題

回歸任務的時限自「使用者首次登入查看」起算，但模型中無任何登入或查看類 Event，此 Postcondition 目前無可觸發的時點。是否應建模「使用者已查看回歸任務」Event，或改以其他可判定的時點起算？

# 定位

流程：回歸任務流程
元素：Event（尚未存在）；Aggregate「回歸任務」的「時限起算時戳」欄位
細節：E1 Actor → Command → Event 串聯（有 Postcondition 但無 Command 可觸發）、A1 事件識別完整性。回歸任務流程檔第 9–11 行、`00_全域規範.md`〈回歸任務 Aggregate〉。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 新增 Event「使用者已查看回歸任務」與 Command「查看回歸任務」（Actor：使用者），寫入時限起算時戳 |
| B | 不新增 Event：時限起算時戳由回歸任務 Read Model 的首次讀取寫入 —— 但此舉使 Read Model 產生副作用，違反〈Read Model 建立原則〉，故須改採其他方案 |
| C | 改以「使用者已開始訓練」或任一使用者主動 Event 作為起算時點，不另建模查看行為 |
| D | 改回自指派時戳起算，並延長時限以吸收使用者未回來的空窗 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響回歸任務流程的 Event 清單與〈Command 清單〉、回歸任務 Aggregate 的「時限起算時戳」寫入路徑、「回歸任務已逾期」的可驗收性，以及是否需要一個通用的「使用者已登入」Event（每日登入提醒亦隱含依賴登入行為）。
相關已解決項目：`resolved/rule/回歸任務已指派_限時的時限長度為何.md`（選項 C 定案首次查看起算，但未定義查看的建模方式）。

# 解決結果

**選項 A ＋ 一併新增「使用者已登入」**

- 新增 Event「使用者已查看回歸任務」與 Command「查看回歸任務」（Actor：使用者），
  其 Postcondition 寫入時限起算時戳；Precondition 為「回歸任務狀態為已指派且時限起算時戳為空值」，
  故對同一筆回歸任務僅發生一次（即「首次」查看）
- 一併新增 Event「使用者已登入」與 Command「登入」（Actor：使用者），
  Precondition 為「帳號狀態不為已刪除」
- 兩者為不同 Event：登入不等於看見回歸任務，時限起算時戳僅由後者寫入
- 明確排除選項 B：Read Model 已定案不改變任何狀態，不得由其讀取寫入時戳
