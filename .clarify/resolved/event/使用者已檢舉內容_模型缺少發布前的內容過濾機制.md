# 釐清問題

App Store 1.2 要求含使用者生成內容的 App 須具備「過濾違規內容使其無法被張貼」的方法，而模型只有事後檢舉與人工審視，完全沒有發布前的過濾機制——是否納入軟體邊界、以哪一種形式建模？

# 定位

流程：發文與互動流程、聊天私訊流程、自訂訓練流程
元素：Event / Rule — 「發文者已發布貼文」「互動者已留言」「使用者已發送私訊」的 Precondition
細節：Apple 1.2 四項要求中，模型已滿足「檢舉機制」「封鎖機制」「公開聯絡資訊（未建模，屬 App 資訊）」，缺的是第一項 "A method for filtering objectionable material from being posted to the app"

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 新增自動過濾為發布前的 Precondition：內容經違規字詞／影像判定後方可發布，判定不通過產生新 Event「內容已攔截」，並可申訴 |
| B | 新增自動過濾但不阻擋：內容照常發布，命中者自動進入管理員待審佇列（新增檢舉來源＝系統自動標記），不新增阻擋型 Precondition |
| C | 過濾機制留在系統邊界之外（視為實作層的第三方內容審核服務），模型僅於規範註明其存在，不建模為 Event |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

- 貼文、留言、私訊三類 Event 的 Precondition；可能新增 Event 與申訴路徑
- 檢舉 Aggregate 是否新增「來源＝使用者檢舉 / 系統自動」欄位
- 〈Read Model：管理員待審佇列〉的案件來源與量體
- App Store 條款：1.2 User-Generated Content

# 優先級

High

# 解決結果

**A＋B（組合）**：明顯違規當場攔截、疑似違規照常發布但自動送審。

- 過濾判定分三值：通過 / 明顯違規 / 疑似違規，門檻為平台級可調參數。
- 明顯違規 → 新增 Command「攔截違規內容」（Actor：系統）與 Event「內容已攔截」，
  內容不寫入任何 Aggregate、不發放互動獎勵、不計入互動成就；使用者可修改後重送。
- 疑似違規 → 內容照常發布，自動於檢舉 Aggregate 開立案件，案件來源為「系統自動標記」。
- 攔截不計入累計違規次數、不觸發處罰；不服者可申訴，申訴對象自「處罰」擴充為「處罰 / 內容攔截」。
- 過濾服務本身（字詞庫、影像辨識）留在系統邊界之外，屬實作層選型。
- 適用對象：貼文、留言、私訊（含分享至站內的貼文）。
