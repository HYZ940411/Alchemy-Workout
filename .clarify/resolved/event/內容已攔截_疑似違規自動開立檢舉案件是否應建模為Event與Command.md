# 釐清問題

發布前的內容過濾判定為「疑似違規」時，系統自動於檢舉 Aggregate 開立案件 —— 這件事是否應建模為一個獨立的 Event 與 Command？

# 定位

流程：發文與互動流程〈發布前的內容過濾〉（2026-08-18 新增），及聊天私訊流程的同一機制。
元素：Event（缺失）／ Command（缺失）／ Aggregate：檢舉。
細節：
- `發文與互動流程.md:38`「疑似違規者照常發布，並自動於檢舉 Aggregate 開立案件，案件來源為系統自動標記」——此句無任何 [串聯] 行、無 Event、無 Command。
- `02_Aggregate定義.md:3923` 檢舉 Aggregate 狀態機的「觸發 Event」欄位列出三個觸發：
  「使用者已檢舉內容 / 使用者已檢舉私訊 / **內容過濾判定為疑似違規**」——
  前兩者為既有 Event，第三者**在全模型中不存在**：無過去式命名、無 Actor、
  未列入 `01_Command清單.md`，僅以此一句描述性文字出現。
- 對照組：同一次裁決的另一條分支（明顯違規）已完整建模為
  Command「攔截違規內容」＋ Event「內容已攔截」（Actor：系統）。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 新增 Command「標記疑似違規內容」與 Event「內容已標記待審」（Actor：系統），與「內容已攔截」對稱；攜帶內容類型、命中的違規類別、判定分數 |
| B | 不新增 Event，改將開案寫為既有 Event（發文者已發布貼文 / 互動者已留言 / 使用者已發送私訊）的 Postcondition，並把 `02:3923` 狀態機該列改寫為這三個既有 Event |
| C | 不新增 Event，改為擴充既有 Event「內容已攔截」的攜帶欄位，以「處置＝攔截 / 標記」二值涵蓋兩條分支，狀態機改指向它 |
| D | 維持現狀（僅以文字描述），但須明文豁免「每一個 Event 皆有對應的 Command」與「每次狀態轉換皆對應一個 Event」兩條既有規範 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

- **Event 清單**：可能新增 1 個 Event；`01_Command清單.md`〈發文與互動流程〉可能新增 1 個 Command。
- **檢舉 Aggregate**：`02_Aggregate定義.md:3923` 狀態機的觸發欄無論選哪一項都必須改寫 —— 現行寫法指涉一個不存在的 Event，屬 D5「每次狀態轉換是否都對應到一個 Event」的缺口。
- **既有規範的一致性**：`01_Command清單.md`〈命名與盤點規範〉明訂「每一個 Event 皆有對應的 Command」；選 D 等同對此開例外。
- **營運可量測性**：`發文與互動流程.md:42` 已裁決「攔截率與誤擋率為須監控的指標」而為明顯違規建了 Event；疑似違規的**誤標率**屬同型指標，不建模則後端無從得知。
- 相關已解決項目：`.clarify/resolved/event/使用者已檢舉內容_模型缺少發布前的內容過濾機制.md`（第十一輪，本機制的來源裁決；當時僅裁決了明顯違規分支的建模方式）。

# 優先級

High
—— 阻礙 Event 是否成立的判斷，且現行檢舉 Aggregate 狀態機引用了一個不存在的 Event，屬核心 Aggregate 建模的實質缺口。

---

# 解決結果

**選項 A**：新增 Command「標記疑似違規內容」與 Event「**內容已標記待審**」（Actor：系統），與「內容已攔截」對稱。

- Event 名稱定為「**內容已標記待審**」（過去式，描述業務事實而非實作方式）。
- 攜帶資訊：內容類型（貼文 / 留言 / 私訊）、命中的違規類別、判定分數。
- Precondition：該內容的過濾判定為疑似違規。
- Postcondition 五條（原子化）：① 內容照常發布 ② 照常發放互動獎勵與計入互動成就
  ③ 於檢舉 Aggregate 開立案件（來源＝系統自動標記、狀態＝待審視）
  ④ **不對使用者發送任何通知** ⑤ 不計入累計違規次數、不觸發處罰。
- 不對使用者發通知的理由：告知「你被標記了」等同揭露過濾器判準，
  承既有裁決「揭露防作弊判準即使其失效」的同型理由。
