# 釐清問題

回歸任務是模型明文指定的流失使用者召回機制（〈訓練中斷流程〉的 `[已知代價]` 寫著「承接機制為既有的回歸任務」），且其時限「自使用者首次登入查看時起算」，理由是「使用者當下多半不在使用 App」。但「回歸任務已指派」既不在〈推播類清單與優先序〉的 10 項之中，也不在〈App 內通知類〉的 12 項之中——指派了，卻沒有任何規則說要讓使用者知道。指派時是否對使用者發送通知？發哪一種？

# 定位

流程：回歸任務流程
元素：Event：回歸任務已指派（`回歸任務流程.md:8`）；Rule（Postcondition）
細節：A1 事件識別完整性、E4 Read Model 支撐。〈推播類清單〉（`02_Aggregate定義.md`）共 10 項，〈App 內通知類〉共 12 項，兩表皆無本 Event；同表的「退步預告已發送」（96 小時）為推播第 1 級。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A（**推薦**） | **列入推播類、第 2 級行動引導類**，寫為本 Event 的 Postcondition，不新增「回歸任務通知已發送」Event。理由：完全比照模型既有的兩項處理——待回應類（師徒申請、團隊邀請）即以「推播寫為既有 Event 的 Postcondition、不另造 Event」處理；而歸第 2 級而非第 1 級，比照「連練中斷通知已發送」的既有裁決「連續天數已經歸零，該通知的用途為召回而非預防」，回歸任務同屬召回 |
| B | 列入 App 內通知類，於回歸任務卡以紅點呈現，不推播。理由：承既有判準「不看就失去東西才推播」，而回歸任務的時限自首次查看才起算，不看並不會失去 |
| C | 列入推播類、第 1 級期限即將失效類，與退步預告同級 |
| D | 不通知：既有的「退步預告已發送」（96 小時）與「連練中斷通知已發送」（36 小時）已對同一批人推播過兩次，回歸任務於第 240 小時再推第三次屬過度打擾；使用者回來時自然看得到回歸任務卡 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響〈推播類清單與優先序〉表或〈App 內通知類〉表的項目、「回歸任務已指派」的 Postcondition、同日推播總量上限 3 則／日的擠壓計算（該上限的定案理由明寫「日常最多同時出現者為簽到提醒、訓練提醒、某一則期限預告——正好 3 則」，新增一則須重新檢視）、以及〈Read Model：回歸任務卡〉是否需要紅點欄位。
相關已解決項目：`resolved/rule/通知類Event_完整清單與各自的優先序歸類尚未盤點.md`（選項 B，建立兩類劃分與三級優先序；當時未盤到本 Event）、`resolved/rule/通知類Event_同日多個通知重疊時的合併與優先序.md`、`resolved/event/回歸任務已指派_首次登入查看是否應建模為Event.md`。
相依：若 `rule/回歸任務已指派_從未訓練者是否無限期每7天重複指派.md` 採「無限重複指派」，本項選 A 或 C 會使該批使用者每 7 天收到一次推播，兩項須合併考量。

# 解決結果

**選項 A** —— 列入**推播類、第 2 級行動引導類**，寫為 Event「回歸任務已指派」的 Postcondition，
**不新增**「回歸任務通知已發送」Event。

判準與理由：

- 歸第 2 級而非第 1 級期限即將失效類：第 1 級的判準為「不處理就失去東西」，
  而回歸任務的時限**自使用者首次登入查看時起算** —— 未看見即不起算、不逾期、不失去任何東西，
  放入第 1 級將使該級的判準失效。其用途為召回而非預防，與「連練中斷通知已發送」同型。
- 不另造 Event：比照待回應類（師徒申請、團隊邀請、加入申請）的既有處理 ——
  推播寫為既有 Event 的 Postcondition。現有 7 個獨立的「…已發送」Event 之所以獨立，
  是因為它們沒有別的事實可掛；本 Event 已是明確的觸發事實。
- 同日總量上限 3 則／日**不調整**：該上限推導的是「日常」同時出現者，
  本項每 7 天至多一則，非日常；擠出第 4 則時依既有規則由低至高捨棄，讓出的為每日登入提醒。
