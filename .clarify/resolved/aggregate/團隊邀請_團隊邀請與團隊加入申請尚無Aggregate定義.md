# 釐清問題

「團隊邀請」與「團隊加入申請」是否應各自成為獨立 Aggregate？（兩者目前有規則、有逾期 Event、被冪等規範指名為「目標 Aggregate」，卻無任何欄位表與狀態機。）

# 定位

流程：團隊組隊流程。
元素：Aggregate（識別與邊界，檢查項 D1；欄位定義 D2；狀態機 D5）。
細節：

1. `00_全域規範.md`〈第二類：一次性狀態判定〉的表格，將「團隊邀請已逾期」的
   **目標 Aggregate 明列為「團隊邀請」**、「加入申請已逾期」的目標 Aggregate 明列為
   「團隊加入申請」，且該類的請求識別碼推導式為「排程名稱 ＋ **目標 Aggregate ID**」
   —— 亦即冪等機制已預設兩者各有 ID。
2. 但 `02_Aggregate定義.md` 全檔**無「團隊邀請 Aggregate」與「團隊加入申請 Aggregate」章節**，
   亦不在〈獨立 Aggregate 清單〉的 55 項之中。
3. 兩者的規則目前寄居於團隊 Aggregate 的〈待回應的邀請與申請〉小節
   （`02_Aggregate定義.md:2931-2938`）：168 小時逾期、待回應不佔 5 人名額。
4. 相關 Event 共 6 個：隊長已邀請成員、使用者已接受邀請、使用者已拒絕邀請、
   使用者已申請加入團隊、隊長已核准加入申請、隊長已拒絕加入申請，
   加上兩個逾期 Event —— 合計 8 個 Event 改變的狀態無處存放。
5. **對照組**：結構完全平行的「師徒申請」**已是獨立 Aggregate**
   （`02_Aggregate定義.md:3072`，含欄位表與狀態機），並同樣列於冪等表的第二類。
   兩者的差異僅在師徒申請佔用帶徒名額、團隊邀請不佔 5 人名額。
6. 另：`02_Aggregate定義.md:1073` 的推播優先序表已將「隊長已邀請成員（待回應）」
   與「使用者已申請加入團隊（待回應）」列為期限即將失效類，其「待回應」狀態
   亦需有欄位可判定。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 兩者各建為獨立 Aggregate，比照師徒申請的既有形狀（欄位：邀請 / 申請者、對象團隊、送出時戳、狀態四值＝待回應 / 已接受 / 已拒絕 / 已逾期），並補入〈獨立 Aggregate 清單〉（55 → 57） |
| B | 合併為單一「團隊成員資格申請 Aggregate」，以「方向＝隊長邀請 / 使用者申請」欄位區分兩條路徑（承「使用者已加入團隊」本即為此二者的多對一 Event 之設計對稱） |
| C | 不另立 Aggregate，改於團隊 Aggregate 新增「待回應邀請清單」與「待回應申請清單」兩個集合欄位，並將冪等表的目標 Aggregate 改為團隊 ＋ 對象使用者 ID |
| D | 不另立 Aggregate，兩者視為 Event 流本身（無狀態實體），並改寫冪等表第二類的推導式以容納此情形 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

- **〈獨立 Aggregate 清單〉**：選 A 為 55 → 57，選 B 為 55 → 56，選 C / D 維持 55。
- **`00_全域規範.md` 冪等規範**：選 C / D 必須改寫〈第二類：一次性狀態判定〉表格中的兩列，該表現行寫法預設兩者為 Aggregate。
- **Precondition 的可驗收性**：`團隊組隊流程.md:33 / 51`「自送出起算 168 小時未回應即逾期」需要一個「送出時戳」欄位；現行無任何 Aggregate 承載它，該 Precondition 目前無法驗收。
- **Read Model**：`04_ReadModel清單.md`〈我的團隊頁〉與〈團隊搜尋〉須指明待回應邀請 / 申請的來源 Aggregate。
- **與師徒申請的一致性**：選 D 會使兩個結構相同的機制採相反的建模方式，須另行說明理由。
- 相關已解決項目：`.clarify/resolved/rule/隊長已邀請成員_團隊邀請與加入申請是否逾期失效.md`（選項 B，確立了 168 小時逾期，但未處理狀態的存放位置）。

# 解決結果

**選項 B**：合併為單一〈**團隊成員資格申請 Aggregate**〉，以「**方向**」欄位
（隊長邀請 / 使用者申請）區分兩條路徑。獨立 Aggregate 清單 63 → **64**。

- 欄位：申請 ID、方向、對象團隊、對象使用者、發起者、**送出時戳**、狀態（待回應 / 已接受 / 已拒絕 / 已逾期）。
- 狀態機四列，每列的兩個 Event 依方向欄位擇一適用。
- **送出時戳補上後，「自送出起算 168 小時未回應即逾期」這條 Precondition 方為可驗收**
  —— 該時戳原本無處存放。
- 逾期時限不做成可調參數，承師徒申請的既有處理方式。
- 待回應不佔 5 人名額、超收由「使用者已加入團隊」的 Precondition 擋下，兩條既有規則不變。

**合併而非拆為兩個的理由**：

- 承「使用者已加入團隊」為多對一的既有設計 —— 兩條路徑的**出口已合併**為同一 Event，
  入口以方向欄位區分、共用同一 Aggregate，與該設計對稱。
- 兩者欄位完全相同，差異僅在「由誰發起、由誰回應」，此即方向欄位所承載者。
- 拆為兩個會產生兩張結構相同的表，日後每新增一條規則須改兩處，易漏其一。
- 比照「使用者已支付」為實體與虛擬兩條購買流程共用單一 Event、以商品類型欄位區分的既有處理。
- **命名不與〈師徒申請 Aggregate〉對稱為刻意**：師徒申請只有一條路徑，無方向可言。
