# 釐清問題

「對話」與「私訊」是否為獨立 Aggregate？其欄位、狀態機（含封鎖與刪除對話）為何？

# 定位

流程：聊天私訊流程
元素：Aggregate（尚未定義）；Event「使用者已建立對話」「使用者已發送私訊」「使用者已讀取私訊」「使用者已刪除對話」「使用者已封鎖對象」
細節：Aggregate 識別與邊界（D1）；欄位定義（D2）；生命週期與狀態機（D5）。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 對話為獨立 Aggregate（參與者、建立時間、狀態），私訊為其下的訊息子集合（發送者、內容、發送時戳、已讀時戳） |
| B | 對話與私訊各為獨立 Aggregate，私訊以對話 ID 關聯 |
| C | 僅建模私訊 Aggregate，對話為由訊息推導的檢視概念，不儲存 |
| D | 封鎖關係另立獨立 Aggregate，不放在對話狀態中 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響「使用者已刪除對話」為單方或雙方刪除、已讀判定的欄位歸屬（`rule/使用者已讀取私訊_已讀的判定條件為何.md`）、
封鎖的 Postcondition 落點（`rule/使用者已封鎖對象_封鎖是否連帶解除關注與師徒與團隊關係.md`）、
檢舉對象類型「私訊」所指涉的標的，以及獨立 Aggregate 清單（`00_全域規範.md`）是否新增項目。
本項為新掃描發現，非承接 `pending-gaps.md`。

# 優先級

High

# 解決結果

**選項 B ＋ D**：對話與私訊各為獨立 Aggregate，私訊以對話 ID 關聯；封鎖另立獨立 Aggregate。

**釐清過程**：使用者提問「對話不就是私訊嗎」。兩者非同一件事——對話為聊天室本身，私訊為其中的每一則訊息，
模型的 Event 亦已分立（使用者已建立對話 / 使用者已發送私訊 / 使用者已刪除對話）。

**對話 Aggregate**：參與者 ×2、建立時間、各方刪除狀態。

- 對話可為空：建立對話時尚無任何私訊，若不建模則該 Event 無承接處。
- 刪除為單方刪除，只改該方狀態，對方仍可見——此狀態只能記於對話層級。
- 單則訊息一經發送即不可刪除（既有裁決），故刪除只發生於對話層級。

**私訊 Aggregate**：對話 ID、發送者、內容、發送時戳、已讀時戳。

- 私訊可被檢舉，需獨立 ID 供指涉（同第 21 題留言的論證）。
- 訊息數量無上限成長，作為對話子集合會使每次讀取對話狀態都載入全部歷史。

**封鎖 Aggregate**：封鎖者、被封鎖者、封鎖時戳；單向關係。

- 可封鎖從未對話過的對象（例如在貼文下被騷擾），此時無對話可掛。
- 封鎖影響範圍超出私訊，掛在對話裡會使後續的連帶解除規則需跨越語意不合的 Aggregate。

- 獨立 Aggregate 清單 36 → 39 項（新增對話、私訊、封鎖）。
