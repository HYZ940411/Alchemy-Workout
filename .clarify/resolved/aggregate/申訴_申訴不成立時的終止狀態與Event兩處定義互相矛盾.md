# 釐清問題

申訴不成立時，00_全域規範〈申訴 Aggregate〉的狀態機為「待審視 →（管理員已審視申訴，判定不成立）→ 已維持原處罰」且明文「申訴不成立時不另立 Event」；而 `管理員管理社群流程.md` 有獨立 Event「申訴已駁回」，狀態轉為「已駁回」。何者為準？

# 定位

流程：管理員管理社群流程（申訴路徑）
元素：Aggregate「申訴」之狀態值域；Event「申訴已駁回」是否成立
細節：D5 狀態機、A1 事件識別完整性、F2 術語衝突。流程檔的〔決策〕欄已寫明補立「申訴已駁回」的理由（模型已有「檢舉已駁回」，同為駁回卻一有一無），但 00_全域規範未同步，兩處目前直接牴觸。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 以流程檔為準：保留 Event「申訴已駁回」，狀態值域改為 待審視 / 已成立 / 已駁回；00_全域規範同步改寫，〈Command 清單〉增列「駁回申訴」（Actor：管理員） |
| B | 同 A 的狀態值域，但不增列獨立 Command：「申訴已駁回」與「處罰已撤銷」同為「審視申訴」的一 Command 兩結果，比照「審核公開訓練」的既有處理方式 |
| C | 以 00_全域規範為準：移除「申訴已駁回」Event，狀態值域維持 待審視 / 已成立 / 已維持原處罰，由「管理員已審視申訴」的判定結果轉入 |
| D | 兩者皆保留但語意分離：「申訴已駁回」指程序不受理（逾 30 天、重複申訴），「已維持原處罰」指實質審視後不成立 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響 Event 總數、申訴 Aggregate 的狀態值域、〈Command 清單〉管理員管理社群流程、〈Read Model：管理員待審佇列〉申訴分頁的結案標示，以及「同一處罰限申訴一次」Precondition 的判定依據。
相關已解決項目：`resolved/event/管理員已審視申訴_申訴不成立是否補立申訴已駁回Event.md`、`resolved/aggregate/申訴_申訴是否為獨立Aggregate及其欄位與狀態機.md`。
相依：`command/全流程Command_八個Event在Command清單中無對應Command.md`。

# 本題須連同「懸空狀態」一併裁決（2026-08-04 第 5 題追加）

第 5 題裁定補上獨立 Command「駁回申訴」（選項 A，與檢舉路徑對稱），但過程中辨識出一個
**檢舉與申訴共有的缺口**，經使用者同意延至本題一併處理：

「管理員已審視檢舉」與「管理員已審視申訴」**皆不改變任何 Aggregate 欄位** ——
兩者的狀態機中，審視後狀態仍為「待審視」，直到後續的處置 Event 才轉換。
故模型沒有任何狀態能表達「有人看過了但還沒決定」，案件可無聲卡在原地。

本題裁決時須一併回答：

1. 是否新增「審視中 / 已審視待處置」狀態值？
2. 或將「審視 X」與「處置」合併為一 Command 兩結果（則兩個「管理員已審視⋯」Event 須移除）？
3. 不論何者，**檢舉與申訴須採同一做法**，不可只修一條。

# 解決結果

**選項 B ＋ 甲** —— 以流程檔的值域為準，並為**檢舉與申訴同時增設「審視中」狀態**；
審視中不自動退回。

## 值域（檢舉與申訴同一結構，四值）

| 你的說法 | 檢舉 | 申訴 |
|---------|------|------|
| 未處理 | 待審視 | 待審視 |
| 處理中 | **審視中**（新增） | **審視中**（新增） |
| 處理完成 | 已成立 / 已駁回 | 已成立 / **已駁回** |

狀態轉換：待審視 →（管理員已審視 X）→ 審視中 →（處置）→ 終止狀態。

**申訴的終止狀態由「已維持原處罰」改名為「已駁回」**：本欄位是**申訴**的狀態，
「已維持原處罰」描述的是處罰的狀態，語意不符；且模型已有「檢舉已駁回」，
同為駁回卻一有一無，日後將被誤讀為遺漏。原「申訴不成立時不另立 Event」的裁決一併推翻。

## 增設「審視中」的三個理由

1. **修正建模缺陷**：增設前，「管理員已審視檢舉」與「管理員已審視申訴」為模型中
   僅有的兩個**不改變任何 Aggregate 欄位**的 Event，違反 E3 檢查項。
2. **多位管理員時避免撞車**：〈Read Model：管理員待審佇列〉的「管理員為同一人」
   為佇列設計時的假設，非硬約束。
3. **積壓與卡住為兩件事**：無人接手（待審視）與已接手但拖延（審視中）需要不同處置。

## 甲案（不自動退回）與其限制

管理員未下判定即離開者，案件留在審視中，由待審佇列的「最久等待時間」呈現。

**不採乙（逾時自動退回）與丙（任何管理員可強制接手）**：兩者皆須在案件上記錄**處理者**，
而模型目前**無管理員 Aggregate**。使用者於本題過程中提出「管理員也要有識別 ID」，
已另建 `aggregate/管理員_管理員的帳號與權限尚未建模.md`（High）；
**該項定案後可回頭改採丙案**，模型中已加註此依賴。

註：Event 共通欄位已含「觸發 Actor（Actor 識別碼）」，故個別管理員在 **Event 層可辨識**；
缺的是 Aggregate 層的管理員實體。

## 適用範圍

**僅檢舉與申訴**。教官測驗簡答題審核與公開訓練審核為單步判定
（「管理員已審核教官測驗」「管理員已審核公開訓練」直接產生結果），無獨立的審視階段。
