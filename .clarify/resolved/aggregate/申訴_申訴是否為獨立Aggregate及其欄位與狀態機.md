# 釐清問題

第三輪新增「使用者已申訴」「管理員已審視申訴」「處罰已撤銷」三個 Event，但承接申訴的 Aggregate 未定義。申訴是否為獨立 Aggregate？其欄位、狀態機、以及同一處罰可否重複申訴與申訴期限為何？

# 定位

流程：管理員管理社群流程
元素：Aggregate（尚未定義）
細節：D1 Aggregate 識別與邊界、D5 生命週期與狀態機。〈獨立 Aggregate 清單〉42 項中無「申訴」；社群分類僅有貼文、留言、檢舉、對話、私訊、封鎖、關注關係。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 獨立 Aggregate「申訴」：欄位含申訴者、所申訴的處罰、理由、狀態；狀態機為 待審視 → 已成立（處罰已撤銷）/ 已維持原處罰；同一處罰限申訴一次 |
| B | 同 A，但同一處罰可重複申訴，不設次數上限，僅設冷卻期 |
| C | 不獨立建模，申訴以檢舉 Aggregate 的一個「案件類型」欄位表達（檢舉 / 申訴），共用同一狀態機與待審佇列 |
| D | 不獨立建模，申訴狀態併入使用者 Aggregate 的處罰相關欄位（申訴中旗標 ＋ 申訴理由） |
| Short | 提供其他簡短答案（<=5 字） |

# 解決結果

**選項 A ＋ 使用者給定的 30 天申訴期限**

獨立 Aggregate「申訴」（獨立 Aggregate 由 44 項增為 45 項，歸入社群分類）。

| 欄位 | 型別 | 說明 |
|------|------|------|
| 申訴者 | 使用者 ID | 提出申訴的使用者 |
| 所申訴的處罰 | 處罰識別 | 指涉「使用者已受處罰」的該次處罰 |
| 理由 | 字串 | 申訴理由 |
| 申訴時戳 | Timestamp | 沿用 Event 共通時戳規範 |
| 狀態 | 列舉 | 待審視 / 已成立 / 已維持原處罰 |

**狀態機**：待審視 →（處罰已撤銷 → 已成立）/（管理員已審視申訴判定不成立 → 已維持原處罰）

**期限與次數**
- 申訴期限 **30 天**，自「使用者已受處罰」的發生時戳起算
- 同一處罰**限申訴一次**，不論該次申訴成立與否
- 永久停權亦適用：其已定案無到期解除，僅能經申訴撤銷

理由：模型已定案「累計違規次數於處罰已撤銷時 −1」，而累計違規次數決定處罰階梯，
該規則要能驗收必須查得到「這個處罰被撤銷過」的紀錄，需要有獨立身分的申訴案件。
排除 C（併入檢舉）：兩者方向相反，且檢舉已定案多人合併為同一案件，申訴不可能合併。
排除 D（併入使用者）：申訴為有生命週期的案件，壓成扁平欄位後第二次申訴會覆寫第一次。

# 處理的措辭衝突

模型有兩處以「申訴機制未設時效上限」作為永久保存的理由（AI 調整對話、貼文與留言的編輯歷史）。
本次給定 30 天期限後，已於模型中新增〈申訴期限與證據保存期限的區別〉小節，明訂兩者指涉不同的事：

| 項目 | 期限 |
|------|------|
| 申訴的**提出**期限 | 30 天（自處罰發生起算） |
| 申訴所需**證據**的保存期限 | 無上限，不得定期清除 |

理由：一則兩年前的貼文可能今日才被檢舉並受處罰，30 天內申訴時仍需調閱兩年前的編輯歷史。
兩處既有的永久保存規則**維持不變**，未被推翻。
