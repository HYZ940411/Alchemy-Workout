# 釐清問題

管理員 Aggregate 已定案（欄位、權限組、27 個管理員 Command 的權限對應），但「管理員本身的維護」——新增管理員、停用管理員、調整某位管理員的權限組——是否建模為 Command 與 Event，尚未定案。

# 定位

流程：（不隸屬任何單一流程，比照系統排程／平台設定維護收納）
元素：Aggregate「管理員」
細節：`00_全域規範.md`〈管理員 Aggregate〉明文「該決策須套用〈平台級設定的軟體邊界〉的既有判準」但未實際套用給出結論。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 建模為 Command 與 Event（新增管理員／停用管理員／調整管理員權限組），理由：管理員的權限組直接被 27 個 Command 的 Precondition 讀取，依〈設定類欄位是否建模的判準〉（該欄位是否被任何 Precondition 讀取）應建模（**推薦**：與「持有器材明細」「AI 自動優化已啟用」適用同一判準，且管理員權限異動屬敏感操作，缺乏 Event 記錄將使「誰何時被誰授予了什麼權限」不可稽核） |
| B | 留在系統邊界之外，比照〈平台級設定的軟體邊界〉右欄的「後台組態」處理，不建模為 Event |
| C | 建模為 Event，但不視為業務流程的一部分，僅作稽核用途，不影響任何 Precondition 的判定邏輯 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響管理員 Aggregate 的生命週期定義、是否需要新增 Command/Event、〈管理員待審佇列〉等 Read Model 是否需要顯示異動軌跡。

# 解決結果

**選項 A**：建模為 Command 與 Event。

| Command | Actor | 導致的 Event |
|---------|-------|--------------|
| 新增管理員 | 管理員 | 管理員已新增 |
| 停用管理員 | 管理員 | 管理員已停用 |
| 調整管理員權限組 | 管理員 | 管理員權限組已調整 |

三者的所需權限組為**平台設定**，收納於〈平台設定維護〉一節，不寫入任何流程檔。
Event 皆攜帶：目標管理員 ID、變更前的值、變更後的值。

## 判準：改用〈設定類欄位是否建模的判準〉

模型原記「該決策須套用〈平台級設定的軟體邊界〉的既有判準」
（該判準為「改動後是否會改變使用者已取得或將取得的實質內容」），**本次改以另一條判準判定**：

> 〈設定類欄位是否建模的判準〉：**該欄位是否被任何 Precondition 或 Policy 讀取。**

管理員的權限組被其餘 27 個管理員 Command 的 Precondition 直接讀取，
與「持有器材明細」「AI 自動優化已啟用」同類，依該判準應建模。

**兩條判準的適用對象不同**：〈平台級設定的軟體邊界〉處理的是平台級組態的**值域清單**
（健身目標、器材明細、檢舉理由等），其改動只影響下拉選單；
管理員權限組不是值域，它是判定條件本身。

## 稽核軌跡不得在最敏感的一段斷掉

模型既有立場為「管理員的每個動作皆有對應 Event，Event 流本身即為稽核軌跡」。
若管理員的新增與授權不建模，該軌跡將**恰好在最敏感的一段斷掉**——
「誰在何時被授予了什麼權限」無任何紀錄，而下游 27 個 Command 的稽核卻完整。

`[已知限制]` 第一位管理員的產生不在本模型範圍內：三個 Command 的 Precondition
皆要求執行者為生效中且具平台設定權限的管理員，故系統中的第一位管理員
須由部署時的初始設定產生。
