# 釐清問題

檢舉 Aggregate 的欄位定義為何？可檢舉的對象類型有哪些？同一內容被多人檢舉如何處理？

# 定位

流程：管理員管理社群流程
元素：Aggregate：檢舉（模型中尚未定義）；Event：使用者已檢舉內容
細節：隱含但未明確定義的 Aggregate（D1）；欄位定義與狀態機（D2、D5）。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 欄位含檢舉者 / 被檢舉對象 / 對象類型（貼文 / 留言 / 帳號）/ 理由 / 狀態；多人檢舉同一內容合併為同一案件 |
| B | 同上但多人檢舉各自獨立成案，管理員逐案處理 |
| C | 同 A，另加檢舉累積次數欄位，達門檻時自動暫時隱藏內容待審 |
| D | 不建立檢舉 Aggregate，檢舉僅為通知管理員的訊息 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響檢舉 Aggregate 的欄位與狀態機、使用者已檢舉內容的 Postcondition、管理員已審視檢舉的作用對象（單案或合併案）、以及自動隱藏機制是否需要額外 Event。

# 既有約束（來自已解決項目）

第 16 題（`resolved/event/管理員已審視檢舉_檢舉不成立時的Event缺失.md`，選項 A）已裁決：
檢舉狀態機的終止狀態為兩個 —— 成立（下架違規內容）與已駁回；
駁回不對檢舉者記點或處罰，故 Aggregate 不需惡意檢舉記點欄位。

第 10 題（`resolved/event/使用者已建立對話_封鎖與刪除對話的Event缺失.md`）已裁決：
檢舉來源含內容檢舉與私訊檢舉兩種，本 Aggregate 須能區分檢舉標的類型。

# 解決結果

A — 檢舉 Aggregate 含 5 個欄位：檢舉者（集合）、被檢舉對象、對象類型、理由、狀態。

- 對象類型：貼文 / 留言 / 帳號 / 私訊（涵蓋第 10 題確立的私訊檢舉來源）
- **多人檢舉同一內容合併為同一案件**，管理員只需審視一次（未採 B 的逐案處理）
- 不設檢舉累積次數門檻，無自動隱藏機制（未採 C）
- 狀態機：待審視 → 已成立（管理員已下架違規內容）／ 已駁回（檢舉已駁回）

# 推導結果（需下輪確認）

提問時已聲明：「合併成案時，若後續又有人檢舉同一內容，是併入既有案件還是另開新案」

- 第 10 題：檢舉來源含內容檢舉與私訊檢舉，對象類型須能區分。
