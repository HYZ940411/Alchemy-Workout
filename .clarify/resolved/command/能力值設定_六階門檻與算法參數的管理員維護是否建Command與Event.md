# 釐清問題

〈能力值設定 Aggregate〉（2026-08-20 新增）承載六階門檻、基準值 27.6、映射係數 23.6、退步百分比 5%、退步間隔 240 小時、相對強度係數等參數，並明寫「上述參數皆由管理員調整」與「六階門檻調整後即時生效，全平台使用者的等級同時改變」。但〈Command 清單〉中無任何維護本 Aggregate 的 Command，該 Aggregate 亦未被列入〈平台級設定的軟體邊界〉表的任一欄。管理員調整能力值參數，是否建模為 Command 與 Event？

# 定位

流程：跨流程（管理員後台，不隸屬既有任一條流程）
元素：Command 與 Event（皆缺失）；Aggregate：能力值設定（`02_Aggregate定義.md:3930`）
細節：B1 Command 識別完整性、A4 軟體邊界判斷、E1 串聯一致性。〈平台級設定的軟體邊界〉（`01_Command清單.md:551` 附近）的左右兩欄共列 11 項，其中不含能力值設定。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A（**推薦**） | **納入軟體邊界**：新增 Command「設定能力值參數」（Actor：管理員，權限組＝平台設定）與 Event「管理員已設定能力值參數」，攜帶變更項目、變更前的值、變更後的值。理由：本表是模型中**唯一一個「改動當下就直接改變使用者已取得之物」**的設定——同節已明寫「六階門檻調整後即時生效，全平台使用者的等級同時改變」，比左欄四者（獎勵數額、成就門檻、課表內容、可選動作，皆只影響「將取得」）更符合既有判準；且申訴機制未設時效上限，使用者質疑「我昨天還是 B 級今天變 C 級」時須查得到何時改的 |

# 解決結果

**選項 A** —— **納入軟體邊界**：新增 Command「設定能力值參數」（Actor：管理員，權限組＝平台設定）
與 Event「管理員已設定能力值參數」，攜帶所變更的參數名稱、變更前的值、變更後的值。

判準與理由：

- 套用既有判準「該設定改動後，是否會改變使用者**已取得或將取得**的實質內容」，
  本項為左欄唯一「改動當下即改變**已取得**之物」者 —— 同節明寫
  「六階門檻調整後即時生效，管理員調整門檻的當下，全平台使用者的等級同時改變」，等級當場可降。
  左欄原有四者改動的皆為「將取得」，本項比其更貼近判準。
- **不歸右欄的兩個理由**：① 右欄其餘六者皆為**值域清單**，改動只換下拉選單的選項，
  不動任何已發生的事實；本項為餵入即時公式的數值參數。
  ② 右欄唯一的非清單成員（帶徒上限設定）當初歸右欄的理由正是「調整後既有教官的帶徒上限
  **不因此降低**」，即改動拿不走任何東西 —— 能力值設定恰為其反例。
- **稽核的必要性有具體後果**：六階門檻調降時，點數落於新舊門檻之間的使用者當場跨階，
  「能力值成就已解鎖」隨即觸發並發放金幣 100–300 ＋ 經驗值 ——
  設定改動直接發出獎勵；而申訴機制未設時效上限，須查得到何時改的、改成什麼。
- 不採 C（門檻與係數拆兩半）：兩者同存一表、同一次後台存檔即可一起改，
  拆開後「改了係數順手改門檻」將只留下半份紀錄。
- 不採 D（併入設定成就定義）：能力值成就的門檻依附六階門檻為單向依賴，
  併入後日後以「六階門檻」搜尋者會在「成就定義」中找不到，重蹈教官初審設定不併入教官測驗設定的同一問題。
