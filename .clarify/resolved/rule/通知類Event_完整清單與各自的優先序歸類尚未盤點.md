# 釐清問題

〈通知類 Event 的發送規則〉已定案「不合併、設同日總量上限、依三級優先序捨棄」，但通知類 Event 的**完整清單**及其各自的優先序歸類從未逐一盤點，同日總量上限的數值亦未給定。清單與歸類為何？

# 定位

流程：跨流程（每日簽到、訓練中斷、訓練紀錄、師徒互動、團隊組隊、每日任務、排行榜結算等）
元素：Rule：〈通知類 Event 的發送規則〉之優先序表與總量上限參數
細節：C3 邊界條件（組合邊界）、F3 待決事項。00_全域規範該節之 `[待決策 Partial]`。〈通知 / 提醒類 Event 的軟體邊界〉僅列 6 個，加上「訓練提醒已發送」為 7 個，但模型另有多個需要通知使用者的事實（師徒申請待回應、團隊邀請待回應、每日任務未領取、每週互動評分提示、排行獎勵已發放、獎勵已補發至信箱、審核結果）尚未確認是否納入。

# 解決結果（2026-08-07，第八輪第 17 題）

**B ＋ 甲** —— 分為推播類與 App 內通知類，**只有推播類受同日總量上限約束**；
上限 **3 則／日**；待回應類**不新增 Event**，推播寫為既有 Event 的 Postcondition。

## 分界判準

> **不看會不會失去東西。**
> 推播類 ＝ 不看就失去（天數歸零、申請逾期、能力值退步）。
> App 內通知類 ＝ 東西不會跑掉（獎勵在信箱等、成就解鎖即為己有、審核結果不會消失）。

關鍵在於**推播與 App 內通知本是兩件事，原規則將其混為一談**。
總量上限要管的是打斷使用者的那種；紅點不打斷任何人。分開後上限只需涵蓋少數幾則。

## 推播類清單（10 項，其中 3 項為本題新增）

| # | 觸發 Event | 序 |
|---|-----------|-----|
| 1–4 | 連簽中斷預告 / 補簽提醒 / 中斷預告 / 退步預告 已發送 | 1 期限失效 |
| **5** | **使用者已申請師徒關係**（待回應） | 1 期限失效 |
| **6** | **隊長已邀請成員**（待回應） | 1 期限失效 |
| **7** | **使用者已申請加入團隊**（待回應） | 1 期限失效 |
| 8 | 訓練提醒已發送 | 2 行動引導 |
| 9 | 連練中斷通知已發送 | 2 行動引導 |
| 10 | 每日登入提醒已發送 | 3 例行提醒 |

## App 內通知類（11 項）

每日任務未領取、獎勵已補發至信箱、三種排行獎勵已發放、成就已解鎖、階級已提升、
能力值等級變動、每週互動評分提示、四類審核結果、AI 調整已拒絕／已失敗、
AI 優化建議、訓練品質評分處理中。

## 三個附帶裁決

1. **待回應類歸第 1 級，不另立第 4 級「社交互動類」**：其本質即「不處理就失效」，
   與其餘第 1 級同性質；另立一級須多一套判定，換不到東西。
2. **待回應類不新增「…通知已發送」Event（選項甲）**：現有 7 項是獨立 Event，
   因為**它們沒有別的事實可掛**（無人做任何事，為排程時間到才發）；
   待回應類有明確的觸發事實，再造 Event 只是把同一件事記兩次。
3. **連練中斷通知歸行動引導類而非期限失效類**：天數已歸零，用途為召回而非預防。

## 上限 3 則／日 的依據

推播類扣除待回應後，日常最多同時出現者為：簽到提醒、訓練提醒、某一則期限預告
—— 正好 3 則。定為 3 使正常情況全部發得出去，僅異常擠壓時才捨棄。

## 不採 D（後台逐一開關）的理由

三級優先序為**設計決定**而非營運參數。逐一指派等同無人真正決定哪則該讓步給哪則；
且新增 Event 時無人記得去後台設定，其預設值又成為新的未定義。
