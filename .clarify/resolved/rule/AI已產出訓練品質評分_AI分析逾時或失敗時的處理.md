# 釐清問題

教官申請流程的「AI 已產出訓練品質評分」若逾時或失敗，該申請無任何 Event 可承接（初審已定案無人工介入），應如何處理？

# 定位

流程：教官申請流程
元素：Rule：Event「AI 已產出訓練品質評分」的失敗路徑
細節：C5 失敗與例外路徑、A1 事件識別完整性。`教官申請流程.md` 以 `[待決策 Partial]` 標記並註明「併入 `.clarify/rule/AI已微調訓練強度_AI回應逾時或失敗時的處理.md` 一併裁決」，但該項已解決且其裁決範圍僅涵蓋三條 AI 調整流程，未及於本處。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 沿用「AI 調整已失敗」Event，來源值域增列「教官品質評分」；申請維持在初審中，由排程重試，使用者於申請頁看到「評分處理中」 |
| B | 新增獨立 Event「訓練品質評分已失敗」，攜帶失敗原因；申請暫留初審中並自動重試 3 次，達上限轉人工審核（該申請進入管理員待審佇列） |
| C | 同 B 的 Event，但達重試上限即**直接駁回**（教官資格已駁回，駁回階段＝初審），使用者可 14 天後重新申請 |
| D | 不建模失敗：AI 評分為同步呼叫，失敗即該次「使用者已申請教官權限」不成立（Command 被拒），使用者重按即可 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響 Event 總數、教官申請 Aggregate 的狀態機（是否需要「評分失敗待重試」狀態）、〈Read Model：管理員待審佇列〉教官申請分頁的進入條件、以及「教官資格已駁回」的駁回階段值域。
相關已解決項目：`resolved/rule/AI已微調訓練強度_AI回應逾時或失敗時的處理.md`、`resolved/event/AI已產出訓練品質評分_攜帶資訊與去重鍵與評分是否保存.md`。
相依：`aggregate/教官申請_教官申請Aggregate的狀態機與教官測驗的關聯基數.md`。

# 解決結果（2026-08-06，第八輪第 14 題）

**使用者自由作答：「掛了隔一天再跑一次不就好？」** —— 新增 Event
「**訓練品質評分已失敗**」，申請維持在**初審中**，**由排程於隔日重跑**，直到成功為止。
**不設連續失敗上限**，不轉人工、不駁回、不通知管理員。

## 助理原推薦 B′ 被使用者簡化

助理原推薦「重試 3 次 ＋ 達上限標示並通知管理員」（比照第七輪〈審核已逾期〉的模式）。
**使用者的方案更好，理由三點**：

1. **使用者不在場** —— 按完申請即離開，沒有人在等。
2. **資料不會變** —— 分析對象為歷史訓練紀錄，今天跑與明天跑結果相同，無時效壓力。
3. **秒級重試 3 次沒有用** —— 服務中斷通常需數小時恢復，連試三次只是三次一起失敗。

助理的錯在於把「使用者在場」的處理模式（第 1 題所定的 30 秒 ／ 重試 1 次）
套到一個沒有人在等的場景，機制多了一堆，效果反而不如隔日重跑。

## 不設上限的理由（子題，使用者選 A）

連續數日失敗為**服務層級的故障**，屬維運監控的職責，非本流程該承載的案件狀態；
真的連掛三天，受影響的不會只有教官申請。設上限須多定一個 N ＋ 多一個通知，
換到的資訊維運後台本來就有。

## 四個原選項的否決理由

| 選項 | 為何不採 |
|------|---------|
| A 沿用「AI 調整已失敗」 | 該 Event 已帶「退還 AI 點數」的 Postcondition，而教官評分第 2 題已定**不扣點**，沿用會使後置條件須分岔判斷 |
| B 達上限轉人工審核 | 推翻「初審無人工介入」；模型第 44 行已為同一件事否決過一次（疑似造假不轉人工），理由為「訓練紀錄難以人工判讀，實務上審不動」 |
| C 達上限直接駁回 | 申請者無過失，把平台的技術風險轉嫁給使用者 |
| D 不建模 | 違反「失敗須建模為 Event，不可僅在前端顯示錯誤」——AI 失敗率為須監控的指標 |
