# 釐清問題

重量允許為 0（自身體重動作），若能力值提升依「訓練總量＝重量 × 次數 × 組數」計算，徒手動作總量恆為 0 而完全不產生提升。此矛盾如何解決？

# 定位

流程：訓練結算流程
元素：Rule：Event「能力值已提升」的計算輸入
細節：特殊值處理 — 零值（C3）；Aggregate 內部不變條件（D3）。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 徒手動作以使用者當前體重代入重量計算 |
| B | 徒手動作以體重乘上動作係數（如伏地挺身取體重 60%）代入計算 |
| C | 改用不依賴重量的計算方式：次數 × 動作難度係數，全動作一致適用 |
| D | 徒手動作另有獨立的能力值換算規則，與負重動作分開計算 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響能力值提升公式、動作 Aggregate 是否需新增「難度係數」或「體重係數」欄位、
個人排行榜分數「依訓練量換算」的同一矛盾，以及「徒手」作為合法器材選項的可用性。
承接 G21；與 `rule/能力值已提升_提升幅度的計算公式為何.md`（G18）為同一組決策，宜併題處理。
相關已解決項目：`resolved/aggregate/訓練紀錄_重量的單位精度與零或負值是否合法.md`（選項 A）。

# 解決結果

**選項 B ＋ 追問乙**：徒手動作以「**基準體重 70 公斤 × 動作體重係數**」代入計算，與使用者實際體重無關。

- 動作 Aggregate 新增「體重係數」欄位，僅徒手動作有值（伏地挺身 0.6、引體向上 1.0 等）。
- 訓練紀錄仍照實儲存重量 0（既有裁決不變）；體重係數僅於計算時代入，實績與計算輸入分開。

**為何不採選項 A（代入 100% 體重）**：伏地挺身實際承重約 60–65%、徒手深蹲約 65%。
一律代入 100% 會使 70 公斤使用者做 12 下 × 3 組得到訓練量 2,520，超過胸的基準訓練量 2,000
—— 三組伏地挺身勝過一場認真臥推，所有人將改去做徒手動作刷分。

**追問「體重高的人成長會更大嗎」→ 改用基準體重（乙）**：

原本的 B 會使 100 公斤使用者比 60 公斤使用者多拿 1.67 倍。物理上正確（確實移動更多質量），
但作為計分規則有三個缺陷：

1. **與 App 自身目標打架**：「減重」為常見目標類選項，減重成功者的徒手成長反而變慢，形同懲罰達成目標。
2. **增重可刷分**：計分系統不應具備此性質。
3. **波及排行榜**：訓練量同時餵給個人排行榜分數，跨使用者名次會受體重影響。

另有實務理由：體重為使用者自填且多數人不定期更新，不依賴該欄位可避免資料過期導致計分錯誤。

**取捨**：體重明顯高於 70 公斤者做徒手動作的額外負荷不被反映，此為刻意接受的代價
——計分規則的第一要務是誘因方向正確，物理精確度其次。

**未採選項 C / D**：C 會推翻第 31 題（把重量完全移出公式）；D 需維護負重與徒手兩套尺度，任一邊調參都須檢查另一邊。
