# 釐清問題

檢舉的審核時限定為 7 天，且逾期不改變案件狀態、被檢舉內容期間仍掛在站上——此設定是否滿足 App Store 1.2 對 UGC 的「timely responses to concerns」要求，時限是否需縮短或加設暫時下架機制？

# 定位

流程：管理員管理社群流程
元素：Rule — 〈四類審核的時限與逾期處理〉之檢舉時限；Aggregate — 檢舉的狀態機
細節：查證 2026-08-18 之 App Review Guidelines 全文，**1.2 並無「24 小時」字樣**，`overview.md` §7.1 原記載的「Apple 對 UGC 要求 24 小時內移除」不成立；條文為「a mechanism to report offensive content and **timely responses to concerns**」，並要求開發者自行負責移除違規內容。模型現況：檢舉 7 天、申訴 72 小時、逾期僅升級提示

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 維持 7 天，僅更正文件中「24 小時」的錯誤前提；理由為條文僅要求 timely 而未給定小時數 |
| B | 縮短檢舉時限至 24–72 小時（與申訴同量級），逾期處理維持不變 |
| C | 維持 7 天總時限，但依檢舉理由分級：騷擾辱罵／色情不雅／暴力威脅三類縮短為 24 小時，其餘維持 7 天 |
| D | 加設暫時下架：同一內容累積 N 筆檢舉即自動暫時隱藏至審視完成（推翻既有「不設檢舉累積次數門檻、無自動隱藏機制」的裁決） |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

- 〈四類審核的時限與逾期處理〉的檢舉時限數值與 `[已知取捨]`（期間內容仍可被瀏覽）
- 若採 D，須新增 Event 與檢舉 Aggregate 的狀態，並推翻「不設累積門檻」的既有裁決
- 〈Read Model：管理員待審佇列〉的排序與逾期標示
- App Store 條款：1.2 User-Generated Content

# 解決結果

**A**：檢舉時限維持 **7 天**，僅更正文件中「24 小時」的錯誤前提。

- **查證結果**：App Review Guidelines 1.2 全篇無「24 小時」字樣，條文僅要求
  "timely responses to concerns"，未給定小時數。`overview.md` 舊版 §7.1 的記載不成立。
- **前提已由第 1 題改變**：加上〈發布前的內容過濾〉後，明顯違規的內容發不出來、
  疑似違規者自動進待審佇列，留給使用者檢舉的已是過濾器判不出來的模糊案件，
  該類案件需要人看仔細，24 小時的壓力只會逼出草率判定。
- **不採依理由分級時限**：檢舉理由為管理員可增刪的值域，新增時無人會記得設定其時限，
  預設值即成為新的未定義（承否決「逐一指派通知優先序」的同一理由）。
- **不採累積檢舉自動隱藏**：會使檢舉成為零成本的攻擊手段，且牴觸既有裁決
  「不設檢舉累積次數門檻，無自動隱藏機制」。
