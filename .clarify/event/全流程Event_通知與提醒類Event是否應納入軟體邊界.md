# 釐清問題

模型中有多個通知 / 提醒類 Event（每日登入提醒、連簽中斷預告、補簽提醒、中斷預告、連練中斷通知、退步預告），這些是否都值得建模為業務 Event？是否應統一為單一通知機制？

# 定位

流程：每日簽到流程、訓練中斷流程
元素：Event：每日登入提醒已發送、連簽中斷預告已發送、補簽提醒已發送、中斷預告已發送、連練中斷通知已發送、退步預告已發送
細節：軟體邊界判斷（A4）；是否為誤列為 Event 的技術動作（A1）；事件顆粒度（A1）。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 統一為單一「通知已發送」Event，通知類型為其攜帶資訊，各 Policy 決定何時發送 |
| B | 維持六個獨立 Event，因為各自的觸發條件與內容不同，需分別驗收 |
| C | 保留為 Event 但標記為「不需精準追蹤」，僅記錄不做嚴格規則驗收 |
| D | 通知發送屬技術動作，不列為業務 Event，改列為各 Policy 的 Postcondition |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響兩條流程共六個 Event 的存廢與合併、通知 Aggregate 是否需要建立、推播失敗的例外處理、以及使用者通知偏好設定欄位的必要性。此為軟體邊界判斷問題。
