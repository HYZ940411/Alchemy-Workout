# 釐清問題

模型缺少「事前的訓練提醒」Event。是否新增？其發送時段如何決定？

# 定位

流程：訓練紀錄流程、新手任務流程、訓練中斷流程
元素：Event（尚未存在）；Aggregate「使用者」的訓練時段偏好欄位
細節：事件識別完整性 — 隱含未寫出的 Event（A1）；軟體邊界判斷（A4）；Command 輸入（B3）。

# 使用者已表態的需求（2026-07-31，第 39 題期間主動提出）

1. 訓練提醒依**使用者慣常訓練的時段**發送。
2. 沒有訓練紀錄的新手：**完成新手訓練後**，引導使用者自行選擇空閒時段。

上述兩點為使用者明確要求，非推導。以下多選題僅就其**建模方式**釐清。

# 現況落差

模型現有的通知類 Event 皆為**事後補救**：

| 既有 Event | 觸發條件 | 性質 |
|-----------|---------|------|
| 中斷預告已發送 | 距上次訓練日界 +24 小時 | 事後 |
| 連練中斷通知已發送 | +36 小時 | 事後 |
| 退步預告已發送 | +96 小時 | 事後 |
| 每日登入提醒已發送 | 每日簽到流程 | 與訓練無關 |

**無任何事前提醒**。使用者要的是「今天該練了」，而非「你已經三天沒練」。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 新增「訓練提醒已發送」Event，比照既有 6 個通知類 Event 標記為「不需精準追蹤」；發送時段由系統依訓練紀錄的時戳分布推算 |
| B | 同 A，但發送時段一律取自使用者 Aggregate 的「偏好訓練時段」欄位（使用者自選），系統不做推算 |
| C | 同 A，採兩段式：有訓練紀錄者由系統推算，無紀錄者取自使用者自選的偏好時段（對應使用者原始需求的兩點） |
| D | 不新增 Event，訓練提醒視為推播實作細節，留在系統邊界之外 |
| Short | 提供其他簡短答案（<=5 字） |

# 尚待決定的子項（不論選何者）

- 「慣常訓練時段」的推算基準：取最近 N 次訓練的開始時戳眾數？平均？時段區間粒度（小時 / 半小時 / 早中晚）？
- 新手選擇空閒時段的操作，是否需要新增 Event（如「使用者已選擇偏好訓練時段」）與對應 Command。
- 該選擇動作掛在新手任務流程的哪一個時點（「使用者已完成新手任務」之後？）。
- 提醒頻率：每日？僅在偏好時段當天未訓練時？連續未訓練是否升頻或降頻。
- 使用者 Aggregate 是否新增「偏好訓練時段」欄位，以及其型別與值域。

# 影響範圍

影響訓練紀錄流程是否新增事前提醒 Event、使用者 Aggregate 的欄位、新手任務流程的終點行為、
以及與既有 3 個事後通知 Event 的職責區隔（避免同一天既發事前提醒又發中斷預告）。

相關項目：`rule/每日登入提醒已發送_發送時間對象與渠道為何.md`（每日簽到的提醒時間，與本項為同一組通知策略）。
