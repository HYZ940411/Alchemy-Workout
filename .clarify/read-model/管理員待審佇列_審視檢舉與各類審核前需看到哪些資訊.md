# 釐清問題

管理員執行 Command「審視檢舉」「審視申訴」「審核公開訓練」「審核教官測驗」「出貨」前必須看到什麼？是否為單一待審佇列，或依類型分立多個 Read Model？

# 定位

流程：管理員管理社群流程、自訂訓練流程、教官申請流程、實體商品購買流程
元素：Read Model（尚未定義）；支撐 5 個管理員審核類 Command
細節：D6 Read Model 識別（服務的 Actor 為管理員）、E4 Read Model → Command 支撐。
現況：全模型的 Read Model 皆服務「使用者」，無任何服務「管理員」的 Read Model，但管理員有 5 個需實質判斷的 Command。

# 多選題

| 選項 | 描述 |
|--------|-------------|
| A | 依類型分立 4 個 Read Model（檢舉待審、申訴待審、公開訓練待審、教官測驗待審）＋ 待出貨訂單清單；各自定義欄位與排序 |
| B | 單一「待辦彙總」Read Model：欄位＝類型、標的摘要、送出時戳、等待時長；點入才載入該類型的詳細內容 |
| C | 採 B 的彙總 ＋ A 的分頁：彙總供掌握總量與時效，分頁供實際審核 |
| D | 本階段僅建立檢舉待審一項（唯一有時效壓力者），其餘管理員作業留在後台實作階段定義 |
| Short | 提供其他簡短答案（<=5 字） |

# 影響範圍

影響 Read Model 清單是否納入管理員視角、檢舉 / 申訴 / 自訂訓練 / 教官測驗 / 訂單五個 Aggregate 的待處理狀態查詢、多人檢舉合併成案後的呈現方式、以及檢舉理由值域是否用於佇列排序。
相依：`aggregate/申訴_申訴是否為獨立Aggregate及其欄位與狀態機.md`、`rule/使用者已檢舉內容_檢舉理由為自由文字或列舉值域.md`。
相關已解決項目：`resolved/aggregate/檢舉_檢舉的欄位與狀態機.md`、`resolved/command/管理員已審核公開訓練_審核的Actor與權限為何.md`。
