僅就「缺少它」與「它的關鍵決策點為何」建立釐清項目。

## 3.3 建議釐清順序

**核心原則**：順著事件風暴的推導方向 —「先確定發生了什麼，再問誰做了什麼、要遵守什麼、狀態長什麼樣」。
不可跳過前一層直接問後一層。

由於本模型的 Command / Aggregate 層完全空白，各階段內同時列出該層的 High 與 Medium：
先橫向掃完 High 建立骨架，再回頭補 Medium 細節，避免在上游未定案時空轉。

## 3.4 釐清策略說明

### 推導順序原則

嚴格由 **Event → Command / Actor → Aggregate → Rules → Read Model**。
本模型的特殊狀況是 Aggregate 層完全空白，而許多 Rule 問題（如計算公式、邊界值）
的答案必須落在某個 Aggregate 欄位上，因此**第三階段的 Aggregate 必須先於第四階段的 Rules**，
不可為了「規則比較好回答」而提前處理。

### 平衡原則

同一階段內避免連續追問同一個 Event 的細節。建議橫向順序：

`註冊 / 新手 → 簽到 / 補簽 → 訓練紀錄 / 中斷 / 結算 → 自訂訓練 / AI 調整 → 任務 / 排行 / 團隊 → 社群 / 師徒 / 教官 → 商城 / 訂閱 / 管理 → 全域跨流程`

其中**全域跨流程項目**（`使用者`、`成就`、`獎勵`、`Actor`、`全流程Event`）雖然排在橫向掃描的最後，
但因其答案會反向約束前面所有流程，建議在**第一階段與第三階段的開頭**優先處理，屬於例外。

### 依賴關係（需先釐清 A 才能處理 B）

| 前置項目 | 被阻擋的項目 |
|----------|--------------|
| `event/全流程Event_每個Event應攜帶哪些資訊與時間戳` | 所有 Event 的資訊欄位定義；所有跨時區規則 |
| `command/Actor_模型中各角色名稱的定義與統一` | 所有 Command 的 Actor 指派與權限規則 |
| `aggregate/使用者_使用者Aggregate的欄位與邊界尚未定義` | 所有 Postcondition 的欄位歸屬；經驗值 / 能力值 / 階級 / 成就的 Aggregate 邊界 |

### 提前終止的判斷

若時間有限，建議至少完成**第一階段全部 High（29 項）**與**第三階段 High 中的全域五項**
（`使用者`、`成就`、`獎勵`、`能力值`、`個人排行榜分數`），
這批答案能讓模型從「Event 清單」升級為「可推導的骨架」；
其餘 Medium 與 Low 可延至下一輪 Discovery。
