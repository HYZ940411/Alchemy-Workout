## 3.3 建議釐清順序

**核心原則**：順著事件風暴的推導方向 —「先確定發生了什麼，再問誰做了什麼、要遵守什麼、狀態長什麼樣」。
不可跳過前一層直接問後一層。

本輪的推導位置與第一輪不同：Event 層大致成形，**瓶頸已移至 Aggregate 層的 6 個空洞與 Command 層的全面缺席**。
因此第三階段（Aggregate）的份量最重，且其中多項會反向決定第四階段大量 Rule 的可驗收性。

## 3.4 釐清策略說明

### 推導順序原則

嚴格由 **Event → Command / Actor → Aggregate → Rules → Read Model**。

本輪的特殊狀況與第一輪相反：Event 層已大致成形，**空洞集中在 Aggregate 層**。
6 個未建模的隱含 Aggregate（本次訓練課表、課表內容結構、留言 / 按讚、關注關係、對話 / 私訊、師徒任務 / 問答）
是本輪的真正瓶頸 —— 它們既阻擋下游 Rule 的欄位落點，也可能反過來要求補上新的 Event。
因此第三階段的 3-A 前 7 項應**優先於第四階段的所有 Rule**。

Command 層仍為全面 Missing，但因 Actor 已定案，可用「總綱先行」方式處理：
先答 `command/全流程Command_...` 決定顆粒度與命名規範，其餘 Command 依該規範批次補齊，
不需逐一提問。

### 平衡原則

同一階段內避免連續追問同一個 Event 的細節。建議橫向順序：

`訓練課表 / 訓練紀錄 → AI 調整 → 註冊 / 新手 → 簽到 / 補簽 / 中斷 → 任務 / 排行 / 團隊 → 社群 / 師徒 / 教官 → 商城 / 訂閱 / 管理`

本輪新增項目在「社群」與「師徒」兩塊集中出現（留言、關注關係、對話、師徒任務四個 Aggregate 空洞），
應一次掃完，避免跨階段反覆回頭。
